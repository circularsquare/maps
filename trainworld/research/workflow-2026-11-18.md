# Workflow, trimming and agent tools: what our own records say (2026-11-18)

By agent workflow, for Anita. Your ask: "workflow improvements, code/test trimming, and agent tools ... what might we
do in this direction?" Research only; nothing in the game or tools was changed. Ranked by what our own transcripts
show each thing costs, biggest first. Outside reading came last and only where it matched a measured cost.

**Units.** "Weighted tokens" counts each model call the way the API prices it (re-read context 0.1, newly cached
1.25, written 5), as checks/token_usage.py does. A task's "145k tokens" in a report is its largest context, not its
cost: helptrip peaked at 143k context but cost 869k weighted over 69 calls. Minutes are wall-clock agent minutes.

**Sample.** 33 agents (last night's 27 under orchestrator f171, today's 6), 2,750 tool calls, 56M weighted, 1,278
agent minutes. Seven orchestrator sessions from 11-17 11:11 to 11-18 13:05 UTC (86.8M weighted). Every finish, land
and remove run since 11-16 (229). Every check run seen in 1,361 transcripts since 11-01.

## The proposals, ranked

**1. A game that stays open between probes, plus a wait command.**
- Today: agents spent 388 of 1,278 minutes (30%) waiting on the game in headless Chrome, more than on anything else,
  and 16-20% of their weighted tokens on the calls that start and poll those runs (the upper figure includes some
  polls of Rust builds). Each run opens a fresh game: a new game
  loads in 13 s, the real save needs 129 s until its trips are calculated (smoke's own figures). Helptrip spent 16 of
  its 20 minutes running its own script 11 times to see that two clicks on bubbles open the trip view; each run sat
  through 40 s and 50 s fixed waits. The harness could have done that job, so for helptrip the waste was fixed
  sleeps and reloads, not a missing feature. Since 11-16 agents tried a blocked `sleep` 173 times and misused Monitor
  61 times, against the written Waiting rule.
- Why the harness alone hasn't fixed it: 41 of the 71 scratch scripts that open a browser skip `checks/lib/play.mjs`.
  The clear gap is reading the simulation (14 of 41 such scripts do, 1 of 30 harness scripts); building a fixture
  with game edits is common in both (16 of 41, 9 of 30). Fixed sleeps are in 36 of 41 and 23 of 30.
- Fix: one small command over the harness. `play start <city|save>` opens the game once and keeps it running;
  `play do '<act/see call>'` returns short JSON in a second or two and waits on conditions, never fixed times;
  `play edits <file>` and `play sim <read>` cover what raw scripts reach for; `wait <file> <pattern> <timeout>`
  replaces the hand-written polling loops. Untried and worth a test first: `play snapshot` / `restore`, keeping a
  calculated state so the next probe skips the 13-129 s. For it to be used, CLAUDE.md's "Playing the game" line
  points to it instead of the harness, and briefs say "probe with play".
- Saves: my guess, not a count, is a third to half of the 388 game minutes (repeat loads, settles and fixed sleeps),
  and most of the polling calls. Adds no standing checks, so it fits the "kept lean" rule.
- Agent time: 2-3 hours (stage 1 of the harness took one Opus agent 35 minutes and 153 calls).
- Retires: improvised poll loops and fixed sleeps in scratch scripts; the "one light check every 4-5 minutes"
  advice for game runs. Not T-3556 stage 2 (outside agents, parked P4): this is for our own agents, though the
  same tool would be most of stage 2 later.

**2. Agents start lighter (your setup, so your call).**
- Today: every agent's first call already carries 56k tokens (55.9k-57.3k across 38 agents; T-2831 measured 54k on
  11-09). Each
  later call re-reads it, so for a small agent the fixed start is 40-50% of its cost (helptrip: 69 calls x 5.6k =
  386k of its 869k). Of that, the text
  files are about 8.5k (your global notes 15.4k characters, the memory index 15.3k characters, mostly other projects,
  maps notes 2.7k). The rest is tool and skill descriptions; the AWS, Stripe, Docs and Artifact parts are, I
  estimate, 10-15k, and trainworld agents made 0 calls to any of them in 2,750.
- Fix: turn the AWS, Stripe and Docs connectors and their skills off for maps sessions (a project setting, if one
  covers connectors; that needs checking first), and
  keep the memory index to maps items. Only trainworld agents writing player text need the "User-facing text"
  section; it could move to a file they read.
- Saves, per 15k removed: about 7% of agent tokens (1.5k on each call averaging 20k) and about 5% of
  orchestrator tokens. Of everything here, the most saved for the least work.
- Agent time: under half an hour, plus your check that nothing you use in maps sessions goes missing.
- Retires: nothing; this was T-2831's item 2B on 11-09, left for your call then and never done.

**3. Reports reach whichever orchestrator is current, so the old tab can stop.**
- Today: counting from the moment each successor started, the six old tabs in this sample made 201 more model calls
  (71 of them relays to the new tab, 96 replies) costing 11.1M weighted, 13% of all orchestrator tokens, about 1.8M
  per handover. Each cost 55k on average against 34k before the handover, because the old context is past 500k. The
  11-17 rule ("one line to her, then only pass reports") holds; the passing itself is the cost.
- Saves: the relays and replies (8.9M) almost all go, since the new tab gets each report once from the inbox; the
  wind-down landings the old tab still does cost 21k less each in a fresh tab. About 9M in 26 hours, roughly 1.5M a
  handover.
- Fix: each agent's final report is also written to a file inbox (a hook when a subagent stops, or the agent's
  last step); the board watch prints new ones to the current orchestrator, which adopts running agents by id from
  the board. The old tab finishes the landing it is in, sends its one line, and stops.
- Agent time: 1-2 hours, including a check that a stop hook can read a subagent's final report on this version.
- Retires: relaying by hand, and the "copied by hand to the new one" paragraph in the handoff skill.

**4. Faster sim test builds for agents.**
- Today: Rust builds and tests took 131 of 1,278 agent minutes (10%). After any edit, `cargo test --release` takes
  about 3 minutes, because the release settings ask for whole-program optimisation at link time (`lto = true`), the
  slowest link there is, and rebuild from scratch rather than reuse unchanged parts. The tests themselves run in
  10 s. A scratch timing on 3 cores, after changing one constant the code reads: build and run 196 s as today, 127 s
  with the link-time step off, **64 s with it off and reuse of unchanged parts on**; the tests took 11 s in all three,
  so nothing ran slower. Agents run this twice per change (with and without the demand feature). A fresh tree's
  first build is still slow (142-223 s). I did not time the WebAssembly builds, which use the same settings.
- Fix: separate build settings for agents' test runs and their own WebAssembly builds; the landing's WebAssembly
  rebuild and 8800 keep today's. The lie: agents test a build linked differently from the one that ships. Same code,
  same optimisation level; I know of no behaviour that differs, and smoke on master after a batch runs the real one.
  An agent timing a solve or the frame rate still uses today's settings.
- Agent time: under an hour (two settings lines, CLAUDE.md's Rust line, the WebAssembly scripts).
- Saves: about two thirds of each warm edit-test cycle; I'd guess 60-80 of the 131 Rust minutes in this sample.
- Retires: nothing; shortens every sim task's edit-test loop.

**5. The handoff's state comes from a command; asks get one too.**
- Today: 290 handoff edits in seven sessions (5.6M, 6.5% of orchestrator tokens) and 48 hand edits of asks.json
  (0.8M). It still drifted: maps-ca rewrote it this morning because "State and In flight had drifted badly". An ask
  was dropped by a hand edit and its id reused. (The 156 hand edits of TASKS.md, 2.7M, are mostly filing her pad,
  which neither command touches.)
- Saves: most of the 6.4M, if the handoff is then edited only when the plan changes; I'd guess two thirds.
- Fix: `handoff.py status` prints the live state from where it already lives: trees with branch, commits ahead and
  dirty files; agents on the board with start times; uncommitted paths and whose; 8800's build, master against
  origin; open asks; night runs and core claims. The takeover reads that; handoff.md keeps only the plan, your words
  and judgement. `asks.py add | answer | list` gives ids that are never reused.
- Agent time: 1.5-2.5 hours (tasks.py, the closest past tool, took one Sonnet agent 102 calls).
- Retires: the "Handoff file churn" item the 11-17 review left as lowest priority (today's numbers move it up), and
  hand edits of asks.json.

**6. Landing: stop the three causes that still fail.**
- Today: since the step 5 fix on 11-17, landing failed 8 times in 60 and tree removal 2 times in 17 (about 13%). The
  orchestrator calls between each failure and its next tree command add up to at most 39 calls and 1.7M weighted in
  17 hours (an upper bound: some of those calls were other work). Causes now: the same file changed both in the tree
  and on master (2, "rebase conflict"), master not moving forward because the main tree has an unsaved edit in the
  same file (3), a tree held open by a shell or process (2), other (3). Of the 5 landings in the finish logs that hit
  a conflict, 4 involved a bookkeeping file: DECISIONS.md twice, TASKS.md, and settle's notes/T-3482.md written in
  both places. Agents edited TASKS.md or DECISIONS.md inside their tree 27 times since 11-16 (8 agents), against
  the written rule.
- Fix: a hook that refuses an edit to TASKS, DECISIONS, ARCHIVE or LINES under `.tw-trees` and says to edit the
  main tree's copy; `finish` settles a notes file written in both places by keeping both texts; `remove` names the
  process holding the tree (and the orchestrator never `cd`s into one); changelog ids in a tree are provisional
  (`<tree>-1`) so four trees can't all report c014.
- Agent time: about 1.5 hours (finish itself took one Sonnet agent 28 calls).
- Retires: the Traps paragraph on landing over others' edits, for the bookkeeping-file case.

**7. A one-line index of the checks, and the broken ones moved to old/.**
- Today: 317 task checks (43k lines) plus 40 tools. 14 are in smoke; since 11-01, 56 were run 10 or more times, 140
  run 3-9 times, 68 once or twice, 39 never. Agents ran standing checks 26 times in my sample against 240 runs of
  their own scratch scripts. I ran 7 of the never-run ones on my own Vite: 4 pass (t1025, t2669, t486, t1805) and 3
  did not: t1201 can't find the Money tab (its selector is out of date); t2626 did not finish in 280 s on 3 cores;
  **t1550 fails its two lines that the bubble's hover tag shows at zoom 7 and 8.4, which may be a real regression**
  worth a small task. t2407-draw.py, t1177-data and t1966-layout are helpers, not checks. code-map's checks section is
  414 lines of prose.
- Fix: a generated table (name, what it proves from its header line, helper or check, runs since a date, last pass)
  that agents grep before writing a scratch script; a check found out of date is fixed or moved to old/ with a line
  saying why, after someone looks at what it caught.
- Saves: little in tokens; fewer agents rewriting a check that exists. Deleting is not worth it (a never-run check
  costs nothing until someone runs it).
- Agent time: about an hour.

**Not proposed.**
- *Dead code.* knip (a TypeScript dead-code finder, run on a scratch copy with TypeScript 5.9, no parse errors) finds
  31 unused exports and class members in app/, about 90 lines of 118,565; 6 of 6 spot-checked by grep are real, and
  `noUnused*` is already on. Of 85 raw findings, 54 are names the checks reach into. In sim/, a scratch build with only
  the WebAssembly exports as roots finds 48 items (about 600 lines) the game never calls: 470 lines are used by the
  pipeline's programs, 53 only by tests, none by nothing. Dead code is not a lever here. The open cleanup tasks
  (T-3458 comments, T-3460 code written twice, T-2374 file splits) are about reading ease, which I did not measure.
- *Ending agents earlier.* 22% of agent tokens were spent above 300k context, almost all by four Opus agents
  overnight (T-3482 twice, T-3474, T-3647): T-3482's settle agent paid 5.2M for its 114 calls past 300k. That is
  your 11-05 rule (agents keep going overnight) and your 500k choice for orchestrators, which spend 70-78% of their
  tokens above 300k. Numbers only; your call.
- *Orientation.* Agents spend a median 25 calls (25% of agent tokens) before their first edit. Moving that into
  briefs would move it to the orchestrator, whose calls cost 3-4 times more.

## Evidence: outside reading (step 6, 9 searches and fetches)

- Anthropic, writing tools for agents: few tools for whole workflows, concise output with a "concise" mode (a third
  of the tokens), errors that steer. Shapes proposal 1's `play do` returning short JSON.
  https://www.anthropic.com/engineering/writing-tools-for-agents
- SWE-agent's agent-computer interface: a dedicated edit command with a linter built in mattered most in its
  ablation; search output is capped and summarised. Same lesson: an agent's own tool beats raw shell.
  https://arxiv.org/abs/2405.15793 (via secondary summaries; the paper itself not opened)
- Claude Code best practices: "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a
  sign the line belongs in a hook." Behind proposal 6's hook (27 tree edits against a written rule) and proposal 1's
  wait command (173 blocked sleeps against the Waiting rule). https://code.claude.com/docs/en/best-practices
- Anthropic, context engineering: sub-agents should return 1,000-2,000-token summaries; context rot as windows grow.
  Fits proposal 3 and the 300k numbers. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- Anthropic, harnesses for long-running agents: state in JSON that models are "less likely to inappropriately change
  or overwrite" than markdown; a script that starts the dev server so sessions don't work it out. Behind proposal 5.
  https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- Cargo profiles: `cargo test --release` uses the bench profile, which inherits release (and its LTO); release has
  incremental off by default; one project measured 77 s to 41 s going from full to thin LTO.
  https://doc.rust-lang.org/cargo/reference/profiles.html
Dropped: worktree practice blogs (nothing we don't do; https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents),
test-impact selection (agents seldom run standing checks), task trackers (T-3451 covered them).

## Method

Scripts in my scratch folder (tally, waits, friction, landcost, orchcost, checks_index, rustdead, knipcheck). Phases
were classified by tool and command text; misclassification is likeliest between "polling" and "game run". Spot
checks ran on my own Vite (6187) with 3 cores; the Rust scans and timings claimed 3 cores and ran in scratch copies.
Advisor called twice. Before ranking it asked for one unit across proposals, harness adoption before a new tool,
landing rates since the 11-17 fix, a real edit for the Rust timing, and not contradicting your 500k and overnight
rules. At the end it caught three measuring slips, now fixed: handover counted from the wrong moment, landing costs
that were caps, and a pattern that matched "finally" as "final".
