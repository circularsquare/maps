# T-4309 Track limits worked out by the lines an edit moved (agent tracklimits, 2026-11-28)

From T-4299: the track limits (`Capacity::line_limits`), with the fleet needs, markers and turn limits built on them,
were worked out whole every model state. Goal: only the lines an edit moved, under 3 ms a state on Asia.

## What was built

`sim/src/track/capacity/limits.rs` (new), small hooks in `capacity.rs`:

- **The index (the "B1" of notes/T-4267.md, for the C stages to read):** `Capacity` keeps `by_line`, each line's limiting
  resources (Follow and Wait resources are not limiting, so not in it). Read it with
  `Capacity::resources_of_line(net, l)`, or run the per-resource limit code over some lines' resources only with
  `each_limit_of(net, lone, lines, at)` (`turn_limits` does). Kept by `update`: `index_drop(r)` before each
  `swap_remove` (the last resource takes r's place: the lists and the kept limits' resource ids are renumbered) and
  `index_attach(first_new)` after the builds. Built on first use from the resources; a fresh `Capacity` (`build`) has
  none. It is a `RefCell` inside `Capacity`, so `line_limits(&self)` stays a read.
- **The limits kept per line:** `line_limits` worked out again only for dirty lines. A line is dirty when a resource it
  used was dropped or built (`update`), or when a line sharing a resource with it changed what the limit reads: its
  `line_tph` or its one-train-or-none test (`occ_at`), compared with what the last pass saw, so a caller that moves rates
  without telling the capacity is still right. A change of the worked slots or of the line count marks every line.
  A dirty line takes the tightest over its resources taken in resource order, each resource worked out once for all its
  dirty lines: the same code (`each_limit_at`) and order as the whole pass, so the result is the same to the bit,
  including which resource wins a tie.
- `turn_limits` reads only the candidate lines' resources (was every resource).
- In test builds `line_limits` also runs the whole pass and asserts equal, so all 826 + 1063 Rust tests (random edit
  sequences included) check the kept limits against the whole.

## Figures (no change expected, none found in the sim)

- Real NYC save, native, agent profile (ignored test `limits_on_the_real_save`, 109 lines, 3512 resources): kept limits
  equal the whole pass to the bit at load and after three lines' rates moved. Whole pass 205 us; kept pass: first 275 us
  (builds the index), unchanged 5 us, three lines' rates moved 23 us.
- perf_bench NYC (1 of the 2 runs, NOISY: 8 other cores claimed): 12672577 rail trips/day; the ledger's v0.4.7, settlestop
  and corridors3 lines all read 12672459 (+118, 0.001%). The limits are bit-identical (above), so I do not read this as
  from this change: the tree is on master after T-4220 stage 9 and the ledger has no master line since. No master
  baseline for nyc, so not separated. Other numbers are noisy: cpu 198.8 s, tab 2070 MB, 63.3 MB down.
- Asia (asianita-day568, native agent profile, ignored test `station_limits_probe_tests`: four stations on edge 1482, 242 lines,
  5833 resources; clicks 1-2 of the run, ms): the limits pass alone 0.4-0.6 whole, 0.015-0.07 kept. A state's model calls:
  peek_changed_lines 2.2-2.7, take 0.06-0.14, line_weekends 0.3-0.5, profile_meta 0.25-0.45, markers+full_track x5
  0.2-0.3, turn_limits 0.03-0.04: 3.3-4.1 ms, not under 3 ms (this build runs about 1.4x slower than release, and the
  harness is Rust native, not T-4299's Node probe, so the sums are not set against its 5.1). About 0.5 ms a state
  (10%) saved. What stays in `peek_changed_lines`: the moved lines' stamps (0.8-1.5) and every line's money key with
  fleet needs and running cost (about 0.7), then `profile_meta`'s copy and the markers scans.
