# T-3939: the clock worker's memory on many-zone phone saves (agent clockmem, 2026-11-21)

From T-3781: on an iPhone reporter's 13-zone Tokyo-start save (B, 1,646 stations) the clock worker held 358-359 MB
settled (JS about 150, buffers 110-115, WASM 93). The players' saves were deleted after reading, so this used a
stand-in.

## The stand-in

`artifacts/trainworld/t3939-standin-13zones.save`: the shipped Tokyo real network (`data/packs/real/tyo.save`, 1,933
stations, 133 lines) with about 480 stations on 32 more lines built by edit ops (scratch `clockmem/build.mjs`, then
`construct.mjs`): a Tohoku trunk Utsunomiya to Aomori, the Ou line Fukushima to Aomori, Joetsu, Banetsu, Joban
north, Nagano, and short lines in Sendai, Niigata, Hachinohe and Hirosaki, every station built. 2,411 stations, 165
lines, 13 zones opened (tyo tcg gnm yns szo fks sdj iwt aom ygt akt nig ngn), 5 fine (the load's own choice).

**It does not reproduce B's clock worker.** On the emulated iPhone it settles at 268 MB (JS 67, buffers 69, WASM 132),
the shipped Tokyo start's 258 (63, 63, 132) plus 10. B's extra JS and buffers (about 140 MB over the Tokyo start)
are not named here. Tried: 10 fine zones in the header (after build: 54 + 69 + 117 against 53 + 71 + 117 with 5, the
same rail trips: fine zones do not move the clock worker); the street speeds and water masks the clock worker keeps
per zone, 2.0 and 2.2 MB in all for these 13 zones (`packsizes.mjs`), so buses across every zone would not reach it
either. Not tried: a long-played game (B was rev 230), many trains per line, the schematic open.

## Method

As T-3160 stage 3: scratch production builds of the tree (`TW_LINK_PACKS=1 vite build --outDir`, one with `--minify
false` for named heap snapshots), `checks/static-serve.mjs`, the stage 3 driver (emulated iPhone, a New York game then
the save imported), clock worker JS used, buffers and WASM after the final. Heap snapshots of the clock worker summed
by dominator (`snapsum.mjs`: retained size per module variable). The WASM's contents natively: `boarding_bench`
(made-up riders on every line, three kinds of day) now prints the live heap after each stage when built with
`--features demand` (its counting allocator), and times the readouts.

## The cuts

1. **The boarding account's stop times** (`sim/src/track/boarding.rs`): each stop's departures in their order kept
   their time of day as an f64 per trip and stop (`order_t`). Now each departure keeps its unwrapped first-stop time
   (`dep0`) and the time at a stop is worked out where read (`RunAccount::leaves`, `stop_times`): the same sum and
   the same remainder, to the bit (`day_rem`: `rem_euclid(DAY)` without the library call; a test checks it bit for
   bit to 1e9 s and on either side of whole days). Account 95.5 -> 70.9 MB on
   the stand-in, 93.3 -> 68.6 on the Tokyo start; live heap 111.9 -> 88.4 and 106.5 -> 83.0. `TW_DUMP` (every line's
   account and periods on three kinds of day, today, the past day, the hour's platforms) byte-identical before and
   after on both saves. Cost, natively on the stand-in: `today` 48-56 -> 66-68 ms a call; every line's account and
   periods on three days 1.5-1.7 -> 2.4-2.5 s for five passes; the account's steps and the hour's platforms
   unchanged within noise.
2. **The bands' rule closure** (`app/src/map/lineBands.ts`): the result kept for an unchanged network no longer holds
   `rule`'s closure; asked of a kept result (only `checks/t1799-bands.mjs` asks), one whole pass is made and kept
   for the asks after. 18 MB of JS on the stand-in.

### The cut: queues kept only where they are not 0

`q_after` (riders left on the platform as a train leaves) and `gone` (riders who went another way then) are 0 on
almost every train. `RunAccount::queues` (`Queues` in `sim/src/track/boarding.rs`) now keeps a bit per trip and stop,
the count of set bits before each 64, and the pair of numbers only where either is not 0 (by bit pattern, so a -0.0
is kept too). Each read is a bit test and a popcount. Built from the dense arrays at the end of each run's simulation
(those last only while one run is worked out).

- In the game (stand-in, emulated iPhone): queues 24.9 -> 0.6 MB; account 69.3 -> 45.0; WASM in use 97.8 -> 73.5,
  memory 117 -> 93 (clock worker 30 s after the final 239 -> 218 MB). Rail trips 17,427,200 in both.
- Natively (`boarding_bench` on the stand-in, made-up riders, one line in seven crowded): account 70.9 -> 45.5 MB,
  queues 0.6 MB. `TW_DUMP` (every line's account and periods on three kinds of day, today, the past day, the hour's
  platforms) byte-identical before and after. Times, one run each: three kinds of day's accounts 987 -> 1,046 ms, the
  readouts x5 456 -> 500 ms, the hour's platforms 10.5 -> 13.9 ms a call (once a game hour).
- Test `queues_read_back_to_the_bit`; both suites pass (739 + 968).

### Also fixed: perf_bench built a stale WASM

`perf_bench build <tree>` shares one Cargo target dir across trees; Cargo keeps a unit's source times relative to its
package, so a tree whose edits were older than that dir's last build (any other tree's) was taken as built, and its
dist carried the other tree's WASM with no warning (this task's first measuring build). `build` now touches the tree's
`sim/src/lib.rs` first.
