## What "extract date" can mean here

Each region's Geofabrik `<extract>-latest.osm.pbf` is downloaded when the region is read and deleted
after it (the batch report says "deleted N files"). Nothing in the plan rows or reports records the
file's own snapshot time. What survives is the download time, from the region read logs
(`artifacts/trainworld/world_run/<batch>/regionN.read.log`, first line `### <time> @read_extract
<extract>`) minus the download minutes in the batch's `report.txt`, plus file times in
`data/raw/osm/`. Times below are local (UTC-4).

The only PBFs still on disk are three, whose headers I read (`osmosis_replication_timestamp`):

| File on disk | Downloaded | Snapshot in the file |
|---|---|---|

So an extract's data is from the evening of the day before the download, or the evening before that
when Geofabrik's newest daily file was not up yet (Toulouse: 30 hours). Read every date below as
"data from 0.5 to 1.5 days earlier"; the exact snapshot is known for Toulouse only.

## One more thing the dates show

The outline layer (`<extract>.admin.fgb`) is written by the first read of an extract and kept, while
the other layers are read again for each batch. A pack built from a later download therefore has its
outline from an older extract: Stockholm (admin 10-17 23:57, rest 10-19), Amsterdam (10-17 00:19,
rest 10-19), Dublin (10-17 02:46, rest 10-19), Rotterdam as above, and Nigeria's three packs (10-16
19:23, rest 10-17). Same-day differences of a few hours are left out. Not a fault, but the date of
an outline is not always the date of the roads.

Proposal (T-766): `world_run` writes each extract's PBF header snapshot time into the row's `run`
before it deletes the file, so the next batch needs no archaeology.
