# T-4410 — Gemini agent reports and claims

## Root causes in `trainworld/tools/gemini_agent.py`

1. **`claim()` failed when `cores.py` had to wait at the cap**:
   - `cores.py claim` writes its `"waiting for N cores: cap ..., claimed ..."` status lines to `stderr`, and writes the granted core count to `stdout` (`cores.py` lines 219-224).
   - `sh()` concatenates `(r.stdout or "") + (r.stderr or "")`. When `cores.py` waited and then succeeded (exit 0), the joined output ended with the `stderr` waiting line rather than the `stdout` integer.
   - `claim()` checked `lines[-1].strip().isdigit()`, saw the waiting line, returned `0`, and `run()` raised `RuntimeError("cores.py claim for %d cores failed or timed out")` without calling `release(a.name)` (because `granted` was `0`), leaving the cores claimed until the runner PID exited.
   - **Fix**: `claim()` now calls `subprocess.run` directly, parses `r.stdout` only for the granted integer, logs both `out=` and `err=`, and calls `release(name)` if `r.returncode == 0` yet no integer was parsed. If a run fails after `claim()` returns a grant (`granted > 0`), `run()`'s `finally` already calls `release(a.name)`.

2. **Interim lines ahead of the final answer in reports**:
   - In `stream-json` mode, `agy` emits a `step_update` (`step_type: "agent_response"`, keyed by `step_index` within each turn) for every interim text message before a tool call, and concatenates all of them into `result.response`.
   - `agy_session.reply_text(res, MARK)` only stripped `MARK` from the end of `res["response"]`, leaving all earlier interim `agent_response` steps in the report.
   - **Fix**: Added `final_reply(log_path, res, marker)` in `gemini_agent.py`, which reads `run_dir / "agy.log"`, resets per-turn `step_index` buckets at each `user message` / `result` boundary, and returns the last `agent_response` step containing `marker` (up to `marker`, `.rstrip()`), falling back to `agy_session.reply_text(res, marker)` if not found. Used for both `MARK` and `ANS_MARK`.
