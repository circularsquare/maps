# T-002 render spike: notes

Done 2026-10-08. Throwaway code in `app/src/` (`main.ts`, `trains.ts`, `synth.ts`); the page at
`localhost:8800/trainworld/` is now the spike.

## What was built

- **Basemap**: MapLibre GL JS 5.24, OpenFreeMap Positron, every symbol layer's text repainted
  `#b0b0b0` with a soft white halo.
- **Synthetic network** (`synth.ts`): 500 lines around New York, deterministic seed. 30% radial
  from eight hubs (10-40 km), 30% crosstown roughly tangential (5-25 km), 40% random walks
  (5-40 km); 10,633 km of line in total. Polyline vertex every 250 m. Built in ~30-40 ms on the
  main thread.
- **Coordinates**: "local units" = web mercator metres relative to an origin at (-73.98, 40.73).
  The JS side multiplies MapLibre's matrix by a local-to-world matrix in float64 and uploads the
  product, so the GPU only ever sees small numbers and float32 is precise to about a centimetre.
- **Lines**: one instanced quad per polyline segment, screen-space width, static buffer.
- **Trains** (`trains.ts`): each line resampled every 50 m into an RG32F texture (2048 wide);
  a line table texture holds first sample, count, length and palette index. Per train one
  instance: `uint line` + `vec3 (offset at reference time, speed, reference time)`, 16 bytes,
  uploaded once. The vertex shader computes `d = mod(offset + speed * (t - t_ref), 2 * length)`,
  folds it for out-and-back, fetches the two neighbouring samples, interpolates, orients the quad
  along the track in screen space. Per frame the CPU sets uniforms and makes two draw calls.
  Train size is 150 x 30 m, never smaller than 12 x 6 px, with a 1 px white edge.
- **Clock**: sim seconds, anchored to wall time. `triggerRepaint` only while running; pause stops
  repainting entirely. `visibilitychange` to hidden freezes the clock and stops the loop.
- **Two modes**: `?mode=layer` (default, the spec's design: a MapLibre custom layer) and
  `?mode=overlay` (the same renderer on a separate WebGL2 canvas over the map, drawn from its own
  `requestAnimationFrame`, and from MapLibre's `render` event while paused and panning).
- **Readout** (top left): trains JS ms (our `render()` wrapped in `performance.now()`), map JS ms
  (MapLibre's whole `_render`, which includes ours in layer mode), GPU ms for our two draws
  (`EXT_disjoint_timer_query_webgl2`, when the browser exposes it), frame interval and fps over
  the last 120 frames, the clock. URL parameters: `trains`, `lines`, `speed`, `mode`,
  `paused=1`. `window.spike` exposes `stats()`, `reset()`, `play()`, `pause()`, `map` for probes.
- The T-001 worker still loads and answers; its status is the readout's last line.

## Surprise: headless Chrome here uses the real GPU

The brief expected SwiftShader. On this machine `--headless=new --enable-unsafe-swiftshader`
still gave `ANGLE (AMD Radeon RX 6600, Direct3D11)`, and the timer query extension was present.
So the GPU numbers below are real, but for a desktop RX 6600, not a mid-range laptop. (The maps
memory note `reference_headless_map_screenshots.md` says headless is software GL; not true here.)

## Numbers

Headless Chrome on Anita's desktop, 1280x800, dpr 1 unless noted, Chrome pinned to 2 cores,
whole-network view (zoom 10.2, nearly every train on screen). CPU is the whole Chrome process
tree (browser, renderer, GPU process), % of one core, 6-8 s windows. Frame interval was 16.7 ms
(60 fps) in every playing case, worst single frame 17-29 ms.

| 50k | 0.05-0.07 | 2.0-2.3 | 0.23 | 34% | 34% | 1.2% |
| 100k | 0.05 | 2.0 | 0.36 | 25% | 30% | 1.6% |
| 300k | 0.04-0.09 | 1.8-2.0 | 0.9-1.4 | 29% | 32% | 1.6% |
| 1M | 0.05-0.07 | 2.0 | 2.7 | 27% | 29% | 0.5% |
| 3M | 0.05 | 2.0-2.3 | 7.9 | 23% | 32% | 1.6% |
| 10k, dpr 2 | 0.05 | 2.1 | 0.23 | 27% | 35% | 0.3% |
| 100k, dpr 2 | 0.04-0.09 | 1.9-2.0 | 1.0-1.9 | 26% | 33% | 2.1% |

Overlay mode (separate canvas, 4x MSAA):

| Trains | Trains JS ms/frame | Map renders/s while playing | GPU ms | CPU playing | CPU playing + panning | CPU paused |
|---|---|---|---|---|---|---|
| 10k | 0.07 | 0 | 0.22 | 15% | 37% | 1.0% |
| 100k | 0.28 | 0 | 0.79 | 16% | 35% | 0.0% |

Paused with the camera panning costs 31-51% in both modes; that is MapLibre itself redrawing
the basemap at 60 fps and has nothing to do with trains.

## What it means

- **The train design works.** Our per-frame JS is a constant ~0.05 ms at any train count, because
  it is two draw calls and a few uniforms. Train count only moves GPU time, which is linear at
  about 2.6 ms per million trains on an RX 6600. 60 fps held up to 3M trains; it did not break in
  this test. A laptop GPU will be several times slower, which still leaves 10-100k far inside
  budget. Spec target (10k trains, main thread under 4 ms) is met on the main thread with room.
- **The real per-frame cost is the basemap, not the trains.** A custom layer lives inside
  MapLibre's render pass, so each train frame redraws the whole basemap: ~2 ms of MapLibre JS per
  frame and about a quarter of a core at 60 fps. The overlay canvas leaves MapLibre idle while
  the camera is still and halves CPU while playing (15% vs 26%). That matches the seoulriders
  measurement in memory `reference_maplibre_animation_loop_cost.md`. Overlay costs: trains are
  always above labels, a separate GL context cannot share buffers with MapLibre, and while
  panning the overlay may lag the basemap by a frame (not visible in a static screenshot;
  needs a human eye). Follow-up task added to choose.
- **Paused is idle**: 0-2% of a core, same as a blank page.
- `?mode=overlay` GPU time is higher (0.79 vs 0.36 ms at 100k) because its canvas asks for 4x
  MSAA; MapLibre's own canvas has none.

## Not tested

Since done in T-016, T-017 and T-018 (notes/T-018.md): MapLibre 6.13, keyframes re-based each
game hour, 10 fps when unfocused, hidden and unfocused measured; globe found not to work (T-033).
As the spike first stood:

- Hidden-tab suspension: implemented, not exercised headlessly.
- Unfocused but visible window: keeps the full 60 fps loop (no blur handling); see follow-up.
- Float32 time: `u_time` is sim seconds since midnight-ish; `speed * t` grows without bound, so
  precision degrades over many game days. Re-basing keyframes is a follow-up.
- Globe projection: the shader is mercator only.

## How it was measured

`scratchpad` copies of `neighborhoods/tools/screenshot.js` (port from `CDP_PORT`) plus a
`measure.js` that loads the page, then for each of playing, playing + panning (per-frame
`jumpTo` in a small circle), paused, paused + panning: waits 1.5 s, resets `spike` stats, samples
CPU of the Chrome processes whose command line holds the private `--user-data-dir`, reads
`spike.stats()`. Not kept in the repo; rebuild from this description if needed.
