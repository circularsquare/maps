# T-4583: demand packs open after the first state (agent mapfirst, 2026-11-28)

Her yes 11-28 to the T-4230 ask. Measurements behind it: notes/T-4230.md.

## What changed (tree mapfirst, not committed)

- workers/clockClient.ts: `onFirstState(f)` calls `f` when the clock worker's first whole state (no `rows`) arrives at the page; `awaitFirstState()` re-arms it.
- workers/demandClient.ts: the existing T-173 `held` list (other solving workers' city packs wait for worker 0's warm-up) now also waits for `stateHold`, which ends at the first whole state or after 20 s (`STATE_HOLD_MS`). `postMarkets` waits on it too. Worker 0 and the aux worker still open their packs at once, so one solving worker opens at once and the rest after. A game loaded into a page already running (the bench, play.mjs) re-arms through `gameLoadSeq`.
- Pool of 1 (a picked count of 1, or Auto on a small machine) holds nothing but the markets; 2+ workers (Auto on her machine, a picked count) hold the workers above 0.

## Measured

Typecheck passes. One `perf_bench` NYC run (invocation 1 of 2), NOISY (11 other cores claimed, 3 cores, 2 demand workers): map 9.5 s, trips 77.8 s, edit shows 0.4 s, tab 2,175 MB, 63.5 MB down, rail 12,677,356/day (v0.4.7: 12,672,459, +0.04%). Not comparable with the stored lines, so no claim on the speed.

One dev game run (play.mjs on the real save): the new gate fired at the first whole state, then again at the save's own (4.8 s and 18.2 s; the first is the boot game). Both bench and play.mjs boot a new game and import the save, so packs for the boot game open beside its state; the import's own packs wait for the import's state (re-arm works). A page that opens a save as its first state was not run: no stored slot to reload from (a ?new=1 game writes none).
