# T-3397: Research browser risks to save integrity

P2, accounts-server. Open; filed at Anita's request, 2026-11-15.

## Context and goal

After the Safari compression incident and v0.3.5 fix, Anita asked for a brief investigation into whether documentation and known browser bugs could predict similar failures elsewhere. Research first; testing browsers is optional, not a completion requirement. This is not a broad compatibility or security audit.

## Scope

- Review Chromium-based browsers, Firefox/Gecko, and Safari/WebKit across relevant desktop/mobile versions. Identify the actual engine on each platform rather than assuming each browser brand is an independent implementation; consider embedded/in-app browsers where a documented issue makes them relevant.
- Trace known bugs and restrictions to the game's actual save paths: compression/decompression and stream completion, IndexedDB transaction failure/durability/quotas/eviction/private mode, worker messages and transferable buffers, cross-tab locks, interrupted cloud downloads/uploads, and memory failures during save/load. Prioritize anything that can silently acknowledge an incomplete write, replace a healthy save, or make valid saves unreadable.
- Distinguish corruption from lost/evicted storage, unsupported features, temporary inability to read, and failed simulation startup. Do not label a theoretical concern or missing feature as a confirmed corruption bug.
- Assess which risks v0.3.5's bundled codec and byte-for-byte compression verification already avoid, and which remain in browser storage, cloud handling or other native-codec consumers. Cross-reference T-3395's planned detection and pinned recovery; do not duplicate it.

## Deliverable and stopping point

A short evidence table: engine/browser + platform/version; documented bug/restriction and trigger; primary-source link; whether reachable in our code; protected/residual/uncertain status; smallest useful follow-up. Separate confirmed documented behavior from inference, include affected/fixed versions when supported, and avoid treating old fixed issues as current risks without checking version applicability.

Use official browser documentation, release notes and engine bug trackers. Starting reference: [WebKit 254021](https://bugs.webkit.org/show_bug.cgi?id=254021), the compression flush bug behind the Safari investigation; see notes/jordan-save-investigation-2026-11-15.md for our evidence and limits.

Done when the relevant save mechanisms have been reviewed and the short risk table plus prioritized recommendations are recorded, including an explicit "no additional documented risk found" where appropriate. File specific actionable gaps or fold them into T-3395. No testing matrix, production deployment, player-data access, or implementation is required for this research task.

## Findings

Agent saverisk, 2026-11-17. Research and code reading only: no browser tests, no player data, no server access. About 25 web searches and fetches. "Doc" marks behaviour stated by an official source or engine tracker. "Inference" marks my reading of how it meets our code. Nothing here was reproduced in a browser.

Engine identity: every iOS and iPadOS browser (Safari, Chrome "CriOS", Firefox "FxiOS", in-app browsers) runs WebKit, so a WebKit bug follows the iOS version, not the brand. Apple has allowed other engines in the EU since iOS 17.4. I did not check whether any major browser ships one, so that is uncertain. Desktop and Android Chrome, Edge, Opera and Android WebView are Chromium. Firefox is Gecko everywhere except iOS. Our minimum is Safari 16.4, Chrome 91 and Firefox 89 (docs/architecture.md).

Save paths read: `workers/gzipCore.ts`, `gzip.ts` and `gzip.worker.ts` (pako, round-trip check); `workers/saveFile.ts` (`encodeSave`, `decodeSave`, `checkSave`, IndexedDB `anitabuilder`/`saves`, `writeSlot`, `writeBackup`, `backupBeforeReplace`, the good copy, `listSlots`, `listBackups`, `leaseSlot`); `workers/clock.worker.ts` (`autosave`, `saveByHand`, `keepOtherTabs`, `hold`, `fetchBlock`); `workers/cloud.ts` (`call`, `fetchGame`, `upload` via FormData); `game/saveSafety.ts` (`persist()`); `game/realGraph.ts`; `ui/FeedbackPanel.tsx` `browserOf`; shonei-server `trainworld_games.go` and `trainworld_community.go` download handlers.

### Prioritised recommendations

1. **Ship T-3395** (deploy server stages 1 and 3, then publish stage 2). Of all the protection still to come, this is the most: it catches cut uploads and downloads, bad bytes that come back from storage, and gives a pinned copy outside the browser.
2. **T-3610 (P2)**: one unreadable IndexedDB record must not hide every save. Lost large-value files are common enough that Chromium gave them their own error name in Chrome 130. Today one bad record takes down the whole list.
3. **Whole-origin loss** (row 6) is the most likely way a player who has no account loses everything. Code can't fix it. Keep steering players who play local-only to sign in or download (the existing card).
4. **T-3611 (P3)**: check the lease again right before the slot and backup writes.
5. **T-3612 (P3)**: feedback names the WebKit/iOS version for iOS browsers, so the next report like Jordan's can be placed in a known bug's version range.
6. Optional, not filed: bundled inflate for terrain and real-network graphs (Safari 16.4-16.5 only); `messageerror` in `gzip.ts`; "or reload the page" in the could-not-save text; watch Chromium's SQLite migration of existing data.

The v0.3.5 codec and round-trip check close the Safari 16.4-16.5 compression bug for saves on every engine. I found no other documented engine bug that writes a cut-short or wrong save and reports success. What remains is loss (eviction, private windows, crash durability), records that can't be read (row 4), and one app-level race (row 9).

Advisor called once before these recommendations. It changed four things: I looked up the shipping fix (Safari 16.6), which narrowed row 1 and demoted the terrain change to optional; I added the engine identity, Lockdown Mode and whole-origin rows; I added the Gecko search (row 5); and for T-3610 it pointed out that catching each read's promise is not enough: the error event also has to be cancelled, or each record read in its own transaction.
