# T-026 demand in the app (with T-021, the worker pool)

Done 2026-10-09 by the demand agent. The game now solves New York's commute demand on the
player's network in a pool of Web Workers, after every service change, without touching the main
thread: the top bar's mode split, the line inspector's riders, fullest train, fares and boardings
per stop, and the station inspector's boardings all come from it.

## What runs where

| Piece | File |
|---|---|
| Rust API one worker owns: `DemandApi` (open the pack, `set_network`, `solve`, `crowd`, results per route node), `demand_periods()` | `sim/src/demand/api.rs` |
| Kernel additions: reverse-run hop times, boardings per route node, the walk share | `sim/src/demand/kernel.rs`, `network.rs` |
| The worker: owns a `DemandApi` and a fixed set of periods; free flow for each, then crowding rounds | `app/src/workers/demand.worker.ts` |
| Messages | `app/src/workers/demandProtocol.ts` (re-exported from `protocol.ts`) |
| Main-thread client: pack fetch, pool, snapshot packing, aggregation | `app/src/workers/demandClient.ts` |
| What the UI reads: `modeSplit`, `demandUpdating`, `lineDemand(id)`, `stationDemand(id)`, `demandView` | `app/src/game/demand.ts` |
| The five periods for the main thread, checked against Rust's at start | `app/src/game/periods.ts` |
| T-005's hand-made network as a snapshot, for `?demandTest=1` | `app/src/workers/demandTest.ts` |

**Flow.** The clock worker sends a `NetworkSnapshot` after each service change (debounced 0.5 s
there, notes/T-025.md); `main.ts` hands it to `submitNetwork`. The client drops it if nothing
demand reads changed (a rename), packs it into flat arrays (`DemandNetwork`) and posts it to every
worker with a new version. Each worker rebuilds station access and subzones once (20-30 ms), then
solves the free-flow estimate of each of its periods, then one crowding round of each, posting a
result per period and round. When all five periods have a result of a round, the client builds a
new `DemandView` and swaps it in whole: the bar moves twice per edit (free flow, then refined).

**Never blocks.** Workers check for a newer network between periods (a `MessageChannel` yield), so
a newer snapshot supersedes a running solve within one period's work (~0.35 s) and the old one's
remaining results are never sent. The client ignores any result whose version is not the newest.
The UI keeps the last finished view until the next one is complete. While a solve runs,
`demandUpdating` is true and the mode-split bar is drawn at 60% opacity (no animation). No long
tasks were recorded on the main thread during any of the timing runs below.

**`?demandTest=1`** makes the pool solve T-005's hand-made network (25 lines, 434 stations; a
port of `synth_network`) and ignore the clock's snapshots, for checks before anything is built.
`?demandWorkers=N` (1-5) overrides the pool size. With `?debug=1`, `window.twDemand` has the log
of solves with their timings, `resubmit()` and `view()`.

## Decisions made here

- **Pool size: half the logical cores less one, at most 3, at least 1** (16 threads -> 3, 8 -> 3,
  6 -> 2, 4 -> 1). Periods go to workers by index (worker i: periods i, i + n, ...). Three
  workers land the split in two period-times and leave most of the machine to the browser, the
  clock worker and the rest of Anita's desktop; five would halve that again (numbers below) at
  the cost of five busy cores for most of a second per edit.
- **Mode choice is not split by origin zone across workers.** At three workers it would save a
  sixth (five periods in thirds is 1.67 period-times against 2), and it needs a reduce step (sum
  the S x S rail tables, then assign where the skims live) for every round. Worth it only if a big
  network makes one period take much longer than a second (follow-up).
- **One WASM module for track and demand.** The app's `npm run wasm` now builds with
  `--features demand`. Both kinds of worker load the same file (the main thread loads none), so
  separate track and demand packages would download the track model twice; one module adds 222 kB
  (74 kB gzipped) to it: 421 kB -> 643 kB, 160 -> 233 kB gzipped. The T-005 benchmark export is
  behind a new feature `demand-bench` (it cost another 78 kB). Most of what is left is
  `serde_json` for the pack header (follow-up).
- **A warm-up solve at worker start.** V8 runs a wasm function's first call in its baseline
  compiler and only later calls get optimised code; the long pair loop is one call, so the first
  real solve took 1.09 s a period against 0.35 warm. `DemandApi::warm_up` solves a two-line cross
  at the pack origin once after opening the city (~20 ms) and the first real solve is as fast as
  the rest.
- **The pack is fetched once, on the main thread**, and each worker gets its own copy as a
  transferred buffer (the last gets the original). 34-88 ms to fetch 8.5 MB from the local server;
  6 ms of main-thread time to copy and post for three workers (14 for five), once at city open.
  Workers fetching it themselves would triple the download while `serve.py` sends no-store.
- **Periods** are `PERIOD_HOURS` / `PERIOD_LEVEL` in `sim/src/track/params.rs`, the one
  definition: the kernel's `PERIODS` is its length, `api.rs` reads it, and the main thread's copy
  (`game/periods.ts`) is checked against `demand_periods()` when the workers start (a console
  error if they differ). `game/clock.ts`'s `demandAt` now reads that table; it had its own hours
  (high 16-19, low 23-6) that disagreed with the schedules.
- **Trips per period.** Each commuter makes a trip to work and one home a day (17.2M trips from
  8.61M commuters). Share of the day's trips to work starting in each period 70 / 12 / 6 / 4 / 8%,
  trips home 2 / 18 / 58 / 16 / 6% (6-10, 10-16, 16-20, 20-24, 0-6). Judgement after US commute
  start times; ACS B08302 (time leaving home) would fit the first (follow-up).
- **Trips home are the morning's station pairs reversed.** Mode choice runs home -> work with the
  period's combined share, and the rail matrix is split `to_work x OD + to_home x OD^T`. Riders
  go back the way they came, which is right for park-and-ride (the car is at the morning's
  station). Costs are nearly symmetric within a period (same headways); what it misses is the
  return direction's crowding in the choice.
- **Busiest hour factor** per period (crowding is judged at the busiest hour): 1.4, 1.15, 1.4,
  1.3, 1.5.
- **Walking**: of the trips not taken by rail, a share walks by zone-centre distance,
  `1 / (1 + exp((d - 1.7 km) / 0.4 km))`: 84% within a 2 km zone, 32% to the next zone, 6% two
  away. With no rail, 5.9% of New York's commutes walk (ACS: about 6% of the region's commuters).
  The rest drive (car, bus, taxi: SPEC's "other"). Computed per zone pair once per city, and in
  the pair loop only as one multiply-add per zone pair (rail trips taken from would-be walkers).
- **Train capacity**: 44 seats and 160 at crush per 20 m car, times the snapshot's cars (a New
  York subway car). The kernel's per-kind capacities were for the hand-made network only.
- **One crowding round** after the free-flow estimate, as T-005; more rounds are T-022.
- **Riders before the first solve are blank**, not demo numbers; the bar shows the no-rail split
  (0% train, 5.9% walking) as soon as the pack is open.

## Numbers

Chrome 154 headless on Anita's desktop (16 threads; all CPU, no GPU work), through the harness
below, New York pack (202,337 cells, 6,154 zones), the hand-made network (434
stations, 25 lines, 6.59M subzone pairs a period), one crowding round. Five solves after start
each, plus one superseded; "split" is from posting the network to the five free-flow results
being published, "refined" to all five crowding rounds.

| workers | mode split updated | refined | per period, free flow / crowding round |
|---|---|---|---|
| 1 | 1,570-1,690 ms | 3,110-3,320 ms | 290-420 / 280-370 ms |
| **3 (default here)** | **720-830 ms** | **1,420-1,500 ms** | 330-450 / 310-430 ms |
| 5 | 360-470 ms | 720-840 ms | 320-430 / 330-400 ms |

- First solve after start, three workers: 735 ms to the split (1,564 ms before the warm-up).
- A network replaced 150 ms into a solve: the old one sent nothing; the new one's split landed
  1.0 s after it was sent (it waits for the period in flight).
- Per worker: WASM start 5-12 ms, pack parse + gravity rebuild 15-45 ms, warm-up 20-27 ms;
  linear memory 18.1 MB after opening the city, 22.8 MB after solving (it never shrinks).
- Station access and subzones on each new network: 21-48 ms per worker.
- Main thread: pack fetch 34-88 ms (async), copy and post to three workers 6 ms, aggregation of
  the results under a millisecond; no long tasks.

Against T-005 / T-020 (Node 22, the same kernel on the 74,920-cell pack, warm): free flow
287-290 ms, crowding round 257 ms, five periods one after another 2,660-2,700 ms. Chrome on one
worker: 3,110-3,320 ms for five, about 20% more, most of it the pack's 2.7x cells since T-013
(native today: free flow 260-300 ms, crowding 255-315 ms a period). Running three or five
workers at once costs each period 5-20% (memory bandwidth), not more.

Result on the hand-made network: train 21.3%, walking 4.7%, driving 74.0% of a day's commutes;
3.67M rail trips a day; by period 20.2 / 21.5 / 22.9 / 21.5 / 18.9% train. Native, the same
(`cargo test --release --features demand nyc_day -- --ignored --nocapture`): 22.0 / 4.7 / 73.4.
The difference is the two networks' run times (the port computes them in f64).

**How it was measured.** While the gameplay agent was rewriting the app (T-025) it did not
type-check, so the table comes from a page loading only the demand client and worker through
Vite's dev server (the same worker code and WASM). Once the app built again, the same probe on
`localhost:8800/trainworld/?demandTest=1&debug=1` gave the same: split 690-810 ms, refined
1,340-1,520 ms with three workers, pack fetch 97 ms, main-thread post 8 ms, and no long task on
the main thread after the page's start. Probe: wait for the first refined solve,
`twDemand.resubmit()` four times, then twice 150 ms apart, reading `twDemand.log`.

**End to end in the app.** Built through the clock worker's edits over CDP: a 10 km double-track
tunnel straight north-south through Times Square, five stations 2.5 km apart, constructed, one
line at 20/10/4 trains an hour. The snapshot reached the pool and the bar went from 0.0% train
(5.9% walking, 94.1% driving: the empty network at start) to 3.5% train, 5.7% walking; the line
inspector showed 595k riders a day, fullest train 100%, $1.72M fares a day and per-stop boardings
of 93k, 108k, 254k (Times Square), 69k and 71k.

## Serving the pack from R2 later

Today `packs/nyc.json` and `.bin` sit beside the page (`app/vite.config.ts` serves them in dev and
copies them into `dist/packs/`). Published, the page would fetch them from R2 (memory
`reference_map_publishing.md`: data on R2 `anitamaps`, the page on the website): a versioned path
such as `trainworld/packs/1/nyc.bin` (pack format, so it can be cached forever), uploaded
compressed with `Content-Encoding: gzip` or `br` (8.47 MB -> 5.15 MB gzipped), `Cache-Control:
public, max-age=31536000, immutable`, and CORS allowing the site's origin. The client's two
`fetch` URLs are the only change (a base URL constant); with the HTTP cache doing its job, a
return visit costs nothing. The clock worker's water-mask Range requests need R2 to answer Range on
the uncompressed object, so the `.bin` may want to stay uncompressed at rest and rely on HTTP
compression negotiated per request instead.
