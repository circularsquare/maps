# T-4004 Search finds far towns, and can never block the game

Anita, 11-21, after T-3997 capped search to towns within 200 km: "i'd rather have it eventually be able to show
towns more than 200km away. i often use it to find places that are far away ... it can come in slowly. also this
is the second time we've had to deal with search crashing so we should make sure that whatever solution we come
up with is general."

## Design

- **World name index** (`pipeline/place_index.py` -> `data/packs/place-index/`), from the 4,765 zones' place lists
  the packs already hold (3,646,809 places, 3.04M distinct names). No data run, no new source. Every word of a
  place's names (normalised exactly as the app does) is keyed by its first 3 letters (2 when the word starts with a
  CJK, kana or Hangul character); a name made only of shorter words is keyed by those words whole; a name of
  several words is also keyed joined ("santafe"). A key with over 2,000 rows is "deep": its own shard keeps the rows
  named just that (up to 2,000) and its best 400 others (kind, then population), and its rows go one letter further
  (265 deep keys in tier a, 698 in tier b; the manifest lists them, 7.2 KB). Keys are hashed (FNV-1a over code
  points) into 2,048 shards per tier: tier a city, town, borough, suburb, village (1,494,803 places); tier b quarter,
  neighbourhood, hamlet (2,152,006). A query picks its most telling word: one that ends on a non-deep key, longest
  first; else a deep key's best rows; else a short word; the words joined whenever that ranks as well.
- **Coverage sweep** (scratch `sweep.py`, mirrors the worker's `bucketOf`): every place searched far by its own
  normalised name. Before the joined keys and the named-first rule, 40,576 of 3,646,793 missed (1.1%: "Santa Fe",
  "San José", "Del Rio", "Pine Hill", Burmese villages; no cities). After: 0 missed.
- **Search in a worker** (`workers/placeSearch.worker.ts`, asked by `game/placeSearch.ts`): it loads the view's zone
  lists (30 km, as before, on first focus), the manifest, the query's tier a shard, its tier b shard, then (T-400 /
  T-3997 rule) the next nearest of the 48 zones within 200 km while fewer than five places match. One fetch at a time;
  at most 56 lists (the farthest from the view dropped) and 24 shards (oldest dropped); it posts the best eight
  after each arrival. The main thread does only stations, lines and zones (unchanged) and merges the eight rows.
  `isRegistryCity` moved into the worker. A missing index or shard just leaves far towns out.
- **Ranking**: score first (exact, starts, word starts, contains, ...), then places within 200 km of the view, then
  kind and population. A query of one or two letters (one CJK character) finds a far place only by its whole name,
  scored after every near match (otherwise "a" listed places called "A" in Vietnam and Norway above Astoria). A
  place more than 200 km away is tagged with its zone ("Hallstatt / Linz"). Rows arriving later don't move the row
  the player arrowed to.
- **Shipping**: `vite.config.ts` copies `place-index/` into the build, `freeze.py` freezes it, `deploy.py` uploads
  it with the other JSON (gzipped; warns when a build lacks it), `world_run.py` rebuilds it after each join beside
  zone_aliases.
- Normalising parity: `place_index.normalise` against the app's `nameMatch.normalise` on all 3.04M names: 21
  differed first, all CJK Extension H ideographs this Python's Unicode 13 doesn't know; kept as letters (Cn), 0 now.
  (Scratch: `parity_dump.py`, `parity.mjs`.)
- Station naming's `around()` now skips lists of zones farther than its reach, as the lists it loads grow over a
  session.

## Sizes

| | raw | gzipped (sampled ratio 0.36-0.40) |
|---|---|---|
| tier a, 2,048 shards | 159 MB; median 66 KB, 99th 245 KB, largest 324 KB | ~63 MB; median ~26 KB, largest 130 KB |
| tier b, 2,048 shards | 200 MB; median 88 KB, 99th 257 KB, largest 356 KB | ~72 MB; median ~32 KB, largest 129 KB |
| manifest | 7.2 KB | |

On R2: about 135 MB gzipped, 4,097 files, per release (the release prefix is versioned). A player fetches only the
shards of what they search: the manifest once, then two shards per query, about 60 KB gzipped typically, 260 KB
at worst. Build: 115 s on one core.

## Checks (real save T-007-real-nyc, 100x, headless, 3 cores; scratch `placeindex/bound.js`, T-3997's sampler)

After a cold reload and `wait.final()`, the clock started and set to 100x (it ran about 1.6 game hours a second
throughout), each query typed in the box and left 6-10 s:

| segment | main thread busy | worst gap | most behind |
|---|---|---|---|
| baseline, box closed | 0% | 104 ms | 1 h |
| control: a 7 s busy loop | | | 12.1 h |
| "s" | 0% | 118 ms | 1 h |
| "qzxv st" (250 ms a key) | 2% | 143 ms | 1 h |
| "san" (deep key), "new", "the", "cho" | 0% | 103-111 ms | 1 h |
| "a", "zhou" | 0% | 105-111 ms | 1 h |
| "xkcdfghjq" | 0% | 127 ms | 1 h |

"1 h" is the pull's own lag (the renderer asks for an hour's trips once it draws in it); no segment went past it,
while the busy-loop control did (T-3997 measured 12.6 h for the same control). Before T-3997, "qzxv st" left the
main thread 81-94% busy and trips up to 70 h behind. The main-thread search (stations, lines, zones) takes 15-27 ms
per settled query on this save (1,756 stations), unchanged.

Far towns from the New York save, each shown in 0.5-0.9 s on the dev server once the view's lists are in:
Hallstatt (Austria, tagged Linz), Bad Tölz (Weilheim-Schongau), Santa Fe, San José, Sandersville GA (Columbus, GA),
Shibuya (Tokyo), 上海. Picking Hallstatt moves the camera to 13.649, 47.562. Screenshot:
`artifacts/trainworld/t4004_hallstatt.png`.

The worker counts every match (near and index) before widening to more zone lists, and posts an answer only when it
changed, so a far town found in the index no longer pulls the 48 near lists.

## Not done

- Substring and nickname matches ("ville" for Hicksville, "south philly") still need the place's list near the view.
- A far exact match outranks a near substring match ("ville" lists Ville, Lyon before Hicksville).
- The index is per release on R2 (135 MB each upload); a fixed prefix like the terrain blocks would save that.
- Freezes made before this have no `place-index/`: a publish built on one ships without far search (deploy.py warns).
  A fresh freeze picks it up. The index is already written in the shared `data/packs/place-index/`.
- Typing a word that is a deep key and stopping there ("pine") lists that key's best 400 and every place named
  just that; the rest show once another letter or word is typed.
