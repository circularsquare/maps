# T-4184: the clock worker's next memory cuts on phones (agent phonemem2, 2026-11-24)

From T-3939 (notes/T-3939.md). Three exact cuts made in the clock worker; the reporter's extra memory named on a real
player save of the same shape; the network draw cache's cut described (map/network.ts has unlanded work, not edited).

## What changed

1. **The boarding account's stop order as 16-bit numbers** (`sim/src/track/boarding.rs`, `TripOrder`): each stop's
   departures in their order of the day were u32 account indices; now u16 when a run has at most 65,536 departures a
   day (every line the game makes), u32 past that. Natively on the stand-in (`boarding_bench`, made-up riders):
   account 45.5 -> 39.0 MB, "order, dep0" 14.5 -> 8.0, live heap 64.3 -> 58.1. `TW_DUMP` (every line's account and
   periods on three kinds of day, today, the past day, the hour's platforms) byte-identical before and after. Test
   `trip_order_reads_back_in_both_widths`. Times, one run each (machine busy): three kinds of day 831 -> 878 and 918 ms,
   readouts x5 363 -> 411 and 385 ms, the hour's platforms 8.6 -> 9.1 and 9.5 ms a call; within the bench's spread.
2. **The outlines copy as varints** (`map/coarseOutlines.ts` `placeOutlines`, `readOutlinesForPlaces`; the clock worker's
   `outlines` message): the page still posts `PackedOutlines`; the clock worker keeps the deltas as zigzag varints
   (1 byte for 1.12 M of the 3.02 M numbers, 2 for 1.89 M, more for 15 k) and drops the Int32 copy: 11.5 -> 4.7 MB.
   Every ring of the current `outlines.json` (7,280 rings, 3,023,866 numbers) decodes to the same doubles as
   `decodeRing`, and the Int32 extremes too (scratch test). Encoding takes 51 ms once, on the worker (desktop).
3. **The corridor records as typed columns** (`map/corridors.ts`, `Raw`): each edge's records of the tracks beside it
   were a JS array a sample (25 m), each array several times its numbers' size; now one `first` index and `edge`,
   `off` (Float64, unrounded), `at`, `rel` columns an edge, none for an edge with nothing beside it. Output
   identical: a scratch test runs the old and new `besideSamples` side by side on made-up bundles of parallel track
   (55 to 2,559 edges, up to 180,853 records), through six rounds of moved, dropped and re-added edges and an anchor
   shift: every `EdgeSamples` array and pair offset the same (Object.is), and the same objects kept between calls.
   On 12,975 edges of dense bundles: held 317 -> 183 MB, the first call 3.4-5.3 s both, an edit's call p50 54-85 ->
   45-74 ms. In the game on the real NYC save (many four-track trunks): the cache 36.8 MB before, 17.4 with the records as one
   Float64 array of fours (heap snapshot of a first version), about 10 with the columns (17 bytes a record instead of
   32; worked out, not snapshotted).

## The network draw cache (map/network.ts, not edited: unlanded work in tree editnetwork)

`netCache` is 21 MB on the stand-in, 29 on 4ethjj2g, 46 on t9gksxmu. On t9gksxmu (heap snapshot, summed by field):
per-edge strokes 15.8 (`seg` 4.6, `band` 3.4, `colour`, `dist`, `edge`, `flags`, `level`, `stretch` about 1.2 each), the
line pieces' strokes and the like about 10, facilities 8.8 (their `grid` 4.3 and `seg` 2.0 as plain JS arrays),
samples 4.0, speeds 3.2, and 17 in the Maps and entry objects themselves (7,337 edges). The cache keeps every piece's
strokes so an edit rebuilds only what changed; `StrokeSender` copies them into the arrays it posts (moved to the page).

Exact cuts, biggest first, for when editnetwork has landed:
- Fewer objects per edge: 17 MB of Map tables and entry objects for 7,337 edges (about 2.3 KB an edge before any
  numbers). One entry object with its arrays, no per-edge wrappers, would take most of it.
- Facilities' `grid` and `seg` (workers' rooms and car parks, T-3803) as typed arrays: about 4 of their 6.3 MB.
- Per-segment fields that are one value over a whole piece: `colour` (the line id, or TRACK for track) and, on track
  pieces, `edge` (one edge a piece): one number a piece, filled in by `StrokeSender` as it copies. About 2-4 MB here
  (from the field definitions; not checked piece by piece).
Together about 20-25 MB on t9gksxmu, 10-12 on the stand-in. The bands' `memo` and `orders` (map/lineBands.ts, 15.6 and
9.4 on t9gksxmu) are the next holders; also not edited here.
