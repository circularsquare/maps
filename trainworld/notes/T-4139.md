# T-4139 One edit-wait bench for every edit-speed task (agent editbench, 2026-11-23)

Anita, 11-23: how do edit-speed tasks land faster? Each agent re-measured edit waits with its own scripts on a loaded machine
(the same edit 2-5x apart between runs). This is one bench they all use.

## The command

    node trainworld/tools/edit_bench.mjs [--url http://localhost:PORT/] [--save asia,nyc] [--runs 3] [--calculating]
         [--compare <hash>] [--only ghost,track,station,construct,stop,reorder,undo,delete] [--label L] [--no-ledger] [--cores 4]
    node trainworld/tools/edit_bench.mjs --show [hash]

From the maps root or a tree, against your own Vite (default http://localhost:6158/; restart the Vite after app edits).
Each save is a fresh game opened from the file (checks/lib/play.mjs: real toolbar, pointer and panels), clock paused, the
trips final first (--final-wait, 900 s), then every action 3 times (--runs). `--calculating` adds a second game per save
where the edits start 3 s after the load, without waiting for trips.

Saves: `asia` = artifacts/trainworld/t3600-asianita-1852.save, `nyc` = trainworld/T-007-real-nyc.save; `--save <file>` takes another.
Where things go is computed from the save (the open ground off the end of its biggest rail line), so it is the same on
every run of one save. One run is 8 min on Asia, 3-4 min on NYC (cores permitting).

## What each number is (ms unless marked, median of 3, then the 90th percentile; with 3 samples that is the worst)

- ghost trail px: with the track tool on open ground (snap switches off), the pointer moves 6 px every 16.7 ms along a fixed
  path of about 1,000 px. At every frame, the distance from the pointer to the end of the ghost last drawn. Median and 90th
  percentile of those frames. Two frames behind at 6 px a frame is 12 px, the floor.
- ghost answer ms: from a ghost being asked of the track model to its answer, per request (median and 90th percentile).
- ghost rest px: the same distance once the pointer stopped (0 means the ghost lands on the pointer). ghost catch-up ms:
  from the last move to the ghost within 3 px.
- track piece: input is the press that places it. stand-in = the first frame drawing the dashed piece, built = the frame drawn
  after the network that holds it.
- station: shows and built are the same frame today (no stand-in event exists for stations; the ghost at the click is not counted).
- construct a line: the Construct button in the line's panel. delete a line: the "Delete line" button, to the frame without it.
- stop click: a press on a station of the big line in Edit stops, removed then added back. panel rows = the frame after the
  rows state; line path = the frame after the network that redraws the line.
- stop reorder: an adjacent swap by the same `edit({op:'setStops'})` the panel calls (no input event, so it times from the
  message). undo: Ctrl+Z.
- shows = the first frame that changes anything after the edit message; built = the frame after the drawn network.

How an edit is timed: in-page stamps (inputs, messages both ways, the state taken, renderer calls, `draw`) as in T-4097's
`inst.js`; the time is the end of the first `draw` after the event. Each stamp is wrapped only when it exists, so a build
that renames one loses that mark and no more. If an edit-speed task adds a new drawing path (pending edits), add its
renderer call to the stamp list in `INSTALL` and to `editsOf`, or "shows" will not see it.

## Steady numbers

- Claims 4 cores in the root ledger (`--cores`, at least 3), refuses to start when the ledger is over its cap, and appends
  nothing when it went over during the run (as perf_bench; `cores.py total --since`). Chrome and its workers are pinned
  (checks/cores.mjs) to the 4 quietest cores above Anita's two, measured for 3 s at the start, and run at above normal priority.
- A lock file (artifacts/trainworld/editbench/bench.lock) keeps two benches apart; the second waits up to 40 minutes.
- Each ledger line records `preBusy` (how busy those cores were with nothing of ours running), `busy` (over the game) and
  `loaded` (preBusy at least 15%). Compare only lines with a similar preBusy, or rerun. Dozens of other sessions share the
  machine and not all pin themselves, so the cores can still be busy.
- Ledger: the main tree's `trainworld/notes/edit-ledger.jsonl`, one line per (build hash, save, pass, action): median, p90, n,
  all samples, cores, mask, loaded. Hash = the tree's HEAD, plus +changes when app/ or sim/ differ. `--compare <hash>` prints
  the change per action as a percent of that build's newest line. `--build <hash>` overrides the name (a Vite on another tree).

## Spread, run B against run A on the same build

- Asia: 6 of 22 within 10% (the machine was 52-81% busy on the claimed cores; a run has 3 samples per action). Large moves:
  station 1265 to 770, delete a line 808 to 1184, undo 549 to 725.
- NYC: 9 of 22 within 10% in those two runs. The pattern is the load: the NYC run A had cores 21% busy before it and B 14%,
  and the numbers that moved were the short ones (track stand-in, Construct a line, undo).
- After that I raised the game's Chrome to above-normal priority and ran NYC twice more with cores at 5-14% busy before
  the game: 12 of 22 within 10% (not in the ledger, `--no-ledger`). Stable to 1-2%: stop click line path 736 and 741,
  added 698 and 694; station 190 and 191; delete a line 334 and 331; ghost trail 6 and 6. Not stable: Construct a line
  (804 and 324: one sample in the first run was an outlier), undo (131 and 186), stop click panel rows (102 and 126).
- So the "within 10% on each action" aim is met on quiet cores for the long edits (the ones worth speeding up) and not for
  the 100-200 ms ones or for any run on cores that are 50%+ busy. A before/after for a change under about 25% needs both
  runs with a low preBusy; run each build twice and look at the spread (`--show`), or use `--runs 5` (sites for up to 8 repeats).
  What would help more: other sessions' pins kept off the bench's cores, or the bench run while the ledger is nearly empty.
- Not met: the 90th percentile of 3 samples is the worst sample, so it swings; read the median.

## Limits

- The Asia solve finished in under 3 s of the load in these runs (`final: true` in the "calculating" lines), so that pass did
  not have trips calculating at the start; edits still start new solves, which is the part it measures. A pass that holds the
  solve back is not built.
- Reorder is not by dragging a stop row (the panel's drag is not driven); it sends the panel's own edit.
- Stations have no stand-in stamp, so station shows = built.
- One game per save and pass, one build per Vite. A dist build is not covered (the reorder falls back to `client.edit`).
- Playwright's mouse call costs 1-3 ms per move; the pacing is on an absolute clock, so the 12 px figure includes that.
- perf_bench's claim code is not shared (its helpers are inside its file); edit_bench repeats the 10 lines.
