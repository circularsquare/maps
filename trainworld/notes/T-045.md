# T-045 panning and playing CPU

Done 2026-10-09 by the performance agent (batch 4). Measured on the batch 3/4 game (real track
model, demand pool, station labels with the invisible symbol layer), then again after the
gameplay agent's batch 4 changes to `stationLabels.ts` and `overlay.ts` (run 3 below is that
build).

## Method

- Headless Chrome (`--headless=new`, real GPU), own profile, **pinned to two cores** (14 and 15,
  `start /affinity C000`, children inherit it), 1440x900 at dpr 1, view `#11.5/40.752/-73.975`.
  Two other agents were building throughout, so every number is a median over repeated
  windows (8 s each; 3 repeats in run 1, 5 in runs 2-3) with the range.
- CPU = user + kernel time of every Chrome process with the profile's path in its command line
  (`Win32_Process`), per process over the window, as % of one core. Also per process type (GPU
  process, renderer) and the page's main thread (`Performance.getMetrics`: task, script, style,
  layout).
- Scenarios: **playing** at 60x with the camera still; **dragging** while playing (CDP mouse
  drag, a move every 16 ms); **hover** (the same moves with no button); **unfocused** (window
  `blur`, the 10 fps path); **paused**; **paused while dragging** (run 1). "Idle" in the brief: a
  page with nothing to do is "paused" (0%); about:blank measured 0.2%.
- Networks: **empty** (a new game) and **lines**: three constructed lines, 24 stations, 92 trips
  an hour, two flat crossings, one capacity marker, built through `tw.client.edit`.
  The app autosaves since T-029: each page load starts from a cleared origin (run 2's "empty"
  rows were not empty and are left out).
- A/B through **measurement-only URL flags** (`app/src/perfFlags.ts`; nothing changes without
  them): `?perfOff=labels,shadow,hover,clock,overlay,markers` turns a part off, `?perfTry=...`
  turns on a candidate fix. Scripts (scratchpad, not kept): a CDP driver (Node's `WebSocket`),
  a `Win32_Process` sampler, a profiler pass on an unminified build.

## Findings

1. **Nothing moves, frames still run** (the biggest, and cheapest). A new game with no trains
   draws 60 frames a second only to move the top bar's minute: 13-15% of a core, 4% unfocused,
   15% with the mouse over the map. `?perfTry=idle` stops the frame loop while there are no trips
   this hour and wakes it once per game minute for the clock: **0.6% playing, 3% hovering, 0.6%
   unfocused**; dragging unchanged (MapLibre's frames draw the overlay). A player planning
   blueprint for minutes before the first line runs is exactly this case. Adopting it is
   one line in `overlay.ts` (`const IDLE = true`): T-073.
2. **Station labels while the camera moves**: 24 DOM labels cost 8.5 points of a core while
   dragging (38.5% -> 30.0%; run 1: 43 -> 33), in the renderer's paint and raster (renderer 18.9
   -> 13.2, GPU 17.7 -> 15.5) more than in JS. Giving each label its own compositor layer
   (`labelLayers`) won back 2 points in run 3 and 6 in run 2: not a fix. It grows with stations
   on screen. T-074.
3. **Double overlay draw while dragging and playing**: 122 overlay draws a second at 60 fps
   (our frame loop and MapLibre's frame each draw). Skipping ours when MapLibre has a frame
   queued (`noDouble`) saved about 2 points, inside the noise. Low value; T-075.
4. **No measurable cost**: the Preact clock, the invisible symbol layer of station names, the
   overlay's WebGL draw, one capacity marker. Hover picking cost 6-7 points in run 1 (24.6 ->
   17.6) and nothing measurable in run 3 after `toScreen` started caching the canvas size; a
   profile of 8 s of hovering shows 12 ms of our JS (`pick`, `nearestSeg`).
5. **Playing at 60 fps is Chrome's presentation cost**, 13-15% for any network. A lower frame
   rate when trains move less than about half a pixel a frame (60x at zoom 11-12 is about one
   pixel) would roughly halve it; it is a smoothness call, so T-076 for Anita.

The drag figure in T-027 (47-79%) was the busy machine plus labels: on two pinned cores the
same drag is 38% with labels and 30% without, against T-015's 37-38% for the spike.
