## What changed

`kernel::with_skims` (sim/src/demand/kernel/search.rs): the thread's cache is now the two kept tables plus a
**spare**, the last table searched "for this call alone" (a graph cheaper to search than either kept table, T-405).
The next caller with the same graph carries on from the spare (searches only the destinations it lacks; if it is
then big enough to displace a kept table, the spare becomes that table instead of an empty one). Any other caller
drops the spare before it searches, and `clear_skim_cache` / `release_skims` drop it, so it never sits beside a new
table. `skims_cached` still looks at the kept tables only (so the market's choice between `with_skims` and
`pass_searched` is as before). Test: `partial_skims_equal_full_skims_where_searched` gained the spare's two cases.
Doc: docs/demand-kernel.md, the `with_skims` paragraph.

## Speed and memory

**Native, Tokyo community network** (base and head side by side, machine shared): solve 1,612.7 s -> 1,345.4 s
(**-16.6%**); by period (sum of stages) 388/349/421/291/139 s -> 302/282/286/320/129 s (period 3 the noisy one). The
smaller zones' everyday layers after their commutes go from 1.3-4.1 s to 65-100 ms, and each crowding round gets
the same: period 0's rounds 125 + 173 s -> 98 + 123 s. Highest heap during the periods 5,630.1 -> 5,631.2 MB
(+0.02%). Live heap between calls is higher while the spare is held (period 0 after its second round 2,879 ->
3,763 MB: up to about 880 MB on this network, a 7,147-station table), but only between calls inside a step: the
step's release frees it, and every stage's peak is the same to 1 MB.

**Native, real NYC**: no change (A/B pairs 74.3 / 74.1 s and 83.2 / 86.6 s); its small zones' one-off tables were
cheap already. Peak 428.9 MB both.
