# T-2653: the far-zone table's start half filled by zone (2026-11-06, agent fartable)

Built from notes/T-2642.md candidate (ii). Files (tree `.tw-trees/fartable`): `sim/src/demand/intercity/api.rs`
(`StPattern` gains the by-zone index: `zoff`, `zst`, `zrow`, `zix`; `Cols::zeros`/`set`), `setup.rs` (one line),

## How it works

- Index, once per network (in `set_st_pattern`): column c's start stations ascending (`zst`, u16 while stations fit),
  and per start entry its place in that order (`zix`, with `zrow` giving each station's run). Start entries are a row's
  first ones, since columns ascend.
- During a pass `st` is `ne` row entries plus the start half again by column. A zone's own column is found through
  `zmap` (station -> place, filled once a zone from `zst`). Another zone's column (commutes' and outings' trips home)
  is found by the entry's place in the rows (`at`, the old cursor) then `zix`, once a station for each commute pair
  (memo with a pair stamp). Windows (never read) keep the old path.
- At the end each start entry is copied back to its row place (still 0 there), then `st` is cut back to `ne`.
- Same adds in the same order into each entry, so the table and every figure are the same to the bit.

## Measurements (M)

`t2653_ab`, Japan `t2621/jp.net.json` period 0, one pinned core on a full machine; both modes back to back in one
process (order alternated between runs), figures compared to the bit, free flow and crowded (3x loads). Section
times are rdtsc shares of the solve's CPU (probes removed afterwards).

| | by row | by zone |
|---|---|---|
| longer trips' spreading, ms | 4,030-4,860 (13 runs) | 1,000-1,650 |
| commutes' adds, ms | 1,040-1,470 | 940-1,450 (about equal) |
| solve cpu, s | 49-57 | 46-54 |

- Spreading about 3.0x (4.4 s -> 1.45 s typical; one ratio 2.9x). The note's 3.85x (6.7 -> 1.7) came with a slower
  baseline; the by-zone time itself is 1.4-1.5 s, as the prototype's 1.7.
- Commutes: equal on Japan within the noise. Two earlier versions were 20-25% slower (a binary search per
  lookup; a gather per term); the memo per pair fixed it. North America (`t2606/na383.net.json`): spreading 245 -> 160 ms,
  commutes 66 -> 80 ms (+15 ms of a 2 s solve), solve 2.0 -> 1.9 s.
- Every figure the same to the bit, free flow and crowded, Japan (3 rounds) and North America (3 rounds): `st`,
  all loads including `pax_min`, rail, pair rail, transfers, fractions, corridors. (pax_min is not touched by this
  change, so no float-order difference.)
- Memory (Japan: 9,253 stations, 9,018 zones, table 12.06M entries = 48.2 MB, start half 6.03M): persistent index
  `zst` 12.1 MB (u16) + `zix` 24.1 MB + `zrow`/`zoff` 0.1 MB = 36 MB held with the network; during a pass the start
  half again 24.1 MB plus `zmap` and two memos under 1 MB; `st` is back to 48.2 MB after the copy (capacity checked).
  Peak working set of the process, Japan, separate processes: 665 MB (by row) vs 684 MB (by zone) at the pass; the
  index itself is in both (it is built either way), so against the code before this change the peak is about 36 + 19 =
  55 MB higher, in the note's 45-65 MB. NA: 1.7 MB zst + 3.4 MB zix, 3.4 MB start half during a pass.
