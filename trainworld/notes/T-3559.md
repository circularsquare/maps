# T-3559 and T-3528: the train count cap on load

## T-3559 was the check, not the game

t3165-cap.mjs imported the over-cap save and then waited 180 s for the count to read cap+1. Opening a file
reloads the page, and the new page only runs capLoad once its demand is final (gameReady), which on the NYC save
takes much longer than 180 s on 3 cores. The wait timed out silently and the check read the old page's 15
("15 -> 15"). The game lowered the count correctly. Fix: the check marks the old page, waits for the new page,
runs its own `loaded()` (game loaded, demand final), then waits up to 60 s for the lowering. Passes: 15 -> 7.

## T-3528

Cause: capLoad sent `setTrainCount` as an ordinary undoable edit, so it sat on the undo stack (and cleared redo).
Fix: `set_train_counts_unrecorded` (wasm/lines.rs, `apply_unrecorded` in world.rs) applies and pays like
`set_train_counts` but touches neither history. `setTrainCount` has `unrecorded?: true`; capLoad sets it. Rust test
`an_unrecorded_count_change_stays_off_the_undo_history` (t1071_tests.rs). t3165-cap now also checks canUndo is
false right after the load, that a player edit then undo restores that edit's count, and that the lowering stays.

Known edge: if the player edits the same line's count before the lowering lands (a second or two), the player's
undo entry holds the pre-edit over-cap counts. Not handled; rare.
