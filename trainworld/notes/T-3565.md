## How the routing code decides stop order and turn-backs

- A line is `stops` (listed station nodes) plus a stored forward `path` (edge entries `edge << 1 | dir`). Run 0
  is the path; run 1 is derived every time (`perdir.rs back_run_of`): the path backward if every piece allows,
  else `Network::route_hops` through run 1's stops reversed. So a line over one-way track has its return run
  re-routed on every derive, through every listed stop.
- `net.rs route_hops` / `find_path_side`: Dijkstra per hop between consecutive stops. A train may turn back only
  at a stop (charged `REVERSAL_SEARCH_S`) or a bare track end (`bare_end`, T-797; T-3541 made an end with only
  blueprint beyond count too). It can never turn back at a junction or on one-way track. Through a one-way pair,
  a hop to a station on the "wrong" leg can only be reached by running past the pair to a turning place and back:
  that is the J and the loops in her saves.
- `net.rs match_stops(nodes, stops, must)`: every listed stop must appear in path order; `must` are the indices
  where the path turns back (`stop_reversals`), which must fall on stops. Used by `check_route`, `build_run`
  (service.rs), `way_stops`, wasm.rs `turn_last/turn_first/every_pass/stop_spread`, lines.rs `dropped/stopped_at`.
  This "every stop is on the forward path" invariant is the heart of the problem.
- Stop ORDER comes from: wasm.rs `best_insert` -> `best_slot` (a click tries every slot, cheapest
  `order_cost` = length + a big penalty per reversal; forward path only, never the return run), lines.rs
  `edited_stops` -> wasm.rs `straighten` (re-insert one at a time when the path turns back), `sort_stops`, and
  `stop_every_pass` on load (loops). `best_slot` also tries `way_others` (T-3348 partner stations within 300 m)
  in place of the clicked station.
- T-3348 (`perdir.rs way_stops/way_station`): a listed stop whose platform a run cannot use is replaced, for that
  run, by the nearest station of its complex or within 300 m serving its way (the "partner"). Ends and turn-back
  stops never are.
- Service (`service.rs build_run`): per-run stop nodes, `stop_idx` into the run's nodes, `run.pass` (T-3332 one-
  track stations passed on the other track: no dwell, demand phi -1 in `span.rs line_span`). Every per-stop array
  (profiles, boarding account, snapshot) assumes n stops per run in the same order, run 1 reversed.

## What I built (all in the tree; worth keeping as a base or a quarry)

1. Leg stop rule (`perdir.rs leg_stop`, `leg_heading`): a station on one-way single track (both pieces single and
   one way, not a T-3332 one-track station) with no unlisted station on the other leg within T-3348's reach
   serving the other way. (First version used any station as a partner; her Line 3 broke on a two-way station
   92 m away that the return run could only reach by looping.)
2. Skip routing (`perdir.rs route_legs`, called first by `net.rs route_hops`, whose old body is
   `route_hops_plain`; also first in wasm.rs `route_memo`): route through the non-leg stops, stop at the leg stops
   that route passes; None (old behaviour) when some leg stop neither run would pass.
3. Skip-aware matching (`perdir.rs match_run`, replacing `match_stops` at the call sites above): a leg stop not
   on a run's path keeps a place at the path node nearest it between its neighbours, marked as passed
   (`service.rs Run::away`, `run.pass`), `LineSvc::stop_node` returns the real station. `back_run_of` returns
   None when a leg stop is passed by both runs. Riders board each leg station one direction only (checked on
   demand's per-run `board`).
4. Ordering, two attempts:
   - (a) one-at-a-time insertion with leg stations inserted last in `straighten`, plus `straighten_legs` on load.
     Fixed her Line 2 and one-per-leg cases; broke on three per leg clicked in natural order (checker): while the
     line's last two-way stop is before the pair, each leg click becomes an end or loops, and `best_slot` picks
     odd slots; its swaps via `way_others` could add a same-leg neighbour instead of the clicked station.
   - (b) skeleton plus set (`wasm/legs.rs`): the line's non-leg stops are an ordered skeleton (clicks go in by
     `best_slot` on the skeleton only), leg stations are an unordered set; `flatten` routes the skeleton both ways
     and puts each leg station in the gap where the run that passes it does (run 0's in its order, then run 1's
     reversed). Used by `best_insert`, `edited_stops` (not hand), `sort_stops`, load (`straighten_legs`).
     `way_others` now only offers stations serving the other way. Results: checker's `scen.mjs multi` PASSES
     (both click orders give the same line, 4047/4047 m, round trip 1348 s, six one-way stops); her Caracas Line
     2 1204 s round trip (was 4082), Line 3 729 s (was 2075); NYC save untouched; cargo suites 615 / 806 passed
     before the last two edits.
   - Open in (b): with fewer than two skeleton stops (or a leg station beyond the skeleton's end) the leg
     stations fall back to cost-based insertion; the last edit made that order fixed (station id order) but is
     untested in the game. The new permutation test (`oneleg_tests.rs t3565_click_order_never_matters`) fails
     only because clicking LO before AR makes the same line in the other direction ([LO, AR, ...] vs [AR, LO,
     ...]); its equality should allow the reversed line. Not yet run past that.

   the order of one-way stations is computed, never stored meaningfully. Derive it in one function from (skeleton
   of two-way stops in the player's order, set of one-way stations): route the skeleton forward and back with
   `route_hops_plain`, place each one-way station where the run that passes it does. Call it everywhere a line's
   stops are set (click, stop edit, sort, load, and after any track edit that touches the line, `world.rs
   way_reroutes`), so the stored list is always the derived one. That is what `legs.rs flatten` does; finish it
   rather than restart, unless the fresh agent prefers storing the set separately.
2. Decide the T-3348 partner rule with Anita: today a lone listed one-way station with a station on the other leg
   within 300 m is "one stop served both ways at its own platform each way", and a click on either leg station
   can add the other (`way_others`). Her model ("a station on one-way track is a one-way station") suggests
   dropping the partner rule; doing so changes T-3348's tested behaviour (perdir_tests.rs).

   leg loops the pair by construction). Order them by distance along the track from the skeleton's last stop,
   not by click or node id.
