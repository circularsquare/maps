# T-3497: real memory savings on phones and low-memory devices (2026-11-16, agent phone2)

## Stage 1: graphics buffers (landed, uncommitted in .tw-trees/phone2)

What a phone's game held that drew nothing: five screen-sized canvases over the map (station circles, demand discs,
a trip's routes, the gap flash, faces) kept their backing stores while blank (by default all but the demand discs are
blank all game); the tutorial's ripple was a whole-screen canvas (824 x 1678 on the phone, about 20 MB of 2D canvas
in the renderer, plus its copies in the GPU process) held while any step ripples; and since T-2794 capped phones'
pixel ratio to 2, a 3x phone's network canvas had MSAA again (T-955 had turned it off at 3x for memory), which the
stroke cache's layers multiply.

- `fitSparse` (map/gl.ts): an overlay canvas is 0 x 0 while it draws nothing and sized like the map's when it does.
  Used by stationCircles, demandOverlay, tripView, gapFlash, faces; the track tool's beside band goes to 0 x 0 when hidden.
- demandOverlay's context has no depth buffer (nothing there tests depth).
- ripple.ts: the canvas covers the target's box plus the rings' reach (GROW_PX + LINE_PX + 1 css px), 0 x 0 between pulses.
  t2123-tutorial's ring box reads the canvas's own position.
- overlay.ts `msaaHere`: MSAA only when both the drawn ratio and the screen's own are below 3 (T-955's rule as she
  set it, 2026-10-27; ?perfOff=msaa turns it off everywhere for measuring). The 3x phone screenshots with and without
  are alike at a glance: artifacts/trainworld/t3497/phone_msaa_before.png, phone_nomsaa_after.png.

Split on the phone at the first line: sparse canvases about -50 (all processes; GPU -40), MSAA off about -70 more
(GPU 329 -> 258, renderer's WebGL context 34 -> 14). Almost all of the saving is in the GPU process; the renderer
(page, workers, WASM) is unchanged within its run-to-run spread. On a real phone GPU memory is the phone's own RAM, so
it counts, but the 600 MB renderer is what this stage did not touch. Smoke 29/29 on the worktree (12,679,832 rail
trips, as before); t2123-tutorial passes every ripple step; its one FAIL is the 1% share step's text check, which none
of these files touch.

## Where the phone's renderer goes now (first line, about 605 MB)

Page 38 JS + 59 buffers; clock worker 13 + 19 + 9 WASM; demand solver 10 + 5 + 49 WASM and aux 10 + 6 + 41 WASM;
MapLibre worker 22; commuters 5; rest (Blink, compiled code, isolates, WebGL in the renderer, malloc) about 320.
A heap snapshot of the page at the first line (scratchpad abown.mjs, 46.6 MB of ArrayBuffers after collection): packed
outlines 10.2, commuter bubble builds kept per end and zone (`commuterView` built.done and keptBuilt) about 12, the
demand overlay's bubble data 2.7, the client's pushed everyday sums 3.3; the rest under 2 each. No single holder is big.

## What is left, none of it quick (for the orchestrator to file if wanted)

1. One demand worker instead of two on a small device: the aux worker's job (zones open bare) done by the single
   solving worker. Saves an isolate (about 15-25 MB) and the aux's WASM high water (41-49); a real change to
   demandClient's pool (aux index = computeN everywhere) and wasmmem's area. Biggest remaining phone cut, hours of work.
2. The clock worker's copy of the packed outlines (10 MB) for place lookups: ask the page instead on a small device.
3. MapLibre's out-of-view tile cache: after five camera jumps 12-13 tiles cached per source of 5 sources (cap 20 on the
   phone, 60 on desktop); `maxTileCacheSize` on a small device. Not measured; likely 10-20 MB of GPU and worker memory.
4. Commuter bubble builds kept for every end (Homes, Destinations, Total) and up to 6 zones: build only the end shown
   on a small device (about 8 of the page's 12 MB).
5. Demand detail on phones (fewer periods, coarser zones): not tried; phones open no market already (T-2794), and
   T-2794 found ?lod=coarse did not move the first line.
