## Method

Headless Chrome (Playwright, own profile, `--use-angle=d3d11`), the app on its own Vite (6121, via the proxy on 6122),
`?debug=1&new=1`, save imported with the debug `importSave`, then wait for the demand final (rail trips above 0), then
60 s more, then read:

- **Process memory**: Windows private bytes (`PrivatePageCount`) of every chrome.exe of the profile, by type. The
  renderer process holds the page and all its workers (demand, clock, shade, MapLibre), so "renderer" is the tab's own
  memory; browser, GPU and utility processes are on top.
- **Demand workers**: the game's own `twDemand.client.memory()` (WASM buffer and JS heap of each worker, plus the aux
  worker). WASM memory never shrinks, so the figure is the peak.
- **Main-thread JS heap**: CDP `Performance.getMetrics`.
- **`measureUserAgentSpecificMemory`**: only works cross-origin isolated; tried through the proxy.
- The clock worker's own WASM can't be read from outside; it is inside the renderer figure.

All runs 1 solving worker (+ aux) on a 2-core claim, except the `w2-` rows (2 solving workers, 4 cores; what a player on
a 16-thread machine gets by default). Saves: the 36 real-network saves are `trainworld/data/packs/real/*.save`
(13 measured), `T-007-real-nyc.save`, `checks/fixtures/t3302-tokyo-day77.save`, `t1156-all-china.save` (maps root),
and fresh games (`?new=1&city=`). A first set of runs for mad, ber, tyo read the demand "final" too early (rail trips
0); they were rerun with a stricter wait and the rerun is what is below.

## What dominates

1. **A fixed floor of about 0.9 GB in the tab and 1.35 GB across all processes before any save is loaded** (fresh game,
   same for every region). Main-thread JS heap about 195 MB; GPU process 300 MB (MapLibre, overlays; headless d3d11 here,
   a real GPU differs); the rest is the clock worker (about 250 MB of JS by the isolated measure, the network model and
   the world), shade and MapLibre workers, demand WASM 98 MB.
2. **The demand workers are the part that grows with the save**: each solving worker holds every open zone and the market.
   WASM 251 MB for a small city, 410-545 MB for Paris, London, Berlin, Tokyo, 378 for NYC, 1.3 GB for all of China
   (274 zones), plus the worker's JS heap (170-340 MB; 1.2 GB on all-China). **Each extra solving worker costs the same
   again**: NYC 1 to 2 workers took the tab from 2.15 to 2.64 GB (+0.49 GB), London 2.54 to 2.80. A default player on 12+
   threads has 3 solving workers, so another 1 GB over the 1-worker rows above on a big save.
3. The other growth (clock worker, main heap: 190 to 250 MB) is small and follows station and train counts.
4. City packs, zone data and map tiles are not separately visible from outside. The UASM breakdown shows the page's JS
   at 450 MB, the clock worker 246 MB, shade worker 66, MapLibre worker 18, and a "Canvas" 66.

**Is memory driven by the save?** Only through what the save reaches. A fresh game costs 0.9 GB tab however big the region.
A save adds the demand workers' WASM, which depends on which zones it touches and how many stations feed demand, and
a smaller part (clock, heap) with station and train counts. The number of solving workers multiplies the demand part.
The save file's own bytes are tiny (7-145 KB, JSON-like) and cost nothing to hold.

Rule of thumb that holds on all rows: tab about 0.9 GB + (demand WASM + heap) x 1.2; all processes about 0.45 GB more.

## What the browser can report (and does the game have isolation)

- **The game is not cross-origin isolated** (`crossOriginIsolated` false; the Vite config and `app/public` set no COOP/COEP
  headers). `measureUserAgentSpecificMemory` is therefore never available to players. The game already calls it
  where it is (T-1205, `measurePage`), which never happens in practice.
- Tried through a proxy that adds `COOP: same-origin` and `COEP: require-corp`: it works, with a per-worker breakdown, but
  it **undercounts**: 1.07 GB against 2.15 GB tab on NYC, because the demand workers' WASM memory is left out (workers
  listed at 60-97 MB of JS while their WASM is 378 MB). So even with isolation it is not the number a player wants.
  Turning isolation on would also block cross-origin tiles, fonts and R2 data unless each sends CORP or CORS: not worth it.
- **Chrome and Edge**: `navigator.deviceMemory` (power of two, at most 8 GB; already used by `deviceMemory.ts`), non-standard
  `performance.memory` (JS heap of the calling thread only, rounded), `performance.measureUserAgentSpecificMemory` (isolated
  only). No call gives the tab's total.
- **Firefox**: none of those three. **Safari**: none; iOS kills a tab near 1.5-2 GB whatever the phone holds (notes/T-2122.md).
- So the only number the game can show on every browser is the one it already has: the WASM and JS heap the demand workers
  report (`twDemand.client.memory()`), plus a fixed amount for the rest. Estimates for a not-yet-loaded save can only come
  from the file (stations and trains).

## Proposal

The question asked: will it brick my device, and how much more can I build. Both want an estimate of the tab, a limit to
compare it with, and a growth rate. The game already has the limit in code (`memBudget`: 8 GB, less on a device with less;
6 on browsers that don't say; 1.5 GB on 32-bit browsers) and already shortens its own worker pool when a load runs out.

**A. On each saved-game card, the memory the game needs (before loading).** Computed from the card's own facts, a
rough tab estimate: 1.3 GB + 0.6 GB per 1,000 stations (R2 0.84; rounded to 0.5 GB), plus 0.5 GB for each solving worker
past the first on this device. Shown as one more fact after the stations. The all-China shape (many zones) would read low,
so the formula would take the count of zones a save has opened when the save records them (it records `opened`). Needs a
design pass from her before building; the formula is simple but the estimate is ±15% on city saves and worse on countries.

Draft strings (not reviewed yet):
- Card fact: `About 2.5 GB of memory`
- When the estimate is over this device's budget, same fact, in the red used for negative money, and on Open a confirm:
  `This game needs about 5 GB of memory and this device has about 4. It may not load.` with buttons `Open anyway` and `Cancel`.
- No hover on the fact (the number is what it is).
- Where the browser does not report device memory (Firefox, Safari desktop): the fact alone, no warning.

**B. A live reading in Settings, under Units and performance.** From the demand workers' real figures. Answers "how much
more can I build" while playing.

Draft strings:
- Row `Memory`, value `2.4 GB of about 6 GB`
- Hover (only what can't be seen): `The game's own count. Another 1,000 stations takes about 0.6 GB.`
- Over 85% of the budget: value turns red and the row reads `Memory`, `5.3 GB of about 6 GB`; no extra message (the
  out-of-memory notice already exists).

I'd do **B first**: it is a reading, not a guess, it works on every browser, and it is a few lines over the existing
`memory()` and `memBudget()`. A is a guess whose error is largest for the saves players worry about (country-wide ones).
The honest limit of both: the "about" budget is the game's own rule, not the browser's; a tab can die earlier (iPhone at
about 1.5-2 GB, a 32-bit Chrome or Firefox near 1.5-2 GB, a laptop that has other apps open).
