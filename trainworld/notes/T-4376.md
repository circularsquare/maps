# T-4376: No sound for days for one player

Outcome (11-28, agent nosound): no code cause found for Chrome on Windows. Nothing changed in the code.

## The report

tw-feedback 1795779886-f61e0c7e, 11-27, v0.4.7.1, Chrome 158 on Windows, language ja, 109 lines, page open 1 min.
The whole message: 数日間ゲームが無音のままなのですが、解決方法はありますか ("the game has stayed silent for
several days; is there a way to fix it?"). The context carries no sound settings and no error.

## What decides whether a sound plays (read from the code)

- app/src/map/audioOut.ts: one AudioContext, opened about 250 ms after the first pointerup or keyup, once no button is
  held and the camera is still, in an idle callback (to keep the 60-210 ms device open off the press). Chrome lets a
  context start once the page has had any click or key (sticky activation), so opening after the click is allowed.
  The listeners go once the context exists; after that `audioOut()` calls `resume()` whenever a sound asks while the
  context is suspended, and Chrome allows that too. A context that somehow opened suspended recovers at the next
  sound after a click. Nothing here survives a reload, so it can't silence a player for days.
- The Sound setting (Settings, under "Stations up close", Sound; ja: 拡大時の駅 / サウンド) is the only switch. It is
  stored per browser (localStorage, game/ui.ts) and nothing but its checkbox changes it: no hotkey, no migration.
  Volume can't go below 10% from the slider.
- Station sounds (map/stationLife.ts, stationSound.ts): only from zoom 14 (STATION_BOX_ZOOM) in, while the clock runs,
  the page is visible, below 16x (speed index 2, any slider speed of 16x or more, plays nothing), for stations in view.
- Building sounds (map/buildSound.ts): at the player's own edits, no zoom gate. The world.ts hooks are still called on
  every edit after the 11-23 to 11-25 edit-path rework.

So a 109-line player watching zoomed out at 16x or faster hears only building sounds, by design.

## Game run (fresh NYC, own Vite 6146, headless Chrome)

Before any input the game's context was not open. One map click: the context was running 504 ms later, its clock
advanced (0.14 to 0.47 s), the snap sample was decoded, and placing track played "snap" through the running context.
The run can't test Chrome's autoplay gate itself: Playwright's page.evaluate counts as a user gesture, so the page
had activation before the click (a control context made then also ran). Opening after a click is Chrome's
documented allowed case.

## Likely causes, all outside the code

1. The game's Sound checkbox unticked (kept per browser, so it lasts for days).
2. Chrome's "Mute site" on the tab (right-click the tab), which Chrome keeps per site.
3. Chrome muted in the Windows volume mixer, or the output device.
4. Playing zoomed out or at 16x and faster, where station sounds are silent by design.

A reply to the player could say: in Settings, under Stations up close, check that Sound is ticked; right-click the
game's tab and pick Unmute site if Chrome shows it; station sounds play only zoomed in close with the speed under 16x.

## A cousin, not checked

WebKit (Safari, every iPhone browser) is said to need resume() inside a live click, not just after one. If so, a
context opened over 1 s after the click (the camera still moving after a pan, say) would stay suspended for the
session, since the listeners are gone by then. The candidate fix, a resume() in the pointerup and keydown handlers
while the context is not running, would cover that. Not filed: no Safari report, and unchecked here.
