# T-2958: why website deploys time out on GitHub Pages

Repo: C:\Users\anita\projects\website (circularsquare/circularsquare.github.io). Workflow: `.github/workflows/jekyll.yml`. Researched 2026-11-10, read-only.

## Cause

1. **The `timeout: 1800000` line does nothing.** `actions/deploy-pages@v4` clamps the input to 600000 ms (10 min): `this.timeout = ... Math.min(timeoutInput, MAX_TIMEOUT)` in [src/internal/deployment.js](https://github.com/actions/deploy-pages/blob/v4/src/internal/deployment.js). The log of run 42746342205 attempt 1 says so: "##[warning]Warning: timeout value is greater than the allowed maximum - timeout set to the maximum of 600000 milliseconds." The action's own default is also 600000 ([action.yml](https://github.com/actions/deploy-pages/blob/v4/action.yml)). So commit 8ec33bb changed nothing.
2. **The hang is on GitHub's side, not in our build.** In every failed deploy the Pages service sat in `syncing_files` (114 of 115 polls in the 2026-11-10 run) until the action's 10 minutes ran out, then cancelled. The same artifact deployed on a rerun in 16-45 s. The action only polls `GET /repos/.../pages/deployments/{id}`; nothing in our files changes how long `syncing_files` takes, short of making the artifact smaller.
3. **Size is not what changed.** The artifact is 386-388 MB every run (checked the last five, 2026-11-09 to 11-10). Normal deploys take 16-45 s. The failures arrived in a cluster, not as a growing trend (below). Size may still make a stall more likely (more bytes to copy), but I could not prove it.

## Options

| Option | Fixes the timeouts? | Cost |
|---|---|---|
| A. Remove the useless `timeout: 1800000` line | No, it only stops the config lying | 1 line, zero risk |
| B. Retry the deploy inside the job, with a short timeout per try | Yes for stalls like these: a stalled deployment is cancelled after 3 min and a fresh one usually lands in 30 s | 10 lines of workflow, nothing to move |
| C. Move heavy files to R2 (`data.anita.garden`) | Probably reduces stall odds and speeds every deploy, unproven | A few hours: upload, change fetch URLs, add `exclude`s, test pages |
| D. Newer action | No newer major exists that I could find; v4 is current. Not a lever | none |
| E. `fetch-depth: 0` trimmed | Only cuts checkout (20 s normally), not deploys | the feed script needs history, so skip |
| F. Leave GitHub Pages for another host | Yes but large | Memory notes say Cloudflare Pages breaks pmtiles; not recommended |

## Recommended: B now, then C for the nycriders data

### B. Workflow change (deploy job)

Replace the single deploy step with three tries. Each uses a 3-minute timeout (healthy deploys finish in under a minute, the slowest recent one in 68 s). `continue-on-error` lets the next try run; later tries only run if the earlier one failed.

```yaml
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deploy3.outputs.page_url || steps.deploy2.outputs.page_url || steps.deploy1.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      # GitHub's file sync sometimes hangs (status stays syncing_files); the
      # action caps its own timeout at 10 min, so cancel early and try again.
      - name: Deploy to GitHub Pages
        id: deploy1
        uses: actions/deploy-pages@v4
        continue-on-error: true
        with:
          timeout: 180000
      - name: Deploy to GitHub Pages (retry 1)
        id: deploy2
        if: steps.deploy1.outcome == 'failure'
        uses: actions/deploy-pages@v4
        continue-on-error: true
        with:
          timeout: 180000
      - name: Deploy to GitHub Pages (retry 2)
        id: deploy3
        if: steps.deploy1.outcome == 'failure' && steps.deploy2.outcome == 'failure'
        uses: actions/deploy-pages@v4
        with:
          timeout: 300000
```

Worst case 3 + 3 + 5 = 11 min, then the job fails (and the last step is not `continue-on-error`, so a real failure still shows red). Caveats, not tested (read-only task): I expect a second `create deployment` for the same artifact to be accepted after the first is cancelled, since a manual rerun (which does the same thing) works, but the first live failure will confirm it. If GitHub's stall lasts longer than the retries, a manual rerun later is still the fix. Also remove the old 30-minute comment and line.

Cost: one commit, about 10 lines, can only be seen working on the next stall. Push waits for Anita.
