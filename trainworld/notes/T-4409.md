# T-4409 Count failures automatically

Reasoning: every failure notice reads one of five signals in game/loading.ts, modelStopped.ts or figuresStopped.ts (load or demand failure via loadFailure, lost graphics via demandStopped "graphics", graphicsGone, modelStopped, figuresStopped). game/crashCount.ts watches those signals in one place, so no screen sends its own and loading.ts, oomRetry.ts and RetryNote.tsx are untouched. A failure that oomRetry takes over and recovers (a fresh page) is never a failure notice, so it is not counted.

Sent: POST trainworld/crash {v: build, line, device}. line = first line of the error, URLs and paths, hex names and numbers replaced (failureLine). At most one send per kind per page load. No session (auth: false), no ids. Quiet where the plays ping is (localhost, ?notrack, automated browsers; ?track forces). Only when the server's config says trainworldCrash. Error text could in theory hold player text (a line name in a thrown message); none of the game's own failure strings do.

Server (shonei-server): trainworld_crashes.go, crashes.json beside playtime.json, read via stats `crashes`; docs/trainworld-api.md "Failure counts". go test: new TestTwCrash*, TestTwEveryRouteIsRateLimited fixed. TestTwSaveCheckFollowsTheGame fails on master already (save LEVEL 42 vs twSaveLevel 41, not this task).

twstats: a Failures table (Today / 7 days / All) in tools/analytics/index.html; says "Not deployed yet" while the server answer has no crashes.

Check: typecheck passes; a game on ?debug=1&track&acct=local against a mock server on 8083 forced two failures: one POST, {"v":"mwz6hrsy","line":"Worker N ran out of memory at <url>","device":"computer"}, auth none.

Deploy needs: the server build and deploy as usual (deploy.ps1, her word); no migration (crashes.json is created on first count); the game ships with the next publish. Until the server is deployed the game's sends are skipped (config lacks trainworldCrash).
