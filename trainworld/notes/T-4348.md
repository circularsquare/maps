# T-4348 Slow edits on a player's 44-year Poland save (agent year44, 2026-11-25)

Anita, 11-25: "someone is having big editing issues still, they're wondering if it has to do with the fact that they're
on year 44. i downloaded their save. not sure if theres anything we can do but it might indicate a bug. if nothing pops
up no need to chase forever"

The save: day 15,922, 70 lines, 1,094 stations, 3,650 pieces, 3,483 km of track, 306 KB. A copy was worked on in the
agent's scratch folder; it is not in the repo.

## Answer

Game age is not why their edits are slow. Nothing an edit does (the track model's apply, the rows, the network, the
post, trips) reads anything that grows with game days. Two things do grow, and both are small next to the edit itself:

- **The save.** The header is 1.6 MB of JSON before gzip, 1.46 MB of it the 25 regions' day ledgers (each 120 days
  plus one entry per month since the start, 12 more entries a region a year, `ledgerFold.ts`). The clock worker builds
  and gzips the whole save on its own thread: in the game on this machine 104-149 ms a save (287 ms the first time).
  Node, the same code path on the same save: 93 ms as saved, 35 ms with every ledger cut to its last 120 days, 14 ms
  with no ledgers at all (copy 11, stringify 17, deflate 58, read-back 8 ms as saved). So year 44 adds about 60-100 ms
  to each autosave. An autosave runs once a minute while there are unsaved changes and right after each paid edit
  (construct, station building); a station or a delete on built track charges nothing, so it only waits on one when a
  click lands during the minute's save.
- **The money record** each state carries: `savedRegions(keptCopy)` walks about 16,800 ledger entries, 3-5 ms a state
  in Node; its diff for the post was 0.4-1.6 ms in the game (`pMoney`).

How the "history cleared" comparison was made: the save's header was parsed in Node, each ledger (the network's and
every region's) cut to its last 120 days or emptied, and the header and network encoded again by the clock worker's
path (`rounded` copies, JSON.stringify, pako Deflate in 16 KB pieces, read back). Not loaded in the game (one run).

## The slow part instead (one run, "Use more cores" off, 3 cores, clock paused, trips final first)

From the click; "ahead" is the edit drawn at the click, "network" the frame after the new network.

| edit | ahead | worker apply | confirmed | network | trips calculated |
|---|---|---|---|---|---|
| station on a 4-line running trunk (the session's first edit) | 17 ms | 707 ms | 740 ms | 1,667 ms | none followed (demand unchanged 140 s) |
| delete on a 3-line running trunk | 39 ms | 471 ms | 542 ms | 1,475 ms | 84.6 s |
| delete on a 2-line running trunk | 3 ms | 912 ms | 1,668 ms | 1,647 ms | (not waited) |
| delete on track whose lines had already stopped | 2 ms | 10 ms | 47 ms | 157 ms | none |

- The worker's apply of an edit that cuts or stops on running lines (the track model's edit and the lines' rework) is
  0.5-0.9 s here, and the state with the network follows 1.1-1.4 s after the apply starts. That is the T-4272 and
  T-4097 work (a click confirmed from what it touches), not game age.
- After the network, the clock worker runs the trips' follow-up: 13 follow-up steps (211 ms), the boarding account
  (stepBoarding, 38 steps, 735 ms, up to 165 ms each), the demand snapshot (45 ms).
- While trips are calculated after a delete (77 s), the clock worker was busy 32 s of it, in 525 blocks of 20 ms or
  more (327 of 50 ms or more, most about 65 ms, the longest about 210 ms). The boarding steps were 3.7 s of that; the
  rest came from async continuations the timer and message wrappers do not see. A click in that time waits for the
  block it lands in. Only one money record was built in the window, so none of it is the ledgers.

## Proposed (not made)

The growth is real but costs about 5% of an edit's wait at most, and only for a click that lands on an autosave, so
nothing was changed. If it is worth doing, in order:

1. Autosave waits for a quiet moment (no edit in the last 3 s and nothing owed; the paid-edit save joins the same
   wait): about 1 h, in `clock.worker.ts` (`rest`, `tick`) and `slots.ts`; after the buytrains tree lands, which
   holds `clock.worker.ts`. Covers every game, old or new: a click never queues behind a save mid-burst.
2. The save gzipped off the clock worker (a codec worker the clock worker starts, keeping T-3869's parts and memory
   retry): about 2 h. Takes the deflate and read-back (about 70% of a save) off the edit thread.
3. Ledgers saved as one array per field instead of keyed objects (JSON about half), with a save level bump: about
   2-3 h. Halves the growth itself; the growth stays.

Pako level 1 instead of 6 was also timed: deflate 39 ms instead of 84, file 349 KB instead of 304 (+15%); not
proposed, it trades every save's size for the same thread time option 2 removes.
