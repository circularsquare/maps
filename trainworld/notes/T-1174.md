# T-1174: a demand worker panicked

Seen once, during T-1156's all-China build (`artifacts/trainworld/t1156/build.log`, last line):
`demand: worker 0: Error: recursive use of an object detected which would lead to unsafe aliasing in
rust`, then `demand: worker 0: RuntimeError: unreachable`. Both came through the pool's `fail()`
(`failed` messages), so demand stopped for the rest of that page ("Demand stopped"); the clock and
the game went on. The build script was not kept, so the exact moment cannot be replayed.

## What the two messages mean

- `unreachable` is a WASM trap. In this crate (`panic = abort` on wasm32) every Rust panic ends as
  one, and so does an allocation the 4 GB memory cannot grow for (`handle_alloc_error` aborts).
- `recursive use of an object...` is wasm-bindgen's borrow check on an exported object
  (`DemandApi`, `EverydayApi`, `IntercityApi`, `MarketPacks`). It fires when a `&mut self` call
  finds the object already borrowed.
- A trap never unwinds: the call's frames are dropped and the borrow wasm-bindgen took for it is
  never released. Every later call on that object then fails with "recursive use".

## Why it cannot be two calls overlapping

Every WASM call in `demand.worker.ts` is synchronous; the `await`s (`yieldNow`, the round barrier)
sit between calls, never inside one, and nothing in the crate calls back into JS except
`performance.now()`. So within a worker two calls on one object never overlap, and no queue in
front of the objects could change anything. "Recursive use" here can only mean an earlier call on
the same object aborted.

## The likely sequence (from the code)

The first message was "recursive use", so the abort that caused it was swallowed. Two places
swallowed WASM errors as an ordinary pack rejection (T-492), keeping the worker going on a broken
instance:

1. `openPacks`'s per-pack `catch` (`new DemandApi`, `EverydayApi.beside_with`, `marketPacks.add`).
2. The `catch` around `recompose()` (composing the market). Its handler then calls
   `marketPacks.remove(...)` on the object the trap left borrowed: that throws "recursive use",
   which escapes to `openQueued`'s catch and is posted as `failed`. This matches the observed
   order exactly: the original trap is hidden and "recursive use" is reported first; the next call
   into the broken instance gives the `unreachable`.

While the China network was built, packs opened all the time (169 zones in the end, each solving
worker at 2.4-2.6 GB of its 4 GB after a clean load, T-1169) and the market was composed again at
each batch, so the most likely trap is running out of memory there. A real panic in the market
code is the other possibility; nothing recorded the trap's cause, so that is now logged (below).

## The fix

- **The worker never carries on after a panic.** `demand.worker.ts`: `isPanic` (a
  `WebAssembly.RuntimeError`, or wasm-bindgen's "recursive use", "null pointer passed to rust",
  "attempted to take ownership" errors); the pack-open and compose catches rethrow it instead of
  rejecting the pack; every other catch (init, open, close, solve, queries) hands it to `died`,
  which posts `dead` once and ignores every later message.
- **The cause is recorded.** `sim/src/demand/wasm.rs`: a panic hook keeps the last panic's text,
  and the global allocator (the system one, wrapped) notes the size of an allocation that failed;
  `last_panic()` returns either ("out of memory: N bytes could not be allocated"). It is read in
  `died` and goes in the console warning with the worker's WASM memory. The wrapper is one null
  check per allocation; figures unchanged.
- **The pool replaces the dead worker.** `demandClient.ts` `workerDied`: terminate it, end the
  pending queries empty, start a new worker in its place (`spawn`); on its `ready`, `reopen`
  downloads again everything open in every worker (`fetching`; for the aux worker also the bare
  zones, `fetchingBare`; the browser cache has them) and opens it there; when all is open
  (`reopened`) the pool counts the worker ready again and sends the newest network again under a
  new version (the shown final stays until the new one). `acks` now counts each worker once
  (`ackedBy`), so a reopen that overlaps a normal `open` never makes an item look open early.
  A second panic before the replacement has finished a solve, or a fifth replacement in a page,
  stops the pool as before: the cause is then one a fresh worker does not cure (memory, T-1169).
- **All workers compose afresh after a replacement** (`freshParts` on the resent solve). The first
  try left the replacement's corridor table ten rows apart from the others' (1,530,357 against
  1,530,367 on the real save; the sums worker then logs "periods with different corridor tables"
  and leaves those periods out of the corridors). Cause: `MarketPacks` keeps the corridors worked
  out at a worker's first composition (T-1204), and they depend on which packs were open then
  (the replacement composed once from all 13, the others as packs arrived). So on that solve every
  worker frees its parts and composition, drops the kept corridors (`MarketPacks.forget_corridors`,
  a new export) and composes again. The dependence itself is T-1354.
- Dev server: `twDemand.client.debugPanic(worker, "now" | "solve")` (`DemandApi.debug_panic`, a
  panic inside a `&mut self` call). "now" swallows the panic and calls the object again, giving the
  same pair of errors as the China build.

## Checks

All on own Vite 6174, 3 solving workers.

- Smoke before: PASS, real save 12,189,003 rail trips a day. After: PASS, 12,189,003.
- `checks/t1174-panic-recover.mjs`: PASS. Idle worker 0 (swallowed panic, then "recursive use",
  the China pair): replaced in 53 s, 12,188,987 = the figure before the panic. Worker 1 panicking
  inside a train count edit's solve: 12,194,507 = the same edit solved earlier with no panic. Aux
  worker: 12,194,507 unchanged. Stations answered after each, no console errors. The warning
  carries the cause, e.g. `RuntimeError: unreachable (panicked at src\demand\wasm.rs:63:9: a test
  panic (T-1174)), 343 MB of WASM memory`.
- Reproduction try (not reproduced): `t1156-all-china.save` loaded with 2 solving workers and six
  lines into zones it does not reach (Kunming, Guilin, Taiyuan, Tangshan, Anyang, Wenzhou) built
  while it loaded and opened packs: final 39,299,868 rail trips a day at 323 s, 600 items open, the
  solving workers at 2,422 and 2,182 MB of WASM, no panic. The 4 GB ceiling was not reached in this
  run; the original build ran 5,300 edits over 4 minutes, far more churn than this.
- Found on the way (not T-1174's): on one page, the busiest line's train count raised and set back
  gives 12,188,987, not the first final's 12,189,003. Possibly T-1225's load-to-load difference.
