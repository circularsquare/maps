# T-4025: the performance bench and its ledger (agent perfledger, 2026-11-23)

Anita, 11-21: "over the past few updates we've kinda been doing some performance improvements blind and in some cases
load times actually have gone up a lot, then we hammer them down, then something else pushes them back up." 11-23: no
ping-pong between memory and load times; measure work, not only how long it takes on a busy machine; the saves are
the real NYC, a big Tokyo game and the Belgrade bus save; not every save for every small change.

## The command

From the maps root (or any tree; the ledger is always the main tree's `trainworld/notes/perf-ledger.jsonl`):

    node trainworld/tools/perf_bench.mjs build <commit | tree folder> --label <name>      production build, ~8 min
    node trainworld/tools/perf_bench.mjs run <dist> --label <name> [--saves nyc,tokyo,belgrade] [--published vX.Y.Z]
    node trainworld/tools/perf_bench.mjs compare <base dist> <head dist> --saves nyc [--runs 2]
    node trainworld/tools/perf_bench.mjs check [--label <name>]
    node trainworld/tools/perf_bench.mjs published <label> <vX.Y.Z>
    node trainworld/tools/perf_bench.mjs run <dist> --label <name> --baseline     orchestrator, on master: all three saves, writes perfbench/baseline.json
    (in a tree, T-4213: 2 invocations ever, --runs 1, nyc by default, tokyo/belgrade/asia only with --heavy "<reason>", no compare, no build of another commit, --dry-run checks the gates; the run diffs against baseline.json by itself; more than 4 other cores claimed at start or end stamps it NOISY)

- `build` of a commit goes through `checks/agent-tree.mjs new bench-<label> <commit>` and `remove` (never a raw git
  worktree: see "The incident"); a tree folder builds that tree's working copy in place (its `app/src/wasm` becomes the
  shipped profile). Shipped WASM profile through `tools/snap_wasm.py` with its own Cargo target dirs, then
  `vite build` with `TW_LINK_PACKS=1`, into `artifacts/trainworld/perfbench/dist/<label>` (packs are hard links,
  so a dist costs ~60 MB). About 8 minutes on a busy machine (WASM 6 of them). A build made by `agent-tree new` also
  carries the main tree's uncommitted `app/src/game/*.json` (the packs were built for them); the build's commit then
  reads `<hash>+main-json`.
- `run` refuses when `cores.py total` says the ledger is over its cap, claims 5 cores (`--min 3`, cores.py waits up
  to 30 minutes, then the run refuses), and appends nothing if the ledger went over its cap during the run
  (`total --since`; Anita: no measuring on an overbooked machine). It serves the dist itself (Range, no-store,
  bytes counted), and per save opens a fresh headless Chrome with its own profile, pinned to the claimed cores,
  `?demandWorkers=3` whatever the cores, outside network blocked. One line per save goes to the ledger; anything
  judged worse by more than 10% than the last line marked published is printed under it. Each run's full record:
  `artifacts/trainworld/perfbench/runs/<label>-<save>-<n>.json`.
- `compare` runs base and head alternately (ABBA) on the same claim, no ledger line: the only way to compare
  wall-clock fairly. Writes `artifacts/trainworld/perfbench/compare-<time>.json`.
- After a publish, `published <label> <version>` marks that build's lines as the reference.

## What a run measures

The page opens a new NYC game (`?new=1`), waits for it to be ready (`boot`), then imports the save; the import's
solve is a load solve (estimates by round, `barrier` and `showEstimates` set, as when a slot opens).

- **Wall-clock** (s from the import): `firstMap` (the save's lines drawn), `trips` (the load's solve final),
  `playable` (the clock running), `editShows` (the fixed edit gone from the map), `boot` (navigation to ready).
- **The fixed edit**: remove the middle station of the line with the most stops (ties: the lowest line id). NYC: 96 St
  on line 1; Tokyo: 神奈川 on line 58; Belgrade: Slavija on line 65. `--edit-trips` also waits for the trips after it
  (on NYC about the load's whole solve again, so off by default).
- **CPU** (s, machine-independent enough to judge): `cpu.load`, the tab process's CPU from the import to playable
  (page, every worker, compositor); `cpu.edit` from the edit to 3 s after it shows; `cpu.page`, the main thread
  (CDP ThreadTime); `cpu.threads`, the busiest threads of the tab (Windows thread times, `tools/perf_threads.ps1`):
  the top three in a load are the three demand workers. CDP gives a worker no CPU time (no Performance domain in a
  worker), and Chrome leaves its threads unnamed here, so a thread is not tied to a worker by name: the lie is that
  "the top three are the demand workers", true on every run so far by a wide margin.
- **Memory** (MB): `tabPeak` (the renderer's private bytes, sampled every second), `chromePeak` (every process),
  `pageHeap` (after a forced collection), `clockWasm`, `demandWasm` per worker (the most each reported) and its sum.
- **Bytes** (MB from this server): `bootMB` (the app and the new game), `allMB` and `packsMB` (the import).
- **Work**: zones, markets, rounds, solves, `periodMs` and `setupMs` (the demand workers' own timing of their
  period passes and setup, summed), rows, rail trips a day (the answer: a change here is printed as changed, never as
  worse).

**Judged** (worse by more than 10% and by more than a floor): cpu.load (1 s), cpu.edit (0.5 s), tabPeak (30 MB),
chromePeak (50), pageHeap (10), clockWasm (10), demandWasmSum (20), bootMB (0.5), allMB (1), periodMs (1 s),
setupMs (0.5 s). **Printed as changed**: solves, zones, markets, rounds, rows, rail trips, lines, stations.
**Never judged from the ledger**: wall-clock; use `compare`.

## Tiers (for docs/orchestrator.md)

- A small change whose effect is expected: one save, the one it touches (buses or walking: belgrade, about 20
  minutes; many zones or the solve's memory: tokyo, 3-4; one zone, loading, rendering, the map: nyc, 2-3).
  `compare` against master when wall-clock matters.
- A risky change, or a batch before a publish: all three, about 30 minutes on master's code, plus 8 for a build.
- Cpu.edit is the noisiest judged number (10.7 against 14.1 s on Tokyo between two builds with the same edit code):
  its floor is 5 s.

## How noisy it is

Every run so far was on a machine 92-99% busy (other agents' checks and builds), 4-5 claimed cores.
- Belgrade on master, twice (16:00 and 16:51 UTC): cpu.load 2,670.4 and 2,669.5 s (0.03%), demandWasmSum 5,439
  MB both, tabPeak 7,967 and 8,347 MB (5%), trips 1,624 and 1,354 s (20%: wall-clock is the noisy one).
- NYC on v0.4.5, twice: cpu.load 247.6 and 238.4 s (4%).
So the 10% line sits above the noise of CPU and memory; wall-clock moves 20% between runs of the same build and is
never judged from the ledger.

## The incident (2026-11-23, about 15:19 and 15:28 UTC)

The first version of `build` made its own git worktree under perfbench/trees with junctions to the main tree's
`trainworld/app/node_modules` and `trainworld/data`, and removed it with `git worktree remove --force`, which on
Windows follows a junction and deletes what it points at (checked in a scratch test). It emptied the shared
node_modules twice (the orchestrator reinstalled it). data/packs was checked against the master build's hard links:
all 47,874 files present. `build` now goes through `checks/agent-tree.mjs new/remove`, which unlinks first
(a throwaway new/remove left node_modules and data/packs untouched).

## Not done, and lies

- The ledger lines use today's `data/packs` with each version's code (packs are not versioned by build).
- Each save is imported over a finished new NYC game, not opened from a slot; its solve is a load solve all the
  same (`barrier`, `showEstimates`), and the NYC game costs the same on every build.
- Per-worker CPU is per thread, ranked, not named (see "What a run measures").
- v0.4.3 and v0.4.4 were not measured (the brief asked for v0.4.5 and master).
