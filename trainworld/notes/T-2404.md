# T-2404 and T-1861: why track placement feels slow on big saves (2026-11-06, agent placelag)

Anita: "what exctly is causing the slow unresponsive feeling track placement on large saves? it feels very
smooth on small ones and its noticeable to come back to a large one". Then (via the orchestrator): "maybe only
rebuilding stuff in the immediate vicinity of the track being drawn would help?"

Status: done in tree `placelag` for New York and North America; all of Japan's steady movement fixed, its
clicks still slow for a reason outside the track tool (the boarding account, below).

## The answer, in plain words

Two different things run while you draw.

**Per pointer move** (the ghost following the pointer). Three small jobs, each of which looks only at what is
near the pointer, so on their own they do not grow with the network:
1. The snap: which node or track is under the pointer. It asks a grid of the nodes and a grid of the track
   points for what is near, then measures those few. About 1 ms on New York.
2. The hover: what the pointer is over, for the tooltip. Same kind of grid, same size of cost.
3. The ghost itself: the track model works out the route from the start to the pointer (5-8 ms in the
   clock worker on New York) and the main thread draws it one frame later. Two frames is the floor.

The catch, and the cause of T-1861: until a grid is built, a query scans everything, and a grid was built
in the page's idle time. On all of Japan one scan of the 750k track and 820k line segments costs ~100 ms,
so a pointer moving every frame with every move scanning leaves the page no idle time to build the grid
in: it stays slow for as long as you keep moving. Measured (master, Japan): each of the four grids was
scanned ~40 times in a row before its idle build got a turn, every move cost 94-118 ms of main thread, and
not one ghost was drawn in the whole 20 s run. T-2388's direct probe called the same code with pauses
between calls, which gave the build its idle time, hence 0.3-0.8 ms. Building a big set's grid as soon as
it is wanted (it costs about one scan) removes this: 1 ms a move on Japan now.

**Per click** (placing a segment). The segment is placed at once in the track model and the ghost moves on
right away (the "early" answer, T-1407). Then comes the follow-up, which is what you feel: everything that
shows the network has to be brought up to date with the new piece.
- In the clock worker: the state (station, line and track rows that changed) and the drawn network
  (`networkFromState`). The network keeps each piece that did not change, but it still walks every edge,
  line, train sample and station to find out which did, and compares the big arrays with the last ones
  posted. So it grows with the whole network, not with the piece: 40-60 ms of work on New York (T-2403),
  more on Japan. While it runs, ghosts asked meanwhile wait.
- On the main thread: taking that state (the world, the GPU buffers, the panels, the demand views): 25-60 ms
  on New York, with no frame drawn meanwhile.
- Together that was the ~190-200 ms freeze after each click on New York (T-2403), and it grows roughly in
  proportion to the network: lines and edges for the worker, line segments and stations for the main thread.

A small save has small versions of all of these, under a frame each, which is why it feels smooth.

## Which per-click costs can be local, and which need the whole network

| cost | where | local now? | could be local? |
|---|---|---|---|
| applying the edit in the track model | worker (Rust) | yes | |
| the state's rows (edges, nodes, lines changed) | worker | mostly (only changed rows are read and sent) | |
| the drawn network: strokes of changed edges and lines | worker | yes (cached per edge and line) | |
| the drawn network: finding what changed, the per-sample and per-station tables | worker | no, a pass over everything | yes, with the edges and lines the edit touched carried from the track model (it already lists them): medium work |
| comparing the posted arrays with the last ones | worker | no | yes, the same way |
| the snap's and the pick's grids | main | yes (carried over the edit, T-1030; nodes rebuilt) | |
| the GPU buffers of the strokes | main | yes (unchanged runs kept on the GPU, T-1028) | |
| the line segments' crowding attribute (`fullAttr`), station buffers, textures | main | no, whole each network | yes for most, by runs as the strokes are |
| panels and demand views reading the world | main | no | partly |
| demand's network snapshot | worker | needs the whole network | a blueprint segment does not change it, so it is not built for one |
| the network diagram's graph | worker | needs the whole network | only built while the diagram is open |

So most of it could be made local, but piece by piece, and each piece is a separate change to code that is
correct now. The quicker way to the same feel is to not do the follow-up while you are drawing at all: the
ghost already shows the new piece (the stand-in), so the rest of the network is treated as unchanged until the
pointer rests. That is the fix below, and the local rebuilds stay as a later task for the moment of rest.

## What changed

1. **The follow-up waits for the pointer to rest** (`workers/clock.worker.ts` `later`, `holdOn`,
   `passesHeld`). After an early segment, the worker holds the state while ghosts keep being asked: it goes
   when none has been asked for 220 ms, 5 s after the first segment held, or when a message comes other than
   a preview, a line query, demand's results (income, points, region shares, riders, transfers), the clock
   or the next early segment (so an undo, a construct or a station release it). The next segment joins the
   held one: one state for both, so a run of clicks costs one follow-up at the end. The hourly trips go
   without it (a blueprint changes no line's run). A segment that paid (a junction off built track) is not
   held: it splits built track, and the client reads the charge's split off the next state.
2. **Stand-ins for every held segment** (`map/renderer.ts` `keepPreviewAsPlaced`, `addPlaced`): its ghost,
   or, when the pointer had moved on before the click's own ghost was answered (every click in the check),
   its edges as the early answer carries them (`held`, from `heldEdges` in the worker).
3. **The tool asks for the state when it needs it** (`map/tools.ts` `releaseNear`, `reset`;
   `workers/clockClient.ts` `placedNow`, the `release` message). The snap sees a segment only once its state
   lands, so the tool asks for it at once when the pointer comes within 24 px of a held segment (away from
   the start, where the newest one ends) and when the run ends (a join, a double click, Esc, another tool).
   A click there waits for that state (at most 3 s) before it snaps, so closing a run on its own first
   point joins it (`checks/t2404-loop.mjs`).
4. **Big grids built at once** (`map/cellIndex.ts` `CellLevels.for`): a set of 4,096 items or more has its
   grid built when first wanted instead of in idle time. Small sets keep the idle build.
5. **The boarding account waits while ghosts are asked** (`stepBoarding`): its steps after new riders hold
   while a preview came in the last 220 ms, at most 3 s a round, then run to the end.
6. **`lineCountry` by lookup** (`game/holidays.ts`): the Lines tab asks it per line on every state; it
   searched the stations list and placed the station in a zone each time (200 ms a state on all of Japan).

What the player sees differently: nothing while drawing, except that the blueprint total and the undo button
catch up when the pointer rests rather than right after each click, and the one hitch moves from just after
each click to the moment the pointer stops (trains skip a frame then, the whole follow-up at once). DECISIONS
has the lines.

## What is left

- **All of Japan's clicks.** Steady movement is fine now (41 ms, two frames and a bit), but after a click the
  edit's own answer comes 100-850 ms late and the ghost waits seconds. The clock worker is busy with the
  boarding account almost all the time there: demand keeps posting new riders, each round redoes every line,
  and one step of 3 lines takes 250-750 ms (one wasm function, 320 ms self in 2.7 s; it looks like
  `boarding.rs` `ensure_some` hashing every line's key from the first line on each call, so a round costs
  lines squared, but I did not confirm it in native code). A step cannot be cut short from JS, so the edit
  waits behind it. Also the track model's route preview takes 40-190 ms a move there (5-8 ms on New York).
  Both are sim work: a cursor in `ensure_some` (or a time budget per line), and a look at what
  `preview_route`'s trial does per edge. New tasks.
- **The follow-up at rest** is still whole-network: on North America the worker's part is 0.4-1.1 s
  (`networkFromState` 150-740 ms, `buildState` 30-110 ms) plus 35-100 ms on the main thread. It no longer
  hits a moving pointer, but a ghost asked right after the rest waits for it. The table above says which
  pieces could be made local; that is a task of its own.
