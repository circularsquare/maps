# T-1029, T-1028, T-1030: track edits on big networks

Goal (T-1156): an edit on a big network should not freeze the page. Measured on Japan's real network
(`../artifacts/trainworld/t737-japan-trains.save`: 709 lines, 10,320 stations, 9,611 edges, 860k
track and 860k line segments) and New York's real save, both at 6x CPU throttling (the throttle
reaches the clock worker too), with one harness: `checks/t1029-edit.mjs`.

## The harness

`node trainworld/checks/t1029-edit.mjs <url> nyc|japan <label>`: the save imported, the clock
paused, then at 6x a fixed series (track added free and from its end, its end dragged, a station on
a running line's plain node when there is one, stations added and removed, a train count, a line's
last stop dropped, track removed, three undos and a redo). Per edit: the worker's ms by step, the
main thread's on the state (`takeStateNow`, `setNetwork`), then six pointer moves with the track
tool, all under a CPU profile (named functions summed; `TOP=1` the top functions, `WORKER_PROFILE=1`
the clock worker's own profile through `Target.sendMessageToTarget`). `DUMP=1` hashes the world, every
array of the drawn network and every stroke buffer read back from the GPU after the series;
`--compare a b` compares two dumps. `PATCH=0|check` passes `?patch=`.

## What changed

**T-1029, the clock worker's state.**
- `buildState` no longer concatenates every edge's points and speeds: `ClockRender.edgeParts` and
  `edgeSpeedParts` hold the worker's own per-edge arrays (the same objects while an edge is
  unchanged), used by `networkFromState` and never posted.
- `postState` posts the edges, nodes and lines as `delta`: only the rows that differ (field for
  field, arrays by value) from the last posted, with the ids in order when they changed. The client
  (`ClockClient.takeRows`) rebuilds the full arrays from its last ones before anything reads the state.
- `networkFromState` keeps per line its train speeds (`lineTrainSpeeds`, checked against the line's
  phase tables, path, edge strokes and built flags) and its samples' strokes and lanes (`LineSamples`),
  so only lines whose inputs changed are worked out again; each edge's speed limits and train speeds
  live in its cache entry, a new entry object whenever its strokes or speeds change.
- The network is posted as changes (`NetPatch`, `netForPost`): the stroke runs (start, count, old
  start or -1) found by identity of the reused pieces, the typed arrays that are byte-for-byte as last
  posted left out (`same`), and only the edges whose points changed. The client merges it with the
  last network (`mergeNet`). A whole network is posted on a load, at a new draw anchor, with
  `?patch=0`, or when the client asks (`wholeState`) because it could not merge (a state it cannot
  take is dropped, not drawn, and the next comes whole).

**T-1028, the renderer.** `setNetwork` takes a patched network: each stroke attribute's new buffer
is made by `copyBufferSubData` of the unchanged runs from the old buffer and `bufferSubData` of the new
segments only; the speed attribute is worked out for the new runs only. Textures are kept per name
(`putTexture`) and a network texture whose field is in `same` is not uploaded again. A network that is
not changes to the one drawn (any mismatch of serial or counts, a restored context) is uploaded whole.

**T-1030, the grids.** `CellLevels.carried`: a pick grid (track and line strokes) or the snap's edge
grid is carried over an edit from the grid before it, when a query first wants that level: the old
grid with its items renumbered through the runs, plus a small grid of the new items. Past 4,096 new
items (or an eighth of the whole), or two edits without a query, a level is built anew in idle time
as before. The edge grid's runs are found by identity of each edge's points array.

**The debug switch** `?patch=check`: the worker also builds each network from scratch and compares
every array; the client compares its rebuilt rows with the whole ones; the renderer reads every
patched stroke buffer back from the GPU and compares; each carried grid is compared with one built
from scratch at 64 points per level. Any difference is a console error starting `T-1028`, `T-1029` or
`T-1030 check` (the harness and smoke fail on console errors).

## Checks

- `?patch=check` on New York, the whole series unthrottled: no differences.
- DUMP of the series, the code before (HEAD in a copy, port 6131) against this: every world field and
  every network array identical (60 fields; the only differences are fields the old code lacks).
- DUMP with `?patch=0` against the default: identical, GPU buffers included.

- The harness: all 12 network edits of each run taken as changes (`renderer.patched`), none
  dropped or asked for whole.
- Smoke passes (12,188,988 rail trips a day, the same as HEAD's code run beside it); `cargo test`
  passes (no Rust changed).

## What is left

- **Main thread effects on station edits** (T-1380): most of what is left of taking a state on
  Japan is not the network but its effects. A station added, moved or removed rebuilds every
  station name (`StationLabels.set`, about 950 ms at 6x) and every complex (`buildComplexes`, about
  400-500 ms at 6x; it runs in the clock worker's snapshot too).
- **The worker still copies every stroke** (T-1381): each edit concatenates both stroke sets whole
  (about 70 MB on Japan) to transfer them, and its garbage is most of the worker's GC (worker profile:
  concat about 60 ms an edit at 6x, GC about 85). Posting only the new runs would move the copy to the
  main thread; keeping the arrays and double-buffering them needs no copy at all.
- **The state's rows are still all read from WASM** (T-1382): every edge, node (a WASM string call
  per station name) and line is asked for each edit, 70-110 ms at 6x on Japan, though only the
  changed ones are posted.
- `t1283-edit-time.mjs` under the load failed twice on its first Medium headway step (1,448 and
  1,445 ms; HEAD's code passed at 991 between them). In that step the Rust `apply`, which this work
  does not touch, was slower by the same factor as the rest (751 against 505 ms; the rest 694 against
  486, mostly the boarding hour), so the load rather than the change; service edits build no network
  and only add a field compare of the rows. Worth a rerun on a quiet machine.
