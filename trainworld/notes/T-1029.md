# T-1029, T-1028, T-1030: track edits on big networks

Goal (T-1156): an edit on a big network should not freeze the page. Measured on Japan's real network
(`../artifacts/trainworld/t737-japan-trains.save`: 709 lines, 10,320 stations, 9,611 edges, 860k
track and 860k line segments) and New York's real save, both at 6x CPU throttling (the throttle
reaches the clock worker too), with one harness: `checks/t1029-edit.mjs`.

## The harness

`node trainworld/checks/t1029-edit.mjs <url> nyc|japan <label>`: the save imported, the clock
paused, then at 6x a fixed series (track added free and from its end, its end dragged, a station on
a running line's plain node when there is one, stations added and removed, a train count, a line's
last stop dropped, track removed, three undos and a redo). Per edit: the worker's ms by step, the
main thread's on the state (`takeStateNow`, `setNetwork`), then six pointer moves with the track
tool, all under a CPU profile (named functions summed; `TOP=1` the top functions, `WORKER_PROFILE=1`
the clock worker's own profile through `Target.sendMessageToTarget`). `DUMP=1` hashes the world, every
array of the drawn network and every stroke buffer read back from the GPU after the series;
`--compare a b` compares two dumps. `PATCH=0|check` passes `?patch=`.

## What changed

**T-1029, the clock worker's state.**
- `buildState` no longer concatenates every edge's points and speeds: `ClockRender.edgeParts` and
  `edgeSpeedParts` hold the worker's own per-edge arrays (the same objects while an edge is
  unchanged), used by `networkFromState` and never posted.
- `postState` posts the edges, nodes and lines as `delta`: only the rows that differ (field for
  field, arrays by value) from the last posted, with the ids in order when they changed. The client
  (`ClockClient.takeRows`) rebuilds the full arrays from its last ones before anything reads the state.
- `networkFromState` keeps per line its train speeds (`lineTrainSpeeds`, checked against the line's
  phase tables, path, edge strokes and built flags) and its samples' strokes and lanes (`LineSamples`),
  so only lines whose inputs changed are worked out again; each edge's speed limits and train speeds
  live in its cache entry, a new entry object whenever its strokes or speeds change.
- The network is posted as changes (`NetPatch`, `netForPost`): the stroke runs (start, count, old
  start or -1) found by identity of the reused pieces, the typed arrays that are byte-for-byte as last
  posted left out (`same`), and only the edges whose points changed. The client merges it with the
  last network (`mergeNet`). A whole network is posted on a load, at a new draw anchor, with
  `?patch=0`, or when the client asks (`wholeState`) because it could not merge (a state it cannot
  take is dropped, not drawn, and the next comes whole).

**T-1028, the renderer.** `setNetwork` takes a patched network: each stroke attribute's new buffer
is made by `copyBufferSubData` of the unchanged runs from the old buffer and `bufferSubData` of the new
segments only; the speed attribute is worked out for the new runs only. Textures are kept per name
(`putTexture`) and a network texture whose field is in `same` is not uploaded again. A network that is
not changes to the one drawn (any mismatch of serial or counts, a restored context) is uploaded whole.

**T-1030, the grids.** `CellLevels.carried`: a pick grid (track and line strokes) or the snap's edge
grid is carried over an edit from the grid before it, when a query first wants that level: the old
grid with its items renumbered through the runs, plus a small grid of the new items. Past 4,096 new
items (or an eighth of the whole), or two edits without a query, a level is built anew in idle time
as before. The edge grid's runs are found by identity of each edge's points array.

**The debug switch** `?patch=check`: the worker also builds each network from scratch and compares
every array; the client compares its rebuilt rows with the whole ones; the renderer reads every
patched stroke buffer back from the GPU and compares; each carried grid is compared with one built
from scratch at 64 points per level. Any difference is a console error starting `T-1028`, `T-1029` or
`T-1030 check` (the harness and smoke fail on console errors).

## Checks

- `?patch=check` on New York, the whole series unthrottled: no differences.
- DUMP of the series, the code before (HEAD in a copy, port 6131) against this: every world field and
  every network array identical (60 fields; the only differences are fields the old code lacks).
- DUMP with `?patch=0` against the default: identical, GPU buffers included.

- The harness: all 12 network edits of each run taken as changes (`renderer.patched`), none
  dropped or asked for whole.
- Smoke passes (12,188,988 rail trips a day, the same as HEAD's code run beside it); `cargo test`
  passes (no Rust changed).

## T-1380: station edits, complexes and station names

A station added, moved, built or removed, a link made, or a line's stops changed used to make every
station name again (`StationLabels.set`) and every complex again (`buildComplexes`: in the world's
`complexes`, again in `dotGroups` once links exist, and in the clock worker's snapshot and
`complexOfNodes`). Both now work out again only what a changed station can touch.

**Complexes** (`game/complexBuilder.ts`, `ComplexBuilder.update`, same result as `buildComplexes`,
numbering included). It keeps per station its platform ends, its cell in a grid and its complex. A
call finds the stations added, removed, moved or resized (by value), and the links made or undone.
The stations worked out again are the old complexes of the removed and changed stations, the new
complexes of those added and moved to (found through the grid), and the complexes at the ends of a
changed link: single linkage means no other complex can gain or lose a member. Single linkage is then
run over just those, with the platform test called in the same order as `buildComplexes` (earlier
station first) so a gap exactly at the limit comes out alike. The output (`of`, `members`) is made
again for the whole list, a plain pass, to keep `buildComplexes`'s numbering. More than an eighth of
the stations changed, a reordering, a new frame kind or a station twice: built anew. The world's
`complexes` and `dotGroups` and the worker's snapshot and `complexOfNodes` each hold a builder.

**Station names** (`map/labelNames.ts`, `NameIndex`, same list and order as `labelGroups`). A name is
one per name per complex. The index keeps per station its group (by the complex's first station and the
name) and each line's stops as station line sets, and the names in order. `plan` finds the stations
that changed (a different object with different name, place, built or upgrades; a different complex;
the bunting; a line through it changed) without touching the index; `apply` takes the names those
stations left and joined out of the list, works them out again from their members and puts them back
in order, and says which went and came, at which places. `StationLabels` follows with its labels and
the shadow layer's features (`updateData` with the features' ids; the source's features are in no
order, which the invisible layer does not need since it allows overlap).

**What the client does so that it can**: `toWorld` gives the same `StationInput` and `LineInput`
object for a row that has not changed, and the same list when none has, so an edit that touches no
station is found out in a pointer compare.

**`?patch=`** (`game/patchMode.ts`): `0` builds everything whole as before, `check` also compares each
patched result with a whole one (console errors starting `T-1380 check`: the world's complexes, the
distance groups, the worker's complexes, and the labels and shadow features against `labelGroups`).

**Checks.** `checks/t1380-complexes.mjs` and `checks/t1380-labels.mjs` (node, a few seconds, in smoke):
random series of edits (stations added at the end and in the middle, removed, moved by metres and
far, resized, renamed, built, upgraded, links, lines made, stops changed, bunting, equal objects),
every step against a whole build: same grouping and numbering, same names in the same order with the
same fields, and the removes and inserts turn the last list into the new one. Both fail at once when
a step is taken out of the code. `?patch=check` on Japan with `checks/t1380-edit.mjs`: no differences.

## T-1381: stroke sets posted as changes

Each edit used to lay both stroke sets (track and lines: 860k segments each on Japan, about 70 MB)
end to end into new arrays in the clock worker and transfer them whole. The page needs the whole
arrays (picking, the pick grids and the renderer's patch all read them), so posting only the new runs
would have moved the copy to the main thread, and double-buffering would have the page hand buffers
back to the worker and keep the last network valid for longer. What is done instead (`map/strokePost.ts`):

- **Posting.** `StrokeSender.post` takes the set's pieces and the runs `NetPatch` already had, and
  posts it as one of three. *Same*: identical to the last network's (a single run from 0 to 0), no
  arrays. *Patch*: every kept run is at the position it had (old start = start), so only the new runs
  are posted, their segments laid end to end, with their start and count (`NetPatch.ranges`). *Whole*:
  anything else (a segment moved, a first network, `?patch=0`, a draw anchor change, a state the page
  dropped), into arrays with room after the last segment (an eighth, at least 2,048 segments) that
  the next patches can grow into.
- **Merging.** `mergeNet` calls `planStrokes` for both sets first and `write` only when both (and the
  rest of the network) can be merged, so a state the page cannot take writes nothing. A patch is new
  views, of the length of the new set, of the buffers the page already holds; its new segments are
  written over what was there. The last network's own arrays therefore change where the new network
  has other segments, and **the last network is not to be read once its successor is merged**. What
  reads it after that: the pick grids of the last network (built from its segments in idle time, and
  carried over through the runs, which drop exactly the segments that were written over), and for the
  few milliseconds of a held state (T-648), or until a staged train-count state is drawn (T-1071), the
  picking against the network still drawn, which can see the new blueprint segments early.
- **Debug.** `?patch=check` also makes the strokes whole in the worker and posts them beside the
  patch; the page compares what it merged (console error `T-1381 check`). The harness now fails on
  the clock worker's console errors too.

**Checks.** `checks/t1381-strokes.mjs` (node, a few seconds, in smoke): random edits to the pieces of
a track-like and a line-like set (added at the end and in the middle, replaced by pieces of the same
size or another, removed, moved, the tail replaced, emptied, many added past the room, a dropped
state), each post through a real structured clone with its buffers transferred, against the pieces

code against this: all 75 fields identical (every world field, every network array, every stroke buffer

## T-1382: the state's rows read from the track model only where an edit changed them

Each edit used to ask the model for every edge (`edges_info`), every node (`nodes_info`, and a string
call for each station's name) and every line (some twenty calls each: stops, path, timetable, stretch
speeds, passed stations and so on) again. `workers/stateRows.ts` (`StateRows`) keeps the rows it made
and reads again only what changed; `clock.worker.ts` `buildState` uses it.

- **Edges and nodes** come from one bulk call each, as before, and are compared number for number with
  the kept row; an equal row is the same object (so `rowsDelta` and the client's merge find it
  unchanged by identity, and the garbage of 20,000 rows an edit is gone).
- **Station names** are kept by node. The model records the nodes whose name was set or cleared
  (`Network::set_station` is the only place; `take_name_changes`, `[u32::MAX]` for a network nobody has
  asked yet), and only those are read again, with new stations. `buildSnapshot` takes its names from the
  same cache.
- **Lines**: `lines_info` and the cheap per-line calls (auto, fast, loop, shift, upkeep) are read every
  time; the heavy parts (name, letter, stops, path, timetable, stop distances, stretch speeds, passed
  stations, reversals, end turns) only for the lines `take_changed_lines` names. The model records a
  line when its service is rebuilt, rescheduled or recomputed (`Service::update_scoped`, so the settle
  rounds and trials count), and when an edit changed the net under it (`TrackWorld::apply_and_derive`:
  lines set, on touched track, stopping at a touched station, bus lines), refused edits and sketches
  too, since their apply and revert leave derived data a little different (the check found a
  refused route moving a passed station). All lines after a load, a reload (water) or edge prices
  worked out again (`rework_ground`, for terrain and water masks added). A bus line, and a line whose
  `ok` or `running` changed, is always read whole.
- **Build and train costs** of a planned line are read after all the other rows. `line_build_cost` runs
  a trial that settles headway lines a little differently each time (4th-6th digits of `tph`, round
  trip, timetable), so rows read between two trials depended on the order; now all of them are from
  one moment.
- `built_cost` is read once; `blueprintCost` is `total_cost() - builtCost` there instead of a third
  pass (`blueprint_cost` summed both again).
- The old `?patch=0` reads every row whole (it resets the kept rows). `?patch=check`: the worker reads
  the whole model again and compares (console error `T-1382 check`); with a planned line in the game
  the lines are left out of that compare (the trial above would make it differ), and
  `checks/t1382-rows.mjs` covers them.

**Checks.** `checks/t1382-rows.mjs` (node, in smoke): two track models take the same random edits in
step (routes from free ground and nodes, stations added, renamed, removed, lines made, copied, restyled,
re-stopped, removed, train counts, headways, constructing, blueprint off, doubling up, links, upgrades,
moving nodes, edge deletes, undo and redo, route previews, bus lines drawn and redrawn, fleet changes;
about a third of the tries are refused and are read too). One is read with the rows kept from the steps
before, the other whole by a new `StateRows`, and after every step the two must be equal field for
field. Two models, because reading is not repeatable on one: pricing a planned line is a trial, and
the second read of the same model sees what the first one's trials left. 3,600 reads over 60 seeds of
New York's real save, 50 over 2 seeds of Japan: equal. `--self-test` (changed-lines list held back)
and `--self-test-names` (name list held back) must fail, and do at the first edit that touches a line
or renames a station. 99% of the rows of a step are the kept objects. Rust: `changed_tests.rs`;
`cargo test --release --features demand` passes. `?patch=check` on New York and Japan with
`t1029-edit.mjs`: no console errors. `DUMP=1` of the Japan series, default against `?patch=0` (every
row read whole) and against `?patch=check`: all 76 fields identical (every world field, every network
array, every stroke buffer read back from the GPU).

## What is left

- **What the state still reads whole** (49 ms of the edit at 6x on Japan): the cost sums (`built_cost`,
  `total_cost` and the construct-all quote `blueprint_cost_items`, 15 ms: three passes over every edge
  and node with the water mask asked per station, the quote a trial of building everything), the phase
  tables (`phases`, 8 ms, 10 MB copied out of WASM each edit and again to compare and keep; a table
  per changed line would do), `edges_info` (6-10 ms with the drawn pieces: only the edges `der.edges`
  names could change), `line_upkeep` (4 ms, a share over every line's track). They are sums or
  copies over the whole network, not rows; floating-point sums kept incrementally would not equal the
  whole sum to the bit.
- **Placing the names** (T-1380): `StationLabels.set` is still 100-140 ms when a new label is made
  (6x), almost all in `place`, and only when a new element is made (a station moved costs 13 there),
  so probably the layout that the first read of the new label's width forces. Measuring a width
  without a layout, or placing only the names near the edit, would take the rest.
- **A line change still posts the line strokes whole** (T-1509): a line whose length or drawing order
  changes moves the segments after it (4 of the 12 edits of the series).
- `t1283-edit-time.mjs` under the load failed twice on its first Medium headway step (1,448 and
  1,445 ms; HEAD's code passed at 991 between them). In that step the Rust `apply`, which this work
  does not touch, was slower by the same factor as the rest (751 against 505 ms; the rest 694 against
  486, mostly the boarding hour), so the load rather than the change; service edits build no network
  and only add a field compare of the rows. Worth a rerun on a quiet machine.
