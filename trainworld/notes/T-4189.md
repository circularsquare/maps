# T-4189 perf_bench base builds reused the head's WASM

## Cause
Every perf_bench build shares perfbench/target-track and target-demand. Cargo takes a crate as built when its source files
are older than the last build in the target dir. The old code touched only sim/src/lib.rs before building (T-3939). A
fresh tree's other files carry their checkout time, so they were older than any build that finished after the checkout:

- two builds started together: the second one's checkout was older than the first one's finished build, so it took that
  build's WASM as its own;
- a base built alone after a head: same thing, the head's build was newer than the base's checkout.

Which one gets the other's WASM depends on who finished first. In check 3 the c3-head dist held the BASE's track WASM
(Dj3qmP-h, the file that bw-base/bw-base2 below also have as their track), and c3-base2 was right.

## Fix (trainworld/tools/perf_bench.mjs, build step)
- One build at a time in the shared target dirs: a lock folder perfbench/wasm.lock (owner pid, stale if the pid is dead,
  gives up after 90 min). Only the WASM step is locked; Vite and the tree checkout run in parallel.
- Inside the lock every sim .rs/.toml/.lock file is touched, so each is newer than the last build.
- perf-build.json records wasm {simSrc, track, demand}: sha256 (16 hex) of the sim sources and of both built modules.
  Ledger rows carry it (via buildInfo). compare prints both builds' hashes and warns when the sim source differs but the
  track WASM is the same.
Cost: a build waits for the WASM step of another running build (about 4 min of each build's 4-5 min; two builds started
together take about 8 min instead of 4-5, not 8 min of extra CPU). No extra disk, no cold builds. A per-build target dir
would run them in parallel but needs a warm copy of the target dir each (GBs) and doubles the cores.

200 s), 294 s alone.

## Short compare (base2 vs head, nyc and tokyo, 1 run each, 5 cores, no ledger; compare-2026-11-241143.json)
Rail trips a day equal (nyc 12672465, tokyo 16262490). Demand WASM nyc 1163 -> 1067, tokyo 1751 -> 1687. Trips ready nyc
103.5 -> 83.2 s (one run, noisy, machine busy). Clock WASM 65 = 65 (nyc) and 97 = 97 (tokyo): T-4184's clock memory cut does
not show here. The bench reads the clock worker's WASM size, which moves in 32 MB steps, and those two saves sit at 65 and
97 either way; T-4184's cuts are a few MB to tens of MB (stop order 45.5 -> 39 MB natively) and were measured natively and on an emulated iPhone (225-244 -> 180-187 MB), which perf_bench does not do, so they fall inside a step. Belgrade
(clock 193/225) was not run for this: it takes hours; it is the save where a step could show.

## Ledger: rel046-e936af30d vs v0.4.5
Not affected. e936af30d was rebuilt with the fixed tool (bw-rel): its track WASM 7e612994 and demand f94d480b are byte for
byte the same as the files in the rel046 dist. v0.4.5's files (87c8007b, b74348fb) differ from both. So the compare measured two
different builds, each its own source.
Other ledger lines could still be affected: t4179-head2 (same commit as t4179-head, but clock 129/225 against 97/193)
had an old track WASM, so its line is wrong. Other pairs built in parallel (c3, busland, trainmove) are suspect; check
their dists' perf-build.json (older ones have no hashes: compare the sha256 of the two sim_bg files with a rebuild).
