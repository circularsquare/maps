# T-4508 New lines vanish when zooming in (agent linezoom, 2026-11-27)

Anita, 11-27 on 8800 (master 888dc9c73): "when zooming in, some lines disappeared for me. they were newly constructed
line. some other people reported this earlier in discord and twfeedback i think."

## Summary

- Two bugs in what the renderer keeps of a stroke set across edits (T-4262, T-4274), both since 0.4.7 (published 11-25
  about 13:50). Both are fixed in app/src/map/rendererStrokes.ts and renderer.ts `setNetwork`.
- **New lines vanish zoomed in** (her report, FireWire, !3RROR! 4O4): the full stroke set's culling boxes were rebuilt
  from boxes two or more networks old, so the chunks holding a newly built line kept boxes from where other lines used
  to be, and were culled as off screen. A reload fixed it (FireWire, 11-26 18:38: "I reloaded and its fixed").
- **Deleted lines and blueprints stay zoomed out** (FireWire, 11-27 08:49): an edit that only cut a set short at its end
  (the last line in the draw order deleted, or blueprints, which sort last in the track set) was read as "nothing
  changed", so the zoomed-out copies kept drawing what was deleted.
- Not the cause, checked: hidden modes and levels (T-4400, T-4407), T-4153 stage 11's train speeds, line bands, the
  gathered instances' widths, lines drawn ahead (T-4114), T-4506's edge cost (a different path: the worker's rows).

## Following a new line from its build to the screen

- Each edit's network comes to `setNetwork` as a patch: per stroke set, runs (start, count, old start or -1) that make
  the new set from the old. Since T-4262 stage 2 the set keeps its object and buffers and an edit writes its segments in
  place (`slotted`), so anything keyed by the set's object outlives the edit unless `setNetwork` resets it.
- What a frame draws (`pickStrokes`): below draw zoom 15 the zoom band's simplified copy, else the full set; from zoom 7
  (`CULL_ZOOM`) only the chunks (16 segments each) whose box may show, gathered into one buffer when few.
- The full set's boxes are made lazily when it is next drawn culled: `chunkBoxes(src, count, s.boxesFrom)`, which copies
  the boxes of chunks wholly before `boxesFrom.upTo` from an earlier set. `setNetwork` set `boxesFrom` only when the
  old set's LOD state had boxes, and otherwise left it as it was.
- Since T-4274 the zoomed-out copy is carried through an edit, so while zoomed out the full set is not drawn, its boxes
  are not made, and `boxesFrom` is not used. At the next edit the state has no boxes, so `boxesFrom` stayed the one from
  the edit before, with that edit's `upTo`. When the later edit changed segments before that `upTo`, zooming in gave
  those chunks boxes from the older network. Wrong boxes then stuck: the next edit kept them as "the old set's boxes".
- Lines are drawn bottom first: lines with no trains, then the rest longest first (`lineDrawOrder`). A line being built
  starts with no trains at the front, moves when it gets trains or grows, and every other line's edit after the first
  change shifts it. So "edit something late in the order, then build a line" while zoomed out is the everyday case.
- `unchangedRuns(runs, count)` asked only whether every segment of the new set came from the old one at its place, so
  an old set cut short at its end (runs `[0, count, 0]`) counted as unchanged: the LOD state, its zoomed-out copies and
  boxes were kept as they were. strokePost.ts already compared the counts; the renderer's copy did not.

## The fix

- rendererStrokes.ts `keptBoxes(old, boxes, runs)`: what a set may keep of earlier boxes, set at every network that
  changes it: the old set's own boxes up to the patch's first change, else what the old set was still to keep, up to the
  first change of either edit, else nothing. renderer.ts `setNetwork` assigns it every time (new buffers too, which
  now inherit what the old set was still to keep).
- rendererStrokes.ts `unchangedRuns(runs, count, was)`: also the old count; `setNetwork` passes the patch's `oldTrack`
  and `oldLines`. A cut set now has its copies carried by `carryLod` like any edit.
- The `?patch=check` comparisons that exist (kept boxes against whole ones, a carried copy against a whole one) cover
  both; nothing ran the sequences that reach them (T-4509).

## Game run (Vite 6129, a new NYC game, `?patch=check`, play.mjs; probes in the scratchpad)

A page-side wrapper on `setNetwork` kept, beside the fixed rule, what the old rule would have left in `boxesFrom`.

1. Lines A (Brooklyn, 56 segments, trains) and C (Queens, short, trains). Zoom 16 over A (boxes made), then 11.4 (the
   zoom 12 copy made).
2. C (last in the draw order) removed: its runs were `[0, 56, 0]`. The copy was carried (`lodCarried` 1 band) and
   holds line A only; with the old rule nothing was reset and the copy kept C. No check errors.
3. Line B (Bronx, 95 segments, longer than A so drawn first). Zoom 15.3 over B, then 11.4.
4. A's stops reversed (runs keep B's 95 segments): both rules keep boxes up to segment 95.
5. Line E (Queens, 52 segments, no trains, so drawn first) built while zoomed out.
6. Judged before zooming in: the old rule kept `upTo` 95, so 5 of 13 chunks would get boxes from before step 4, holding
   all 52 of E's segments and 28 of B's; the fixed rule keeps nothing. Zoom 15.3 over E: no check errors, E drawn.
   The old rule's leftover put back by hand: "T-4262 check: the culling boxes kept from the last set differ from whole
   ones", and E drawn as bare grey track with a plain station box, as in the players' pictures.
