# T-4130 Bounded rows keep a stale flat crossing after an edge is deleted (agent crossfix, 2026-11-23)

**Summary for Anita**
- Fixed a slip in last round's faster edits (T-4113, not yet published): when an edit broke a line far away, a junction the line ran through could keep its crossing badge (the flat junction mark) until something else nearby changed.
- Why: a built junction shows its crossing only while some counting line's moves cross there. Deleting track elsewhere stopped two lines counting (they were left broken, their paths kept as they were), so the junction's crossing went away with no edit touching it and no line's path moving at it. The bounded read only looks again at track whose lines' paths moved, so it kept the old row.
- Fix (app only, `app/src/workers/stateRows.ts`): a line that stops or starts counting (ok or running flips) now has its whole track read again, as if its path had moved. And a record outside the read's scope is now kept only while its bulk numbers (position, ports, the crossing and flying flags, length, cost and the rest, which the read already has in hand) are as last read, so any of those moving for another reason is caught too.
- Cost: on the Asia save the records read again per edit are the same as before for station, track, stop, undo, trains, rename and Construct all; an edit that breaks a line reads its whole track again (202 to 267 edges, 212 to 279 nodes), and the read after carries its ends, as for any line whose path moves. The bulk comparison costs about 0.5 ms of a 30 ms rows read in Node. Part A's saving stands.
- Advisor not called (a bug with a clear cause).

## Cause, from the repro (Asia save, seed 2 step 8 with T-4125's first page-check stream)

deleteEdge removed edge 0 (touched: edges 0-2, nodes 1, 2, 8, 12). Lines 0 and 64 (one a copy of the other) went from ok to broken; their paths, back paths and plan paths stayed entry for entry the same. Both ran 175 -> 718 -> 706 through junction 718, line 16 ran 705 -> 718 -> 175 the other way: those moves crossed. `conflict_nodes` takes moves from ok lines only, so with 0 and 64 broken, 718 has no crossing and `nodes_info` clears its crossing flag. Node 718 was not touched, its region was not dirty, and `moved` (the path entries of each re-read line, before against now) found nothing, so the bounded read kept 718's row with `crosses: true`.

The general shape: some bulk numbers on a record derive from every line (a junction's crossing moves; built junctions only, T-3745), so they can move on a record no edit touched. Part A's read skipped an out-of-scope record without looking at its bulk numbers.

## What changed

- `StateRows.begin`: `flip` (a line's ok or running differs from the last read) marks the line's whole path, plan path and back path, both the old and the new, instead of only the entries that moved.
- `StateRows.edges` / `nodes`: an out-of-scope record is kept only when `edgeBulkSame` / `nodeBulkSame` say its row holds what `edges_info` / `nodes_info` give now; otherwise it goes through the normal path, which redoes its own calls when anything bulk moved (as before for records in scope).
- Either change alone fixes the repro and the standing case (checked one at a time). Both are kept: the first is the cause, and covers what a broken line moves through the records' own calls; the second covers any bulk number that moves for a reason nobody listed.
