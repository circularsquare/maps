# T-4368: a high-speed line made normal still shows as high-speed

Report: tw-feedback 1795690226-83dc41c9 (v0.4.7 mwwfej2q, 11-26, Japanese, anonymous, 66 lines, no picture):
"高速線を通常線にしても路線の表示が高速のままです", "even after I make the high-speed line a normal line, the line's display stays
high-speed". In Japanese 線 covers both a line and track, so it could mean the line panel's kind switch or the track type
(toolbar and blueprint picker, 高速 / 通常).

Outcome: not reproduced. On current code (tree hsrstroke, master at 7384af533) a line switched to normal is redrawn at
once, at every zoom tried. Both causes the sweep named are ruled out by the code and one run. No code change.

## The two suspected causes, from the code

1. Cached line strokes after lineFast (map/network.ts, the `c.fast !== l.fast` check skipped when `sameRow`). `sameRow` is
   true only when the line's row is the same object the network last drew. `set_line_fast` runs `Op::Line`; `set_line`
   pushes the line into the touch, `note_lines` notes it, and `take_changed_lines` stamps it (`line_stamp` includes
   `line_fast`, sim/src/track/wasm/touched.rs). workers/stateRows.ts then treats it as fresh and makes a new row with the
   new `fast`. The rows-first rows state (clockWordLines.ts ROWS_FIRST) takes it; the full state after reuses that row,
   which is not the row the network last drew, so the check runs and the line's strokes are made again, flagged
   `l.fast && hsrEdge`. The entry copy guard compares flags. The GPU patch (`strokeRuns`) keys runs on the line's part
   object, new on a rebuild, so its slots are rewritten; the zoomed-out copies (`carryLod`) work out the made run again.
   The same code was in v0.4.7 (cf7b483e0): the rebuild check, the flags, the row rules, ROWS_FIRST, the follow-up's
   `net`, `joined` and `light`.
2. The edge's own hsr flag (track kind changed by the blueprint picker or a rebuild). An edge's piece is made again when
   its flags change (F_HSR is in the piece's key), which puts it in `fresh`; every line on it is `touched` and fails
   `keptEdge`, so its strokes are made again with the new `hsrEdge`.

Also read and ruled out: a line run on both pairs (`twin_ops` runs on every checked edit and `twin_data` clones `fast`);
the schematic (posted after every network; `regionSig` includes `fast`); the ahead layer (lineFast's guess is panel
fields only); a kind change merged with a train count's follow-up (`net || service` keeps the network, the service
shortcut needs `!net`); line bullets (shape by vehicle, not `fast`); the auto high-speed rule for a new line (T-1899:
`autoFast` sees a manual change through `clickWorld`, reset when the rows state is taken; only a stop click in the moment
before those rows land could make the line high-speed again).

## What the player may have seen

The track stays high-speed track when the line is made normal, and keeps its look wherever no line covers it: beyond the
line's end stations, the other pair of quad track, sidings. In the Level, Speed and Profit views only track is drawn (at
line width), so a normal line on high-speed track looks high-speed there. Both are the track's kind, drawn as designed.
A picture from the player would settle it.
