## How it was measured

- **Native profile**: `sampler.rs` (scratch), an in-process sampling profiler for Windows (no admin): a thread
  suspends the solving thread about every 1.8 ms, unwinds its stack (`RtlVirtualUnwind`, nothing allocated while it
  is suspended) and symbolizes with dbghelp, inline frames included, from a build with line tables
  (`CARGO_PROFILE_AGENT_DEBUG=line-tables-only`, own target dir `tgt/`). It is hooked into `demand_prof.rs`, a copy
  of `demand_mem.rs` (untracked in the tree's `src/bin`, never landed) with `TW_PROF=<out>`, `--periods N`,
  `--lines FILE` (boardings by line over the five periods) and `--table` (the corridor book alone). `cats.py`
  buckets the folded stacks, `searchby.py` splits the search by caller, `cmp.py A B` compares two `--lines` files.
- **In game**: the tree's Vite on 6112, `play.mjs` with 4 cores (3 solving workers), the real save; one edit (a
  three-station line in Brooklyn, `edit1.json`), timed from the demand log (`workread.js`: arrival, each worker's
  units by period, final) and scratch timers in `demand.worker.ts` (Rust passes, cap, figures and its parts,
  sums, queries, yields), posted as a `t4057` message (`listen.js`, `tread.js`). The timers are reverted.
- The machine was shared all morning (8-14 of 14 cores claimed), so single runs swing 10-40%; the shares are
  steadier than the times.

## Shifting speedups

Measured on the real save natively (default order with the market; boardings by line over the five periods, every
population; line numbers are the real network's). Base: 3 rounds, as the game.

**1. Two crowding rounds instead of three** (`ROUNDS` 3 -> 2). Saves a quarter of each heavy period: in game the
busiest worker's 4 passes a period become 3, so the edit's wait goes from about 100-113 s to about 75-85 s
(estimated from the per-period unit times). Native, master's `demand_mem`, interleaved: 3 rounds 118.5, 132.4 s;
2 rounds 94.9, 97.3 s (about -24%). Shift: rail trips 13,107,375 -> 13,138,238
(+0.24%); summed line changes 2.6% of boardings; lines that move most: NJ Transit NEC +19.4%, PATH 861 -14.5%, PATH
860 +14.4%, HBLR -12.7%, PATH 859 +10.8%, NJ Transit MNBNP +8.8%, LIRR Oyster Bay +8.4%, subway B +7.8%. One
round instead of three: up to +65% (NEC), PATH 860 +59%, so the rounds are far from settled.
Worst case: parallel crowded lines between the same places (PATH's four routes into Manhattan, a crowded trunk
beside a slower alternative): their riders swing from one to the other round to round, and stopping a round
earlier lands them at another point of the swing.

**2. A looser settled test** (`SETTLED` 1% -> 3% or 6%, stalls.rs). On the real save a round moves 2.6-40% of the
segment loads (period 0: 31%, 18%; 1: 10%, 4.4%; 2: 40%, 22%; 3: 5.8%, 2.6%), so the test rarely fires. At 3% it
skips period 3's last round (1 of 15 period-rounds; about 11 s of the busiest worker in game, since period 3 is
on it): rail trips +0.001%, lines within 4% (HBLR -4.0%, PATH 859 -3.4%). At 6% it also skips period 1's last round
and period 3's second: rail trips +0.004%, lines within 6.1% (NEC +6.1%, PATH 860 +5.3%, PATH 861 -4.9%).
Worst case: the same parallel crowded lines, in a period whose loads happen to move little in total.

**3. Fewer demand stations on bus networks** (not measured; an idea for Detroit-like saves). Merge bus stops
within a few hundred metres into one demand station (as `station_merge_m` already merges stations), or search only
the bus stops riders change at as destinations. The search's work goes roughly with destinations times nodes, so
halving the stops would cut Detroit's solve by well over half and its memory by about three quarters. The lie:
trips start and end at the merged stop, so a walk of up to the merge distance is counted to the wrong stop. Changes
what demand sees, so it is Anita's call before anyone measures it.

## For solvespeed (search.rs, not edited here)

- **One-off searches on multi-zone clusters** (Tokyo above: 41% of the period). Same answers: keep the last table
  searched "for this call alone" for the next caller with the same key (a zone's everyday right after its
  commutes), about 18% of Tokyo's time natively (less in game, which releases the skims every step; not measured
  there); or more `SKIM_TABLES` where memory allows.
- **One graph across a cluster's zones** (shifts answers slightly): build every zone's graph from the same
  coordinates (one frame, or distances from longitude and latitude), so all zones and the market share one search
  a period and round. On Tokyo most of the 41% and part of the rest; the lie is a zone's walks between stations
  measured in another frame, about 1-2% off for zones a degree of latitude apart.

- **The search is the cost on bus-heavy saves** (Detroit 82%, 4,316 destinations over 7,573 stops), and its tables
  are the memory (3.8-4.2 GB a worker in game).

## Stage 2 (agent solvereuse, 2026-11-24): each zone's everyday layer right after its commutes

Tree `.tw-trees/solvereuse` (branch tw/solvereuse, from master 20d3a0029). Scratch:

**What was left of the one-off searches.** The cut this section names ("keep the last table searched for one call
for the next caller") had landed already (T-4123, `with_skims`' spare), measured natively, where `demand_mem`
solves a zone's everyday layer right after its commutes. The game does not: the worker's `solveOrder` was every
zone's commutes, then every zone's everyday layer, then the market. So in game the spare never served: every zone
whose table the cache does not keep (all but the two biggest) searched its whole table twice per period and round,
once for its commutes and again for its everyday layer.

**Change** (app/src/workers/demand.worker.ts only, no Rust): `solveOrder` puts each zone's everyday layer right after
its commutes (zones still in pack-open order, the market last). Populations are independent within a step and the
figures are added up in `pops`' order, so no figure changes. Set-up keeps its old order (all commutes, all everyday
layers, the market: `setUpOrder`), since T-405 found the set-up order moves each worker's first WASM solve by
seconds; a first build that set up in the new order too came out 1-6% more CPU on NYC in all four perf_bench pairs.
Doc: docs/demand-kernel.md, the `with_skims` paragraph.
