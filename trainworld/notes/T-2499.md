# T-2499: a reload of a big game missed the demand cache (2026-11-05, agent loadfix)

## Confirmed on the player's path

Headless Chrome on the loadfix tree's Vite (6196), one profile kept across the loads: the Tokyo save
(`artifacts/trainworld/anita-2026-11-03e/tokyo-day-414.save`) imported into a game (`?paused=1`, which owns a slot),
its final and cache write waited for, then the page loaded again with `?slot=` (as the saves panel does) or plainly
and the save picked on the start menu (as after F5). Every cache read logged (`client.cacheLogs`), the canonical
network both sides written out and diffed. Script and log: `artifacts/trainworld/loadfix/` (`warm.mjs`, `warm.log`,
`netdiff.mjs`, and `net-*-a.json`/`-b.json` the two loads' networks).

Before the fix, every reload missed (3 of 3): the reload's network hash was not the one written (`miss: "none"`).
The two networks differed in one line alone, a 7-stop bus line: run times 7-47 s a hop longer and trains an hour
6.40/4.80/3.20 against 6.11/5.34/3.05 on the reload. On the first load the bus ran at the 18 km/h top speed all
the way: its zones' street speeds never installed.

## Why

The clock worker reads a zone's street speeds (T-1577) as Range requests on the pack's `.bin`. For the first
array of the zones whose packs demand was downloading at the same moment (Tokyo, Gunma), Chrome answered the
Range request with a **200 holding the range alone** (245,728 bytes, no Content-Range). The code took any 200 as
the whole file and sliced the range out of it: an empty array, so `StreetGrid::from_zones` refused the zone and
the zone counted as done, never fetched again. The game's buses there ran at the top speed until a reload, and
the network the final was cached under was one no reload works out (on a reload the street fetch goes first,
from the browser's cache, and succeeds). The walking barrier (`game/walks.ts`) and the water masks read ranges the
same way; a walk grid would have come out empty and a mask failed (and been fetched again).

Loadwait's earlier "zones" miss was the harness reloading with no view in the address: the page opened on New
York, whose pack then went into the reload's solve. Neither the saves panel (it keeps the view) nor the start
menu (its world view loads no zone) does that.

## Fix

- `workers/rangeFetch.ts` `fetchRange`: the bytes asked for from a 206, a whole-file 200 or a 200 of the range
  alone; anything else is an error (the fetch is tried again later). Used by street speeds, water masks and walks.
- A load waits for the street speeds under its bus routes (`masksForLoaded`), so its network comes from the save
  alone, whichever fetch is quicker. The water masks were already waited for; streets are the same few ranges.
- `storedSize` counts the corridor table the days share once.

## After

| path | first load's network | reload | second reload |
|---|---|---|---|
| `?slot=` | the reload's (06cd3cf4) | hit, by the network's hash, 5.5 s into the page | hit ahead of the network (T-1539), 4.2 s |
| start menu | the same | hit, 6.1 s | hit ahead, 5.0 s |

The first reload cannot hit ahead of its network: the pointer written by the import's final is keyed by the
imported file's bytes, and the slot's bytes differ (the slot's own save); its final then re-points it.

## Size

The 1.32 GB was `storedSize` counting the corridor table once per kind of day (7). Counted once it is 193 MB in
memory; on disk the whole IndexedDB folder (the slot, the start game's cache and Tokyo's) is 77 MB, Chrome
compressing the values. On master after memhunt's T-2485 (cache format 8) it is 123 MB counted and 67 MB on disk,
and the same hits hold (reload by hash at 5.2 s into the page, second reload ahead at 3.1 s). One result per slot,
replaced at each final: fine for a desktop browser's quota, so not filed.
