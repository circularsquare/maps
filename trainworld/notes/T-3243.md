## Games (the 769 MB)

Measured on the box (all accounts, 2026-11-12 01:55 UTC):
- 2,704 accounts with a games folder (more than the 202 on boards: every signed-in player), 5,270 games, 23,792 files.
- 755 MB on disk: current saves 228 MB (30%), backups 425 MB (56%), pictures 98 MB (13%).
- One game's save: median 26 KB, p90 93 KB, max 1.7 MB. One account: median 187 KB, p90 617 KB, p99 1.7 MB,
  max 7.8 MB (24 games). Games per account: 1,429 have one, 660 two, the most 24.
- Old versions kept: yes, up to four per game (two recent 30 min apart, a day one, a week one; T-1830). That is why
  backups are nearly twice the current saves. A DELETE takes all of them at once; nothing older is kept.
- Caps (trainworld_games.go): 4 MB a save, 50 games and 64 MB an account, 8 GB for everyone (alert at 4 GB),
  1 GB uploaded per account per day. The per-account cap never binds (the biggest is 12% of it); the total is the
  only real bound. Past it, a save that would grow the store is refused and the game stays in the browser.
- Growth is mostly new accounts (~1,100/day x ~0.3 MB) plus existing games growing. Incoming upload traffic is about
  20 GB a day (Nov 11 sysstat average 228 kB/s), so each byte kept is rewritten many times; that costs nothing on
  Hetzner (incoming is free) and the disk holds it.

What bounds it: accounts x size per account. At the 10,000-account cap and today's mean (0.29 MB) that is ~2.9 GB;
as games get older and bigger it rises toward the 8 GB cap. If the account cap goes up again, the games cap is next.

Proposals (server changes; for Anita, none made):
1. Keep three backups a game instead of four (one recent, day, week): about a quarter of the backup bytes, ~100 MB
   today, a quarter of growth from existing games. Small change in `trainworld_games.go`; the restore menu shows one
   fewer "recent" entry.
2. Raise `MaxTwGamesBytes` to 16 GB with the alert at 8 GB when the account cap is next raised. The disk has 31 GB
   free and the box backups image the whole disk. Cheap, and it keeps the cap from biting before the disk would.
3. Later, if it keeps growing: drop the backups (not the current copy) of games not opened for 30 days, and only
   then think about games of accounts not seen in months (that one changes the privacy page, her call).
4. Lowering the per-account cap (64 MB to 16 MB) would only matter against abuse; the daily upload cap already
   covers a looping page. Not worth doing now.

T-3251 (2026-11-12) built proposals 1 and 2 and the account caps below in shonei-server 3f97067: one recent backup
plus the day and week ones (the recent one went, so the day and week ones keep their reach). An index from before
keeps its four until that game's next backup, which offers the newer old recent one to the day slot and drops the
older, its file removed by that same write; idle games keep four until written. Until the deploy, the daily check
reads the new caps from the clone, so its account and games percentages are optimistic.

## Real R2 counts (ops token, 2026-11-12 ~03:55 UTC)

Anita's token (`~/cloudflare-ops-token.txt`) reads account analytics, R2 buckets, zone settings and cache rules, not
zone analytics (so no hit ratio for data.anita.garden yet). The check now reads R2 operations from GraphQL.
- Class B: 68.7 M this month, 32.1 M in the last 24 h, almost all `anitamaps` GetObject (Nov 9 9.6 M, Nov 10 21.6 M,
  Nov 11 31.2 M). At the last 24 h's rate the month ends near 674 M, about $239 past the free 10 M. My estimate of
  38 M a month (33 reads x plays) was 18x low: plays re-read their data on every visit (below).
- Class A: 378k so far (uploads of each version, ~45-140k on release days), about 1.35 M projected, ~$1.56.
- GetObject per 15 minutes around the "trainworld data" cache rule (02:39 UTC): 01:30-02:15 about 0.89-0.97 M an
  hour; 02:45-03:30 about 0.78-0.85 M an hour. Roughly 15% lower, and not falling further hour by hour (03:30 ticked
  up; yesterday the same hours rose ~3% an hour toward Japan's morning, so against that ~20%).
- Why the drop is small: a GET for a trainworld file answers `Cache-Control: public, max-age=31536000, immutable,
  no-store` (HIT). The `no-store` comes from the earlier "data bypass" rule's Browser TTL "bypass"; the new rule
  sets only edge caching, so browsers still keep nothing and refetch every file on every visit. The edge cache is
  per data centre, and a large Range-read file misses once in every one. Range reads from the cache answer 206
  (checked on nyc.bin), so the rule is safe for the game. A `.json` asked for with a Range header answers 200 with
  the whole gzipped file, which is how it behaved before.
- Fix (dashboard, hers): in the "trainworld data" rule set Browser TTL to "Respect origin" (the files say a year,
  immutable, and every version has its own path), and turn on Smart Tiered Cache (Caching, Tiered Cache, free on
  every plan), so a miss in one data centre asks an upper tier before R2. Add "Zone Analytics: Read" to the token so
  the check reads the hit ratio.
- The off-site backup went in during this task: `shonei-backups` created 02:41 UTC, first run 03:17 UTC, 811 MB.

## Notes on the script

- The box probe is a Python string sent to `ssh root@5.161.112.237 "nice -n 19 python3 -I -"` on stdin; it writes
  nothing on the box and prints only counts and sizes (no names, ids, addresses or hashes).
- R2 operations need a token the machine doesn't have; the wrangler OAuth token has no analytics scope and expired
  2026-10-19 (refreshing it would rewrite her wrangler config, so the script doesn't use it).
- The R2 listing is ~285 list calls (Class A) a run, ~8.5k a month: nothing against 1 M.
- An orchestrator's permission check may refuse ssh; the script is one `python` command, which a rule like
  `Bash(python trainworld/tools/ops/check_resources.py:*)` (and the venv form) would allow.
