## Cause (a MapLibre bug, still in 6.19.0, the newest)

MapLibre lays labels out in grapheme clusters. `toGraphemes` (worker bundle) takes a fast path, one cluster per code
point, when `textCanContainGraphemeClusters` finds no mark in the text; otherwise it runs `Intl.Segmenter` and then
`canCombineGraphemes`, which joins every `gc=Mc` spacing mark onto the cluster before. The fast-path list leaves out
31 Mc code points: U+102B-102C, 1038, 1062-1064, 1067-106D, 1083, 1087-108C, 108F, 109A-109C (Myanmar: Burmese aa
and visarga, Shan and Karen tones), 1A61, 1A63-1A64 (Tai Tham), AA7B, AA7D (Myanmar Extended-A), 11720-11721 (Ahom).

A label is broken into lines with `TaggedString.substring`, which keeps the sliced `sectionIndex` (one entry per
cluster of the whole label) but re-splits the slice's text from scratch. When the whole label holds a listed mark
(so it was segmented and `ကား` was one cluster) and a line holds only the unlisted ones (so the line takes the fast
path and `ကား` becomes three), the line has more clusters than section entries; `getMaxImageSize` then reads
`"imageName" in undefined` and throws. The throw fails the whole vector tile's parse: everything in that tile
(roads, water, all labels) is missing, not only the label (before shot:
`C:\Users\anita\projects\maps\.tw-trees\maperr\artifacts\trainworld\t3842_dawtachar_before.png`, the right half
blank; after: `t3842_loikaw_after.png` beside it).

## Fix (ours, in app/src/map/basemap.ts)

`guardWrapMarks` wraps every point-placed basemap label's text-field: a place whose `name` holds any of the 31 marks,
or any Myanmar-script letter (105 code points in all), shows its `name:latin` alone, or nothing when it has no Latin
name. Line-placed labels (rivers, roads) are left as they are: MapLibre lays them out on one line (max width
Infinity), so they never split. Letters are in the list too so the rule is per script: with marks only, villages
with and without their Burmese line sat side by side. The test reads `name`, not the label text: a first version
bound the label with `let`, but MapLibre's `var` re-evaluates its bound expression at every use (`Var.evaluate`), so
it built each label 105 times.

Cost (`cost.js`: the same test as a `querySourceFeatures` filter on the `place` layer, against `filter: true`, 20
runs): about 3-11 us per place feature where there are many (Bangkok z12, 846 features: 1.2 ms to 10.7 ms for the
lot; Mandalay 1,710: 1.8 to 6.8 ms), so roughly 1 ms per tile's place labels at parse, in the workers.

Places that go blank (Myanmar-script `name`, no `name:latin`): Loikaw z12 0 of 1,217, Yangon 0 of 723, Mandalay 23 of
1,700 (`ပုဂံ` Bagan among them, a second feature of that name). Two-line labels in other scripts unchanged (Bangkok
shot `t3842_bangkok_after.png`: Thai under Latin as before).

The lie: Myanmar place names (villages, towns, cities, states, the country) show their Latin name only, no Burmese
line under it; a Myanmar-script place with no Latin name shows no name. River and road names keep their Burmese.
For DECISIONS (the orchestrator's to add): `2026-11-20: Basemap point labels in Myanmar script (and any holding a
Tai Tham or Ahom spacing mark) show their Latin name alone: MapLibre 6.13-6.19 throws on some wrapped Burmese labels
and loses the whole tile (T-3842).`

Upstream fix to propose to MapLibre (not done here): `TaggedString.substring` should hand the slice its clusters
(`_graphemes = graphemes.slice(start, end)`) instead of re-splitting the text, or `textCanContainGraphemeClusters`
should include every `gc=Mc` mark `canCombineGraphemes` joins on. Either makes this guard removable.
