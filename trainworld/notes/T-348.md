# T-348: main-thread lag while demand loads

Anita, 2026-10-14: the game lags (low fps, unresponsive) while demand loads, and on a pan just
after a city's load bar fills.

## How it was measured

`checks/t348-lag.mjs` (modes `prepare`, `startup`, `pan`, `resolve`, `reach`), headless Chrome
with its own profile, 1400 x 900, the real New York save, Destinations bubbles on (or off),
weekday shown. Throughout, the page pans the map 3 px and back every 50 ms (a move end every
50 ms: input the main thread has to keep up with), counts frames with requestAnimationFrame and
records long tasks with a PerformanceObserver. With a Chrome trace (CPU samples of every thread)
`checks/t348-analyze.mjs` says what each long task spent its time on. Pages: scratch production
builds without minification (`vite build --minify false` into the scratchpad, served by
`checks/static-serve.mjs`): "before" is HEAD (359ed79), "after" is HEAD plus this task's four
files only (not the T-347 hold or the top bar work going on at the same time). `&perfOff=nocache`
(an unknown flag) makes the T-328 cache key miss, as after every new build. 16 logical cores
(8 physical), so 5 solving workers; the machine was 40% busy with other work before each run.
Outputs and traces: `../artifacts/trainworld/t348/`.

Scenarios: **startup** from the network drawn to the fresh final (no cache, or the cache shown);
**early pan**: a jump to Philadelphia as soon as the network is drawn (during the startup solve),
then to Toronto, 12 s each; **pan**: the same once solved, 15 s each (both open bare);
**re-solve**: the same network solved again once settled; **reach**: a three-station line built
in Toronto, which fetches Toronto for every worker and re-solves everything with it.

## What was lagging

Once the startup solve is final, nothing lags: pans to Philadelphia and Toronto (opened bare),
a re-solve of the whole network with five workers at full speed for 15 s, and a line built in
Toronto (Toronto fetched for every worker and solved with everything) each gave 0-5 long tasks
and 59-60 fps. **So the workers' CPU alone does not starve the main thread, and "putting a loaded
city into play" costs about 50 ms.** All the lag is in the first 10-14 s after a load:

1. **The Lines tab's sort** (`ui/tabs.tsx` `natural`): `localeCompare` with options builds an ICU
   collator per comparison. The tab re-sorts on every move end, so every pan paid 2-5 ms when
   idle and up to 380 ms of samples inside a single 1,525 ms long task during loading. 5-15% of
   the main thread throughout the test (a move end every 50 ms exaggerates it).
2. **Placing every station in its zone** when the network first arrives (the Lines tab's scope,
   `stationZone` to `distanceTo`, `Math.hypot` on every outline segment): 140-225 ms, in a
   360-660 ms task with the clock worker's first state.
3. **The rest is the main thread being descheduled, not working.** The remaining long tasks run
   3-7 ms of CPU in 50-230 ms of wall time (Commit, Paint, animation frames), and in the worst
   seconds every thread of the page got a quarter of its usual CPU samples. They come only in the
   first 10-14 s, when the five solving workers open packs and set up, MapLibre's worker parses
   the basemap tiles, and the box was already 40-70% busy with other work. With 2 or 3 solving
   workers they about halve (the final lands at 26-35 s instead of 19-21 s): T-355. Not the
   cause, tested and ruled out: WebAssembly tier-up (`--no-wasm-dynamic-tiering`, no change);
   workers' memory growth (a page growing 5 x 400 MB in 0.5 s gave at most a 67 ms gap);
   demand result messages (the final publish is 70-110 ms once, T-354).
4. Smaller: copying a pack for each worker in one task (45-70 ms for New York), the final
   publish (70-110 ms), a long pan's whole clock state (about 50 ms, T-356).

## Changed

- `ui/tabs.tsx`: the Lines tab sorts names with one shared `Intl.Collator` instead of
  `localeCompare(b, undefined, options)`, which builds a collator on every comparison (5.5 ms a
  sort of 109 names in Node against 0.12 ms; same order). The tab re-sorts on every move end
  (T-332's distance column), every game hour and every world change.
- `game/search.ts`: the same for search results and line lists.
- `game/zones.ts` `nearestZone`: a zone whose bounding box is no nearer than the best so far is
  skipped.
- `workers/cityReach.ts` `distanceTo`: the nearest point by squared distance, `Math.hypot` for
  that one only. Placing the save's 1,756 stations (the Lines tab's scope, at the network's
  arrival) went from 140-225 ms to about 20 ms. Checked against the old code on 20,000 random
  points over all 14 zones: every distance and nearest zone identical to the bit, 8.7 x faster.

Demand results are untouched (no demand code changed); `checks/smoke.mjs` "demand final" passes.
