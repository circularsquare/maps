# T-2716: the `--profiling` build's panic

Done 2026-11-07, agents boarding then heapfix, in tree `boarding` (uncommitted, with T-2699 and T-2700).

## Cause

An LLVM optimisation, allowed by what rustc tells LLVM about the allocator, applied to dlmalloc's
size check once that check is inlined into ordinary code. Not an integer overflow, and the heap was
never corrupt.

- rustc marks `__rust_alloc_zeroed` as an allocator returning a fresh zeroed object, and `__rust_alloc`
  one returning a fresh uninitialized object. Std's wasm32 allocator is dlmalloc; with LTO its
  `free(ptr, size, align)` wrapper inlines into callers, and that wrapper first runs `validate_size`,
  which reads the chunk header 4 bytes *before* the block (`assert!(psize >= size + min_overhead)`).
- Where a function keeps the allocation as a call (not inlined) and has the free of the same block
  inlined, GVN reads the header load as a load from that fresh object: from a zeroed allocation it
  folds it to 0 (from an uninitialized one, to undef). With 0 the assert always fails.
- T-2699's (and T-1594's) grow-ahead trick allocated and freed a big pad inside the global allocator's
  `alloc`. That made `__rust_alloc_zeroed`'s body too big to inline at some call sites, which left
  exactly that shape. In `--release` (16 codegen units before LTO) it happened in `geom::fit_capped`:
  `vec![0.0; n]` then its drop. In the app's `wasm` profile (1 codegen unit) the inlining fell out
  differently and that site was clean.
- Found with `-C llvm-args=-opt-bisect-limit` (serial LLVM via `CARGO_BUILD_JOBS=1`): last good
  1,207,703, first bad 1,207,704 = `gvn on fit_capped` in the LTO pipeline. Its IR before and after:
  the header load `getelementptr i8, ptr %110, i32 -4` disappears and the branch to the panic
  becomes `br i1 true`. A second site in the same build, `TrackApi::building_quote` (`building::ground`
  collects a Vec), aborts the same way.

Variants that told the cause (release, Japan load): pad kept and never freed: fine. Pad of 1 MB, or
of 32 MB with align 8: abort. All of Ahead's methods `#[inline(never)]`: fine. Pad a no-op: fine. No
custom allocator: fine.

## Were players' builds affected

No corruption. The fold only reaches the inlined size check; dlmalloc's own `free` and `malloc` stay
out of line and read the real headers. The worst it can do is a false abort (zeroed) or a skipped
check (uninitialized). Every test, smoke, the byte-identical dumps and `building_quote` pass on the
app's builds (the main tree's, T-2699's), so no abort site sits on a path they run. The demand
module (trick since T-1594) in `--release`: t066, t1374 (Kansai, Hangzhou, New York markets), t1277
pass with no abort. The latent shape is in every build where the allocator inlines: 420-511 functions
of the app's builds hold an inlined size check.

## Fix

`sim/src/heap.rs` rewritten: `Heap`, a `dlmalloc::Dlmalloc` (crate 0.2.14, the version std uses; a
wasm32-only dependency) over `Grow`, its own system side, which grows the memory by at least
`min` (32 MB), or `1/frac` of the memory once that is more (track module 1/8, as T-2699; demand none,
as T-1594). The linker's spare heap is handed out first, as dlmalloc's own wasm side does. No allocation
inside an allocation. `Heap`'s four `GlobalAlloc` methods are `#[inline(never)]`, so no caller sees a
chunk header: in the release IR only `Heap::dealloc` and `Heap::realloc` hold the size check (419
functions before). `demand/wasm.rs`'s `NotingAlloc` now counts over its own `Heap::new(32 MB, 0)`.
No WASM interface change.
