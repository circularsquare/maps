# T-4367: demand crash after making a line in 0.4.7

Player report: tw-feedback 1795696901-713ef342 (11-26, Safari 27.2, Apple GPU, 161 lines, one solving worker):
`worker 0: TypeError: null is not an object (evaluating 'o.beside')`, mostly after making a new line; "Demand
stopped, so the game is paused" until a reload.

## Cause

`app/src/workers/demand.worker.ts`, the edit's local stage (`run`, the loop over `early`), 0.4.7 and master alike:

    const part = c.part, { ed, reach } = e;
    const sub = e.window && !ends ? part!.beside() : null;     // part is null here

`c.part` is null for a cluster with no market part: every cluster when intercity trips are off (`regional` is
null: the default on a phone or iPad, "Load without intercity trips", "Play without intercity trips" after a memory
stop, or the setting), and a cluster no market zone reaches with them on. `regional.beside()` in `assignParts` never
sees a null (it runs only `if (regional)`), so this is the one.

How a new line gets there: T-4237 (dce8cc608, 11-24, in 0.4.7) reads an edit against a kept city's baseline when the
cluster has no market part (`base = marketNet.get(kept)`; before, `ed` was null without a part). `window` kept its old
formula, `!!ed && (reach > 0 || ed.switched)`, which used to imply a part. So with no part:

- a new line, or stops added or dropped, on a run of 20+ minutes (`WINDOW_EDIT_MIN`): `reach > 0`, and `intercity`
  (stops on a 20+ minute run), so `ends` is false;
- a line switched on or off at a level (`switched`): window and intercity at once;

and the touched cities under 35% of the cluster's passes (`LOCAL_SHARE_MAX`, else the edit goes straight to the whole
solve and skips this code) reach `part!.beside()`. A big network with many cities in a cluster is exactly that, and
T-4241 keeps a city baseline at the last whole solve without a market part, so a line built stop by stop is read as one
long new line from then on. A short city line (under 20 minutes, not switched) ends at its local result and never got
here, which is why it showed mostly after new lines.

Other `!`s on the part in that block (`part!.zones_at`, `part!.solved_mask`, `part!.window_loads`, `e.market!`,
`ed!`) are all inside the window, so they failed with it. `whole!` and the `c.part!` in the `finally` are safe: `whole`
is non-null exactly when `c.part` was at the stage's start, and a part is never freed mid-solve (closes wait in
`closeLater`; `recompose` frees no part a cluster holds). `localSolve` already guards with `c.part instanceof
IntercityApi`.

The published 0.4.7 (cf7b483e0) has the same demand.worker.ts as master's HEAD (d74892e6f): nothing touched the file
since, so the bug is live in 0.4.7 for every player with intercity trips off.

## Fix

A window holds the market's pairs, so the edit's `window` is now the market part it opens beside, with that part's
route nodes, the edited stations and the reach (`{ part, market, ed, reach } | null`), made only when the cluster has a
market part. The local stage reads everything from it, so no `!` is left on the part in the window code and the type
keeps a later change from opening a window without one. A cluster with no market part then does its local solve with
no window and goes on to the whole solve, as T-4237 meant. Figures: unchanged wherever the old code ran (with a market
part the window is as before); the case that threw now gets figures.
