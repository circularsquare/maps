# T-3802 Real world station rings drift while zooming (hotfix for v0.4.3)

Tree `.tw-trees/ringfix`, branch tw/ringfix from d39db027 (before save level 30). Agent ringfix, 2026-11-19.

## Cause

The ring canvas (T-3760, `map/realStations.ts`) scaled its 2D context by `map.getPixelRatio()`, the ratio
MapLibre was asked for, while its backing store is sized like MapLibre's canvas (`fitSparse`). The two differ when:

- the map is wider or taller than 4096 device px (MapLibre's default `maxCanvasSize`): MapLibre then draws at a lower
  ratio than `getPixelRatio()` returns. A 5K screen (2560 CSS px at 2x) or a 5120 px ultrawide hits it;
- `devicePixelRatio` changes with no CSS resize (a window moved to a screen of other scaling): MapLibre has no
  listener for that and keeps its old canvas, while `getPixelRatio()` reads the new ratio at once.

Either way every ring lands at (its true point) times a constant, measured from the map's top left corner, so the
rings sit off the track, further off the further from the corner, and slide at a different speed than the map while
zooming or panning: "completely offset from the actual tracks (no fixed position)". The station circles
(`stationCircles.ts`) already scale by `canvas.width / cssW` for this reason.

Reproduced with `map.setPixelRatio(6)` in a 1098 CSS px map (MapLibre's canvas clamped to 4096, ratio 1.65 off):
`artifacts/trainworld/t3802/before_ratio6_z14.png`. At ratio 1 the rings were exact, also in a frame partway
through a zoom animation (an 8 s easeTo, frame at zoom ~14.0), so a per-frame lag was ruled out: the 2D canvas is
drawn in MapLibre's own render (`afterMapFrame`) with the camera of that frame. The swap of `devicePixelRatio` without
resizing was not reproduced headless (the CDP override did not take); the code path shows it.

The player's screen is unknown. Screens that hit the 4096 cap: 5K, 5120 px ultrawides, and a Mac on a 4K monitor at
"looks like 2560x1440" (2560 CSS px drawn at 2x).

Same bug elsewhere, left for a follow-up (this ships alone): `map/tripView.ts` `draw` (a trip's routes and the veil)
and `map/gapFlash.ts` scale their 2D canvases by `map.getPixelRatio()` too, so they sit off on the same screens. The
WebGL overlays pass `getPixelRatio()` only for line widths (positions come from clip space), so lines draw a little
thick there but in place.

## Fix

- `realStations.ts` `draw`: scale by `canvas.width / overlay.cssW` (the kept CSS width, no layout read per frame,
  T-063). The canvas stays (a MapLibre layer would sit under the network canvas, where T-3792's dots are).
- Hover while placing: the station tool's own tag holds the demand hover back whenever it shows (T-526,
  `main.ts` `buildAbove`), and on open ground it always shows ("Place stations on track"), so the ring's name never
  showed. The finder's body is now `realStationUnder(lng, lat)` (exported); the station tool (`tools.ts`) puts that
  name as the first row of its tag: above the red refusal ("Place stations on track", "There is already a station
  here.", any `verdict().why`), or as `helpLines`' first row on track. Same `.tool-tag` look as the dot's hover tag.
- Tram stops: the dots show a station whose every line is a tram/funicular/monorail/narrow gauge one only under All
  or while tram track snaps (`keep`, unchanged). As rings (station tool on) a tram stop (every line one of those kinds,
  at least one a tram) shows always, at 0.65 of a station's radius and stroke widths. The hover uses the same rule.
  Under Passenger these rings sit where no real tram line is drawn (the real network layer leaves trams out there).
- Docs: `docs/ui-map.md` Real stations paragraph.
