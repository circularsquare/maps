session for many zones, (c) publishing from a frozen copy of the last good state.

## 2. Design

### (b) One browser session for a gate's zones

`checks/city-browser.mjs` takes `ROWS` (a JSON list of rows) and checks every zone in one page: a
sandbox game (no money limit, so later zones' lines still build), each zone in turn: jump, opens,
active, split, water pair, test line built and solved, screenshots, then its line removed so the
next zone's solve does not carry it. Each zone gets the same 8 checks and its own browser JSON. The
fixed waits become waits for the condition with the old wait as a cap (the demand view final, the
map idle). A zone that throws closes the page; the rest go on in a fresh one. At most
`ZONES_PER_PAGE` (20) zones a page, to bound the page's memory (every opened zone stays in it).

`checks/pack_gate.py --browser` with several ids makes every row first, runs one session, then
judges each pack. A gate is a region's rows, so one session a region: China's regions are
provinces of 30-100 zones, so this is close to one a batch, without moving the browser check out
of the region gate (which would change when rows park). `changed_since` hashes each other pack
once a gate instead of once a zone (the packs cannot change during a gate), and now compares every
pack (section 3).

### (c) Publishing from a frozen copy

The published build copies `data/packs` (at build time, by vite.config.ts) and bundles
`app/src/game/registry.json`, `market-rows.json`, `zone-aliases.json` and `zone-names.json`. A batch
rewrites all of them, so a build during a batch can mix states (a pack mid re-solve, a zone
registered but not yet gated).

- `pipeline/freeze.py` makes `data/frozen/<stamp>/`: `packs/` as NTFS hard links to every file the
  build copies (no space; 4,123 links in about 2 s), `game/` copies of the four JSON files, and
  `manifest.json` (every file's size and modified time). Every pipeline writer replaces a file
  (write a `.part`, rename), never rewrites it in place, so a hard link keeps the old content.
  `freeze.py check` compares the files with the manifest, to catch a writer that did not.
- The runner freezes at the end of every run whose join finished with its market step (no other
  run live), holding the packs lock; by hand, `freeze.py` refuses while a run is live (`--force`
  to override). The newest three freezes are kept.
- `freeze.py build [stamp]` builds the snapshot tree's app (its own commit's code) with the
  freeze's packs (`TW_PACKS` in vite.config.ts) and the freeze's four JSON files laid over the
  tree's for the build only, into `artifacts/trainworld/publish/<stamp>/dist` with `frozen.json`.
  `tools/deploy.py --dist <that>` then takes the registry from the freeze and warns if the freeze
  changed since.
- One small risk: Windows refuses to replace a file another process has open without delete
  sharing, and a hard link is the same file; a batch step replacing a pack in the minute a freeze
  build copies it could fail once. The runner's steps retry once (build steps) or fault visibly.

### (a) Incremental join: measured, not built

Today a join re-solves every member of each solve unit (a country, or a Chinese province, T-897)
holding a new row. The design tried: solve the new rows and the members within `CUT_KM` (150 km)
of them, hold the others at their factors as T-786 holds a neighbouring country, keep every member
in the solve so the frame and border table match, and check the hold: `joint_gravity --new <ids>
--hold-report F` reports how far the solve moved each held pack's row and column sums; a held
member moved over 1e-4 joins and the unit is solved again. Built in joint_gravity and the runner,
tested by dry runs against the full solve (section 3), then taken out of the runner: in the
compact units China's waves fill it is slower than the full solve, and where it is faster it does
not give the full join's packs. `--hold-report` stays as a diagnostic (it found T-932). Starting
the full solve from the old factors (`--warm`, tried) gives the same answer in as many steps, so it
was taken out too.

## 3. The check of (a)

Dry runs of my tree's `joint_gravity` (nothing written) on copies: the members' res-9 packs from
the runner's own pre-join backups (`join.group-*-backup`), the fixed packs as they are, the main
registry and borders. First, the dry full solve was checked against what each real join wrote:
every pack's kept trips agree to 6e-8 (f32 storage), so the harness reproduces the join. Then the
held packs' old flows (what an incremental join leaves) and the solved packs' new ones against the
full solve, per zone with at least one commuter (`notes/t928_exp.py`; its paths point at the T-928 scratchpad and the batches' backups):

| Case | Full solve | Incremental | Largest zone difference from the full join |
|---|---|---|---|
| osl-no, ves new (5 members) | 24 s | widened to all 5, 42 s | none in the end (stf held: 0.26% in round 0) |
| hel-fi, poj new (5 members) | 124 s | widened to all 5, 267 s | none in the end |
| Jiangsu, xuz new (39 members, synthetic: "before" = the unit solved without xuz) | 200 s | 4 rounds to 25 solved, 378 s | held: 0.035%; far packs 0.02% (Shanghai, 400 km off) |
| GB, hih new (68 members, 20 fixed) | 765 s | round 0: 13 solved, 155 s | held up to 0.88% (Cardiff), solved up to 0.67% |

Two things decide it. A new pack moves every member of a unit a little (Shanghai's zones by up to
2e-4 from a pack 400 km away), because the gravity's power-law tail couples the whole unit; so the
hold check keeps widening, and in a province-sized unit the rounds cost more than one full solve.
And a real unit's last factors are not a converged "before": each was solved against neighbours
that were re-solved since (T-786's country-at-a-time order), so the full join repairs drift
everywhere, which held packs keep (GB: up to 0.9% a zone; pack totals within 1.3e-4). Neither is
float noise, and the second would give market packs that quietly differ from a full join's.

The same check found T-932: in the GB solve, Ireland's fixed bod moved 28% on its row sums and mis
3%, the size of the error T-786's holds of a neighbouring country already carry.

## 4. What it saves, and what is left

For a China wave of about 150 zones in five regions:
- Browser checks: 150 x (27-30 s) = 70-75 min becomes about 150 x 11 s + five page loads, 28 min:
  **about 45 minutes saved**; over the last three days' 760 gated zones it would have been about
  5 of the 9 browser hours.
- `other_packs_unchanged` now compares every pack, each hashed once a gate: about 2 s a gate.
- Publishing no longer waits for a batch to end: the wait was the batch's remaining hours.
- The join is unchanged. What is left there, all exact (follow-ups filed):
  - **T-929** market rows only near changed zones: `market_pack` over every place takes 85 s a
    call now and grows with China; it runs at every region's gate (2-2.6 min a register) and every
    join (3-6 min). For a five-region wave, about 10-20 minutes, more as places grow.
  - **T-930** the join's re-gate only on what a solve changes: 9.8 of the GB join's 31 minutes.
  - **T-931** the gate's cargo test built once a run: 10-65 minutes each time sim/ changed between
    regions (both of the two-hour batch's slow gates).
  - The two-hour batch's biggest item, hih's 72-minute failed build, is T-903's.
