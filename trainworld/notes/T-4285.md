### T-4274/T-4280 1: return-run caches keyed by a moving slot (real; for netcut)

`backBaseOf` (network.ts:3029) is `meta.length / META_PER_LINE`, one block per line id up to the highest
(clockMain.ts:441). A return run on its own way back has slot `backBase + id` (`backSlotOf`, :3021). A new line takes
the next id, so making one moves every return run's slot up by one; undoing it, or deleting the top line, moves them
down. `cache.samples` and `cache.passOf` are keyed by that slot (:2354, :2398, :2422, :2423, and `runPaths`'
`samplesSeen.get(id)`, :2785), so in that build:

- line l's return run reads line l+1's old return-run entry, or none. `kept` fails on `sm.c === c`, so its samples
  are made again, but `stretchesNew` and `lanesNew` come from comparing them with line l+1's old values (:2394), and
  the passing places with line l+1's (:2423).
- the new line's run 0 (its id is the old `backBase`) reads line 0's old return-run entry, and `alikeSamples` (:2345)
  can copy its `rel`, `lane` and `band` for leading entries where the two paths happen to agree.

The GPU tables key by the stable row key (trainSlots.ts `rowKey`: id * 2, id * 2 + 1) and trust the names
(`putSlots` with `listed`), so a missed name leaves that run's lane or stretch slot as it was until the line
changes again. A miss needs line l's own values to change in the same build (a new line beside its way back moves
its bands; a passing place gone) while the wrong line's old values equal its new ones, or neither has passing
places. Rare, but a whole rebuild would differ.

Fix, network.ts `runSamples` (:2352): key both caches by the run's row key, as trainSlots.ts does.

- `const runSamples = (slot: number, key: number, path, strokeOf, back) => ...`, with `cache.samples.get(key)`,
  `samplesSeen.set(key, sm!)`, `passOf.set(key, mine)`, `cache.passOf.get(key)`; the calls (:2425, :2427)
  `runSamples(l.id, l.id * 2, ...)` and `runSamples(slot, l.id * 2 + 1, ...)`.
- `runPaths` (:2769-2774) carries the key: `[l.id, l.path, l.id * 2]` and `[slot, l.back, l.id * 2 + 1]`, read with
  `samplesSeen.get(key)` at :2785 (`pathTable` stays indexed by slot).
- `NetCache.samples` (:1649) and `passOf` (:1670) docs: per run by its row key (line id times 2, plus 1 for a return
  run's own way back, trainSlots.ts `rowKey`). `shiftNetCache` needs nothing.

netcut's tree has edits at :2424 and :2428 (timing laps around these calls), hence not edited here.

### T-4274/T-4280 2: two networks before a frame (real, one frame; fixed)

`frameSetup` (rendererDraw.ts:27) puts in every staged state due (`releaseStaged`, renderer.ts:1337) and calls
`freshFill` in the same frame, before the microtask that sets the layers (demandViews.ts `schedule`). Two staged
networks due in one frame each set `trainsWrote` to their own writes, so the first's lines kept the fill from
before both, on their new samples, for that frame; `setLayers` puts the right fill before the next one. At most a
one-frame flicker in a demand view. Fixed at the cause (renderer.ts:796-798): while the fill is stale, a network adds
its lines to `trainsWrote`, which now holds every line written since the fill was last put or blanked.

Cousins: `flushStaged` then `put` run in one task, so the layers' microtask comes before any frame; slots that moved
across several networks were already caught (`freshFill` compares with the fill's own last layout).

### T-4274/T-4280 3a: a carried copy checked before it is settled (real, checks only; fixed)

`carryLod` keeps the old `a_full` and `a_wmul` on a carried copy's kept slots (`fullKept: true`) and checked them
whenever the copy was current before the edit (`v` -2). `setNetwork` decides only afterwards (renderer.ts:760):
current while the marks are kept and no demand widths are drawn, else -1, which `pickStrokes` writes whole before
drawing (rendererStrokes.ts:476). So an edit that changed the crowded marks, zoomed out under `?patch=check`, logged a
false "T-2403 check" error. The lines copies' widths and marks are now checked in `setNetwork` once settled, only
for copies it calls current (renderer.ts:762-763); track copies in `carryLod` as before (rendererStrokes.ts:712).

### T-4274/T-4280 3b: room for a carried copy (real, memory only; fixed)

`carryLod` passed `room: true`, so a carried copy laid out again took `slotShare.room` (a quarter), and a copy made
with a sixteenth never passed `slotted`'s reuse test (cap at least n plus half the share): new buffers with a
quarter's room each time. Now `room: BAND_ROOM` (rendererStrokes.ts:682), as `workBand` makes them. GPU memory
only; the `BAND_ROOM` comment has a quarter at 5.7 MB for two zoom bands on her Asia save.

### T-4281: a span's drift (real, checks only; fixed)

`span_of` (service.rs:809) keeps an entry past the cut when its offset moved by the length change give or take
`SPAN_EPS_M` (1e-6 m), but reported `drift` as the length change alone. With the length the same bit for bit and an
entry moved by a rounding step, drift was 0, `spliceRun0` set none (clockMain.ts:218) and `checkSamples` compared
those samples bit for bit (:250): a false "T-4149 check" error under `?patch=check`. The drawn error is under a
micrometre and its share of `DRIFT_MAX_M` (5 cm) under 1e-6 m a cut, so no player sees it. Fixed at the cause: drift
is the most any kept entry moved, at least the length change. Test `track::service::span_tests::drift_covers_every_kept_entry`.

### T-4150 1: `sameBuilt` and missing keys (real, not reachable today; for pagestage3)

`sameBuilt` (worldDiff.ts:328) compares key counts and then a's keys' values, so `{x: undefined}` equals
`{y: undefined}`. Production callers: `buildingsKept` and the income and points posts (clockClient.ts:417, :1081,
:1114). Their values (the worker's buildings, `[per, rides, lines]`, the points rows) never have a key on one side
only with the same count, so nothing is missed today.

Fix, worldDiff.ts:341: `return ka.every((k) => Object.prototype.hasOwnProperty.call(b, k) && sameBuilt(...))`. One
line, worth it now that the income and points posts rest on it.

### T-4150 2: `PerLine` after a throw (real, only after another bug; for pagestage3)

`PerLine.begin` (worldDiff.ts:309-314) sets `this.w = w` at the start of a pass and `end` swaps in its values. A
`make()` that throws leaves `w` beside the values of the world before it; the next pass diffs from `w` and keeps,
for lines that changed between the two, the older world's values until they change again. Only after a reader has
thrown (its own bug, which logs).

Fix: `begin` keeps the world as `this.at = w`; `end` sets `this.w = this.at` with `this.m = this.next`, so a pass
that never ends leaves the last finished pass's world and values together.
