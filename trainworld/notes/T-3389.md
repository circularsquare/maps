## What exists (searched 2026-11-15)

- **T3 Code** (Theo / Ping.gg, MIT, alpha since 2026-03): a desktop and web front end for running Claude Code, Codex
  and others in one window. It runs agents; it does not track work. Could later replace VS Code tabs for watching
  agents; no help with the task list. https://flaviocopes.com/t3-code
- **Vibe Kanban** (BloopAI): a kanban whose cards start coding agents in their own worktrees. The company shut down;
  its hosted board is retired (export only). Its idea worth taking: a card shows the agent working on it.
- **Backlog.md** (MIT): tasks as one markdown file each in the repo, a local web kanban (`backlog browser`), made for
  humans plus AI agents. Closest off-the-shelf fit, but it means 437 files and new agent rules, has no player inbox or
  agents panel, and runs its own server. https://github.com/MrLesk/Backlog.md
- **beads** (`bd`, already used in shonei): issues with dependencies, so "waiting on a prereq" and "ready" come for
  free (`bd ready`); several community web kanbans (beads-ui, bdui, beads-kanban). Moving trainworld would mean
  migrating 437 tasks and rewriting the TASKS/ARCHIVE rules. https://beads.gascity.com/community-tools
- **GitHub Projects**: maps is a public repo, and the board would carry player reports and her notes. No.

## Proposal: build a small board on 8800, keep TASKS.md as the record

Nothing above does the three parts she most wants (player requests to accept or reject, a "waiting on me" queue, what
agents are doing), and all of them would change how 437 tasks are kept. So: a page `twboard` on 8800 that reads the
files agents already keep, plus one inbox file for her answers.

Layout: columns are status, rows (swimlanes) are areas; a switch flips it to one column per area, each an ordered
queue.

- **Status, one colour each**: Ready (one pool; the card shows its best task's priority and lines sort P1 first), Waiting on Anita, Waiting on another
  task (names it), In progress (names the agent), Done this week (with what to test on 8800).
- **Areas** (a first cut, hers to rename): Track and stations, Scheduling and fares, Demand, World data, Schematic,
  Community and accounts, Interface, Performance, Ops and code health. Big updates (v0.4 track and stations,
  scheduling and fares) are a filter across areas.
- **Cards**: id, title, priority, area, estimate in hours, players asking (count), notes link opened in a side panel
  rendered as text.
- **Her actions**, each with an optional comment: reorder within an area (the queue the orchestrator works from the
  top of), change priority or area, answer a question, accept or reject a player request, "text acknowledged", quick
  add a new item.
- **Agents panel** at the top: each running agent with its task, model, start time, last report; long runs and core
  claims; what master, 8800 and live are on.
- **Player requests**: new feedback reports, grouped by what they ask for (an agent sorts them daily), each group with
  a count, a reach guess and links to the reports; Accept (pick area and priority), Reject, Merge into a task, Comment.

Getting her changes to the orchestrator: the page saves each change at once to `notes/board-inbox.jsonl` through a
small addition to serve.py (it already has page-triggered actions). The orchestrator watches that file and acts on a
batch once she has been idle for 3 minutes, or at once when she presses Send now. With no orchestrator running, the
changes wait in the file for the next one; `/takeover` starts the watch.

What agents change: every task line gets two short tags, area and status (`{track}` `{waits: Anita}`,
`{after: T-3348}`), added once by one agent over all 437 lines and then kept up by whoever edits a line, like the
priority today. The orchestrator writes a small `notes/board-live.json` when it starts or finishes an agent.

TODO.md stays hers. The board's quick add can take over the short-term section's job if she likes it; nothing
forces that.

## Stages (hours of agent time, rough)

2. Her actions and the inbox: serve.py endpoint, the watch, Send now, reorder. About 2 h.
3. Player requests: daily grouping, accept and reject. About 2 h.

## Format (decided by the orchestrator, 2026-11-15; both T-3390 and T-3391 follow it)

**Areas** (rows, in this order), slug then name: `track` Track and stations; `schedule` Scheduling and fares;
`demand` Demand and world data; `schematic` Schematic; `community` Community and accounts; `interface` Interface;
`performance` Performance; `ops` Ops and code health.

**`trainworld/LINES.md`**: a short header, then one `## <Area name> {area:<slug>}` heading per area in the order
above, and under it one line per line:

    - <slug> | <name> | <one or two plain sentences for Anita> [| update:<track-stations|scheduling-fares>] [| done:YYYY-MM-DD]

Slugs are lowercase-hyphenated and unique (`quad-track`). Names are short, sentence case, her vocabulary ("AA/BB quad
track", "Timetables"). `update:` marks a line as part of one of her two planned big updates. `done:` is set when a
line's last open task closes; a done line stays in the file.

**Tags on task lines** in TASKS.md, inserted right after the priority (or after the id where a line has no
priority): `- T-3348 [P2] {L:per-direction-stops} {after:T-3346} Per-direction stops...`

- `{L:<slug>}` on every open task: exactly one line each.
- `{waits:Anita}` when the next step is her decision or answer.
- `{after:<what>}` when it waits on something else: a task id (`{after:T-3346}`) or a short phrase
  (`{after:Europe rebuild}`). Several are allowed.
- A task keeps its `{L:...}` tag when it moves to ARCHIVE.md.

**Task status** (board, derived): its id is a task in board-live.json's agents, or its line says `taking` ->
In progress (T-3390 clears the stale `taking` marks, so the word is reliable from then on); else
`{waits:Anita}` -> Waiting on you; else `{after:...}` -> Waiting on another task; else -> Ready (any priority; the
old Ready high and Ready low columns were merged on 2026-11-20).

**Line status** (board, derived) = the first that any of its open tasks has, in this order: In progress, Waiting on
you, Ready, Waiting on another task. Inside a Ready cell lines sort by their best open ready task's priority (P1
first), ties in LINES.md order, and each card shows that priority. A line with no open tasks and `done:` within 7 days -> Done this
week; older done lines are hidden.

**Columns** in this order: In progress, Waiting on you, Ready, Waiting on another task, Done this
week (Up next sits second).

**`notes/board-live.json`**, written by the orchestrator when agents start or finish:

    {"updated": "...Z", "orchestrator": "maps-b8",
     "builds": {"master": "<hash>", "8800": "<hash>", "live": "v0.3.4"},
     "agents": [{"name", "task", "model", "started", "doing"}], "runs": [{"name", "pid", "started", "doing"}]}
