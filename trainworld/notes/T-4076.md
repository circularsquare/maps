# T-4076 Track can't be placed on a tablet (touchtrack, 2026-11-23)

Report (Discord, Firefox on an Android tablet): start and end can be tapped, the ghost and its tag show, but
nothing reaches the blueprint. Picture: artifacts/trainworld/board/20261123-081229-cce9.png.

## Cause

The picture has no touch bar and no handle ring, and the tag sits by the end as the mouse's does: the game had
gone back to mouse mode (`touchInput` false) while the finger was drawing.

`map/touch.ts` `watchInput` let any `pointermove` with pointerType "mouse" take the hover back from the finger
(meant for a laptop with a touch screen). Firefox for Android follows a change in the page's layout with a
synthesized mouse move at the last mouse spot, which after a tap is the tap's own spot (Mozilla bugs 1973014,
1292041; 1973014 fixed only in Firefox 154). Every tap changes the page (the ghost, the bar, the tag), so after
each tap that move flipped `touchInput` to false, and the effect in `Tools` that runs on the flip dropped
`touchAt`, the end waiting to be placed. The next tap set the end again, the move dropped it again: the end
was never placed, by a second tap, the bar's tick or the handle (which the flip also hid).

## Reproduced

- Chromium (system Chrome, hasTouch, isMobile, 1280x800, Android UA) and Playwright's Firefox 1532 (hasTouch,
  already installed): plain taps place the segment in both. Playwright's Firefox makes its tap's mouse events
  itself, not through Gecko's tap handling, so it never sends the synthesized move.
- With the move added by hand after each tap (a `pointermove` pointerType mouse plus a `mousemove` at the tap's
  spot, 150 ms after the tap) both fail exactly as reported: no bar, ghost and tag by the end, 0 edges after
  three taps. Not tried on a real device.
- Playwright 1.61's Firefox asserts on a websocket it never saw (`FFPage._onWebSocketOpened`); the scratch probe
  ignored that uncaught error. Firefox also needs `http://[::1]:<port>`, since Vite listens on IPv6 only.

## Fix

`watchInput` now counts a mouse move only when it is at a new spot: it keeps the last mouse spot from mouse
pointer moves and from the mouse events a browser makes of a tap, and a mouse `pointermove` within 1 px of it
does not take the hover back. A real mouse always moves to a new spot, so a hybrid laptop still switches back
(checked). `touch.ts` is shared by every build tool, so the bus, ferry, building, station and delete tools on
Firefox for Android get the same fix.

## Checks

- `checks/t4076-touch-track.mjs` (about 1 minute, Chrome with touch emulated and the move made by hand): bar
  shows, a second tap places, the bar's tick places the next segment, a real mouse takes the hover back. Fails
  three of five on the old `touch.ts`, passes on the new.
