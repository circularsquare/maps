Worker timers (temporary, in `demand.worker.ts`, dev Vite, agent WASM, 4 solving workers on a busy machine), each

## What changed (figures the same to the bit)

- `Market::corridors_of` (sim/src/demand/intercity/market.rs): the ground and tail curves and the pull's phase-in once a
  pair rather than once a direction (`directed_with`, as `eachway_with` already did for zones); each place's pull as a
  destination (home, abroad, unfaded local) once a place; the income ratio's power once a pair of incomes (120
  incomes, a 14,400 table) rather than once a pair of places. Natively 1.89 s to 1.10-1.22 s (about -38%).
- `IntercityApi::table_summary` (exports.rs) walks the rows with `each_table_row` (selection.rs): a plain loop over the
  trips bitset and the commute list together, handing each row its commute legs, where it used `table_rows`'
  iterator plus a binary search of the commutes a row. Natively 1.52 s to 1.36 s (about -10%).
- Proof of sameness: a temporary fingerprint natively, before and after: corridors `daily` bits 41b0c1c7e5746708,
  23,321,335 pairs, FNV of every trip, bitset word and place sum d2a3a161a22b8370; the book's whole output vector
  26f051df7ff3e85d, rows 11,663,062, key 425766286. Montana and New York rail trips identical in every run below.
- Tried and dropped: skipping the drive and the shares for pairs no plane serves in `corridor_mode` (half the rows):
  same fingerprint, no measurable gain (1.45 s against 1.65, noise), so the cost is not there.
- `tools/perf_bench.mjs`: each run's record has `timeline` (every pack's request, download and open, every solve's
  arrival and sending, ms from the import), and `--saves` takes any name in perfbench/saves (the same hunk as
  T-921's tree commutechunks, so the two merge).
- Tests: `agent_cargo.py test` 746 and 976 passed.

## What is left, and the design call

The corridors and the book are still about 6 s of each worker's 7 s on this load, and they are the same for every save:
they depend on the world's market rows, the drives and the rule (and, for the book, which places' zones on two lands are
open). The fix that removes them is to work them out once rather than per worker per load:

- **Precompute in the pipeline** (recommended): run the same demand WASM in Node at pack build time (the same code, so
  the same bits; native Rust would differ in the last bits of pow and exp) and ship what a load needs: the corridors'
  sums (`daily`, each place's `leaving_by`, the commute list, the pair count) and the book's summary (4,830 x 6
  numbers, about 230 KB, plus its key); the trips of one corridor or one place's row are cheap to work out when a view
  asks (one place's 4,830 pairs). Expected: Montana's load from about 8.6 s to about 3 s (zone open 1.3-2 s, rows 0.9 s,
  solve 0.5 s), New York's by about 6 s of CPU a worker. Costs: a new data file per pack build, the book and rows code
  moved to on-demand, the zones-on-two-lands part of the book worked out at load (small: open places only). About
  2 stages. Players see nothing different; it is a data layout and pipeline change, so it is hers to approve.
- Smaller, no design call: the market rows (13.9 MB JSON parsed in every solving worker, 0.4-1.0 s each) could be parsed
  once and sent as a binary; one worker could make the book and send it to the others (CPU only, not wall time).
- Not tried: starting the corridors before the save's packs arrive. In perf_bench's import the workers already exist,
  so there is no gap to fill; in a player's load from the menu the gap is the save read and network, about 1-2 s.
