Why: 11-28 the orchestrator ran on account 1, hit its spend limit at about 07:00 UTC; it and its agents stopped and nothing noticed for 5.5 hours. Anita: yes to a scheduled watchdog, "maybe hourly".

What: trainworld/tools/ops/orch_watchdog.py, run hourly by the Windows task "trainworld orchestrator watchdog" (pythonw.exe from the venv, so no console window; first run 30 min after registering, then every hour; StartWhenAvailable, runs on battery, 5 min limit).

Rules, as built
- Session id from the Orchestrator line of notes/handoff.md; transcript found by glob in every claude2.project_dirs() folder; its account is the config folder's place in claude2.ACCOUNTS.
- Stalled (a): last main-thread assistant entry is an API error (isApiErrorMessage or synthetic model) whose text matches usage/spend limit or "hit your ... limit". Successor on the other account.
- Stalled (b): transcript and <id>/subagents/*.jsonl all unwritten for 60 minutes and board-live.json lists agents. Successor on the same account.
- Skip (only stamped, not logged elsewhere): target account's newest main transcript (any session) ends in a limit error whose reset time has not passed ("resets <Mon D,> <h[:mm]am|pm> (zone)" parsed; no parseable time: out 5 hours after the error); a start within 3 hours; a successor already started for this session id.
- On a stall: "Stalled: session <id>, name <name>, <reason>, seen <UTC> by the watchdog" goes under the Orchestrator line of handoff.md and at the end of handoff-log.md (once per session id), then next_orchestrator.py trainworld --advisor fable --account N runs with CREATE_NO_WINDOW. A failed start is stamped and retried next hour without repeating the lines.
- Any other run writes only %TEMP%\claude-orchestrator\watchdog.json (last_run stamp, last_start, started_for).
- takeover SKILL step 6 and docs/orchestrator.md "Your own cycling" carry one line each.
