# T-963, T-965, T-966: build and gate speed (from notes/T-962.md)

Built 2026-10-23 in the agent tree `.tw-trees/t963` while China's wave 2 ran from the main tree;
every test on scratch roots through world_run's `TW_RUN_ROOT` redirect, at most 3 cores. Scripts
(throwaways) in the session scratchpad `t963\`: `eq.py` (build rows in a fresh scratch root, timed;
`compare` hashes every file two roots' builds wrote), `cut_bench.py`, `sea_check.py`,
`outline_cmp.py`, `gate_cmp.py`, `mkold.py` (a copy of the pipeline with de90dea's two files, for
timing the old code on a warm disk).

## What changed

- **T-966** `world_run.py`: `--workers` defaults to `--jobs`, so each build step gets one thread
  (`threads = jobs // workers`). Steps outside a row's build (reads, the gate, the join's merges,
  solves and re-gates) now get all `--jobs` threads: a run's regions go one at a time, so its builds
  are idle while they run (before, they got `jobs // workers`, and with workers = jobs that would
  have been 1).
- **T-963 (a)** `osm_units.cut_packs` reads only the pack outlines whose bounding box meets the new
  outline's. The boxes are cached in `data/work/pack_boxes.json` by file name, size and
  `st_mtime_ns`; a file not matching its entry is read and the cache rewritten (`write_atomic`; a
  failed write is skipped, the next build writes it). The candidates are taken in the same glob
  order and unioned the same way, so the cut is the same geometry, bit for bit.
- **The redirect bug**: `osm_units.PACKS` is now computed from the file's own path, not
  `build_city.ROOT` (already moved to the scratch root when osm_units loads), so scratch builds cut
  along the real packs as `Redirect.KEEP` meant.
- **T-963 (b)** `osm_water.sea` reads `data/raw/osmdata/water-polygons-split-4326.fgb`, a
  FlatGeobuf with a spatial index holding the zip's 53,323 polygons, each with its place in the zip
  as `zip_fid`; a box read is sorted by `zip_fid` (stable), so the polygons come in the zip's
  order. `sea_fgb()` makes the file when it is missing or older than the zip (the `sea` lock, one
  process; about 80 s, 3 GB of memory, 1,281 MB on disk); `osm_water.py read` makes it too. To
  remake it, delete it. Made once here on 2026-10-23 (new file; nothing in the live wave reads it).
- **T-965** `pack_gate.browser_run` splits the rows in plan order over `BROWSER_SESSIONS` (3)
  city-browser sessions at once. `city-browser.mjs`: `ZONES_PER_PAGE` 8 (was 20), the solve wait
  `SOLVE_WAIT_S` 180 s (was 900), and a zone whose wait timed out is tried once more in a fresh
  page (the result's `tries`); pack_gate's own retry in a second session is gone. All three are
  environment overrides, used below for the old settings.

## Equality

**Builds** (`eq.py`): build_city on three real rows, each in a fresh scratch root: bin (Binhai,
Tianjin coast, 6 sea polygons), feh (inland Hunan, 3 neighbouring boxes), zhx (Hubei and Henan,
21 neighbouring boxes). Old code (with the redirect fix only) against the new: **all 36 files the
builds wrote are byte-identical** (each row's pack `.json`, `.bin`, `.boundary.geojson`; in
data/work its `.outline.geojson`, `.units.geojson`, `.cells.json`/`.bin`, `.tier0_signals.npz`
and the audits), with the box cache cold (`after`) and warm (`after2`). Two old-code builds
(`before`, `before2`) were identical to each other too. The scratch outlines match the main tree's
(feh same WKB; bin and zhx within 0.00002 and 0.0001 square degrees, neighbours rebuilt since),
so the scratch builds now cut along the real packs.

**cut_packs alone** (`cut_bench.py`, real outlines widened 0.02 degrees, 1,200 outline files):
same WKB as the old code on all three.

**Coastline** (`sea_check.py`): the whole file against the zip, every polygon's WKB at its
`zip_fid` equal to the zip's (0 of 53,323 differ, `zip_fid` a permutation of 0..n-1); and
`osm_water.sea` against the old zip read on 11 boxes (bin with and without osm_units' pad, zhx,
the Pearl River delta, the Fujian coast, Hainan, the Venice lagoon, the Oslofjord, Istanbul, a box
at 0,0, Fiji at the antimeridian): same WKB in the same order on every box.

**Gate** (`gate_cmp.py`): `pack_gate.py --browser --no-rust` on 24 wave 1 Henan zones, the old
settings (one session, 20 a page, 900 s) then the new. The browser's 8 checks the same on all 24
(all pass; all 24 SHIP on the new run's verdicts); riders and riders by purpose identical on 23,
pua 77,313 against 77,310 (work 29,395 against 29,391: other zones open in its page). The retry
path (`SOLVE_WAIT_S=1`, 4 zones): each zone timed out, was tried once more in a fresh page
(`tries: 2`), and parked on the browser check with the timeout as its error.

## Times

build_city, three rows built at once at one thread each, with the wave running (seconds):

| Row | Old, cold disk | Old, warm | New, box cache cold | New, warm |
|---|---|---|---|---|
| feh | 52.3 | 57.8 | 23.1 | 10.5 |
| bin | 70.9 | 75.4 | 33.9 | 22.1 |
| zhx | 89.8 | 95.2 | 49.1 | 58.8 |

About 37-53 s a row saved, as T-962 measured. The parts: cut_packs 28.0-33.5 s old, 0.14-0.37 s
with the cache warm, 7.9 s cold (every outline read once: the first build in a tree after this
lands, and each build that runs beside it before the cache is written); `osm_water.sea` 6.6-23
s a call old (two calls a row), 0.006-7.4 s new: the difference is the zip read, and what is left
is make_valid and the clip (most of the Oslofjord's 7.4 s), the same in both.

**T-966**: zhx alone, new code: 56.6 s at two threads, 46.3 s at one (noise from the wave's load;
no gain from the second thread, as T-962's CPU poll showed: a build step uses about 0.9 cores).
So workers = jobs doubles the builds a run makes at once for the same `--jobs`.

**T-965**: the 24 zones' browser phase took 367 s the old way (15.3 s a zone) and 166 s the new
(6.9 s a zone of wall; a zone 11-32 s in its own session, three sessions on a busy machine). A
timeout now costs at most 2 x 180 s instead of 2 x 900 s.

## Wave 3 settings

`--workers` need not be given now. Overnight (12-15 cores): two runs of `--jobs 6`, 12 builds at
about 0.9 cores each; a region's gate takes about 2.5-3 cores during its browser phase (three
headless Chromes at about 0.7 each, 1.3 GB each, plus the gate's Python) while that run's builds
stand idle, so the machine stays within the budget. Daytime (10): two runs of `--jobs 4`. Run the
small regions beside the big ones, as before. A row's own steps should come to about 55 s (93
before), a 100-zone gate's browser to about 12 minutes (25 before).
