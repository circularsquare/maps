# T-2388: the ghost after a click, how fast it picks up the pointer (2026-11-04, agent lagblue)

Anita: "placing line blueprints is still a little laggy tbh ... the lag is after i click, how fast it
picks up my cursor and updates in the future".

## The answer

On the real New York save the ghost **freezes for about 0.3-0.4 s after every click**, then stutters
once more about half a second after the click. T-1780's 9-13 ms was click to the *first* ghost, and
that is still true (~20 ms): the first ghost shows, then the edit's follow-up blocks both threads in
turn while the pointer keeps moving.

1. **Clock worker, ~20 → ~150 ms**: the state for the new segment is built in one task of 115-180 ms
   (`networkFromState` 80-120 of it). Previews asked during it wait.
2. **Main thread, ~150 → ~330 ms**: taking that state is one task of 150-265 ms, with no frames.
   **110-190 ms of it is the achievements' demand figures** (`game/achievements.ts` `demandFigures`),
   recomputed on every world change, blueprint segments included. They landed 2026-11-03 (5faa828f),
   after T-1780 was measured, so the 2026-10-30 fix measured well and has since regressed.
3. **Main thread, ~400-580 ms**: one 60-90 ms frame rebuilds the zoomed-out copy of the line strokes
   (`renderer.ts` `pickStrokes`, the T-1639 LOD band) for the new network.

A fresh game shows none of this: 35 ms p50 right after a click, the same as steady movement. Steady
movement on New York is fine too (36 ms p50, two frames). The lag scales with the network: it is
the per-edit work on the whole network, never the preview itself (5 ms round trip).

## How it was measured

`artifacts/trainworld/t2388/scripts/follow.mjs` (run from its folder: `node follow.mjs <url>
<new|nyc|japan>`; env `PROFILE=1`, `TRACE=1`, `STOPS=1`). Headless Chrome on my Vite (6191),
`?debug=1&new=1&demandWorkers=1`, track tool, keep placing on, zoom 14 on open ground (New York:
Staten Island). The pointer is driven through CDP every 16 ms and never waits for the page (a hand
keeps moving while the page is busy): 4 s of moving after the run's first click, then a click every
1.6 s, still moving. Per pointer position: the time until the first frame showing a ghost asked from
a move at or after it. Moves that ask no ghost (the pointer on the start) are left out. Main thread
attribution from a CPU profile, the worker's from the trace's samples (`prof.mjs`, `wprof.mjs`,
`tasks.mjs` beside it). Outputs and logs: `artifacts/trainworld/t2388/`.

**How it differs on her machine.** Dev server (unminified), dpr 1, and a loaded machine: 11-14 of
15 cores were claimed during the New York runs and the machine was at 100% for the Japan runs. Her
absolute numbers will be lower, maybe by a third, but the shape (a freeze of a few hundred ms per
click on a big save) is code, not load. The LOD hitch (item 3) depends on her screen: it happens
where `ceil(zoom + log2(dpr)) < 15`, so at zoom 14 on a dpr-1 screen, from zoom 13 down on dpr 2.

One New York click, run 1 and the profiled run (ms after the press):

| when | what | ms |
|---|---|---|
| +15-20 | edit answered early, first ghost asked and drawn | ~15 |
| +20-50 to +120-180 | worker: the follow-up, one task (profiled 116-179) | `networkFromState` 79-122 (`complexPassages` 37-49, `lineBands`+`sameBand` 20-30), `buildState` 8-15, post 5-10 |
| +120-180 to +300-350 | main: the state taken, one task (run 1: 152-187; profiled 164-266) | achievements `demandFigures` 112-191 (`eachCorridor` 49-182), `setNetwork` 46-62 (`fullAttr` ~35, `strokes` ~28, `writeFull` ~17), demand views ~9, panels ~10-13 |
| +330-450 | ghost moves again; first moves 12-25 ms (snap grids carried over, the track hover's pick), a ~30 ms frame | |
| +390-580 | one frame of 57-89 ms: the LOD band for the new strokes | `simplified` 18-33, `fullAttr` 26-36, `strokes` 21-28 |

Steady movement, any save: the move is dispatched with the frame (~11 ms), the preview answers in
~5 ms, after that frame has started, so the ghost shows a frame later: two frames, ~35 ms. That
floor is the design (previews in the worker); only a main-thread stand-in ghost could cut a frame.

**The line tool** (placing a line's stops; no ghost follows the pointer there, the line redraws
after the click): New York, a new line along an existing route, 7 stops added: click to the line
redrawn 509-773 ms. The worker's edit 265-489 ms (stroke buffers 182-330, boarding account 31-60),
then the main thread takes the state and trips, achievements included. Run 3, loaded machine.

**All Japan** (`artifacts/trainworld/t737-japan-trains.save`, 807 lines, 746k track segments): not
settled. In all four runs with this harness every pointer move took 100-145 ms of main thread for
the whole 30 s (frames 1.5 s apart, almost no previews answered): the snap projecting every node
(`tools.ts` `snap` → `screen`, ~50-60 ms, so `nodesNear` gave no grid) plus the track hover's pick
(`pick.ts` `topSeg`, 35-40 ms). A direct probe of the same page (`snapprobe.mjs`) found the grids
answering and a move at 0.3-0.8 ms, a run under way or not, with the same UI settings. So
something in the drawing session keeps the grids from answering, and I did not find what. The
clicks there add a 200-370 ms task each. This belongs with T-1861.

## Fixes, by expected gain against effort and risk

1. **Achievements off the edit path.** `demandFigures` (and `networkFigures`) read `world.value`, so
   every edit reruns the corridor sweep and the busiest-station pass. Key them on what they use:
   the running lines (ids, stops, trains) and the built stations, kept as one signal that changes
   only when those do; and sum the corridors by place once per demand result. **Gain 110-190 ms off
   every click on New York** (more where there are more corridors), and off the line tool's clicks
   and every other edit. Small, low risk (same figures). `app/src/game/achievements.ts`, maybe
   `game/demand.ts` (`eachCorridor`).
2. **The worker's state, carried further across edits.** Complex passages worked out again only for
   complexes whose members or platform lines changed; line bands and their comparison skipped when
   no line's path changed. **Gain 50-70 ms of the 115-180 ms worker freeze.** Small to medium, low
   risk (same buffers; check with `?patch=check`). `app/src/map/network.ts` (`complexPassages`,
   `lineBands` use, `NetCache`), `workers/clock.worker.ts` (`complexOfNodes`).
3. **The LOD band without a long frame.** Build the band in slices as the significance already is
   (`workLod`), drawing the full set or the old band until it is ready. **Removes the 57-89 ms frame
   at ~0.5 s.** Small to medium, low risk. `app/src/map/renderer.ts` (`pickStrokes`, `workLod`),
   `map/strokeLod.ts`.
4. **Hold an early edit's follow-up while the ghost is being asked.** The stand-in ghost already
   shows the segment; build and take the state when the pointer rests ~150-200 ms, the tool changes
   or a non-preview message comes, and fold a next early segment into the same follow-up (several
   stand-ins). **Takes what is left after 1-3 (~60-110 ms worker + ~60-70 ms main a click) off the
   moving pointer**; the cost lands when the pointer rests, where a pause in the trains shows
   instead. Medium to large, medium risk (a junction's money split per edit, undo while held,
   autosave). `workers/clock.worker.ts` (`later`, `EARLY_WAIT_MS`), `workers/clockClient.ts`
   (`ghostFirst`, `earlyShares` as a list), `map/renderer.ts` (`keepPreviewAsPlaced` as a list),
   `map/tools.ts` (`earlyNode`).
5. **`setNetwork`'s 46-62 ms.** `fullAttr` runs over every line segment in `strokes()` and again in
   `writeFull`, whole even when the network came as a patch; patch it by runs as the GPU buffers
   are. ~20-30 ms. Small, low risk. `app/src/map/renderer.ts`.
6. **The first moves after a state** (5-25 ms): `toWorld` makes a new `nodes` map every state, so the
   node grid is built again; keep the map when the node rows are the same. Small.
   `workers/clockClient.ts` (`toWorld`), `map/snapIndex.ts`.
7. **Japan's per-move scan** (above): find why the grids stop answering in a drawing session; on its
   own task, with T-1861.

After 1-3 a New York click should freeze the ghost ~150-200 ms instead of ~400, with no second
stutter; after 4, not at all while the pointer moves. A check worth keeping for the fix task:
`follow.mjs` into `checks/` (it reads `checks/lib.mjs` by an absolute path now).
