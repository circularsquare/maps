# T-4137 Regions drift from a fresh build after an edge delete (agent regionfix, 2026-11-23)

**Summary for Anita**
- Fixed a slip in the bounded edits' regions (T-4113, not yet published). When one edit removed some track and added as much (here: a delete that took away a node and a piece of track and made one new of each), the regions kept the removed ones on their lists.
- A player could not have seen it: no row came out wrong. The rows step walks the model's own records and only asks whether each is in a region, so a removed id on a list does nothing. The worst it did was keep a region split one station too early, until the next edit that changed the counts put it right.
- Fix in `app/src/workers/regions.ts` only. No changelog item.
- Advisor not called (a bug with a clear cause).

## Cause (Asia save, seed 9 step 15 of `t1382-rows.mjs 9 40 asia`)

`Regions.sync` takes a short way after an edit: when the counts of nodes and edges are the same as last time, it looks only at the records the edit touched (`take_touched`). It went through the model's records and handled the touched ones it found there, so a touched record that was **gone** was never met and never dropped. The count check was meant to send removals down the full way, but it holds when an edit removes as many as it adds.

Step 15 (`deleteEdge`, the first edge, after Construct all at step 11) removed node 8 and edge 1 and added node 2078 and edge 0: 8,768 nodes and 8,585 edges before and after. Touched: edges 0, 1, 8; nodes 0, 2, 8, 2078. The regions kept node 8 and edge 1 in leaf 964717453830; a fresh build has neither.

## Could rows be wrong?

No, by reading and by test:
- `StateRows.edges`/`nodes` loop over the model's `edges_info`/`nodes_info` and ask `scope.edges.has(id)`; a stale id in a region's set never makes or keeps a row.
- Every record still in the model was in its right region: the short way handles the touched records that are there exactly as the full way does, and `begin` still marks the gone record's old region dirty (it is in the touched list and still in `at`).
- With the regions compare turned off, seed 9 ran all 40 steps with every read equal to a full read (41 reads), including step 15 and after. The drift was gone at step 16: that edit changed the counts, so the full sync dropped every id the model no longer has.
- What could degrade: a removed **station** would keep its region's station count one high, so the quadtree could stay split where a fresh build merges (the hand-made case shows it: a leaf only in the kept regions). It lasts until an edit changes the counts, and could pile up over a run of edits that each remove as many as they add. That changes only how finely the regions cut, not which rows are right.

## Fix

`Regions.sync`, short way: after the model's records, every touched node or edge the model no longer has is dropped (nodes first, then edges, as the full way). The count check stays as a guard for a touched list that missed something.
