# T-4071: crashes and loads that never finish (stage 1, triage)

Agent crashes, 2026-11-23. Read-only: no code changed. Inbox read with `tools/ops/feedback.py --hours 240` (267 threads;
the full pull hit the inbox's 429 after ~70 threads, the rest fetched by id). v0.4.4 went live 11-19 20:05, v0.4.5 11-20
23:43 (local times, as the inbox prints them). Every crash, page that died, load that never finished, save that would not
open, and "too heavy" report from v0.4.4 on is below; older ones only where they add a device or a cause.
`artifacts/trainworld/crash-reports/` (her Discord screenshots) was empty at the start and at the end.

## How to read the diagnostics

- `lastFailure` with "page open 0-1 min" and the out-of-memory sentence is **T-2545's died-load screen**: the last load
  in this tab never ended (the tab was killed, iOS reloads it), so the next page says "ran out of memory". It is a
  guess from the flag, not a measured allocation failure. v0.4.5 has no `diedLoad` line yet: T-3927 (which game, zones,
  stations, last step) landed 11-21 after the publish, so the next release's reports carry it.
- "clock: oldest unanswered today/blueprintQuote Ns" with no demand line is **the start menu** (no game picked, the clock
  worker not started): normal, seen in many feature reports.
- `simTimeout` ("the train simulation did not respond after 10 minutes") is the loading card's watchdog (T-950) with no
  game state from the clock worker yet (`world` null); `demandTimeout` the same once the game is in.
- demand "w0 silent" = that worker never sent any message; "opened Ns" = its last message was the packs opening.

- All phone ones are Japanese players on iPhones with Tokyo-start games of 1,100-2,100 stations. T-3781 measured those
  saves at 1,254-1,705 MB peak in an emulated tab, against iOS's kill at about 1.4-2 GB. A phone already runs the least
  pool (1 solving worker plus the aux worker), so T-3933's retry with fewer workers cannot help it, and Safari reports no
  memory, so no warning fires before the load (T-3940).
- After an iOS kill the died-load screen has only Try again (`loadCannotFinish(..., game=true)` hides the "Play without

- The desktop Chrome 126 one is a 64-bit browser (resizable ArrayBuffer present, so `addressLimited` was false) on an 8 GB

**What it would take.** No single small fix.
- T-3940, a warning before a big load on Safari (by stations and zones, since Safari reports no memory): about 1.5-2 h.
  It turns a crash loop into a message, no more.
- A lighter load for phones, her call: e.g. on a 1-solving-worker device, only the zones near the view solved at full
  detail and the rest coarse (the fine/coarse split T-889 already has; T-3781's 13-zone save held 10 fine). About 4-8 h
  with measuring; it changes riders away from the view, so it is a demand design choice.
- The memory cuts already filed: T-3939 clock worker (359 MB settled on a 13-zone phone save; 3-5 h), T-3160 solving
  worker (open-ended), and the "rest" (430-800 MB of Blink and compiled code) that nobody has traced.
- T-3373 B for the 551-zone desktop save (24-40 h, 6 stages left, paused for usage).

### 2. A load stuck before the game appears, Mac Safari (3 reports, 2 devices)

| report | version | device | diagnostics |
|---|---|---|---|
| 1795238894-92519822 "loading doesn't finish after 10+ minutes and crashes" | v0.4.5 | Safari 26.6.2 Mac, Japan, signed in, 5 slots | simTimeout. Demand: 4 workers, last message "opened" 682-695 s before the report (about 30 s after the page opened), no solve, status before the failure "ready". Clock at report time (12 min): ready (init 368 ms), trips 68 s ago |
| 1795252967-9fb0c6d0 "loading is too slow" | v0.4.5 | Safari 17.6 Mac, China, signed in, 4 slots | simTimeout. Clock never answered (status loading, blueprintQuote unanswered 794 s); demand w0 and w1 silent, no download in flight |
| 1795256881-082b5e8a "the save won't load" | v0.4.5 | same player, Safari 17.6, an hour later | at 2 min: demand w0, w1 silent; clock status loading |

- **92519822**: the demand workers opened packs ~30 s in. They open what `stationsAhead` names, which the clock worker sends
  after decoding the save and before `openNetwork`. So the clock got that far and then sat over 10 minutes before its
  first state; it finished later (trips 68 s before the report). Between those two points the clock awaits
  `saveNetKey` (a SHA-256) and `openNetwork`: the world water, terrain index (capped at 15 s), every zone's water mask
  (32 at a time; each a header, a second header read for the pack index and a Range read of the .bin, each with a 60 s
  timeout, one retry), the bus zones' street speeds, then masks again for any zone still missing. A connection where these
  reads stall until their timeout gives 6 min per batch of 32 zones and twice over (failed masks are not marked in, so
  `masksForLoaded` asks for them again): 12+ minutes, which fits. Not proven.
- Probe (scratch `rangeprobe.mjs`): Playwright's WebKit (Safari 26.5 user agent) on this machine, against the live data
  (`data.anita.garden/trainworld/2026-11-20/`), 40 Japanese zones' header, header again and 64 KB Range read with
  `no-store`, 32 at a time, beside a whole 6.7 MB `.bin` download: all 40 answered 206 in 7.8 s, no stall. So WebKit's
  Range reads against R2 are not broken in general; the player's connection or something on that Mac is the suspect.
  (The live 2026-11-20 packs are not gzip-packed yet: no `bin_gz` in their headers, so T-2486's path is not live.)
- **qwer (Safari 17.6)**: every worker silent, the clock never "ready": no worker got through its start (module script,
  then the WASM, 2.2 and 2.5 MB from the page's origin, with no timeout in `initWasm`). A worker whose script fails to
  parse should fire `error` (→ "could not start"); none came. Either Safari 17.6 swallows a module worker's load error, or
  the downloads stalled on that connection (China, the page and its files behind Cloudflare). This player has 4-7 saves, so
  the same Mac loaded earlier versions. Not reproducible here (no Safari 17.6).
- What the reports cannot say: the clock worker's own progress. Its diagnosis line has no booted/ready flag for the
  worker's start, no count of ground reads pending (`ground` messages carry it, the line shows only failures), and
  `noteLoad` has no step between "clock worker started" and "network in the page".

**What it would take.**
- Diagnostics, small and clearly right (about 45 min, in a tree): the clock line names whether the worker booted and is
  ready, the ground reads pending, and the load's last step (`noteLoad` at "ready", "stations ahead" and the ground
  waits); the simTimeout reason carries that step. The next report then names the wait.
- With that, the fix (2-4 h guessed): likely a cap on how long a load waits for water masks, as terrain already has
  (`LOAD_TERRAIN_WAIT_MS`, 15 s), with the late ones applied when they land; and a timeout on a worker's start (no
  `booted` or `ready` in, say, 2 minutes: start it again once, then the failure screen naming it).
- Reading 92519822's save on the server (its size and zones) would test the mask theory; allowed but slow, not done.

### 3. Spain: the game unreachable during football matches (1 report)

1795377906-0ad4208c (Safari 27 Mac, es, signed in): could only play over a VPN or a non-Spanish mobile network.
Since early 2025 a Spanish court order lets LaLiga have Spanish ISPs block IP addresses that carry pirate match streams
during matches; Cloudflare's shared addresses are blocked with them, taking down unrelated sites for those hours.

- **The page and the data are both on Cloudflare shared addresses**: `anita.garden` (GitHub Pages behind Cloudflare,
  `Server: cloudflare`) and `data.anita.garden` (R2 custom domain) both resolve to 104.21.86.116 and 172.67.219.6.
  `market.anita.garden` (accounts, feedback) is not (5.161.112.237, Caddy), which is why his report arrived.
  `circularsquare.github.io/trainworld/` redirects to anita.garden, so it is no fallback.
- Options, all her call: (a) nothing: the blocks last match hours, VPN works (0 h); (b) a data mirror off Cloudflare (the
  Hetzner server, or a non-Cloudflare CDN) the page falls back to when data.anita.garden fails to connect, plus a page
  reachable off Cloudflare (anita.garden set DNS-only so GitHub Pages serves it directly, which changes the whole website,
  or a second host): 4-6 h plus an upload at every publish and the server's traffic. Recommend (a) for now.

### 5. WebGL context lost at startup (1 report)

1795359887-21607ace (v0.4.5, Safari 27.0.1 Mac, ja): "forced to quit while making a line". The report is from the next page:
graphics `null`, lost 1, restored 0, `lastFailure` "the page stopped during startup (shader: null)". The context was lost
when the overlay started (Safari after its GPU process went down), `renderer.init` compiled on it, `getShaderParameter`
returned null and `compile` threw, so the page-stopped screen showed instead of the graphics screen (T-3582), with a
reason no player can use. The first crash (during line making) is unknown. About 45 min to fix: an error at startup
while a context is lost goes to the graphics path (wait for the restore, which `renderer.restore()` already handles, else
the restart-the-browser screen). The v0.4.2 twin (1795070377-56c9adc9, `saveBeforeReload` on undefined) is fixed
(`earlyClient` in main.ts).

### Seen only in diagnostics: the focus pool stopped

1795389654-bd164836 (Firefox 160, 179 lines, 5 workers): "last trouble focus pool stopped: focus worker 0: too much
recursion"; 1795180502-98e64801 (v0.4.4, Chrome): "focus worker 0: undefined". The figures stay, so players don't see a
crash; the city in view just loses its fast updates. Firefox's smaller stack points at a deep recursion in the focus
worker on big networks. Not filed; a P3 if it shows again.
