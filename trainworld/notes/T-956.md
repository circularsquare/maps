# T-956 Demand bubbles stay drawn in Safari after turning them off (safaribubbles, 2026-11-19)

Report: skytamer, Safari 26.6.2 on macOS (Apple GPU), v0.4.2, feedback 1795056382-275dc957: "When changing the
demand bubble views from any option to None, the bubbles are retained and seemed to be fixed to the screen?" The
second picture shows None selected, the map panned, and bubbles still over Manila Bay where there is no demand: an old
frame, stretched over the map and never redrawn.

## Cause (inferred from code and the player's picture, not reproduced)

Since T-3497 (42f48652, 2026-11-16, in v0.4.2) an overlay canvas with nothing to draw shrinks its backing store to
0 by 0 (`fitSparse` in map/gl.ts) and keeps its CSS size. With the bubble view at None and no selection, the demand
canvas's `draw()` returns with no clear and no draw call: the 0x0 resize is the only thing meant to remove the
pixels. Safari evidently keeps compositing the WebGL canvas's last presented frame instead, at the canvas's full CSS
size, and the canvas is never touched again while blank, so the frame stays put while the map moves.

The app state is right in WebKit: after None, `showBubbles` false, `blank` true, canvas 0x0 (probe below). So nothing
upstream keeps the bubbles on; it is how the blank canvas is shown.

The older sighting (T-953 item 5, 2026-10-22, Playwright WebKit 2272) predates the shrink. Then the empty path did one
clear-only frame and stopped; T-953 found WebKit presented clear-only frames fine in isolation, so that may have been a
different trigger with the same symptom: the last content frame of a WebGL canvas that is then left alone.

## Fix

`fitSparse` also sets `visibility: hidden` on a canvas while it is blank and clears it when sized on again. A hidden
canvas is not painted or composited in any engine, whatever its stale buffer holds, so this does not depend on how a
browser presents a 0x0 or clear-only WebGL buffer. It covers all six sparse overlays (demand discs, trip routes,
station circles, real stations, gap flash, faces; only the demand one is WebGL, the rest 2D). `visibility` keeps the
layout, and nothing reads these canvases' own size anyway (gapFlash and stationCircles read the map's canvas). Every
caller draws only after `fitSparse(..., true)`, so a canvas is never drawn while hidden.

## Checks

Probe: `scratchpad/safaribubbles/game.mjs <webkit|chrome> <tag>`: a new game, New York at z12, Total by the real
button, then None, then a 300x150 px pan, then Total again; logs the demand canvas's state and takes screenshots.

- Chrome, after the fix: bubbles draw (54,170 discs), None clears them, the pan shows no bubbles, Total draws them
  again. Canvas `visibility` hidden while blank, "" while drawn.
  Screenshots `artifacts/trainworld/t956_chrome_after_{1on,2none,3moved,4again}.png`.
- WebKit (Playwright 1.61.1, WebKit 26.5, build 2311), before and after: state as in Chrome; after the fix the canvas
  is hidden while blank and shown again on Total.
- `npm run check`: clean.

## Why there is no WebKit screenshot pair

Headless Playwright WebKit on Windows puts no WebGL canvas into `page.screenshot` at all: the basemap is missing too,
and a bare page with one 2D and one WebGL canvas shows only the 2D one (readPixels on the WebGL one returns the drawn
colour). Same with build 2272, the one T-953 used. A headed window would open on Anita's screen, and the Windows build
is not Safari's Mac compositor anyway. So the fix is checked by state in WebKit and by pixels in Chrome; a real Safari
is the confirmation still missing.

Playwright's WebKit 2311 is now installed (`%LOCALAPPDATA%\ms-playwright\webkit-2311`, about 60 MB) for the cached
Playwright 1.61.1.

No standing check: the thing that would catch a regression is a Safari screenshot, which we cannot take here.
