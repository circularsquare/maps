# T-2853 Feedback threads: design for Anita to decide

Design only. Nothing is built. Read on 2026-11-09: `feedback.go`, `FeedbackPanel.tsx`, `account.ts`, the API doc, the server's CLAUDE.md, `privacy.html`, `tools/feedback.py`, and the live store (sizes, ids and field counts only).

## The design in short

Each piece of feedback becomes a private thread on shonei-server: the player's message, Anita's replies, and any answers from the player. The panel keeps its form and gains a tag choice and, below it, the player's earlier feedback. Without an account the thread belongs to a random key in the browser. Signed in, it belongs to the account and shows on every device. Anita works from a page at `localhost:8800/twfeedback/`, unlocked by a long secret key. She still gets the email.

Built by hand on this server. Canny and Fider are public voting boards with sign-up at heart (Canny's private boards are on a paid plan). A helpdesk or Chatwoot is a second always-on service for about one report a day.

## 1. Identity

**Without an account: a random key in the browser.** 32 random bytes, in localStorage as `trainworld.feedback-key.v1`, made the first time someone sends feedback signed out. Players who never send feedback have no key. It goes in an `X-Feedback-Key` header, never in a URL, so it stays out of logs. The server stores only its SHA-256, so a stolen disk or backup can't be used to act as a player.

It is a new key on purpose. `trainworld.device.v1` is promised to be sent only while signed in, and the play-count id is promised to be never linked to anything. The key must not ride on `/trainworld/ping` for the same reason.

- Can: list that browser's threads, read replies, write back, delete them.
- Can't: reach another device or browser. Survive clearing site data. Exist in a private window after it closes. If localStorage is blocked, sending still works and no list shows.
- Safari deletes localStorage after 7 days of Safari use with no interaction on the site. A regular player is fine; someone who stops for a few weeks may lose the key.
- A lost key can't be recovered, and there is no key export: signing in is the answer for devices. The thread stays on the server and Anita still sees it.

**Signed in: the account owns it.** The panel sends the token as now, and the list comes from the account id, so every device sees the same threads and the same read state. An expired token counts as signed out, as it does today.

**A key holder who signs in:** whenever the browser has both a key and a valid session, it calls `POST /trainworld/feedback/claim`. Every thread on that key moves to the account, the server drops the hash from those threads, and the browser forgets the key after a 200. No prompt. Signing out then shows nothing, which is right on a shared computer. A later signed-out message makes a fresh key. One accepted edge: two people on one browser, and the second signs in: the first one's threads go to the second account.

## 2. Storage, limits, deletion

**Store.** One file per thread, `feedback/threads/<id>.json`, inside the existing feedback folder, so the deploy already skips it and the 512 MB budget already measures it. Written temp + rename, as noritetsu saves are. A file that can't be parsed is logged, shown as broken in the inbox and never overwritten. On start the server reads them into a small memory index (owner, tag, open or closed, times, unread flags). `reports.jsonl` can't do this: it is append-only and deleting must really remove the words.

A thread holds: `id, kind (tag), status, created, updated, keyHash or account, accountName, name, contact, ip, context, shot, playerReadAt, anitaReadAt, messages [{at, from: player|anita, text}]`.

**Size.** Today: 9 reports, 8 of them trainworld (28 Oct to 8 Nov), 4 KB of text and one 5 KB screenshot; 32 GB free on the disk. Even 20 threads a day at about 1 KB is 7 MB a year. Budget stays 512 MB, shared with shonei.

**Abuse limits.**
- Per IP: the existing 10 an hour, burst 5, now shared by new feedback and replies. This is the real limit, because anyone can make new keys.
- Reading: 60 an hour per IP, burst 20.
- Per message 4,000 characters, as now. Per thread 20 player messages. Per owner 100 threads.
- Context on this route capped at 16 KB in all (today's cap allows about 390 KB; the game sends under 2 KB). Worst case about 32 KB a thread, so 8 MB per IP per day.
- Past the 512 MB budget or 20,000 threads, new trainworld feedback is refused with a message and one alert goes out by `notifyAlert`. Today's rule of accepting text forever past the budget has no ceiling. Shonei keeps that rule.
- Email keeps its limiter (10 back to back, then 30 an hour), so a flood stays in the inbox and out of the mail quota.
- `X-Feedback-Key` gets added to the allowed headers of `noriCORS`, and each new route to `twRoutes` so the tests cover it.

**Deletion.** A Delete button on each thread removes the file and any screenshot at once. Deleting an account deletes its threads (from `twServer.deleteAccount`, like its playtime; lock order nori before feedback). Nothing expires by itself, as the privacy page says now. Backups hold a deleted thread for up to 7 days. The email already sent stays in Anita's mailbox, and the privacy page has to say so.

**Privacy page, old to new.**

Feedback section, keep the paragraph and change two things: after "the message you type," add "the tag if you pick one,", and after "your browser's name and version," add "the language the game is set to,". Then add:

> So you can see your earlier feedback and Anita's replies, the game makes a random key the first time you send feedback without an account and keeps it in this browser's storage. The server keeps only a hash of it. The key is not connected to your play counts or your games. Anyone using this browser can read that feedback. If you clear your browser's site data the key is gone and you can't see that feedback again, but it stays on the server. If you sign in, feedback sent with the key moves to your account and the key is removed.

What other people can see, add: "Your feedback is private. Only you and Anita can see it."

How long, old: "Feedback reports stay until Anita deletes them; write to her if you want yours removed."
New: "Feedback stays until you delete it in the feedback form or Anita deletes it. If you can't reach it any more, write to her. The email Anita got about it stays in her mailbox unless you ask her to delete that too."

Deleting your data, add to the account sentence: "That removes your login details, email address, games, scores, feedback and leaderboard entries..."

## 3. What the player sees

Same modal, same name, email and message fields. New, in order:

- **Tag choice**, under the message: three small buttons, none picked, click again to clear. It fills the `kind` field the server already stores. No tag stays `feedback`.
- **Earlier feedback**, below the send button, newest first, only when there is any. Each row: first line of the message, date, a dot if unread. Click and it opens in place: the messages, a box to write back, Delete.
- **Closed is private to Anita.** Players see no status. If they write back, it reopens.
- **The reply signal:** a dot on the Submit feedback button and on the Settings tab, plus one passing note per new reply. The game checks on load and every 30 minutes, only if it has a key or a session. That call answers from memory.
- The game language goes in `context` so Anita sees what to answer in.

## 4. What Anita sees

**Where.** One static page, `trainworld/tools/feedback/index.html`, registered as `twfeedback` next to `twstats`: `localhost:8800/twfeedback/`. Dark and plain like twstats. The page holds no data and no secret.

**How it is protected.** The page is only a viewer. The data comes from new routes `/trainworld/inbox/...` on the live server, which require `Authorization: Bearer <key>`:
- The key is 32 random bytes in `/opt/shonei/shonei.env` as `SHONEI_FEEDBACK_ADMIN_KEY`, compared in constant time. If the variable is unset the routes answer 404.
- She pastes it into the page once; it stays in that browser's localStorage. If lost, it can be read from the env file by ssh.
- It travels only over HTTPS to `market.anita.garden`. `noriCORS` already admits `localhost:8800`.
- Its reach is feedback only. Her game account stays an ordinary account. I would not use "her account id is the admin": every session of that account on anita.garden would become an inbox credential.
- Stored player text is hostile input: the page sets it as text, never as HTML. Screenshots are served as `image/png` with `nosniff`, fetched with the key and shown from a blob.
- What's left: every map on 8800 shares that browser storage, and they load scripts from CDNs. A stricter option is a second localhost-only port on the server reached over an ssh tunnel, with no public route at all. It costs a tunnel to keep running every time she opens the page, so I wouldn't.

**The page.** List sorted by latest activity: unread dot, tag, who (account name, or typed name, or anon), first line, age. Filters: unread, open or closed, each tag. Open a thread: messages, name and email (with a mailto link), version, browser, memory, language, last failure, screenshot. Actions: Reply, Close or Reopen, Delete.

**Telling her.** Email as now, the full text, with one added line: the link to the thread in the inbox. A player's follow-up mails too, under the same limit. Her reply mails nobody in the first version.

## 5. Stages

**Stage 1, worth shipping as one piece.** Thread store, key and claim, delete, tags, the panel list with replies and the signal, player write-back, inbox page, privacy page, import of old feedback. About 450 lines of Go and 200 of tests, 200 lines of game code plus 19 strings in 5 languages, and a 300-line page: 2 or 3 agent tasks. Server first behind a new `/noritetsu/config` flag, then the game. Deploy needs her say-so and the env line.

**Stage 2, once it is in use, small.** An "also email this reply" tick for players who left an address (without it, an anonymous player who never comes back never sees the reply; `contact` is unverified, so only ever by her hand). Change a tag from the inbox. A junk button that blocks a key hash or IP.

**Later or never.** Shonei's reports in the inbox, read-only. A code to move a key between devices (signing in covers it).

**Feedback already stored.** On first start the new server imports the 8 trainworld reports as threads, using the report id as the thread id, so a crash can't double them. Their tag is plain feedback. The 5 reports that have an account get that account as owner and appear in those players' lists; the rest have no owner, so only Anita sees them, and she can still email the ones with an address. Then those lines are taken out of `reports.jsonl` by temp + rename, so a player's delete really deletes. The one shonei line stays. Shonei's route, panel and `tools/feedback.py` work as they do now, and `reports.jsonl` remains shonei's.

## Decisions only Anita can make

1. Can players write back in stage 1? I'd say yes: otherwise each answer becomes a new thread and the conversation scatters. It is a small part of the work.
2. Inbox only on her PC, or from her phone too? On 8800 it is PC only. The same page could also sit on anita.garden, since the key is what protects it.
3. Keep the full text in the notification email (as now), or send only "new feedback" with a link? I'd keep it. Text-free mail would make a player's delete complete and keep words out of Resend, but she'd open the inbox for everything.
4. Does "language" mean translation problems? The label stays "Language" in her word; if she means something else the label changes.
5. Old reports with an account appear in those players' lists. I'd allow it, since they wrote them; she can say no and leave them all ownerless.
