# T-3687 Normal games marked as sandbox

Anita, 2026-11-18: "a while ago people were reporting their games getting marked as sandbox when they were normal
games". Her old note: ylik's save shared to Community shows as sandbox though it is a normal game.

No report of it is left in the feedback inbox (all 202 threads read in full, 2026-11-18; none mentions sandbox,
leaderboards or a tag), so ylik's save could not be looked at. What follows is from the code and from reproductions.

## How "sandbox" reaches a normal game: every path

Community's Sandbox tag and the leaderboards both read one thing: the server's latch on the game id
(`twGame.Sandbox` in the account's scores file). A share copies it at share time (trainworld_community.go
`in.sandbox = g.Sandbox`); a latched game's figures are refused 403 for good. The game itself never turns sandbox
from any of these: its mode lives in the save header and nothing below writes it.

| Path | Verdict |
|---|---|
| **Score send during a load** (account.ts `sendScores`) | **Real cause, fixed.** See below. |
| A copy of a Community share, played on and shared again | By design (T-3115, DECISIONS 2026-11-10): it plays as a normal game, never ranks, and its share is tagged Sandbox. To its player that reads as a normal game marked sandbox. Fits ylik as well as the race does. The label is Anita's call (For Anita). |
| A 403 on `PUT /trainworld/score/<id>` remembered as a latch (v0.4.1 and now) | Harmless to a normal game. The live server's only 403s on that route are the real latches (sandbox, and modded since T-3707). Expired auth is 401, a bad id 404, a bad body 400, the 20-games cap evicts the oldest (never refuses), a store full 507, broken 503, unpublished 426 (T-3707), rate limit 429; there is no CSRF check (bearer token). A Cloudflare 403 would be the only stray one. The remembered flag is read only for unranked games and by `dropDeleted` (a deleted game's figures stay on the account); the normal branch ignores it. Now cleared by the next accepted send. |
| Save header `mode` | No path sets sandbox on a normal game. A missing `mode` loads as normal (clock.worker `h.mode === "sandbox" ? ...`), a new game defaults to normal (NewGame sheet, `newGameHeader`, the start menu's `?mode=` takes only the exact "sandbox"). Make a copy, export and import, backups, cloud sync, version restore and the shared copy all carry the header as it is (sharedSave checks `mode` is normal or sandbox). |
| Settings' Switch to sandbox, then a restore from before it | Not a wrong latch: a restored version goes into a new slot, which gets its own game id. |
| Modded mark (T-3707) | Latches by design. Its host test can misfire only where the game runs off anita.garden (e.g. a translate proxy, `anita.garden.` with a trailing dot); those pages have no account, so the mark can reach the boards only through an exported file. Not fixed. |
| Game id reuse through the original `autosave` slot | Possible, not reproduced. A new game started in the fixed `autosave` slot while the browser's score entry of a deleted game there is still kept (`dropDeleted` skips the active slot) would take that game's id and latch. Only the load fallback starts games in `autosave` now. Not fixed; a guard would compare the slot's `origin` with one kept in the entry. |

## The race (fixed)

A load (Open a file, a backup's restore, Community's Open, which views a copy of a share) reloads the page, which
first lists the slot it came from as playing (`msg.slot = pending.from`), then loads the new game. The worker sends
the new game's money state at the end of `loadGame` (`restart` -> `sendState`), and the slot list moves on only after
the slot is written (`autosave`, then `publishSlots`, which reads every save in the browser). In between, the page
holds the new game's money (a sandbox, a copy, or modded) and the old game's slot. `sendScores` runs every 15 s and
when the tab is hidden; landing in that gap it sent `{"mode": "sandbox"}` under the old game's id.

Measured on a dev server (11 small saves in the browser):

- Open a file, the real New York network made a sandbox: 2243 ms with the old slot listed and the sandbox money held.
- Community's Open of a copy of the same: 2835 ms. Of an empty normal game's copy: about 550 ms.
- Opening an empty game from a file: the slot list never moved on (still the old slot, writable, 30 s later):
  `autosave` keeps nothing for an empty new game, so `intoNewSlot` never published.

A latch needs a score send inside the gap: the 15 s tick (its phase counts from the account's start on that page, so
whether it lands in the gap depends on how long the load takes) or a tab hidden during the load, which sends at once.
How often that happened across players was not measured; each Community Open or file opened from a normal game
with figures is a fresh chance. Modded saves (T-3707) widen it on paper: the modded latch has no "has sent figures"
condition, so it would latch even a game that never sent any (from the code; not run).

End to end against a local shonei-server (dev sign-in, figures for game A on file, the real `sendScores` called in the
gap; scratch `e2e.js`):

- Before: Open a file of a sandbox: PUT `jswzcdirwbmd` `{"mode":"sandbox"}` 200; A's next figures 403 "this game has
  been a sandbox, so it is not listed". Open a share's copy (normal mode, copy mark): PUT `dprkmv5i7ahi`
  `{"mode":"sandbox"}` 200; then 403. v0.4.1 (3ce746f9) has the same load order (`msg.slot = pending.from`,
  `sendState` at the end of `restart`, `publishSlots` after `autosave`) and the same `sendScores`.
- After: no PUT from either; A's next figures 200 `{"listed":true}`.
- After, a normal game still sends: a 3 km line built in a fresh signed-in game, trips calculated, kept in a slot,
  then the real `sendScores`: PUT `{"mode":"normal", ..., "points":6457470}` 200 (scratch `send.js`).

**Fix.** The money state names the slot its game is played in (`MoneyState.slot`, the worker's
`loadingInto ?? activeSlot`), and `sendScores` and the share's latch go only when it is the slot the page lists as
playing. Make a copy (and so a viewed copy's Save) sends the money again at once with its new slot. `intoNewSlot`
publishes the slot list when `autosave` kept nothing. A send the server lists clears a remembered `sandbox` flag.
Checked after: Make a copy, a new game from the New game sheet and its first save, opening a saved game, Open a
file, a backup's restore, and Save of a viewed copy all end with the money and the list on the same stored slot
(scratch `after.js`, `after2.js`); the load fallback sends its state after setting the new slot. An empty file opened
now moves the list to its slot (`empty.js`).

## Games already latched

The latch can't be told apart from a real one by the page, and the page never asks for an unlatch (any page could,
so the latch would mean nothing; DECISIONS 2026-11-18). The account server's inbox can (shonei-server c960adc,
`trainworld_latch.go`, not deployed):

- `GET /trainworld/inbox/latched` lists every sandbox latch (modded left out) with what the game's current save on
  the account says (mode, copy mark, modded) and its share; `wrong` marks a normal game that is not a copy and not
  modded. A game not on the account shows no mode: nothing says either way.
- `POST /trainworld/inbox/latched {"account", "game"}` takes one off: the game's next send lists it again (its
  figures were dropped by the latch, so the first send after puts them back) and its share loses the Sandbox tag; its
  points come back with its next share. A modded latch is refused (409).
- `venv\Scripts\python.exe trainworld/tools/ops/latched.py` lists (`--wrong` only the normal ones), `--unlatch <account>
  <game>` takes one off. Tried against the local server: list, unlatch, then figures listed.
- shonei-server `go test .` passes (new: TestTwLatchedInboxListsAndUnlatches; the route is in the rate-limit and CORS
  lists).

The fix only stops new latches once the next version is published; an open v0.4.1 tab can still latch until then,
so unlatching is best done after that publish (a game unlatched earlier can be latched again by an old tab).
`wrong` reads the account's current save: a game switched to sandbox whose upload never reached the account (tab
closed within the upload gap) also shows as `wrong`, so look before unlatching.

Left open for the orchestrator to file: the copy's Sandbox label (For Anita), and the `autosave` slot reuse guard.
