## How shared state works

Everything the parts share is a top-level `let` in one module. ES module imports are live bindings, so every other
module reads such a variable as an ordinary import, unchanged. Writing across modules is the one thing an import
cannot do, so each variable written outside its home module has an exported `putX(v)` next to it (`putFares`,
`putLedger`, `putClk` ...), and the writing sites call it (`fares = x` became `putFares(x)`, `n++` became
`putN(n + 1)`, `a ??= b` became `putA(a ?? (b))`). A variable written in only one other module was moved into that
module instead of getting a `put` (`firstBuiltAt`, `snapTimer`, `moneyLag`, `regions`, `game` and others). Parts never
import from `clock.worker.ts` (the entry), only from `clockState.ts` and from each other; the cycles between parts are
harmless because every cross-part reference at module load is a function declaration or an arrow, and the one eager
`const` that needs another's (`rowEnv`'s `PERIOD_HOURS`) sits in the same module.

Changes beyond moving lines (all forced by the move): added `export` on declarations used from another file; the
`put` functions; assignment sites rewritten as above (three chained `a = b = x` statements became two statements,
and four value-position uses got a comma expression); import lines pruned per file; a one-line header comment in each
new file. No other line was edited. A scripted comparison of the old file's lines against the new files found only
those differences.
