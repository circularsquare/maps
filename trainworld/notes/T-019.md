# T-019 notes: zone gravity in the city pack

Opening a city used to solve the 2 km zone gravity in the browser: 2.9-3.2 s native, 8.0-8.3 s in
WASM on a first call (3.4 s warm). The pipeline now solves it once and ships the result; the game
rebuilds zone trips from it in about 2 ms. Format: notes/T-004.md (format 1).

## What ships

Per cell a zone id (u32); per zone its grid column and row (u16 each) and the two balancing
factors as f32, `zone_row` = A_I·O_I and `zone_col` = B_J·D_J; a `gravity` header block with the
zone size, grid origin and size, the decay (`exp`, 9 km), the intrazonal distance, and the solve's
iterations, error, mean trip and total. Zone trips are `row[I] · col[J] · exp(-d_IJ / 9 km)`.

Everything else the kernel needs is rebuilt on load in O(cells) or less: zone population and jobs
(sums over cells) and the decay table by grid offset (2w-1 by 2h-1 = 79k entries for New York).
`mean_trip_km` and `trips` are shipped because recomputing them is a full 33M-pair pass.

f32 factors: the round trip changes them by under 1e-7 relative (checked by `pack_gravity`
before writing), far inside the solve's own 1e-4.

## One implementation of the gravity

The pipeline runs the sim crate's own `kernel::gravity` through a native bin,
`sim/src/bin/pack_gravity.rs` (behind the `demand` feature), instead of a numpy copy:

- The game rebuilds trips with the same `decay_table` function the solve used, so the decay, the
  zone-centre distances and the intrazonal 0.52 x side cannot drift between two codebases. A
  numpy re-implementation would have to match the float32 grid assignment and the table exactly,
  and every later change to the gravity (T-006's fitted decay) would have to be made twice.
- Native Rust takes 4.6 s for New York at a 1e-4 tolerance (60 Furness iterations), single
  thread and a few MB. Numpy would want a dense 5,710² float64 matrix (260 MB, and 4x that for a
  city twice the area) or the same grid-offset loop written again.
- Cost: building a pack now needs Rust installed (it already is for the app). `build_city.py`
  finds cargo in `~/.cargo/bin`, builds into `data/work/target` (never `sim/target`, so it does not
  block or wait on the app's wasm builds) with `CARGO_BUILD_JOBS=2`.

Flow: `build_city.py` writes the cell arrays as a format-1 pack without gravity to
`data/work/<city>.cells.json/.bin`, then runs
`cargo run --release --features demand --bin pack_gravity -- <cells.json> data/packs/<city>.json`,
which solves, adds the zone arrays and the `gravity` block (keeping the rest of the header as
Python wrote it), parses its own output back, and replaces the pack via `.part` files.

`read_pack.py` stays independent of both writers: it re-derives every cell's zone from its
coordinates and recomputes all 33M zone-pair trips in numpy (400-row chunks) from the shipped
factors. New York: worst row sum 6.9e-8 off the workers, worst column sum 9.1e-5 off the jobs (the
Furness stop is on rows after a column update, so columns carry the residual), trips 10,176,424,
mean 15.35 km.

## Loading

`pack::parse` reads format 1 only (format 0 support dropped; nothing else read it). Arrays carry
`"per": "cell"` or `"zone"`; unknown names or `per` values are skipped. `kernel::city_gravity`
uses the pack's gravity when its `zone_m` and `decay_km` match the run's parameters and solves it
otherwise (the bench's zone-size sweep, a pack without gravity, or a future decay change before
the pack is rebuilt). `demand_bench --solve` (wasm opt `solve`) forces the solve for comparison.

## Numbers (New York, 2026-10-08)

| | before | after |
|---|---|---|
| city open, native | 2,900-3,200 ms (Furness, 1e-3, 43 iterations) | parse 1-4 ms + rebuild ~1 ms |
| city open, WASM (Node 22.20), first call | 8,000-8,330 ms + parse 3-5 ms | parse 4-5 ms + rebuild 1.9 ms |
| city open, WASM, warm | 3,370 ms | parse 1 ms + rebuild 1.0-1.7 ms |
| pack | 1.80 MB raw, 0.87 MB gzipped | 2.17 MB raw, 0.97 MB gzipped (zone id 0.30 MB, zone arrays 0.07 MB) |
| pipeline | 12-15 s | +4.6 s solve (first run also compiles the bin, ~25 s) |

The shipped solve is tighter than the old in-browser one (1e-4 instead of 1e-3); mean trip 15.35 km
either way.

## Left over

- The zone id is u32; u16 would save 0.15 MB raw for any city under 65,536 zones (all of them,
  realistically). Readers accept any integer dtype, so this can change without a format bump.
- `with_gravity` leaves the old zone arrays' bytes as dead space if run on a pack that already has
  them; the pipeline always starts from the cells-only file, so it never happens in practice.
