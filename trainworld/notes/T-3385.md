## Candidate fix and deterministic reproduction

`RelatedStops` measures rows in a layout effect, then updates geometry state when the measurements
change. `guessRow` hides a clicked stop with `display:none` before its edit lands. A hidden row's
offsetTop is zero, but its list's offsetTop includes the diagram's padding. Subtracting them gives
a negative row position. The next render adds padding to fit that position; the hidden row then
measures still further above the list. This feedback can keep rendering and growing the layout,
starving page messages and timers while the clock worker keeps running.

`checks/t3385-hidden-row.mjs` mounts the real RelatedStops/layout with isolated world/query inputs.
Before the fix, hiding its first row caused 41 renders and padding of 33,554,400px in one second.
After the fix, the same case settles in two renders at 0px; hiding/restoring first, middle and last
rows all settle. The fix retains a hidden row's last measured centre (or the existing default row
position before the first measurement), instead of reading its nonexistent box.

Typecheck and existing `t1168-layout.mjs` pass, including real NYC diagrams, flipped and narrow views.
This proves and fixes a concrete layout feedback bug consistent with the user's captured main-thread
stall. Confirmation on the user's actual browser/save is still needed before declaring the report
resolved. No player-facing strings changed for the fix. Diagnostics remain enabled for that check.

The seven captured edits were replayed with optimistic row hiding on the saved 186-line Asia network.
Both the fixed and original dev servers completed that full replay on the agent's browser. Thus the
full-user reproduction remains environment/timing-dependent; the isolated hidden-row regression is
the failing-before/passing-after test. Larger saves can leave guessed rows hidden longer while edits
wait in the worker queue, making this feedback window more likely.

Additional opt-in diagnostics retain `activePhases` for the map overlay, map-frame callbacks, related
diagram layout/measurement and row fitting. They are persisted by the recorder while the page is
blocked; completed phases are removed and only phases over 100ms enter the bounded event log.
Normal drawing no longer needs to flood the event log with checkpoints to identify a stuck phase.

## Use

Open the diagnostic-enabled build with `?diagnostics=1` (or `&diagnostics=1` if the address already has
a query). A small bottom-right panel confirms **Diagnostics recording locally**. The choice persists
in this browser on this origin, so it stays on after reload. Load the large save and edit stops normally.
After a freeze, close the stuck tab if necessary, reopen the same address in the same browser profile,
and click **Download diagnostics**. Keep that JSON and the save used. The download contains the current
session and the previous three retained sessions. Download promptly, before repeated reloads rotate
the interesting session out. **Stop recording** disables it on subsequent loads too; it leaves the
download available on the current page. `?diagnostics=0` also disables recording.

No diagnostics are uploaded. The log contains numeric edit arguments, the affected line's stop IDs
(up to 256), network counts/version, browser/build, page heap usage where available, errors and timing
checkpoints. It does not include the save or account details. Error messages/stacks are local diagnostic
data too; a player chooses whether to share the downloaded file.

## How to interpret

`game/freezeTrace.ts` starts a dedicated recorder worker only when enabled. The clock worker talks to
it through a MessageChannel, bypassing the page. Both page and clock send one heartbeat a second.
The recorder notes visible-tab gaps over five seconds, and recovery if the heartbeat resumes.
It batches IndexedDB writes once a second, retaining 400 events per session and four sessions total.
At most the newest second is uncommitted on abrupt process death. Browser/OS shutdown or storage
failure can still lose evidence. Storage failure is shown on the panel; its in-memory download remains.
Background throttling, sleep and extreme CPU contention can cause gaps too: a gap is evidence, not
a crash verdict. The log's last page health includes visibility and page JS heap usage, not total
browser RAM. Clock checkpoints and its last heartbeat also carry the track WASM memory size;
demand worker heaps are not measured.

- `edit-click` then `clock-post`: the page got as far as sending the action (includes sequence ID).
- Clock `handle-start` / `apply-start` / `apply-end`: queue entry and the synchronous track-model edit.
- `build-state-start` / `build-state-end`: preparing the resulting world snapshot.
- Clock `edited` then page `clock-answer`: worker answered and page received it.
- Page `receive-start` / `receive-end`: taking state/trip messages on the page.
- A clock heartbeat gap while page heartbeats continue points toward the simulation thread; the
  reverse points toward the page. Both can stall under system pressure.
