# T-4063 trip explorer fails just after a change

Cause: openPacks reopens a zone at another level once the solve ends (reopenLater); dropCity/forget frees the old
population and removes it from every kept cluster's pops. A question about that network then took a = cities.get(city),
the new population, which the cluster's views never held, and viewOf(cl, a).nodeGlobal threw.

Fix (demand.worker.ts, query): a is undefined when the cluster has no view on it (cl && !cl.views.has(own)), so every
query kind answers as for a zone not open (the existing not-ready answer), whatever reads viewOf. The old population
is freed, so answering from its own data is not possible.

Checked: typecheck only. No game run (time: Windows update). No strings, no changelog item.

## Follow-up (coordinator's two questions)

1. Not-ready answer: with a undefined the worker answers the trip query with mask 0 and answers null; the client's tripAt
   returns null. tripView.ts then shows "Calculating trips" (cityInspector.calculating) / "Working out this trip" while a result is
   updating, and re-asks with the next result. On a final it re-asked once after 3 s, then showed "This trip could not be worked
   out." Changed to 3 retries (RETRIES in tripView.ts) so a reopen that takes longer than one wait is still covered. No new strings.
2. Game run (new game NYC, port 6122, 2 cores): two edits, trip selected before and after; the explorer answered normally both
   times ("Walking there is quicker than transit"), no "demand query" / nodeGlobal errors in the log. The stale-version race itself
   (a reopen at another level after a final) was not forced; the fix rests on the code reading above.
