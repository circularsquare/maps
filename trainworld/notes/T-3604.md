# T-3604: restarted demand workers sometimes never reopen (agent restarts, 2026-11-18)

Outcome: replacements' downloads now share 6 places (`reopenSlot`, REOPEN_FETCHES in demandClient.ts); needOf's rest factor 1.38 to 1.12.

Setup: tree `.tw-trees/restarts`, Vite 6189, headless Chrome pinned to 4 claimed cores (3 solving workers), all-China save `t1156-all-china.save`, weekday. Script `restarts.mjs` in the agent's scratchpad: load, then `debugRestart(0,1,2,3)` repeatedly, each waiting for the pool's final.

## Cause
`reopen` ran `Promise.all` over every item the pool holds (541 on all-China, three downloads each: json, bin, json again), in each of the 4 replacement workers at once: about 6,500 fetches at once. Chrome refuses most with ERR_INSUFFICIENT_RESOURCES; `patientFetch`/`download` retry, so normally it reopens, and the once-in-seven stuck pool is a retry run that ran out.

## Before (reproduced the cause, not the stop)
Restarts 0-3 on all-China: 82, 3,994, 4,336, 4,182 ERR_INSUFFICIENT per restart; each still reopened (158, 168, 213, 171 s). The stuck pool did not recur in 4 restarts (stopped after 4).

## After
20 restarts in a row: all reopened, 0 ERR_INSUFFICIENT in any, 107-206 s each (median about 130 s; the last four 177-206 s, probably the machine, not the change).
Load (first final after import): all-China 190 s before, 156 s and 202 s after; the load path is untouched (only `reopen` changed), so that is run-to-run noise. New York real save loads in 11.5 s (not measured before; same path).

## needOf
Fresh worker, WASM / heap at rest / last solve peak, MB: all-China after load 1236/1067/1175; after restart 1203-1268/1048-1075/1148-1174; New York 355/200/282.
need = max(rest x f0, peak x 1.07) + 64. With f0 = 1.12 all-China at rest gives 1238 (fresh 1203-1268); 1.38 gave 1512. New York is set by its peak term (366 vs 355), so unchanged. The peak term still gives 1320 right after the load.
Does the restart fire on all-China now? Rule: WASM at least 15% and 384 MB above need. A worker at rest holds 1236-1268 against a need of 1215-1320, so no: there is nothing to give back (T-3492: a restart returns about 100 MB). It fires when a worker's WASM passes about 1.6 GB (was 1.8 GB). Not fired in a test, since no all-China worker grows that far on its own.
Side effect: capPool and growTo use needOf, so a pool sized from the rest term (peak cleared by a close) sees about 190 MB less per worker on all-China.
