# T-1482 Japan's solve sent twice; T-1544 "Invalid value used as weak map key"

Tree t1482. Both found and fixed.

## T-1482: a worker out of memory

**What happened.** On Japan's save (t737-japan-trains.save, picked from the start menu in a fresh
profile, 3 solving workers), worker 0 ran out of its 4 GB of WASM about 350 s in, in the market's
free-flow pass: "RuntimeError: unreachable (out of memory: 1464139776 bytes could not be
allocated), 3398 MB of WASM memory". T-1174 replaced it: the new worker downloaded every pack
again (the "new download" T-1479 saw) and opened them, and `reopened` sent the network again under
a new version. The workers drop a solve as soon as a newer one is pending, so the other workers'
350 s went too. On tonight's tree it happened in 2 of 2 loads, and the replacement ran out the same
way at about 700 s (3,615 MB), which fails the pool: the load never ends. T-1479 saw it once in
three with the retry getting through.

**Where the memory went.** A diagnostic build (allocator logging every allocation over 200 MB with
the JS stack, names kept with `wasm-pack --no-opt`; reverted) showed, in each worker's
`IntercityApi::pass_streamed` on all of Japan (s = 9,249 served stations): the route costs `r`
(s x s f32, 342 MB), the fare km table (342 MB, always made since T-1431's income groups), and a
`Vec<(src, dst, cost)>` of every station pair with a planned-first-wait cost (T-1430), grown by
doubling: 261, 522, then 1,044 MB, the old block held during each copy; then `re = r.clone()` (342 MB)
and `demand`'s OD (342 MB). With about 1 GB held at rest that crossed 4 GB on worker 0 (two periods).
T-780 had the market at 2.2-2.4 GB a worker; T-1430 (2026-10-26 13:00, before T-1479's runs) added
the list and `re`, T-1431 (22:10 the same day) the km table, which took it from rare to every load.

**Tonight's changes** (T-1533 rough solve, T-1538 estimates, T-1539 cache ahead) do not touch the
market pass and are not the cause; they neither fixed it nor made it more likely.

**Fix** (`sim/src/demand/intercity.rs` `pass_streamed`): `re` is built as the sweep goes. A search
writes only its destination's column of `r`, so `re` starts as `r.clone()` at the first destination
with entry costs, each later column is copied in and its entries written. No list. Peak drops by
the list (about 1-1.5 GB with its copy). Figures unchanged: `a_streamed_pass_is_the_pass_to_the_bit`,
the full `cargo test --release --features demand` (419 + 2 passed), smoke's 12,484,134 rail trips.

**Why the running solve is dropped** after a replacement: by design (T-1174), the dead worker's
periods have to be solved again and every worker steps through the rounds together, so the
network goes again under a new version. Left as it is: with the memory fixed nothing triggers it.

Repro script: scratchpad `t1482/japan.mjs` (hooks `dispatch`, `workerDied`, `reopened`,
`submitNetwork`); JSON per run in `../artifacts/trainworld/t1482/japan-*.json`.

## T-1544: commuterView's `sync(null)`

**Sequence.** The focused zone's bubbles are built for the shown result. In one task the draw
anchor moves and then the zone in view changes: a loaded game's first state does both
(`takeStateNow` sets the anchor, then `fitView` fits the camera, whose move sets `activeCity`),
which T-1539 made likely by showing a cached result, and so its bubbles, before that first state.
The anchor change reruns the bubble effect; the bubbles' modes are reused (`built`), so it goes
straight to `await startWorker()`, already resolved, and continues as a microtask. Before that runs,
the focus change in the same task sets `worker = null`. The continuation then called
`buildOn(worker!)` and `sync(null)` did `told.set(null, ...)`: "Invalid value used as weak map key",
an unhandled rejection, which Playwright reports as a page error.

**Fix** (`map/commuterView.ts`): after `startWorker()`, an ask whose focus has moved, or that finds
no worker, stops there (the focus change has started the new zone's own ask).

**Reproduced** deterministically: `checks/t1544-focus-race.mjs` (new, about a minute) sets the
anchor and the focus in one task three times on a new game: 2 of 2 page errors before
(`sync < buildOn < commuterView.ts:378`), none after, the bubbles back. Three China runs of the
t1533 sequence (scratch `t1482/china.mjs`, every non-object WeakMap/WeakSet key logged) were clean
before the fix: the timing is narrow. `checks/lib.mjs` `collectErrors` now adds the first stack
frames to a page error, so a rare one can be placed.
