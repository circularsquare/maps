# T-3531 Street tram drawing slow (2026-11-17, not reproduced)

Anita reported street-snapped tram drawing taking over 1 s per ghost on 8800 (master 68aacc99), against under
100 ms on live v0.3.5. Later the same day she found 8800 fine again; the machine was then near its core cap with
many agents running and two 8800 rebuilds. Closed without a code change.

Measured in headless Chrome on 3 claimed cores (bench script: tramlag scratchpad `bench.mjs`), the time from a
pointer move to the finished ghost (street search on the page, `trace_kind` fit in the router worker, preview in
the clock worker, one frame after):

| Build | Place | Setup | Median per move | Search / fit / preview |
|---|---|---|---|---|
| dev master | NYC, z15 | new sandbox, paused | 33 ms | 0.5 / 0.2 / 1.4 ms |
| dev master | NYC, z14, 0.9-1.6 km legs | Real world network All | 38 ms | 3.4 / 0.3 / 2.4 ms |
| dev master | Caracas, z15 | new sandbox | 36 ms | 3.5 / 0.3 / 1.9 ms |
| dev master | Caracas, z15 | normal game, clock running | 33 ms | 0.7 / 0.3 / 1.4 ms |
| 8800 production | Caracas, z16 | terrain on / off | 31 / 34 ms | under 2 ms each |
| 8800 production | Caracas, z16 | 2400x1300 at 2x, terrain on | 31 ms | under 3 ms each |

A sweep (40 moves 16 ms apart, then rest) ended 33 ms after the last move. Clicks placed in 30-95 ms.

The one slow move is the first after a run's first click: 330-780 ms. The street snap starts its router worker
lazily (`streetSnap.ts` `router()`), and that move pays for the worker loading and its WASM starting (`apiReady`).
It happens once per page. Starting the worker when the street snap turns on would hide it; not done.

Not tested: the real NYC save with autosave on, panning between segments (the terrain tint redraws on `moveend`),
and v0.3.5 itself, since master was already at live's speed.
