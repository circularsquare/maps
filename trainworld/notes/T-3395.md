# T-3395: Detect corrupted saves and preserve recovery copies

Priority P1, line accounts-server. Filed 2026-11-15 at Anita's explicit request. Stage 1 (server checks, quarantine, pinned copy) is built and committed in shonei-server, not deployed; stages 2 and 3 below wait for Anita's go on their design.

## Context

Jordan's cloud saves contain truncated gzip streams. The current server accepts uploads after checking only the first four decompressed bytes (TWG1), without reaching EOF/checksum. Browser and cloud backup tiers can eventually rotate through damaged versions and discard the last usable one. Anita requested a scan/archive of affected games and an automatic way to detect corruption and preserve the last intact version for restoration.

The local Safari fix verifies newly compressed output byte for byte using a bundled codec before a slot/backup write. It does not replace server validation, a scan of existing stored files, or a pinned recovery revision. Details: jordan-save-investigation-2026-11-15.md.

## Goal

Automatically detect a damaged save, retain its original bytes for diagnosis, and keep a verified intact version that ordinary saves, syncs, backup rotation and storage cleanup cannot evict. Provide a clear restoration path for the affected player. Preserve explicit account/game deletion semantics; do not resurrect deliberately deleted games or retain them forever under an unrelated recovery policy.

## Required behavior

1. Validate incoming saves completely before acknowledging or replacing anything: bounded gzip to EOF, checksums/length, bounded UTF-8 JSON header and a structurally readable track network. Never trust the four-byte prefix or card metadata alone. Distinguish corrupt bytes from an unsupported newer/retired format, a network/download failure, memory failure and a simulation/runtime failure; an unsupported format is preserved unchanged rather than classified as corrupt.
2. Validate and pin the newest known intact revision before replacement. Failed validation leaves the current verified revision and its recovery copy intact. Repeated bad writes or backup rotation must never replace the pinned intact copy with corrupt bytes. Make validation, durable writes and metadata updates crash-safe; acknowledge only after the durable preservation point.
3. Handle both browser-local slots/backups and cloud saves/backups. Sync must not propagate a corrupt revision over a healthy copy. A failed load must not turn a fresh empty fallback world into a replacement for the failed game.
4. Quarantine the bad payload separately with account/slot/game/revision, timestamp, validation result and checksum; retain the original bytes. Keep recovery copies outside normal rolling tiers and cache cleanup. Respect storage limits by failing visibly instead of silently discarding the only verified intact copy.
5. Add a recurring bounded integrity scan for existing cloud revisions. Record coverage, unresolved/missing files, validator version and races with concurrent uploads/rotation; alert on new failures. Avoid personal information or save contents in public logs. Start from tools/ops/archive_bad_saves.py, but its current header/magic check is not full track validation.
6. Offer restoration as a distinct copy/version with its date and provenance, preserving the damaged original and any newer progress. Require a deliberate player restore action; do not silently roll back their game. List when no verified intact revision survives, so partial salvage remains an explicit separate action.

## Done when

- Tests cover truncated gzip, CRC/size-trailer corruption, valid gzip with malformed/truncated header or network, decompression limits, and unsupported versions without destructive migration.
- A valid revision followed by repeated corrupt uploads, rotation through every backup tier, restart and cleanup still has the original verified recovery copy available and restores its exact bytes.
- Failed/cancelled writes, concurrent devices, interrupted downloads and failed validation do not advance a success acknowledgement or overwrite the last intact local/cloud version.
- An end-to-end player flow restores the preserved copy without overwriting the bad original or a different device's newer intact progress.
- Explicit deletion removes the corresponding recovery material, with the intended retention/privacy rules documented. Quotas cannot silently delete the sole recovery point.
- Scan/alerting is installed and checked only with Anita's authorization for a server deploy; the task can be built and tested locally before that final step.

## Stage 1: server (done 2026-11-16, agent savesafe; not deployed)

shonei-server commits 37217ea, 4623fde, 094b830. Rules: `docs/trainworld-api.md` "The check, the pinned copy and refused uploads".

- **The check** (`trainworld_savecheck.go`): gzip unpacked to its end (128 MB cap, one unpack at a time for the 2 GB box) with CRC and length trailer, nothing after the member but zero padding; `TWG1`, header length in bounds, header UTF-8 JSON object with game `anitabuilder`, whole-number `format`, finite `clock` >= 0, `level` if present; then the network walked as `save.rs` `decode_read` does, without building a model: every varint, count and string in bounds, names UTF-8, node levels -3..3, edge ends naming nodes, no self-loop, 1 or 2 tracks, LUI1 count = lines, LTW1 kinds, all 24 known blocks in order (LBD1 tolerated when damaged, as the game does), the ERA1/ERA2 tail set aside. Not checked: the eras' content, header fields beyond those four, model rules (ports, crossovers on tram or high-speed track, what lines run over), simulation.
- **Verdicts**: intact (stored, pinned); unverified (stored as sent, never pinned: format != 1, level > 18, TWT2/TWT3 or unknown TWT, bytes past the known blocks); corrupt (422 `damaged`); too-big (413 `too-big`).
- **Quarantine**: refused bytes in `games/<acct>/quarantine/` with a JSON record (account, game, name, device, baseRev, account rev, time, bytes, SHA-256, verdict, check version). 3 a game, 10 an account, same bytes kept once, 1 GB for everyone (then refused but not kept, one alert). Not in the account's quota. No age limit: kept until pushed out or the game or account is deleted. A damaged upload to a deleted game is still 410 and nothing is kept.
- **Pinned copy**: `pinned` in each game's meta, the newest intact rev, its file kept whatever the backup tiers do; counted once against the account; a PUT with no room for it is 507 `full`. Games from before the check get a pin at their first unverified PUT (newest stored rev that passes). `GET /trainworld/games/<id>/pinned` serves it. Config reports `trainworldSaveCheck: 1`.
- **Coupling**: `twSaveLevel` (18) and the block list follow `save.rs`; `TestTwSaveCheckFollowsTheGame` fails when the game raises LEVEL or adds a block. Until the server learns it, new saves are stored "unverified" and the pin stops moving.
- **Tests** (all pass, `go test ./...`): truncated gzip, bad CRC, bad length trailer, damaged deflate, garbage, empty, data after the stream, two members, not TWG1, header past the end / not JSON / not UTF-8 / wrong game / bad format / no clock, network cut short or naming no node, bad LUI1 and LTW1, eras tail, unpack limit, newer format/level/network, retired network, unknown block; real local saves (Anita's own) intact and their truncations and byte flips refused; upload flow: 422 with the game untouched, quarantine contents and bounds, too-big, deleted game, two weeks of newer uploads rotating every backup tier with damaged uploads between, restart, the pin's exact bytes, account cap refusing rather than dropping the pin, an old game's pin found past a damaged current rev, game and account deletes clearing pin and quarantine. A one-off sweep of 301 local saves (artifacts and app data, levels 0-18, player data excluded) found all intact.
- **Not covered**: Community's "open a copy" saves still use their own lighter check (already read to the end with the checksum, so truncation is caught; no network walk). Stored revs are not rescanned (stage 3). Old game builds show the 422 as their generic sync failure until stage 2.
- **Seen on the way**: three stored saves unpack to 68-76 MB, almost all header (the scan of 2026-11-15). A header that size is worth a look on the game side; the 128 MB cap leaves them room.

## Stage 2 as built (2026-11-16, agent savesafe2; tree tw/savesafe2, not published)

Rules: docs/architecture.md "Damaged saves", "Backups", "Uploads", "On load"; docs/ui-panels.md "A damaged game".

- **The check** (`checkSave`, workers/saveFile.ts): the strict gzip to its end, TWG1, a header length inside the bytes and a JSON header; in the clock worker also the network decoded (`TrackApi.save_stations`, TWT4-6 only). The main thread has no track model, so its check is gzip and header, which a cut-short save fails. Verdicts: intact, damaged, other (no save, newer, retired: never called damaged), unchecked. `decodeSave` throws the key `clockWorker.saveDamaged` only for a real decode failure of the bytes: gzipCore's own `GZIP_DAMAGED` error on a file starting 1f 8b (bad trailer, truncated or bad stream), a header cut short, a header that is not JSON (a SyntaxError), and the two network loads that fail; a file that is not gzip is still "not a save".
- **Could not check** (savefix, 2026-11-16): any other failure of the check (the gzip worker not loading, "Gzip worker failed."; an allocation failing on the main thread or in the clock worker; the output cap; a trap in the network decode) is `SAVE_UNCHECKED` / "unchecked". It never marks a slot, never writes an unreadable copy (`backupBeforeReplace` makes it the `pull` backup as before, not the good copy), never stops a download or a pinned copy (the load checks again), and an upload waits for the next try. A file opened that way says `loadFailText` of the cause ("Failed to load :( Try reloading the page." or the out-of-memory line): existing strings, no new one.
- **Every upload is checked first** (savefix): `upload` runs `checkSave` on the slot's bytes before any request, whatever the server (one from before the check, as production's 372a8ce today, stores whatever it gets), cached per slot by `at` and size so a copy is unpacked once. In the clock worker this includes the network decode, so the open game's uploads get it; the main thread's (start menu settling) is gzip and header. Damaged: marked, `rescueGood`, the same note as a 422 (`WHY_DAMAGED`), "failed", no request. Unchecked: "failed", no request, nothing written.
- **Refused upload** (`cloud.ts upload`): 422 `damaged` (now only for damage the server's check sees and this thread's does not: a network cut inside a whole gzip, sent from the main thread) writes `error` (the note) and `refused` (the slot's `at`) on the sync record, then checks the slot. A slot marked damaged, or whose `at` was refused, is never sent; the next write of the slot (a new `at`) goes up as usual. The retry timer still fires but returns before any request.
- **Downloads** (`fetchGame`): the bytes are checked before `writeFetched`; a damaged copy returns null (slot untouched, nothing in `pull`) and the id goes in `damagedGames` (main thread: `damagedAccount` signal). Open on such a game says "This save is damaged.".
- **Marked damaged**: `StoredSave.damaged` on the slot record (bytes untouched), set by a failed start load with the damaged key or by a 422 whose slot fails the check here; any later `writeSlot` drops it. `rescueGood` then copies the slot's newest backup that passes into `backup:<slot>:good`.
- **Good copy** (`backup:<slot>:good`): written with tier 0 by `writeBackup` (the autosave's bytes, already read back by `compressGzip`), or at any backup write while missing; a `pull` that passes and is newer replaces it. Outside `BACKUP_CAP` and rotation; deleted with the slot. A damaged slot about to be replaced goes to `unreadable-<at>:<slot>` (`unreadableKey`), never into `pull`.
- **Unreadable copies go with their game** (savefix): `unreadableKey(slot, at)` = `unreadable-<at>:<slot>` for both writers (`backupBeforeReplace` and the failed start load, T-743), and `deleteSlot` deletes every `unreadable-*:<slot>` with the slot's backups. Copies written by builds before this under `unreadable-<at>` name no slot and stay where they are.
- **Saves** (`groupVersions`, `VersionsLine`): a card whose top is damaged starts with its other versions open; the first row is the newer of the slot's good copy and the account's pinned copy ("Last undamaged copy · Saved ..." with "Open a copy"); the backup it was copied from is not listed twice. Pinned opens through Open a file's path (`restorePinned`, the start menu's `pinnedFile` + `fileChoice`), the good copy as a backup restore; both are new slots, versions of the game, the damaged one left. With neither: "No undamaged copy of this game is left", except for an account game whose current rev has no `check` (stored before the server's check, or an old server), where a missing pin says nothing. The card's facts end with the note or "This save is damaged.".
- **Failed load**: already a new slot with no sync record (T-743); the check shows no PUT for the game and its rev unchanged.
- **Old servers**: no 422, no `pinned`, no `check`: uploads are still checked here (a damaged slot is never sent), downloads too; no account restore row and no "none left" for account games.
- **Differs from the design**: the restore row shows only while the top copy is known damaged, not whenever `pinned` differs from the current rev (after a save-level bump every game's pin lags until the server learns it, which would put the row on every card); a damaged slot about to be replaced is kept as `unreadable-` instead of `pull`.
- **Check**: `node trainworld/checks/t3395-saves.mjs http://localhost:<port>/ [--exe <shonei.exe>] [--old-exe <pre-check shonei.exe> | --old-rev 372a8ce]` (without --exe builds shonei-server's committed HEAD from a `git clone --shared` in a temp folder, no tar; --old-rev builds that commit the same way; 8083 must be free; about 5 minutes). G1 is now a network cut inside a whole gzip (the 422 path); added: G7, a cut-short slot on the new server, never PUT; G8 on the old server, never PUT (no PUT at all from that browser), marked, with the note, the account's bytes unchanged; the gzip worker blocked: checkSave/checkSlot "unchecked", nothing marked, the slot's pull written, no unreadable copy, Open a file says the load failed; deleting slot-l2 (a failed load) and slot-u1 (a pull replacement) removes their unreadable copies. 51 PASS on 2026-11-16 (savefix) with shonei-server HEAD (85e2945) and 372a8ce built by --old-rev. Earlier: 41 PASS (savesafe2) with 094b830 and 372a8ce. Also: smoke on 6156 passed (28; again after savefix); t2037-versions and t2614-cloud-fail passed (again after savefix); t1826-saves has only its three failures from before (the newer-save wording and four backup rows; its pull assertion now allows the good copy beside the pull); t2738-delete stops at the Delete button T-2784 disables until a big game's station count is typed, and t988-cloud at device B, which stays on the new game sheet after signing in with no saves, so never lists the account card: both outside this change.
- **How to see each by hand**: run the check (it leaves nothing behind) or, on a scratch server and profile: put a cut copy of a save into a slot (IndexedDB `anitabuilder`/`saves`) and open it (`?slot=<key>`): "This save is damaged.", a new game, the Saves card with "Last undamaged copy" when a backup or pin exists. A cut save in Open a file: "This save is damaged."; a non-save: "This file is not a saved game.".
- **Left for stage 3**: games stored before the check have no pin until their next upload or the scan; until then their damaged card shows no restore row and no "none left". The good copy doubles a slot's storage (one more save-sized record).
- Screenshots: artifacts/trainworld/t3395-sync-note-{light,dark}.png (start menu), t3395-restore-{light,dark}.png (Saves panel).

## Stage 2 design: the game (for Anita before building)

1. **Damaged answer from the account**: `cloud.ts upload` treats 422 `damaged` as its own failure: the sync record says so, the slot is not sent again until it changes, and the slot itself is left alone. Only reachable from a slot written before v0.3.5's checked compressor, so rare.
2. **Downloads never write a damaged copy over a healthy slot**: `fetchGame` strictly decodes (`gzipCore` inflate to the end, header, `TrackApi` decode) before `writeFetched`; a copy that fails keeps the slot as it is and is offered as the pinned copy instead (3).
3. **Restore**: Saves, "other versions" lists the account's pinned copy (`GET .../pinned`, when `pinned` differs from the current rev or the current one failed) beside the local tiers and account backups, with its date. Open makes a new slot from it, as backups open now; the damaged original and any newer progress stay. When the game has no `pinned`, the panel says no undamaged copy is left. No automatic rollback.
4. **Browser slots and backups**: before a tier or `pull` backup is written, the copy is strictly decoded; a copy that fails never enters the tiers, and the newest copy that passed is kept under its own key (`backup:<slot>:good`), outside `BACKUP_CAP`'s trimming. New saves already pass (v0.3.5 checks every compression); this covers slots and pulls from before.
5. **A failed load never replaces the game**: the existing T-743 path keeps the unreadable slot aside and starts a new slot. Add a check that the new empty game never inherits the failed slot's sync record or cloud id (so it cannot upload over the account's copy), and a load error that names a damaged save ("This save is damaged.") apart from a file that is not a save.
6. Checks: Playwright with a truncated slot, a damaged account copy, the pinned restore, and the empty-world fallback not syncing. Plus the changelog line.

Player text to propose (stage 2; none is in the game yet):
- Sync note on a slot: "This copy is damaged, so your account kept the last good one"
- Load error, damaged save: "This save is damaged." (old: "This file is not a trainsworld save." for every unpacking failure)
- Saves list entry: "Last undamaged copy" with its date, button "Open a copy"
- No pinned copy: "No undamaged copy of this game is left"

Estimate: about 3 hours.

## Stage 3 design: the recurring scan (for Anita before building)

- **In the server**, a goroutine reusing the Go check (one source of truth; `archive_bad_saves.py` stays the one-off offline tool, its validator now weaker than the server's). Once a day at a quiet UTC hour, never at start.
- **Bounded**: account by account, `gamesMu` held only per account, one unpack at a time, a pause between files, a time budget per run that resumes where it stopped next day. Skips revs already checked at the current `checkV`, so after the first pass it reads only new or older-check revs.
- **What it does**: writes `check`/`checkV` on each stored rev and backup; pins games that have no pin; copies a corrupt stored rev into the quarantine (marked "found by scan") and leaves it in place. Never deletes, repairs or replaces a rev.
- **Report**: `trainworld/scans/<date>.json` with coverage (accounts, games, revs, bytes), unreadable indexes, missing files, revs that rotated away mid-scan, games with no intact rev, and the check version. Counts and ids only, no names or contents. An alert (counts only) when a corrupt rev is found that the last report did not have. A small tool prints the latest report from the box.
- Tests on a made-up store: corrupt, missing, rotated mid-scan, unreadable index, resume after the time budget.

Estimate: about 2 hours, plus Anita's go for the deploy that installs it.

## Stage 3 as built (2026-11-16, agent savescan; not deployed)

shonei-server `trainworld_scan.go` (+ `trainworld_scan_test.go`), a `foundBy`/`rev` pair on quarantine records, docs in `docs/trainworld-api.md`, `tools/trainworld_scan.py` prints the latest report from the box.

- **When**: a goroutine started with the server, first run at 04:00 UTC at least an hour after start, then daily. `TRAINWORLD_SCAN=off` turns it off.
- **Budget**: one rev at a time (reads under `gamesMu`, unpacks outside it under the check's one-at-a-time slot), 100 ms pause per file, 30 min and 1 GB read per run; a run always checks at least one rev. A run that runs out stops and the next day resumes after the last finished account (`scans/state.json`); a pass is one trip through all accounts. A rev already checked at this checkV is not unpacked again, only looked at (file there, same size as the index says), so a truncated file is still caught.
- **Does**: writes check/checkV on each rev and backup; pins a game with no pin, or whose pin is damaged, at its newest intact rev (adds no bytes); copies a damaged stored rev to the quarantine as `foundBy: "scan"` only when that evicts nothing and it is not the game's only stored rev; never deletes, repairs or replaces anything.
- **Report**: `scans/<date>.json` (60 kept): coverage, checkV, damaged revs, missing files, unreadable indexes, games with no intact rev, unverified/too-big revs, races (rotated away during the read or check, game deleted), stopped reason. Ids and counts only. The log line has counts only.
- **Alert**: one `notifyAlert` with counts when damage appears that the last whole pass did not have (the first pass alerts on whatever already exists). Missing file and unreadable index count as damage.
- **Tests** (made-up stores): clean store then skips; truncated backup found, recorded, copied, left in place, no second alert, new damage alerts again; only copy recorded not quarantined; scan copy never evicts a refused upload; missing file and unreadable index (index untouched); pin where none and re-pin off a damaged pin; resume across runs by bytes budget and by time budget, no stall at zero budget; upload, rotation and delete during a scan; report holds no names or contents; report cap; schedule and never-at-start; off when games are off.
- **Not done**: bit flips that keep a file's size are only found when its rev is rechecked (a new checkV, or never: a checked rev is not unpacked again). Raising twSaveCheckV rechecks everything over the following days.
