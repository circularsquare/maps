# T-4271 Patch check flags a hub node after a station on a line (agent patchhub, 2026-11-25)

Tree patchhub (master 4b5088233). Not committed.

**For Anita.** Nothing a player sees changes. Right after an edit, the worker sends the page a quick patch of the map the
tools click on, ahead of the full update. For stations it reused the names worked out at the last full update, so a
station placed beside another (the two become one complex) went into that patch without the complex's name. The DEV
check caught it. The patch now works out the complexes again whenever a station changes, so its station names match the
full update. That includes stations the edit never touched, such as the other half of a complex that a station removal or a
"separate" splits.

## What `hub` is

A station row's `hub` (workers/protocol.ts `ClockNode.hub`, made in workers/stateRows.ts `foldNames`) is the name of its
complex, carried beside the station's own name when they differ: an unbound station (its own name, the default for new
stations since `bindNew` is off for new players) in a complex of two or more whose name source (the oldest typed name,
else the oldest station's, `nameSource`) is another station. A bound station shows the complex's name as its `name`
instead. The Stations tab and the complex view title read it (`complexTitle`).

## Why the patch differed

`StateRows.touchedRows` (the patch's rows, workers/clockPatch.ts) never worked out complexes. A touched station took the
fold of the last full read if its stored and own names were unchanged, and a new station took none: "A station shows the
name the last read folded for it ...; a new one its own." A full read folds every station with the complexes as they are
now. So any edit that changes a complex gives the patch stale names:

- A station placed within 100 m (centres) or 50 m (platforms) of another joins its complex. The new one has no fold, so its
  patched row has no `hub`. The state's has the old station's name. A bound new station would have differed in
  `name` instead. The logged case (uploadedit's station on line A's track near A's stations; the node was not recorded)
  is this or the next one: `hub` alone can differ only for an unbound station whose complex changed.
- The same for a station moved, resized, removed or brought back by undo or redo, for a `separate`, and for its undo (the
  separated pairs), and for a removal that takes a station's links with it.
- Stations the edit never touched also change: a complex split or rejoined, or one whose name source goes or arrives,
  changes the hub or shown name of members with no touched record. Those were not in the patch at all, so the page's tools
  kept stale names and the check, which compares only patched records, could not see it. (Links and buildings send a state
  at once, so no patch spans them, but an undo or redo can move links.)

The patch was wrong, not the check.

## The fix (workers/stateRows.ts)

- `foldNames` is split into `complexGroups` and `shows` (the name and hub a station row shows, one rule), and it now
  keeps the stations it folded (`lastStations`, unfolded, node order).
- `touchedRows` gives the touched rows unfolded to `patchNames`. When a touched record is or was a station, or the
  links, buildings or separated pairs differ from the last read's (`complexKey` against `lastFoldKey`), it takes the last
  read's stations with the touched ones as they are now (in node order, as the read lists them, so the complexes' builder
  sees the same order), works out the complexes through the same `rowEnv.complexes` the read uses (the incremental
  builder, so only the changed complexes are worked out again), and folds every touched station. It also adds every
  untouched station whose shown name or hub moved against the last read's fold.
- A station sent that way goes again in every later patch until the next read (`nameSent`, cleared in `begin`), since
  the page lays each patch on the ones before. Otherwise a later patch that put it back (an undo) would leave the page with
  the earlier patch's row.
- An edit touching no station, with the links and the rest as at the last read and nothing sent so, costs one key compare
  as before.

game/mapPatch.ts, now map/clickMap.ts).

## Left, not this task's

- A station's platform line can move with no edit touching its node (track changed next to it, the read's carry and
  regions find it). The patch keeps the last read's row and complexes for it, so a complex change through such a station
  alone is missed until the state. Never seen; not chased.
- The patch's cost on a big save is not measured (no benchmark in this budget): for an edit touching a station it now walks
  every station about four times (the list, the builder's diff, the groups, the compare), likely 1-2 ms on her Asia save
  (2,698 stations) against the patch's 6-13 ms there.
- The `edges N: cost` warning in notes/T-4214.md ("A DEV warning seen elsewhere") is another cause (repricing with no
  edit), not this one.
