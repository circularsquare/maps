# T-4390: Trips worker crash on a 2 GB phone (`Columns::pack` OOB)

## Reported panic

- Version: 0.4.6 (2026-11-25, around `a825a5357`). `everyday.rs` lines 1-2149 are unchanged from `a825a5357` to `HEAD` (only `set_apart` was added at line 2150 in `bb321567e`).
- Device: 2 GB Android phone, one worker, intercity trips off, 30 lines, Japanese UI / JPY game, 17 MB WASM memory, round 1 period 2.
- Panic: `sim/src/demand/everyday.rs:655:25`, `index out of bounds: the len is 10191 but the index is 10191`.
- Line 655 col 25 is `src[j]` in `Columns::pack`:
  `(src[j], trips[j]) = (a as u32, *v);`

## Root cause

Under the Rust / IEEE 754 abstract machine, `Columns::pack` cannot panic at line 655:
- Pass 1 (lines 635-641) counts `(*v != 0.0) as u32` per column `b` over all rows `a` where `self.rows[a]` is true, prefix-sums `off`, and allocates `src` and `trips` of length `n = off[s]`.
- Pass 2 (lines 648-660) visits the exact same `(a, b)` pairs (taking `self.rows[a]` once per `a`), checks `if *v != 0.0`, writes `(src[j], trips[j])` at `j = at[b]`, increments `at[b]`, and zeroes `*v`.
- Neither `od` nor `self.rows` is aliased or mutated between passes (single-threaded WASM), and `n = 10191` is nowhere near `u32::MAX`.

The only way `j = at[b]` can reach `n = 10191` is if Pass 1 and Pass 2 disagree on whether `*v != 0.0` for at least one element of `od`, with Pass 1 returning false (not counting it) and Pass 2 returning true (placing it, pushing `at[b]` past `off[b + 1]` and into `off[s] = n` when `b` is the last non-empty column).

That exact divergence happens in WebAssembly with `+simd128` (`sim/.cargo/config.toml`) on **32-bit ARM (ARMv7a) Android** (which 2 GB Android phones run for Chrome):
1. Pass 1 (`off[b + 1] += (*v != 0.0) as u32`) is a contiguous, branchless loop over `row: &[f32]` and `off[1..=s]`, so LLVM auto-vectorises it to WASM `f32x4.ne` + `i32x4.sub`.
2. Pass 2 (`if *v != 0.0 { ... }`) has a data-dependent branch and scatter writes, so LLVM compiles it as scalar WASM `f32.ne`.
3. On ARMv7a, V8 lowers `f32x4.ne` to ARMv7 NEON `VCEQ.F32`, which **architecturally flushes subnormals to zero (FTZ=1)** (ARMv7 NEON has no non-FTZ mode), whereas scalar `f32.ne` lowers to VFP `VCMP.F32`, which **preserves subnormals (FZ=0)**.
4. `EverydayApi::pass` routinely writes subnormal `f32` values (`0 < v < f32::MIN_POSITIVE ≈ 1.175e-38`) into `od`: `fast_exp` clamps at `-80.0` (`1.8e-35`), and `od[ia * s + ib] += trips * wa[ka] * wb[kb] * er(ka, kb)` multiplies that by small access weights and trip shares. In round 1, crowding raises generalized costs `e`, pushing products further down into the subnormal range (and in round 0, any subnormal in an earlier column silently overwrote the start of the next column instead of hitting `off[s]`).

## Cousins checked

Checked every two-pass count-then-place (`off.clone()`, `chunks_exact_mut`) across `sim/src/demand/`:
- `busmerge.rs:387`, `intercity/api.rs:298`, `intercity/build.rs:603,628`, `intercity/logsum.rs:191`, `kernel/gravity.rs:132,664`, `kernel/subzones.rs:392`: integer/bool keys only.
- `intercity/market.rs:271`, `kernel/access.rs:165`: scatter bucket index in both passes (not auto-vectorisable).
- `kernel/subzones.rs:558`: `&dyn Fn(usize) -> bool` with scatter `off[sz.zone[s] + 1] += 1` (not auto-vectorisable, and `pop`/`jobs` are never subnormal).
- `api.rs` (commutes) and `intercity/pass.rs` do not pack `od` with a two-pass count-then-place.

`Columns::pack` is the only float-keyed two-pass count-then-place in `sim/`.

## Fix

In `Columns::pack` (`trainworld/sim/src/demand/everyday.rs`), test `v.to_bits() != 0` instead of `*v != 0.0` in both passes:
- Both passes compare `u32` integers (`i32x4.ne` in Pass 1, `i32.ne` in Pass 2), so floating-point FTZ cannot affect either pass.
- Using `to_bits() != 0` (rather than `(to_bits() & 0x7fff_ffff) != 0`) also prevents LLVM from ever folding the integer bit-test back into `fcmp une` (`f32x4.ne`), because `(-0.0f32).to_bits() != 0` is true while `-0.0f32 != 0.0` is false.
- Trip figures are bit-for-bit unchanged on every platform that did not panic: `od` is initialised to `+0.0` and only accumulated via `+=`, so `-0.0` never occurs in `od` under IEEE 754 round-to-nearest-even.

## Tests

- Added `columns_pack_uses_integer_nonzero_for_subnormals` in `trainworld/sim/src/demand/everyday/tests.rs`.
- Native x86_64 has no asymmetric NEON/VFP FTZ, so the test verifies subnormals in the last column and includes `-0.0` (`0x8000_0000`) to distinguish integer `to_bits() != 0` from float `!= 0.0` (fails before the fix, passes after, and catches any regression back to float comparison).
