## PR 24 (caelum418): waiting room, car park and building layout

Ported by hand onto master's facility cache (T-3803 option 3), tree `pr24`. Same output as master everywhere it was
compared. Credit line for the landing commit:

    Co-Authored-By: caelum418 <150506911+caelum418@users.noreply.github.com>

### What changed

- `map/facilityPlace.ts`:
  - The near cells (`FacilityCache.near`) are 32 x 32 tiles of row masks, so marking a complex's square is a word per
    row and `isNear` (the edge pass's hottest line) is one map lookup and a bit.
  - A car park try's segments come from a stamp array (no Set per try); `segHitsRect` clips without making four
    arrays a call (the same arithmetic, so the same answers bit for bit).
  - A try stops scoring once it can no longer beat the best so far. The cells and box it would read are recorded
    first, so a kept complex still depends on everything it would have read.
  - Rooms, lots and station buildings are looked up in a grid (`map/shapeGrid.ts`, new) instead of scanned in full
    for every try and every room spot; the first building holding each complex is a map. Both grids are made each
    build, and kept and re-placed complexes both go in them.
- `map/buildingNet.ts`: one line. The edge loop's `{ id, p, ...e }` made a copy of every edge's box for every
  building; it now reads the box in place.

### What was not taken

- The PR's obstacle cache (keeping the segment grid when nothing moved): master's per-edge grid from T-3803 already does
  that, and finer.
- The PR's grids in `buildingsDrawn`: the one-line fix above, which sits inside the PR's change, is faster on its own
  for the pass with insides, and the grids cost more than they save with few buildings (one process, three arms,
  medians of 31, 2,647 save with synthetic buildings):

  | a build, insides kept | master | PR's grids | one-line fix |
  |---|---:|---:|---:|
  | 442 buildings: outlines pass | 9.8 ms | 1.7 ms | 10.6 ms |
  | 442 buildings: insides pass | 660 ms | 62 ms | 43 ms |
  | 5 buildings: outlines pass | 1.0 ms | 0.6 ms | 0.1 ms |
  | 5 buildings: insides pass | 19.5 ms | 33.9 ms | 5.0 ms |

  The PR's station grid alone would save about 8 ms a pass at 440 buildings and cost about 0.5 ms at our 4; left out
  for now, an easy follow-up if a big builder's save shows it.
- `checks/facility-layout.mjs` as a standing check: no bug behind it. Its cases ran in scratch against the port and
  master (24 cases, the same).

## PR 23 (caelum418): intercity assignment

Ported by hand in tree `pr23`, partly. Same figures to the bit on the real NYC save. Credit line for the landing
commit (the same as PR 24's):

    Co-Authored-By: caelum418 <150506911+caelum418@users.noreply.github.com>

The PR has three parts: (1) the market's skims searched without walking columns, filled later for a local caller;
(2) the log of every access weight stored once at network setup; (3) `fare_col` pricing only stations.

### What changed

- `intercity/setup.rs` `fare_col` (part 3): the column is cut to the stations after the trip km pass, so the
  pricing (fare curve, km multiplier, fare zones, base multiplier) runs on the 1,756 stations, not every node of the
  graph. Both callers (`pair_km`, the pass's `kmc` copy) and `start_column` only read stations (a start walk's
  pair is station to station).
- `intercity/logsum.rs`, `pass.rs` (half of part 2): `rail_logsum_by` and `rail_mix_by` read the far end's
  logs through `ln_b(j)`. In the pass, the per-zone columns the zone's pairs already share (`bc`, `hc`,
  `hc_ride`, `hc_walk`) carry each far station's weight log (`EndCol`), so it is taken once a zone and period
  instead of once a pair: up to 10 of a call's up to 20 `ln`. The whole-table wrappers (`rail_logsum_x`,
  `rail_mix_x`: the explorer and tests) keep today's expression. `k * ln` is the same product as before.

### What was not taken

- Stored logs (the rest of part 2). `(usize, f64)` is 16 bytes in WASM against 8 for `(usize, f32)`, so every
  access list doubles; T-1611 measured them at 98 MB on the all-China save. Natively both are 16 bytes, so
  `demand_mem` would not have shown it. An f32 log fits in 8 bytes but moves figures (about 1 part in 10^6) and
  loses the loads-hash check. The near end keeps its `ln` per call.
- Part 1, deferred walking columns. Since T-4179 the shared table drops a destination's wait times right after its
  walking column is made (`share.without_waits()` in `skims_extend`), so the PR's later fill from
  `sk.strategy(slot)` has no waits to read. What it saves is real: the market solves last in its period and round,
  so the walking columns it makes for stations no city asked for are never read. To take it: skip `walk_column`
  for the market's new slots, mark them, and have a caller that needs walks search such a destination again (as
  `trip.rs` `routes` does), or keep those slots' waits until filled (memory). On NYC few stations are the
  market's alone, so it would show more on wide markets like the contributor's. Not filed.
