# T-405: solve speed and population order

## Cause

The skim cache (`kernel::with_skims`), not `STATION_WALKS`. On the real save each city converts
station positions to its own frame, so a period and round brings three graphs that differ in the
last bits of their walk costs: New York's (shared by its commutes, its everyday layer and the
market), New Haven's (2-4 stations searched) and Litchfield's (0 stations: nothing to search, but
it still took a slot). The cache kept the two newest. Registry order (nyc, nhv, lit, then the
everyday layers) let Litchfield's empty table push out New York's 873-station table just before
New York's everyday layer needed it, so all 873 were searched twice per period and round. Pack-open
order (nhv, lit, nyc) happened to keep it.

`STATION_WALKS` holds one entry per station, pack and bound (about 10k here, under its 50,000
clear) and set-up times were the same in both orders natively, so it plays no part.

Native bench (the startup's network and each population's station positions captured from the
game, one thread solving all five periods, free flow and three rounds, `cargo test --release`;
the test was removed afterwards):

| | searched per round | solve |
|---|---|---|
| before, pack-open order | 4,395 | 50.1, 44.2 s |
| before, registry order | 8,760 | 57.1, 50.3 s |
| after, pack-open order | 4,385 | 41.4, 41.3, 42.5, 41.3 s |
| after, registry order | 4,385 | 45.8, 45.9, 39.4, 40.6 s |

After the fix both orders search the same 4,385 destinations a round (the after spread is the
machine: two cross runs, set-up and solve in opposite orders, gave 41.2-42.0 s). The pack-open
order searches 10 fewer a round; no real speed-up there. Every output (summaries, segment loads,
boardings, alightings of all seven populations, every period) has the same hash in all runs.

## Fix

`with_skims` still keeps two tables (`SKIM_TABLES`). When a third graph comes, the table with the
fewest searched destinations gives way (oldest of equals), and only to a graph that wants at least
as many; a cheaper one is searched for that call alone and dropped. Memory is unchanged: at most
two tables a worker, here New York's 45.4 MB and New Haven's 3.2 MB (stations² costs, 3 MB at 873
stations, plus about 12 bytes a node per searched destination). Test:
`partial_skims_equal_full_skims_where_searched` checks a third, cheaper graph evicts neither.

## Browser

Startup final, real save (as smoke imports it), back to back:

- before: pack-open 29.8, 31.5 s; registry 34.9, 35.1 s
- after: pack-open 29.4, 29.9, 31.4, 30.0 s; registry 30.1, 33.2, 33.3, 33.2 s

A residual is left in WASM only, in each worker's first round-0 solve (New York's commutes 1.9-3.0 s
against 5.1-5.9 s; later periods equal) and set-up (+0.2-0.3 s). It follows the set-up order, not
the solve order: set up in pack-open order and solved in registry order the final was 29.3 s, New
York's first solve 1.9 s. Heap size is the same either way (281 then 326 MB); likely which set-up
leaves already-touched memory for the first solve. So the worker keeps `solveOrder` (set-up and
solve in pack-open order); T-414 is the follow-up.

Checks: `cargo test --release --features demand` 167 passed; `npm run wasm`, `npm run check` clean;
smoke passed, demand final 7,597,261 rail trips a day.
