# T-3788 The two failed opens T-3773 left

Agent openrest, 2026-11-19, tree `openrest`. Follows notes/T-3773.md.

## What changed

Both paths now end like any failed open (T-3773's `openFailed` message, `letGoSlot`, the page's record and menu notice).

1. **Newer account copy loaded in place** (`openOnAccount`, slots.ts). The copy is loaded first; the slot is replaced
   (`writeFetched`) only once the load succeeded. If the load throws, the slot is untouched and the worker calls the
   new host method `openFailed` (`failInPlace` in clock.worker.ts: `afterLoadPanic` for a panic, `letGoSlot`,
   `openFailed` with from "slot", the slot's name). The sync record gets `badRev` (the account rev that failed), and
   `openOnAccount` skips fetching that rev again, so the slot opens normally next time instead of bouncing to the menu
   every time; a newer rev is tried again. If `writeFetched` fails after a good load, the game in hand is the
   account's copy and `saves.dirty` is set so autosave writes it.
2. **Real-network new game that fails** (clock.worker.ts init, `msg.newSlot` only). It no longer falls back to an empty
   game in its own slot: `letGoSlot` (the new slot was never written), `openFailed` from "new". `?new=1` pages
   (`msg.fresh`, no slot) keep the old fallback. The start menu's notice for from "new" reuses `startMenu.openFailed`
   with the start's name ("New York sandbox could not be opened."); no card (no slot).

New dev hook: `?debug=1&loadPanic=late` panics the first load after the game has opened (the in-place copy).

## Strings

No new or changed strings. `startMenu.openFailed` ("{name} could not be opened.") is reused for a new game.

## Proof (scratch probe, probe.mjs in the scratchpad, local shonei-server, two profiles as devices)

  opening the slot again stays in the game (writable). No page errors. Typecheck clean.
