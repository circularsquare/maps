# T-401: one period's round by layer and step (native, real New York save)

2026-10-15. Measurement only; no change to `sim/`. Basis for T-036 (faster pair loop) and the
periods T-124 keeps.

## Method

A copy of the crate at HEAD (5d44e40) with `Instant` timers wrapped around the kernel functions
(graph, crowding, skims search, station exp table, assignment, the mode choice loop's phases, each
layer's pair loops, the averaging) and a **release binary**, not a test: the everyday pass has extra
`#[cfg(test)]` work (an extra assignment and an S x S sum per purpose), so test-build probes
overstate that layer (T-398's and T-399's everyday figures likely do). The binary does what
`demand.worker.ts` does for one cluster: open the commute engine, the everyday layer beside it and
the market part (`MarketPacks` of the seven Northeast packs the real save reaches, `beside()`), set
the network (stations as longitude and latitude for the market), then for each of three rounds, each
of the five periods: every layer solves or crowds from the summed loads, then `release_skims`. One
worker solving all five periods; the target's two workers split them 3 and 2. The real network is
`data/work/realnet/nyc_real_track.json` (1,756 stations, 109 lines), the packs the working tree's.

Machine: Windows, single thread; the box was shared (CPU load 34-57% before each run from Chrome,
Rainmeter and an editor; no builds of mine ran at the same time). Six New York solves of the same
size came out at 36.7-41.5 s and the shares moved under 1 point, so read times as +-10%. Native is
about 1.5-2x faster than WASM. Between my first and second run another agent changed the
registry's market rows, which moved only the market's total trips (+2.3%), not any rail figure.

## Which steps each task would speed

- **T-036 (SIMD or a packed layout for the pair loop)** acts on the commute pair loop and its
  scatter, 49.7% of New York's solve (a loop twice as fast: -25%), and on the same shape in the
  everyday pair loop (10.7%) and the market's zone pair loop (7.9%, f64 and a random S x S lookup
  per access pair; a different loop, so it needs its own change). At 42 + 15 ns a pair the commute
  loop is 42 ns here against the ~35 in T-036's line.
- **T-124 (kept periods)** skips whole periods, so it speeds every step alike by the periods it
  keeps and none of one step in particular. Measured here: a train-count edit to line 0's high level
  re-solved periods 0 and 2 and kept 1, 3 and 4: 15.4 s against 38.3 s for the same network with
  the layout edit (5 periods, one worker), 60% less. A layout or fare edit keeps nothing.

## Ranking for solve time

1. **Commute pair loop and scatter, 50% (T-036).** The biggest single block, in every network
   measured. The scatter was taken out of the pair loop on purpose (comment in `mode_choice`: in the
   loop it chains each pair to the last through `y_row`), and on its own it is 13%.
2. **How many rounds** (75% of the solve is rounds 1-3, each a full pass): if the third round moves
   no figure a player sees, stopping early would cut up to a quarter. It changes the model, so it
   is measured first (T-434).
3. **Everyday: assignment once instead of once per purpose (8.6%, 12.6% at Tokyo scale) and its
   pair loop (10.7%, 15.7-23.6%).** One walk of each destination's strategy carrying a flow per
   purpose would do the assignment work once (T-433).
4. **Strategy skims, 12% (21% at 2,000 stations).** Searched again every round; shared already
   across the three layers. No cheap fix known; worth a look at searching only the destinations
   whose costs moved after round 1.
5. **Market pair loop, 8%** at New York's size, falling as a share on bigger networks (T-435).
6. Nothing else is worth a task: set-up is 2% of a solve and a quarter of that on an edit,
   crowding costs, graph building, averaging and the exp table together are under 1%.
