# T-3451 — review of how trainworld organises its work

For Anita, 2026-11-16, by agent workflow (Fable). Your ask: look at the kanban, task organisation and subagent
workflow, compare with what others running many coding agents do, and advise. Nothing was changed except this note.
Sources and the numbers behind each claim are in the appendix.

## Short version

The setup is ahead of most of what is written up publicly. The task list, the board and the takeover system are
sound and I would not swap any of them for an outside tool. The weak spots are all the same kind of problem: a rule
written in a doc that a busy orchestrator has to remember, where a small tool or a single place would do it for them.
Seven recommendations, biggest payoff first.

## What already works well (keep)

- **Tasks in one markdown file with `{L:}`, `{waits:Anita}`, `{after:}` tags.** The main thing dedicated trackers
  (beads, Taskmaster) add is "what is blocked and what is ready". Your tags and the board already give that. Beads
  itself is now described as heavy, with reports of lost data. Staying put was the right call.
- **Lines on the board.** Nobody else I found has a good answer to "the human gets lost in 400 agent tasks". Yours is
  better than the published ones.
- **Takeover without waiting for the old session.** Anthropic's own advice for long work is state in files, fresh
  sessions that read it. You have that, plus a hook that stops the old session starting new work.
- **A worktree per code agent, small batches of 2-4 tasks, one smoke on master after a batch.** This matches the
  common advice. Throughput is very high: 80-110 commits and 60-170 tasks closed on a working day.
- **Briefs** (goal in your words, decisions made, files owned, what done looks like) are what Anthropic and Cognition
  both name as the thing that prevents duplicated and wrong work.
- **Sonnet by default, Opus for judgement.** In the last full session Sonnet did about two thirds of agent turns.

## Recommendations

**1. A second agent checks risky work before it lands.**
- What changes: for changes to the simulation, saves, demand numbers or money, the orchestrator starts a fresh
  checker agent before landing. It gets the task's Goal and the change, not the first agent's report, and tries to
  break it in the running game. One round only, pass or fail with evidence. Labels, text and docs skip it.
- Why: you can't read the code, so today "done" rests on the agent's own word, its own smoke run and the
  orchestrator's look at screenshots. The most consistent finding in the research is that agents say done when it
  isn't, that asking the same agent to double-check does not help, and that only an independent check does.
  Cognition reports its reviewer finds about 2 bugs per change. Two bugs reached players last week (the stop-edit
  freeze, the Safari save damage).
- Cost: one extra Sonnet agent per risky landing, roughly 10-15% more usage on those tasks, and landings a few
  minutes slower. About 1 h to write the checker brief into docs/orchestrator.md.
- Caveat: I did not measure how often landed work here was wrong. The outside numbers come from vendors.

**2. One place for everything that waits on you.**
- What changes: every ask goes on the board's "Waiting on you" column, including asks that are not tasks (a commit
  that needs your yes, a process to stop). notes/for-anita.md is retired. The For you block in chat stays, as a copy.
- Why: right now asks live in three places. The board shows 8 waiting tasks. The handoff file holds at least four
  more that are on no list (commit serve.py, six leftover Shenzhen scan processes, the coastal scan proposal, the
  graffiti backup window that opens at 11:15). for-anita.md says "Nothing open (2026-11-11)". With 5-15 agents running,
  your answers are the scarcest thing in the system, and the advice everywhere is: unblock before anything else,
  longest wait first, one status view.
- Cost: about 2 h of board work (an "ask" card with no task behind it, sorted oldest first).

**3. Bookkeeping by command instead of by hand.**
- What changes: one small script, three commands. `start` (marks tasks taken, adds the agent to the board),
  `done` (moves the task to ARCHIVE.md, clears the mark, closes the line if it was the last task, updates the
  board), `check` (finds badly formed task lines, tags naming a line that doesn't exist, taken marks with no agent).
- Why: "what is running" is kept in three hand-edited places (handoff, board-live.json, the taking marks) and they
  drift. Today's sweeps closed tasks that were already fixed or no longer true, and folded 7 duplicates: closing is
  leaking. 135 of last week's 550 commits were pure bookkeeping, each one an Opus orchestrator editing a 110 KB file.
  T-3395, one of only two P1s, does not follow the task format. This is the useful half of what beads offers,
  without moving anything.
- Cost: 3-4 agent hours, then a line in CLAUDE.md. Saves orchestrator usage every day after.

**4. The handoff file goes back to being a short state page.**
- What changes: at each takeover the new orchestrator rewrites the file to current facts and moves the old text to a
  dated file in notes/archive/. Timestamped diary entries go in a separate log nobody has to read. The `check`
  command above warns when it passes 80 lines.
- Why: the rule says about 60 lines. It is 190 lines now and has been 140-190 for most of the week. Its "State"
  section says 8800 runs 6feec4b4 while the top says 404768f5, and one block is headed "Stale below". A new
  orchestrator has to work out which half to believe, and every agent that reads it pays for the old half.
- Cost: under 1 h (two skill edits), then a few minutes per takeover.

**5. Treat Someday as a parking lot, and prune on a schedule.**
- What changes: the number you watch becomes "open P1 + P2" (56 today). P3 and Someday (289) stay on file but the
  board hides them by default. Once a week an agent lists P3 tasks that are done, untrue, duplicate, or older than
  about four weeks with no player asking, and you tick closes on the board. Agents search TASKS.md before filing.
- Why: open tasks went from 144 to 438 in four weeks, because agents file follow-ups faster than anyone closes them.
  Everyone running agents reports the same thing. Today's push took it to 346, but the pile will regrow without a
  standing sweep. This reverses your 2026-10-26 rule that Someday tasks count as open, so it is your call.
- Cost: about 1 h of board work, plus one Sonnet agent for 20 minutes a week.

**6. Shorter agent lives, to save usage.**
- What changes: an agent finishes its batch and ends. A follow-up goes back to the same agent only when it is small
  and about the code it just touched. Otherwise a fresh agent starts from the notes. The orchestrator hands over at
  about 300k tokens in the daytime instead of 500k.
- Why: in the last full orchestrator session, roughly two thirds of all usage was agents re-reading their own long
  conversations on every step. The orchestrator itself was about a fifth of the total, almost all of it re-reading.
  Five agents went past 320k tokens. A fresh agent pays once to learn the code. A long one pays on every step.
- Cost: nothing to build. Slightly more time spent on briefs and notes. My guess is 15-25% less usage for the same
  work, from one session's figures, so try it for a week and compare.

**7. Small fixes.**
- docs/orchestrator.md still says worktrees are "used sparingly, two or three at most". Practice is one per code
  agent, six or more at once, and that is the better practice. Update the doc.
- Trees copy four game JSON files from the main tree and the orchestrator must remember to restore them before
  landing. Fix that in agent-tree.mjs. Same for any trap in the doc's "Traps" list that has bitten twice.
- P1 means "now", but neither P1 (T-2912 security follow-through, T-3395 corrupted-save detection) has an agent.
  Start them or make them P2.
- Committing the root serve.py was refused by the permission check three times today although you approved it.
  It needs a permission rule in .claude/settings.json.

## What I would not do

- Move to beads, Backlog.md, Linear or GitHub Projects. No gain that the board doesn't already give.
- Lower the number of agents. Others cap at 2-5 because a person reads every change. You don't, so the limits here
  are your answers (2) and the quality of checks (1), not the count.
- Let agents coordinate with each other without an orchestrator. The public examples of that are showcase projects
  with huge test suites and five-figure bills.

## Your calls

- Recommendation 1: try a checker agent on risky landings for a week?
- Recommendation 5: may Someday and P3 stop counting as "open", with a weekly close list on the board?
- Recommendation 6: orchestrator hands over at 300k in the daytime instead of 500k?
- 2, 3, 4 and 7 need no decision from you beyond a yes to spend about 8 agent hours on them.
