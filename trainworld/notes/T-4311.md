# T-4311: the review's findings on track runs sent at their clicks (agent fixes22, 2026-11-25)

Tree fixes22 (master d491a5f8b). Not committed. The review: artifacts/trainworld/gemini/batch22/review.md (review22, of
T-4214 stages D and E, notes/T-4214.md "Stages D and E").

**For Anita**
- Four holes in how a track run's clicks wait were real; all four are fixed. None of it was ever published (stages D-E
  aren't out yet), so there's no changelog item and no new text.
- A click on a segment of the run that the game hasn't answered yet now waits in line with the other clicks (with the
  spinner, at most 5 s, then it goes anyway), for taps and the touch bar's confirm too. Before, it could wait over and
  over, and later clicks could jump ahead of it.
- Ctrl+Z or redo while drawing a run ends the run at once (as it did before stage D, only sooner). Backspace on a
  segment that turned out to be refused now leaves the run where it was instead of ending it.

## The findings, checked against the code

**1. The unanswered segments' wait (`flying`) never ends: real, fixed.** `trackClick` waited up to 3 s, then called
itself, found the segment still unanswered and waited again, so the "3 s" was "until the answer". The wait sat outside
the click queue (it only held `clicksOut`), so after the queue's 5 s backstop the clicks behind it went ahead of it, and
a double click's second click, Enter or Backspace went past it at once. `flying` was never cleared by reset.
The lost answer the review gives as the trigger can't happen mid-game: `clock.worker.ts` 747 (`if (!api) return`) is
reached only before the first game opens (`api` is set at init, and a panic swaps the model in the same call), and the
client starts its worker again only while no game is in (`watchStart` stops once a world is in). Every edit gets an
answer: refused for another game, `failAnswer` after an error or panic, refused while the model is down.
Fix: the wait is now the click queue's own (map/toolWait.ts `mapBehind`): a track click on the run's own track the
tools' map lacks (`Tools.ownTrackOut`: a segment sent and unanswered, or a held one, T-2404) waits like any waiting
click: in order, with the spinner, dropped on Escape or a load, carried out after 5 s whatever happens. `trackClick`'s
own waits (`flyingLanded`, `heldLanded`) are gone. `flying` is cleared at reset (a new game or load resets the run
through the tool switch), and each answer runs the queue.

**2. Touch confirm and tap skip the wait; routes with no ghost have no `flying` entry: real, fixed.** Taps and the
touch bar's confirm already went through `waitClick` with their map spot, so moving the wait into the queue covers
them; a carried-out tap or confirm re-snaps (`move`) before it acts. A real or street route with no ghost of its own
now gets its line through its route's points, and any segment with no ghost a straight line from its start to its end
(`sentLine`), so every onward segment has an entry.

**3. Undo mid-run leaves the run on a gone end: real, fixed.** Ctrl+Z (or the blueprint panel's undo/redo) went at
once and the run still started from `endOf` the undone segment; before its answer nothing noticed. Now an undo or redo
the run didn't send ends the run at its send (game/pending.ts: `pendingSent` sees `asRun`'s tag is not set and calls
`breakRun`; map/tools.ts `dropRun` resets and bumps `run` so the segments' late answers don't put the run back).
world.ts `edit()` now keeps the run tag across an undo's waits (it awaited before sending, losing `asRun`'s tag, so
Backspace's own undo could have counted as foreign). With no segment ever sent from an undone edit's end, the LIFO node
reuse can't be reached. The worker's `ends` map is not cleared on undo or redo on purpose: Backspace takes back only the
newest segment and the run goes on from the end of the one before, which the worker still holds; clearing would refuse
it. On a panic the model is replaced: `forgetEnds()` in clockPanic.ts `replaceModel`, and the page's "recovered" calls
`breakRun` (the rebuild also opens a new game number, so older edits are refused before `ends` is read anyway).

**4. Backspace on a refused last segment ends the run: real, fixed.** `takeBackSegment` popped the chain before the
answer and reset the run on a refused undo. Now it pops only when the undo is taken: a refused undo (the segment it
meant was refused, so nothing came off) leaves the run where that refusal put it. A run reset or taken back past the
segment meanwhile stays as it is (before, the answer brought the run back even after Escape). Backspace is also ignored
while a click is being carried out.

**Cousins fixed on the way**: Enter and the touch bar's stop end a run in click order (`inClickOrder`), after the clicks
still waiting, whose segments belong to it; before, a waiting click then started a new run.

**Left**: a right click on the map ends the run at once (it is Escape by its doc, but Escape drops waiting clicks and
the right click neither drops nor orders them; older than T-4214). Backspace takes back the newest undoable edit, so a
panel edit made mid-run would be taken back in the segment's place (T-418, not checked whether any panel edit is
undoable there).

## Game run (new New York game, sandbox, 2 cores; scratch fixes22/run.js)

The worker's messages were held at the page (`c.arrive` buffered, then let in in order) to make answers as late as on a
busy big save.
- Touch: segments A and B sent by taps and confirms, their answers held; a tap on A's middle waited (1 click waiting,
  2 segments unanswered). Once the 9 held messages were let in: nothing waiting, the tap's point snapped onto A (hover
  "edge"), and its confirm placed a segment from B's end joining A: a node at A's middle with 3 edges.
- Backspace: A2 (#18) answered; B2 (#21, from endOf#18) made refused (its end named as a node no model has), Backspace
  before its answer sent undo #23 after 21. After the answers (B2 refused NoSuchNode, the undo refused): the run on at
  A2's end, chain 1. The next click went from endOf#18 and was built: A2's end node has 2 edges, nothing at B2's end.
- Undo: A3 (#40) answered, B3 (#43, from endOf#40) out, Ctrl+Z sent undo #44 after 43: at that moment the run was ended
  (no start, run 3 -> 4). A click right after waited for the edits out; once in (B3 placed, then undone) it started a
  new run from open ground. No segment was sent from endOf#43; A3's end has 1 edge, nothing at B3's end.
- No page errors.
