# T-715: money on loading a save

**Cause.** Opening a game from the saves panel (or a file) while a game with a later clock was open.
On "loaded" the main thread first held its clock (`holdForGameLoad`), which sent a "clock" message
still carrying the old game's time, then set the new time. The worker settles at the top of every
message, so the second message settled the just-loaded game from its own clock to the old game's:
the gap's running costs, with no fares (a load clears the income), at most a year at once. Money time
never goes back, so the cash then stood still until the clock reached the old game's time. Each such
load charged the gap again. The start menu and `?continue=1` paths were not affected (their only stale
clock is the page's start time, earlier than any save).

**Her bodega save** (`anitabuilder-nyc-day-5.save`, Downloads, 13:43): clock day 5.08, cash
-13,123 US$M, ledger days 44-73 with 205.2 running and no fares each, every hour charged at exactly
twice the network's rate (5.67 / 4.35 / 2.28 an hour by level): two loads each charged day 5.08 to
day 73.4 (her other game's clock), about 7,009 each. On today's tree the load repair gives
**+893.6 US$M**, the cash before those two loads. Fares she would have earned in the stuck stretch
are not invented.

**Fix.** `loaded` carries a load count (`game`); every clock message carries the count the main thread
had seen, and the worker ignores one from before its latest load. A load drops ledger entries after
the save's clock and returns their net (`unsettleAfter`). The main thread also resends income,
region shares and points after a load: they were deduplicated against the last game's, so reopening
the same network ran with no fares. The worker now also clears per-line income on a load (region
fares were being paid from the previous game's lines).

Check: `checks/t715-load-money.mjs` (fails on d9fe075: 6000 to 3096 to 194 over two switches, money
frozen; passes after).
