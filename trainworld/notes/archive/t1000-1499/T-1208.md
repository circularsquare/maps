# T-1208 and T-1210: demand's sums off the main thread

Done 2026-10-26 (agent t1208). Follows T-1200's ranking (notes/T-1200.md, items 3 and 4).

## What changed

- **`workers/demandSums.ts`** (new): pure functions, no WASM. A solve's views of the four kinds of
  day (`dayViews`: what `dayResult`, `dayDemand`, `purposeDemand` and `dayCorridors` in
  demandClient did), a bubble selection's commuters (`flowsBody`, the tail of `flowsAt`), its longer
  trips (`selectionFlows`) and a station's (`stationFlows`, with `signature` and `addIntercity`), and
  the packing of the day views (`packDays` / `unpackDays`).
- **`workers/demandSums.worker.ts`** (new): runs those on messages from demandClient; started on
  first use. For a selection it also deals the far end for the display under every filter
  (`farChunks.dealtCells`, the zone's cells sent once and their curve rank kept per zone).
- **`workers/demandClient.ts`**: `publish`, `publishNewLines` and `publishCluster` ask the sums
  worker for the views (`daysOf`) and apply them through `inOrder`, a promise chain, so views land in
  the order published; the final-round bookkeeping (`demandUpdating`, cache write, timings) and
  `progress`/`checkHold` run when the views are applied. Corridor tables stay on the main thread
  (`corridorsOf` attaches them by key); bare zones join the cities there as before.
  `intercitySelectionAt`, `intercityStationAt` and `flowsAt` hand the workers' answers over
  (transferred) and get the finished object back. If the sums worker fails to start or crashes,
  `inSums` runs the same functions on the main thread (`sumsBroken`).
- **`game/farChunks.ts`**: `dealtCells` (the dealing, usable in a worker) and `primeDealt`, which
  `flowsAt` uses to fill `dealFlows`' memo, so the map's `dealFlows` calls only look it up.
  `dealFlows` still deals on the main thread when nothing was primed.

No WASM interface change; the Rust crate is untouched.

## Why packed

The first version posted the views as objects. Reading that structured clone on the main thread
(tens of thousands of maps, objects and small Float32Arrays) took 620-950 ms at 6x, worse than
adding them up there (edits' apply task 1,099-1,456 ms). The views now travel as three flat arrays
(`f32` for the Float32Arrays, `f64` for every double, `idx` for station order) plus small
skeletons, and `unpackDays` rebuilds the same maps; the Float32Arrays are views into the one
buffer (a `slice` each cost about as much as the rest of the unpacking).

city view, the regional figures and corridors, versions left out), and for the four busiest stations
`intercityStation` (as a complex and alone) and for three bubble selections `flows`, its dealt far
end under "all" and "work", and `intercitySelection` at both ends. The real New York save and a new
game with three built lines (Eighth, Flatbush, Canarsie), each with two demand workers and with one,
old against new on the same frozen packs: the JSON (404 MB and 278 MB) is byte-identical in all
four cases (sha-256 prefixes 939afe146b2fa62a / 3aa5879b58c0532c with two workers, 07a2740f4a43cfe2
/ 0188ad46168a0da0 with one).

Two things found on the way: a new game's bubble `intercitySelection` differs between two runs of
the same code (its days, stations and flows do not), presumably which market packs had opened by
then; and between runs on live packs the New York figures moved, from the data batch's pack writes.
Neither is from this change.
