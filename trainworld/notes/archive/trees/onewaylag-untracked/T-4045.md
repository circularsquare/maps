# T-4045 one-way stations make adding stops slow (onewaylag2, 2026-11-22)

Toy net (native, agent profile): 13 sections, 41 stops, 2 one-way platforms per section, with a faster bypass track
beside the legs (the case that makes route_legs run take_legs). Without the bypass it is cheap (add 23 ms, tiers 74 ms
over all 41 clicks), so one-way stations alone are fine.

Cause found: with a bypass, stop_tiers (run after each click, per station x slot) and add_stop go through
route_legs_t -> take_legs, which call Network::find_path_side without the HopMemo. About 30,000 searches per
stop_tiers call for 1,200 distinct hops (25x repeats), growing with stop count; each search allocates 2*edges vectors,
so on a big net it is far worse than the toy's 4 us.

Fix in tree: thread-local search memo (SearchMemo guard in net/paths.rs) held over stop_tiers, insert_stop and
add_stop's search; find_path_side answers repeats from it. Same answers (tests: 731 pass).
Timing, 13 sections bypass, 41 clicks: tiers 1894 ms -> 805 ms (2.3x); add 391 -> 346 ms (noise). No-bypass: 74 -> 52.

Not solved: remaining ~20 ms/click of tiers is not path searching (route_legs/match_run per station). The player's
"40 minutes" is not reproduced here; real net (NYC, nyc.net) lines time at 0.1 ms. Suspects not checked: the
Op::Line rebuild after each edit (trains, trip calculation) with many one-way stops, and app-side work.
