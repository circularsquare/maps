# T-302 and T-400: zone files on demand (2026-10-15)

Rules now in docs/zones.md 6. This note has the measurements and the choices behind them.

## Startup requests, before and after

Request log of every `packs/` request on the dev server (my own Vite, 6102), one run each; script
was `scratchpad/t302/reqlog.mjs` (a new game `?new=1`, then the real save imported, autosaved and
reloaded). "World" is ms from navigation to the track drawn, one run on a dev server: noise.

At 200 zones: water before about 400 requests and 50 MB in front of every load; after, the same as
now (the view's zones, or the zones the save's track reaches), whatever the count. Boundaries are
unchanged (T-404): 200 requests, 15-20 MB. Place lists were never at startup; a first search now
fetches the lists of the zones whose boxes lie within 30 km of the view's centre instead of every zone's (1.3 MB now,
15-30 MB at 200), widening four zones at a time only when a search finds fewer than five results.
A query with fewer than five matches anywhere ("Montmartre" from New York: two) still ends up
fetching every list, four at a time; only searches that find enough nearby stop early. A search
index of place names in one small file would fix that if it matters at 200 zones.
Outlines: one GeoJSON source and line layer instead of one per zone (18 now, 200 then).

## Choices

- **Wait and work out again**, not a refusal or a hold on the whole worker: an edit or preview that
  makes track is worked out as a preview first; if its geometry (the sampled polyline, not the
  control points, so curves that bulge are covered) comes within 2 km of a zone whose mask is not
  in, the worker installs the mask and works it out again. The worker's message queue is serial, so
  nothing else runs against a network missing that mask meanwhile. Checked: on a new game viewed at
  New York, routes across water at Paris, Shanghai, Mumbai and London sent with no view near them
  are refused with GroundOverWater, tunnels accepted (`scratchpad/t302/gate.mjs`).
- **Loaded saves**: the network is opened, its nodes and sampled edges tested against the boxes, and
  if a mask is missing the worker installs it over the empty network and opens the save again (a
  mask installed over a loaded network reworks every edge). No zone list in the save header: the
  geometry is the source of truth and the test is cheap.
- **Each install reworks the loaded network** (`rebuild_water` then `reload`): measured on the real
  save, a first edit in a zone with no mask yet took 0.28-0.32 s against 0.07 s for the next one, so
  about 0.2 s an install. Fine once per zone; no Rust change. If world tours make it matter, have
  `add_pack_water` skip the reload when no node or edge lies within the raster.
- **Boxes in the registry** (`pipeline/zone_boxes.py`): the union of boundary and water extent, so a
  test against the box never misses mask pixels. New York's box is large (its mask reaches past
  Philadelphia and Hartford), so a view at New York also fetches Philadelphia's mask.
- The `ready` message no longer carries the first pack's population and jobs (the placeholder
  WorldView city never showed them).
