## T-174: the market opens without its zone pairs

**What it did.** `IntercityApi::new` grouped the 229,885 sites into 2,913 zones, then made two
passes over all 4.2M zone pairs: the first summed each zone's row normaliser (attraction times
decay over every other zone), the second built the kept pairs (2,263,260 directed pairs over
0.01 trips a day) with their trips, drive time and corridor, and indexed them by each end.
1.0 s natively, 1.2-1.6 s in each Chrome worker, and about 80 MB of each worker's WASM memory
(pairs at 24 bytes, two index lists, a rail figure per pair per period). Both grow with the
square of the zones.

**What it does now.** Two things, neither of which fixes the market's design:

1. The figures that need every pair are computed offline by the same Rust code into the pack's
   `derived` block: each zone's normaliser, the day's trips, each corridor's trips, the pair
   count (`intercity::derive`, run natively by `sim/src/bin/market_pack.rs`, which
   `pipeline/intercity.py` calls after writing the sites; `--derive` reruns only that step on the
   pack as it is, 0.46 s). Floats are stored as their bit patterns (u64), because serde_json's
   default parser can be one unit in the last place off and the opening should be exact.
2. `set_network` builds zone pairs only between zones some station serves (a zone whose
   population or jobs have a station within walking reach). Any other pair has no access at one
   end, so no rail trip and nothing to assign. Pairs keep the whole list's order (lower zone,
   then higher), so every rail sum adds the same numbers in the same order. Rebuilt only when
   the served set changes. The real NYC save serves 127,646 directed pairs (5.6%).

All-mode figures still cover the whole market: `summary` and `corridor_summary` read the block,
and `selection_flows` computes each selected zone's row (every other zone, partner ascending:
the order the old per-zone index had) when asked.

**Staleness.** The block records `FORMULA` (a string naming the decay, the pair formula, the
pruning and the drive time), the decay at 50, 75, 200 and 900 km, and a checksum of the zones
(their x, y, people and attraction). If any disagrees, or the block is missing or unreadable, the
game derives it at opening exactly as before T-174 (slow, same result) and the worker logs a
warning. So the market's formula can change freely: bump `FORMULA` and run
`python pipeline/intercity.py --derive`. The probe compares to 1e-9, because the pipeline's exp
and powf are the platform's and the browser's are Rust's own (they differ in the last bits).

**Same results.** `cargo test --release --features demand intercity_real_network_outputs --
--ignored --nocapture` solves the market alone on the real New York network plus one
Philadelphia line (five periods, free flow and three crowding rounds) and dumps or compares 62
outputs (summaries, corridors, loads, boardings, entries, exits, load of crush, nine stations'
flows, twelve selections across all ten markets). Before T-174 against after, with the block and
without: every value identical (Python's exact comparison; the only text difference is -0.0 for
empty corridors, where the old sum started at -0.0). In the production WASM
(`checks/t174-market-check.mjs`, writes `../../artifacts/trainworld/notes-outputs/T-174-market-check.json`): opening 145 ms with the block
and 871 ms deriving it; the f32 outputs differ by at most 1.2e-7 relative (one or two f32 units:
the native-derived normalisers against the WASM-derived ones), the day's trips identical.
Unit tests: `derived_block_from_the_pack_gives_the_same_market` (block against derived on a
five-market fixture with two unserved zones: identical outputs, served pairs are the whole list's
subset in order, stale and unreadable blocks fall back, pairs follow network changes), and the
older market tests adapted to `all_pairs()`.

**Pack.** `data/packs/intercity.json` now carries the block (8.16 -> 8.22 MB). Its sites were not
rebuilt (the city packs have changed since; rebuilding would mix that change into this one). The
previous file is in `data/work/pre-T174/intercity.json` (gitignored; delete when no longer
needed). Old packs without a block still open (derived at opening).

## T-173: the slow mode

**What it is.** When the five solving workers open New York's everyday layer at the same time
while its code is still the browser's baseline (Liftoff) code, each takes 7-8 s instead of
1.3-1.8 s. Measured on a new game, opening times by pool size (`?demandWorkers=N`): 1 worker
1.6-1.8 s, 3 workers 4.1-4.2 s each, 5 workers 6.8-7.5 s each, as if they shared one core. With
Chrome's `--js-flags=--no-wasm-dynamic-tiering` (everything optimised up front) five workers take
2.1 s each, in every load. Not changed by `--no-wasm-native-module-cache-enabled` (each worker its
own compiled module), `--efficiency-mode=false`, or a 13x lower `--wasm-tiering-budget`. So V8's
dynamic tier-up of these functions stalls when several workers run them in baseline code at
once; why, inside V8, is not known. With the market now cheap, it happened in most page loads,
first ones included (T-172 saw it in a third, only on later loads; the market's own long opening
before New York's probably changed the timing).

**Fix.** Worker 0 opens a small synthetic everyday layer before reporting ready
(`sim/src/demand/warm.rs` `everyday_warm_up(150)`: a 150 x 150 grid of cells 400 m apart, 900
zones, the errand and social purposes; about 150 ms in baseline code, 90 ms after). The client
holds the other solving workers' city packs until worker 0 is ready (`held` in
`workers/demandClient.ts`); the aux worker and the market are not held. Compiled code is shared
by a page's workers, so all five then open on optimised code. Worker 0 is ready 0.36-0.66 s after
navigation, about when New York has downloaded (0.3-0.7 s), so the hold costs little. Results above: 10 of
10 loads fast; in the same build with `?perfOff=stagger` (no warm-up, no hold) 7 of 10 slow.

Tried first: holding the others until worker 0 had opened New York itself. That avoids the slow
mode too, but the others then open after it (clock 4.2-4.9 s on a new game against 2.7-3.1 s).

## How it scales to 30 cities (about 3x the sites and zones)

- **Market opening**: linear in sites now: parse and group 8.2 MB of JSON, 0.09 s natively and
  0.1-0.4 s in each Chrome worker today, so about 0.3-1.2 s at 3x, in parallel. Before T-174 it
  would have been about 9 s per worker and about 20M directed pairs (some 500 MB of pairs per
  worker: it would not have fitted). The block grows linearly (60 kB now). The offline derive
  grows with the square (0.46 s now, about 4 s at 3x zones, once per pipeline run).
- **Pairs** depend on the zones the network serves, not on the cities registered.
- **Download**: the market JSON grows linearly (8.2 MB now, about 25 MB at 3x; it compresses).
  A binary site format would roughly halve it; not done (performance is adequate otherwise).
- **Everyday openings**: the warm-up is the same whatever the cities. Each city with construction
  opens its everyday layer in every worker in parallel on optimised code.
- **Estimate**: new game about 3-4 s to the clock (today's 2.7-3.1 s plus the larger market
  parse); before T-172 it was 12-20 s with 9 cities.
