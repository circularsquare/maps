# T-229: changing a line's train count lags

Anita (2026-10-13): "theres a bit of lag (preexisting) when changing the number of trains on a
line. we should make this feel more responsive / not freeze stuff up."

## Where the time went (real New York save, subway G, clock running, `notes/t229-browser.mjs`)

Before, per click on the high-demand stepper (`../../artifacts/trainworld/notes-outputs/t229-browser-before.json`):

| Step | ms |
|---|---|
| Clock worker: the edit (`apply`: the whole-line fleet's headway solve, eras) | 13-27 |
| Building the state (`buildState`) | 8-10 |
| Building the renderer's buffers (`networkFromState`) for the whole network | 39-49 |
| The hour's trips (both hours) | about 1 |
| The boarding account's hour (the edited line worked out again) | 8-9 |
| Worker total, before the answer | 83-89 |
| Main thread: new world and renderer upload | 11-17 |
| Click to the stepper's number changing | 128-155 |
| Demand's new result | about 11 s (other workers; nothing blocked) |

No main-thread task over 50 ms in the 14 s after a click, and frames stayed at 16.7 ms (worst
18-19 ms) through demand's re-solve in headless Chrome. The stepper showed the world's count, so
it changed only when the worker's state arrived, and a second click before then counted from the
old figure: two quick clicks added one train.

## What changed

- `game/world.ts`: `pendingTrains` (the counts asked for, shown by the stepper at once),
  `stepTrainCount` (steps from what the stepper shows), and per line one edit in flight: clicks
  meanwhile are folded into one edit sent when it lands, so fast clicking never queues an edit
  (and a demand snapshot) per click. A refused edit (money) puts the stepper back.
- Clock worker: a train count sends a service-only state (`ClockState.service`): no geometry
  moved, so `networkFromState` is skipped and the main thread keeps its buffers, taking only the
  new phase tables and profile meta (`renderer.setService`).
- `?debug=1`: `tw.client.editLog` has each edit's worker time by step and the main thread's time
  for its state.

After (`../../artifacts/trainworld/notes-outputs/t229-browser-after.json`): worker 36-48 ms, main thread 6-10 ms, click to the number
changing 32-51 ms (most of it Playwright's click; the number is set before the edit is sent), two
quick clicks add two trains, frames 16.7 ms (worst 18 ms). Screenshot
`../artifacts/trainworld/T-229-after.png`.

## Not changed

- Demand's re-solve (about 11 s on New York) runs in its own workers; figures moving during it
  are T-232's.
- The headway column follows the worker's answer (a few tens of ms later).
