# T-2071 (with T-1891): the page out of memory after a line's removal in Jakarta

Agent t2071, 2026-11-03. Main tree, Vite 6160. Scripts in the agent's scratchpad (`repro.mjs`, `hash.mjs`,
`summ.mjs`); logs and JSON in `artifacts/trainworld/t2071/`.

## Cause

Not the zone's size, not a leak, not the focus pool: **an endless loop in the demand worker's JS**.
`toWhole` (demand.worker.ts, T-1735's market window) steps through a population's loads three blocks
of `m` route nodes at a time, `at += 3 * m`. When the view it maps through has no route nodes (`m = 0`),
the stride is zero and the loop never ends, pushing an empty `Float32Array` each turn until the
worker's JS heap fills the renderer and Chrome kills it (0xE0000008).

It runs on the local solve after an edit (T-1733) when the market's window is on (the edit's longest
changed run at least 20 minutes, T-1735), through either of two maps with no route nodes:
- **The new network's market view** (`marketBlocks`): removing the last line of a cluster. The new
  network has no route nodes, so each block is a zero-length array: a JS-heap object each turn, and the
  renderer dies at the heap's cap (about 4 GB of JS heap, 5.4-5.9 GB private bytes, 15-20 s in).
- **The old network's market nodes** (`less`, `e.market`): **the first line on stations already built**
  (a station-only network, solved, then a line on them). The new network has route nodes, so each block
  is a real `Float32Array(3N)` whose memory sits outside the JS heap: no crash, the renderer just grows
  (15.7 GB at 180 s and climbing) until an array allocation fails in the worker.

Jakarta's gate line (12 stops, about 20 km in deep tunnel) is long enough for the window; Surabaya's and
Probolinggo's test lines are not, so their removals passed. Nothing depends on the zone's size: any
zone with a market pack hits it with a line of 20 minutes or more. T-925's 90-minute hang in pot's line
removal (2026-10-30, the day after T-1735 landed) was very likely the same loop.

**T-1891** (Anita's new New York game, one line, Chrome at 16 GB, "Demand ran out of memory"): the second
path matches it. Stations placed, a solve, then a 20-minute line on them: the renderer climbs to 16 GB,
and an `ArrayBuffer` allocation failing in the worker is a `failed` message whose text ("Array buffer
allocation failed") the alert counts as memory, then as now (`loading.ts`). Not taken to the failure
itself here (stopped at 15.7 GB on Anita's machine), and her save is not needed any more.

The focus pool (T-2045) plays no part: it runs only during a game load, and these are new games; the
stacks show no focus worker. `?perfOff=focus` was not run for that reason.

Found with a CDP client beside Playwright (`--remote-debugging-port`): every worker's
`Runtime.getHeapUsage` each 2 s, and a `Debugger.pause` of the demand worker once its heap passed
600 MB: every stack was `toWhole < marketBlocks < run`.

## Measurements

Headless Chrome, `?debug=1&new=1&mode=sandbox&opened=all&paused=1&demandWorkers=1` (the gate's page; the
cores ledger granted 1 core), jump to Jakarta, the gate's line built (`jak.row.json`), its final, 10 s,
then `removeLine`. All Chrome processes' private bytes summed; the renderer holds the page and its
workers.

| Case | Before (renderer, peak) | After |
|---|---|---|
| line built, removed (`repro.mjs`; base1, gc1, cdp1, cdp2, fix1) | 5.3-5.4 GB renderer, 5.8-5.9 GB all Chrome; demand worker's JS heap 25 MB to 3.7 GB; renderer gone 15-20 s after the removal, 4 of 4 | 2.14 GB all Chrome (1.6 GB renderer, as before the removal); worker heap 29 MB; final without the line in 10 s |
| stations, a solve, then the line (`hash.mjs` stations,line) | 15.7 GB renderer at 180 s, still growing, no final | 1.7 GB; final in 22 s; its removal 1.5 GB, final |
| line built, then trimmed at both ends (window with route nodes) | 1.66 GB | 1.66-1.70 GB |

The worker's WASM stayed 395 MB (solving) and 65 MB (aux) throughout: the WASM heaps play no part.

**To the bit** (`hash.mjs`: SHA-256 of the final view less its version, each of its fields, and every
zone's city view, after each step). The fix changes only the case that never returned (a zero-length
map), so every figure that completed before is unchanged; checked on the window's normal path:

| Step | Before | After (run 2) |
|---|---|---|
| line built | view 0d358e5b0013bd9c, cities 639a3ec5b341d700 | the same |
| trimmed (the window solved, 52 zones' pairs) | view 463d9301b23e87f3, cities 9b053fb64b7bb3a1, 400,602 rail trips | the same |

One other after-fix run gave a different view hash on both steps (its city views and rail trips the
same); two runs of the same code differ that way too, so the view carries something load-timing
dependent, as T-2045 met.

Smoke on 6160: passed, 22 checks, the real save 11,297,375 rail trips a day. Typecheck passes.

## Fix

`toWhole` returns no blocks when its map has no route nodes (`app/src/workers/demand.worker.ts`). With
no route nodes on the new side, nothing rides the window's pairs. With none on the old side (the first
line on built stations), `less` finds no blocks and the period's local result leaves the window out, as
for an edit under 20 minutes: the market's riders on the new line come with the whole solve a few
seconds later, which replaces everything as before. The only zero-stride loop in the app; the other
stride loops step by constants.
