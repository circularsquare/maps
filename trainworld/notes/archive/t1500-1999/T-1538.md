# T-1538 and T-1539: a cheaper first answer, and the cached result before the network

Follow-ups to T-1533 (notes/T-1533.md). Tree t1538. Spec: docs/demand-runtime.md "The zone in view
first" (one period first), docs/architecture.md "Demand cache" (ahead of the network).

## Where the rough solve's time went

Native, New York's pack on its real network (`nyc_real_track.json`), one core, busy machine:

| step | ms |
|---|---|
| open the commutes / the everyday layer | 480-520 / 790-850 |
| set the network: commutes / everyday | 530-590 / 230-270 |
| a period's free flow, commutes | 2,000-2,550 (skims 600-800, mode choice 1,300-1,700, the rest assignment) |
| a period's free flow, everyday | 900-1,200 |

In the browser (headless, pool of 3, the same load) a rough solve's set-up was 0.9-1.2 s a worker and a
period's free flow 3.6-5.6 s. The pool is at most 3 solving workers (`poolSize`), so two workers hold
two periods each and the published round waits for both: about 1 s + 2 x 5 s. That second period
was the cheapest thing to drop.

What was looked at and not done:
- **The coarse level** (T-1206): the rough solve would need a second, coarse copy of the zone in every
  worker (opening 1-1.5 s, 60 MB a worker for New York) for a period 15-20% shorter.
- **Bigger commute chunks for the rough solve only**: chunks of 5 and 20 trips cut mode choice from
  1.6 s to 0.6-0.9 s a period, but skims and the everyday layer stay, so a period 20-30% shorter, and
  changing the chunk sets the population's network up again. Not worth it beside one period.
- **Fewer rounds**: the rough solve already shows its free-flow round.
- **One period split over the workers** (each worker the same period, a third of the origins): about
  3.5 s a worker instead of 5.6, but it needs partial results summed on the page, a new message flow.
  A possible next step if 5 s on this machine matters.

## What changed (T-1538)

`DemandApi::estimate(from, to)` and `EverydayApi::estimate(from, to)`: period `to`'s first figures from
`from`'s free flow in about 10 ms: `to`'s own network and graph (its trains and run times), `from`'s
mode choice, loads and places scaled by the trips (commutes by the two periods' shares of the day,
the everyday layer purpose by purpose, its pairs' mode shares kept). The worker (`demand.worker.ts`
`estimate`):
- a rough solve's free flow is the worker's first period, the others estimated; it crowds on from
  them, and is never marked held, so a whole solve never reuses it;
- after an edit, the zone in view's cluster: its first period's free flow, the others estimated (the
  market solved, having no estimate), the preview sent (T-1533's new-line figures), then those
  periods solved, which replaces the estimates whole.
`?perfOff=estimate` turns it off. `estimate_keeps_trips_and_solve_replaces_it` (cargo test): the
estimate's trips are the period's, and a solve after it is a fresh solve's to the bit.

Accuracy on New York's real network (estimated / solved, the free-flow round):

| period, from the morning peak | commute rail | everyday rail | load on the segments |
|---|---|---|---|
| midday | 668,894 / 668,895 | 3,548,110 / 3,548,110 | +1.8% |
| evening peak | 1,426,973 / 1,426,973 | 2,795,848 / 2,795,848 | +2.2% |
| evening (medium trains) | 445,929 / 420,039 (+6%) | 927,415 / 879,885 (+5%) | +6.7% |
| night (low trains) | 312,150 / 242,022 (+29%) | 107,655 / 80,343 (+34%) | +19% |

Directions are the first period's (the morning's inbound load estimates the evening's), a short-lived
estimate's error. Final figures: the real save's final, and its final after a new line on Staten
Island, are the same to the bit with and without the estimates (every kind of day's lines,
stations, splits and zones; scratch script, two fresh browsers).

## What changed (T-1539)

What the China save waited on, zoomed out with a cached result (before; T-1533 measured 17-42 s on a
busier machine): the network from the clock worker (6-8 s here), then the cache read, and the camera,
which moved to the game only with its first state.

- **The result keyed by the save.** The clock worker sends `netAhead` before it works the network
  out: a SHA-256 of the save's track bytes (ids dense, so the same network gives the same bytes) and
  the header fields the snapshot reads (city, fares, fleets, mode). A cached result written for the
  network a load of the same inputs worked out also holds that snapshot (`ahead`), and a small
  pointer `ahead:<slot>` leads to it, so the page finds it by the key and shows it through the usual
  checks (packs, build, zones) on the stored network. The arriving network is compared with it
  (JSON of the service): the same one takes its place, a different one takes the result down and is
  looked up as on any load. A result is rewritten once to gain its network.
- **The camera and realms ahead.** A game opened from the menu fits its built stations as soon as
  the clock worker has read them (`stationsAhead`; the first state fits the same view), and before
  the first game's first state the realms shown are those of those stations, not every realm.
- Checks: `demandFinal`'s strict wait now skips a cached result (version 0), which before the
  network can be the only entry in the solve log; t328's tamper waits for its write to commit (a
  reload right after the put's success aborted it, and the stale cases failed with and without
  `perfOff=cacheAhead`).

`?perfOff=cacheAhead` turns all three off. On a game whose network comes quickly (New York, about 3
s) the network often wins the race and the cache shows on its arrival as before.

Known: the zone bubbles drawn before the clock worker's `opened` count every zone as opened, so some
turn to dots a second later (behind the loading card). One full run saw a page error "Invalid value
used as weak map key" (in the China part, after the Wuhan jump or the second pick); two more China
runs and one of every other case were clean. Not found.
