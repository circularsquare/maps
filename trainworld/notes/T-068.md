# T-068: Browser save slots and tab protection

Settings now lists independent named browser games, with Save to new slot, Open, Rename, and Delete (with an inline confirmation). Saving to a new slot copies the currently running game and makes that copy active; the previous game remains saved. New game replaces only the active slot after the existing confirmation. Export/import files remain available. The original autosave stays at IndexedDB key autosave and needs no migration; new keys are slot-UUID. Metadata name/city are optional so legacy records still load. Active selection is remembered per browser.

The clock worker holds a browser Web Lock per active slot. Only its owner writes autosaves. A second tab can read/play/export, but autosave is off and a persistent global notice offers the Saves pane. Different slots can save concurrently. Reload after closing the owner reads the latest committed bytes before becoming writable. Opening a slot obtains its lock before rereading bytes, avoiding a last-owner-write race. Rename/delete are refused while another tab owns the target. Active slots cannot be deleted.

Switching flushes the current writable game and waits for its transaction to commit. An unsaved read-only game cannot be discarded by opening another slot; save it into a new slot first (or export and reload). In-flight autosaves capture their target key, and all user command handling is serialized. Worker BroadcastChannel events refresh other tabs' slot metadata without polling. All byte encoding/compression stays in the worker. Failed writes preserve dirty state and a persistent warning, including quota failure when metadata still remains readable. A browser lacking Web Locks disables browser writes safely and keeps file export usable.
