# T-3773 A saved game that fails to load goes back to the menu

Agent failopen, 2026-11-19, tree `failopen`. From T-3772 cause B (notes/T-3772.md).

## What changed

Before: a game whose load threw inside the clock worker at start (damaged, a Rust panic, a failed allocation) kept
its slot but put the player in a new empty game ("Game N", a new slot and lease) with a notice: it read as a lost
save. A file, backup or Community view that failed fell back to opening the game the player came from.

Now both failure sites in the worker's init block (`clock.worker.ts`: the stored-slot catch and the incoming
file/backup/view catch) end the same way:

- the panic's model is replaced (`afterLoadPanic`, as before), the slot's bytes kept aside under
  `unreadable-<at>:<slot>` and a damaged slot marked with its good copy found (T-3395, as before; each now
  best-effort so a storage error can't turn this into the failure screen);
- `letGoSlot()` (slots.ts, new; the T-2703 failed-start code pulled out and used by both): lease released,
  `activeSlot` "", nothing unwritten or named. That is T-3734's existing `noLease` write block: autosave, leave and
  the cloud claim all refuse. No new flag, no new slot, no game started;
- the worker sends `openFailed` { from: slot | file | restore | view, slot, name, error, why } and returns (no
  `keep`/state/snapshot);
- the page (clockClient.ts) records it and reloads to the start menu (`toStartMenu`, the T-1196/T-3478 route:
  every game change is a reload). `pageWith({})` drops `slot`, `continue`, `paused`, so no loop.

The menu shows a notice once (the `.start-refused` line) and the saved game's card shows the reason in the
existing `.save-damaged` line (SlotFacts, so the in-game Saves panel too): "This save is damaged." for damage
(the existing mark takes precedence), "This save could not be opened (<panic>)." for a panic, and the device's
out-of-memory line (`loadText.outOfMemory*`) for a failed allocation, whether it came as a Rust panic or a JS error
(`openFailReason` in the worker, through `isMemoryFailure`): T-3772's "won't open on this device" versus
"damaged" point. Anything else: "Failed to load :( Try reloading the page." or the thrown reason. A card's line goes when
that slot next opens fine. A backup restore's failure is notice only: its card's top game is fine, and a line
there would say the wrong game is broken. A file or view has no card: notice only, with the reason.

Not changed: a real network's new game that fails still starts empty in its own new slot (a new game, nothing
lost; T-3478 territory). A load inside a running game (openOnAccount's newer account copy, after `writeFetched`
has already replaced the slot) is not an open from the menu: if it throws, the game in hand and the slot disagree.
**Worth a task** (no id given to me): make openOnAccount's in-place load failure keep the slot as it was.

## The record (for T-3774)

`localStorage["tw-open-failures"]`, written by the page (`game/openFailures.ts`, `readOpenFailures()`):

    { count: <every failed open in this browser>, recent: [ { at, from, slot?, name, error, why?, version } x <= 10,
      newest first ], unseen?: true }

`error` is a message key (`clockWorker.saveDamaged`, `clockWorker.savePanic` with `why`, `loadText.outOfMemory*`,
`loadText.failed`) or a thrown reason as text; `version` the build (`__TW_VERSION__`, "dev" on a dev server).
`count` never goes down; an entry for a slot is dropped when that slot opens fine.

## Strings

New: `startMenu.openFailed`: "{name} could not be opened." (Anita's wording, 2026-11-19; the menu's notice for a
saved game; context note added). Reused on the card and for files/backups: "This save is damaged.",
"This save could not be opened ({why}).", the `loadText` out-of-memory and "Failed to load" lines.

Changelog `failopen-1` (other, fix): "fixed a save that fails to open leaving you in a new empty game; you now go
back to the menu and the save is left as it was".
