# T-3689: transfer fare at the cap still pays

Agent xferfare, 2026-11-18. Investigation only, no code changed. Proposal for Anita at the end.

## Cause

Commutes are priced one way and ridden both ways. The commute layer runs mode choice, station choice and route
choice on the trip to work only (home station a -> work station t); the trips home are the same station pairs
reversed (`api.rs` header: "the trips home are the same station pairs reversed", `DemandApi::pass`, the `od`
transpose into `to_work x OD + to_home x OD^T`), assigned on the strategies towards the home station.

A rail trip may end with a walk between stations but never start with one: walking transfers run only from a route
node, having ridden (`build_graph`, "walking transfers: from each route node (having ridden) to the stations nearby",
300 m, `xfer_walk_m`, and every member of a station complex however far). So a commute can go out as "ride line B,
get off, walk 160 m to the station on line A that is nearer the job", with that A station as its work station and no
change. Its trip home starts at the A station, cannot walk back to B, and has to board A, ride to a stop near B and
change. Route choice on the way home sees the transfer fare but has no change-free way; mode choice never sees the
way home. So these riders keep riding whatever the transfer fare is, and income rises in step with it: the cap is
the only limit.

Evidence that it is these riders:
- The paying changes do not move with the fare: real save at transfer fare 100 and 1000 (curve units): rail trips
  8,614,060 / 8,614,079, changes 573,418 / 573,415; income x10 with the fare.
- They fall by period as the commutes' trips home do (`TO_HOME` = 0.02, 0.18, 0.58, 0.16, 0.06), not as trips to work
  (70% in the morning): walk-off network, weekday, 100 / 903 / 2,708 / 803 / 299 against 96 / 866 / 2,791 / 770 / 289
  for 4,812 x TO_HOME; real save (day kind 6) 5,774 / 63,333 / 171,651 / 50,347 / 16,324, within about 20% of
  307k x TO_HOME.
- In the walk-off network the paying changes are the walk itself, done backwards: "A west one stop to A's 2nd
  station, walk 160 m, board B" (2,685 a day) and its mirror (634), plus "A's 3rd station -> B's 2nd" (299, 209).
  These are trips home that started at the A station their trip to work walked to from B.
- The real save's biggest changes look like the same thing (consistent with it, mixed with the market's free
  changes there): "7 Times Sq -> M/D/F at 5 Av-Bryant Park" (2,649 + 2,228 + 1,653 a day, none the other way).
- A huge base fare (transfer 0) empties rail completely: the leak is specific to changes.
- The everyday layer prices each pair's rail share both ways (`EverydayApi::pass`, "each pair's rail share both
  ways"), so outings' trips home are priced; the leak is the commutes'.

Cousin bug: where the way home has no route at all, the trip is counted as a rail trip but never rides home. The
"control" network below has that: at fare 1000 (day kind 6) 302,487 rail trips against 298,081 boardings and 0
changes, so about 4,400 rail trips a day board nothing; the walk-off network has no such gap (312,929 boardings less
3,882 changes = 309,047 against 309,046 rail trips).

Ruled out on the way: income counting (`fare_extra_usd` = changes x fare, checked: small network $1 fare gives
fareX 32.7k against 33.0k changes); the regional market (its changes are free and pay nothing); the strategy search
(every alight-and-board in it carries `change_at`, fare included); the first-boarding take-back; ferry fans.

## Proposal (for Anita; fare rule, so hers)

Smallest fix in the "simple prices" spirit: **the transfer fare can't be more than the base fare** (a change never
costs more than starting a new trip). The stepper and `tidyTransfer` hold it to the base of the trip's curve (in the
same units, before a country's scale), and a loaded save is held the same way. Then the riders who can't avoid a
change on the way home pay at most one more base each, the same as a second trip would, and raising the transfer fare
past the base buys nothing. It bounds the leak without removing it: those riders still pay up to one base fare
their choice never saw. A base of 0 then means no transfer fare can be set. On the real save (base 0.1298 curve units, US$1.51) that is about 307k x $1.51 = $0.46M a day
of fare extra at most, against $3.57B today at the cap.

The bug under it (demand, not fares) is worth its own task: a trip can end with a walk to another station but not
start with one, so a commute's way home is not the mirror of its way out. Two fixes, either needs her word since it
changes demand: (a) let a trip start with the same walk from its station to a nearby one (or within a complex) as it
can end with, so the way home mirrors the way out; (b) price the commute on both ways (the mean of out and back costs
in mode choice). (a) is the more natural and also gives the stranded trips (cousin bug) their way home; both move ridership a
little everywhere and need the ceiling tests run.

Advisor called twice: first to rule out the count (curve units and the market's free changes) and run the
fare-insensitivity and base-fare controls; then to check the change pairs on the small network, the day kinds, the
everyday layer and the "control" network's stranded trips.

## Fix (agent farecap, 2026-11-18; Anita: "cap transfer fare at base fare")

The transfer fare is held to the base fare (curve's 0 km node); base 0 leaves none. `transferFare()` (fareCurve.ts) clamps at every
read: demand worker (`set_transfer_fare`, also min with the charged base after currency rounding), the demand cluster key,
the Money tab. `capTransfer()` brings the stored value down in clock.worker (load, "fares" edit so a lowered base takes it
down, "fareTransfer"). The stepper and typed field stop at the base. No Rust change (no cargo tests run).

Proof (play.mjs, Vite on 6183; 6182 was another tree's, see report):
- Small walk-off net (net3.json, new game, base 2 curve units there): transfer 0 -> income 96,230,179, rail 318,186;
  0.5 -> 97,087,629; transfer = base (2) -> 95,917,050, rail 311,254; attempted 1000 -> stored 2, income 95,917,050 (same).
  Before the fix, 1000 was 573M here.
- Real save: transfer = base 0.1298 -> income 4,628,526,897, rail 11,851,674; attempted 1000 -> stored 0.1298, identical.
  Before the fix 1000 was 384.6B.
The leak itself (T-3718) remains: those riders still pay up to one base fare their choice never saw.
