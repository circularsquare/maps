# T-3609 Double track splitting into two singles marked a flat junction

Agent splitflat, 2026-11-17. Tree `.tw-trees/splitflat` (branch tw/splitflat), not landed.

## What decides the mark

`capacity::junction_crosses` marks a junction where two moves in its move table cross (`Moves::at`: each
end's lane sits at its own slot by rank, the double's two lanes at -2/+2 m; a pair of moves crosses when
their order swaps). At a double splitting into two singles (all scenarios below, right- and left-hand):

- both singles one way, each on its own side (the outgoing one on the side of the outgoing track): no mark;
- either single two way (a terminus at its end, or pinned both ways) with the other two way or on the wrong
  side, or both one way the wrong way round: marked. These are real crossings (a train back from one
  single has to cross the other's track), as T-3137 decided for a terminus branch. Kept.

So the mark rule is sound; the wrong marks came from singles put on the wrong track while drawing.

## Causes found and fixed (`sim/src/track/wasm/draw.rs`)

1. **The pointer picked the far track at a split.** Zoomed in, a press on a junction node that is not a
   double's loose end always picks the double's track on the pointer's side (`tools.ts` `joinPoint`, no
   dead zone there). At J, a few px off centre on the far half, the second single joined the far track: it
   then runs that track's way, from the wrong side, and with the first single a terminus the junction was
   marked. Reproduced in the app (fixture below): far-half press plus a station at the first single's end
   gave a junction mark; the same press with both ends open gave both singles running north (nothing could
   go south). Fix in `end_joins`: where only single track is on the route's side of the node (a double
   splitting into singles) and the single has a side (`beside`), it takes the track on its own side
   whatever the pointer. Off a double that carries on, the pointer still picks (a far join there is a
   deliberate crossing of the near track).
2. **A single joined at both ends by one route lost one join.** Drawing the second of two singles between
   two doubles' loose ends gave the first single a join at each end, each op built from the network's copy,
   so the second overwrote the first (`[0, 2]`): the first single ran both ways. Fix: the second join goes
   into the op already queued for that piece.

Neither fix changes track already drawn: saves load the same (both are drawing-time only). An existing
wrongly-joined single is fixed with the track inspector's "Reverse direction" (moves its join to the other
track), or by redrawing it.

## Proposed, not built

- **The "Run trains one way" switch** stores `autoWay ?? 1` (TrackInspector.tsx): on a two-way terminus
  single that is a to b whatever its side, which at a split can make a crossing. Better: default to the way
  of the track it joins (the run's join votes without the station's "both"). Needs a sim field and the app.
  Not reproduced in the app.
- **First single picked at a loose end, then the second drawn**: `theirs` never moves an existing join, so
  a straight-on single pressed onto the "wrong" lane keeps it and the second single, now forced to its own
  side, takes the same track (both one way the same way). Re-placing the first join when the second single
  shows which side it is on would fix that, but flips an existing piece's way.
- **The snap ring** still sits on the pointer's track when hovering a split node before the press; the
  placed single ignores it. The app could skip the pick there.
