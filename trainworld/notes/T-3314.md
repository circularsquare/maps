# T-3314, T-3315: the figures-stopped notice and the no-SIMD screen

Agent notices, 2026-11-12. From T-3313 (notes/T-3313.md "Proposed").

## What was built

- `game/figuresStopped.ts` checks every 2 s. The notice (`ui/FiguresStopped.tsx`, the demand-stopped note's
  style) shows when the oldest unanswered clock-worker edit or read (`ClockClient.unansweredSince`) is 180 s old,
  or the demand pool has a network waiting (`stuckSince`) with no download or worker step for 180 s. Time in a
  hidden tab is not counted. Off before the game is up and while the demand-stopped or new-version notice shows.
  It goes when the wait ends. Reload asks for the autosave (1.5 s at most) then reloads.
- `?figuresMs=N` sets both thresholds (checks); `window.tw.figures.peaks` holds the longest quiet seen.
- `map/realNetwork.ts` `regions.json` goes through `patientFetch`.
- `map/wasmSimd.ts` `hasWasmSimd()` (the wasm-feature-detect probe module) is asked in main.ts right after WebGL2.
  `loadNoSimd()` puts the same failure screen up as WebGL2's, with `loadText.noSimd`.

## Measured: what normal looks like (1 core, own Vite, headless Chrome)

New game NYC, a line built, the clock running, the real save imported, then 3 minutes with a new line every
30 s. Longest quiet while something was waiting: clock worker 17 s (the real-save import on one core), demand pool
8 s. Never showed the notice. 180 s for both is about ten times the worst. A slow laptop runs these longer, but
the clock worker answers in order and each edit is small; the demand side counts every pack byte as a step.
The tab in the background is not measured: its time is left out by design.

## Not covered

- A demand solve in flight (after dispatch) that never finishes is not watched; only a network still waiting is.
  Add it if a report shows one.
- The notice cannot tell a stuck clock worker from one working on a very large single edit for 3 minutes; none
  seen.
