# T-3869: a big game that cannot be saved or downloaded

## For the player, now (before any fix ships)

> Close every other tab and program, wait a minute, then press the download arrow on the game's card once. If a
> file downloads, you have everything, and you can open it later with "Open a file". If nothing downloads, reload the
> page: the game opens as it was saved 18 minutes ago (that copy is safe in your browser and on your account), so
> only those last minutes are lost.

Why this advice, from the code as published: autosave, Save, Make a copy and Download all build the file the same
way (`saveBytes` in the clock worker), and nothing in the published build frees memory before trying again, so
Download only works if memory came free elsewhere (other tabs and programs closed). A failed Download says nothing on
screen (its error went to the console only), so "a file appears or not" is the test. Nothing failed was ever written
over the slot, so the 18-minute-old copy in the browser and on the account is intact, and reloading opens it.

## Cause

The report: Save says "The browser could not save this game...", Download seems to fail the same way, Make a copy
says "Array buffer allocation failed".

- **Which step fails.** Make a copy (`manageSlot` "create") shows its error's own text, and that text is V8's
  `RangeError: Array buffer allocation failed`, thrown when the engine cannot get a new buffer. Before its write, a
  copy only makes the file (`saveBytes`) and the card (`slotSummary`); a browser storage failure is a DOMException
  with other words. So the failing step is a fresh buffer in the clock worker while it makes the save. Autosave and
  Save run the same step and hide the error behind `clockWorker.browserCouldNotSave`.
- **Why Download is no fallback.** Download (`whole()` "export") ran the very same `saveBytes`. When it threw, the
  worker sent only `{kind: "error"}`, which the page logs to the console: nothing on screen. What the player saw
  after pressing Download was the autosave's failure toast, which comes back every minute.
- **What the save asked for.** The old path held at once: the header as UTF-8 (J), the raw file (J + network, R),
  the gzip output in chunks and then joined (2C), and the read-back check's whole inflated copy in chunks and then
  joined (2R). On her North America save (`na-day-491.save`): J 3.6 MB, R 3.9 MB, C 0.7 MB, so about 17 MB of
  ArrayBuffers in one go, four of them single buffers of 3.6-3.9 MB. An India game of 230 cities has a header of the
  same order (the per-region ledgers dominate it).
- **Which limit.** Not known for sure. I capped a headless Chrome renderer's committed memory with a Windows job
  (`joblimit.py`, three tries at 3, 10 and 12 MB of headroom, one filling the room with buffer-holding workers): every
  time the whole tab crashed, never a graceful "Array buffer allocation failed". The player's tab kept running across
  several failed saves, so the limit they hit refuses big new buffers while the rest of the page still finds memory
  (Chrome gives ArrayBuffers their own allocator that returns null rather than crashing; small allocations reuse
  freed room in memory already committed). Either way the game, at about 4.7 GB on its card, is near the browser's
  limit, and most of that memory is the demand workers' WASM.

## Fix

1. **Parts, not one buffer** (`saveFile.ts` `encodeSaveParts`, `gzipCore.ts` `compressGzipParts`). In the clock
   worker the header is written into the compressor 16,384 characters at a time, the output kept in 64 KB parts and
   read back against the same pieces as it inflates: no buffer the size of the file or of the bytes it packs. A slot
   still stores one joined buffer (C); Download sends the parts to the page, which puts them in the file without
   joining them (`new Blob(parts)`). The page's own `encodeSave` (Community shares) keeps the codec worker. Same
   bytes as before.
2. **Free memory and try again** (`clock.worker.ts` `roomFor`, `demandClient.ts` `restartForSave`). A save, save by
   hand, copy or download that fails for memory (`isMemoryFailure`, not a panic) is tried again after 1 s; then the
   worker asks the page ("room"), which replaces every demand worker at once (the existing `restartStuck` path: focus
   pool stopped, replacements reopen what was held, newest network solved again, figures shown stay) and halves the
   solving workers for the tab's session (as T-2867 does when a worker itself runs out); the save is tried again
   0.25, 0.75, 1.75 and 3.75 s after the page answers, while the old workers' memory is free and the replacements are
   still small. An autosave has the workers replaced at most once in 10 minutes, so a game always short of memory is
   not solved again at every autosave; Save, copy and Download always may.
   - First version stopped the workers and started them only after the save; messages the page posted to the
     stopped workers meanwhile were lost, and on `na-day-491` the pool then sat "ready, network waiting" for minutes.
     Replaced by the restart path above, which is the code T-3868 (bigload) is already fixing for this save.
3. **Messages.** A save that still fails for memory says `clockWorker.noMemoryToSave` instead of sending the player
   to Download; a failed Download now says why on screen (that string, or the existing `savesPanel.downloadFailed`)
   instead of nothing; Make a copy says the same string instead of V8's words. A card that fails for memory reuses the
   game's last card. The save's error is logged.

## Proof

- Same bytes, same time (Node, `checks/tmp-t3869-encode.mjs`, kept in the scratch folder): old and new encoders give
  identical files on T-007 (75,178 bytes, 14.4 vs 14.1 ms median of 7), `na-day-491` (728,158 bytes, 237 vs 228 ms)
  and `jpn_real` (573,160 bytes, 84 vs 72 ms), also with a header of 16,383 "é" and 20,000 emoji (surrogate pairs at
  the piece edges); each decodes back to the same header and network and passes Node's own gunzip.
- Failing condition with the final code (`?debug=1&saveRoom=all`: every buffer the save asks for is refused until the
  page has replaced its demand workers; `big` refuses those of 1 MB or more), T-007 on 1 solving worker, after its
  final (v3: 848,081,216 trips a day, 12,558,064 by rail): Download came in 1.7 s (90,671 bytes); the renderer's
  committed memory went 1,798 -> 1,246 MB at the replacement and climbed back over the next seconds. The replacements
  solved again to v4 final with the same figures to the trip. The downloaded file opened with 109 lines, 1,756
  stations, 4,498.6 km of track, as the game it came from.
- The same with the first version (workers kept stopped until the save was done), `na-day-491` (175 lines, 2,240
  stations), 1 solving worker; the save steps are unchanged since:
  - Download: the file came (728,173 bytes) in 4.2 s; the console shows the refusal and the workers replaced. The
    renderer's committed memory went 2,946 -> 1,857 MB within 1.3 s of the stop and was back to about 2,300 MB 4 s
    later: about 1.1 GB free for the retry.
  - Make a copy: written in 4.6 s, card 175 lines, 2,240 stations, picture drawn. The page reloaded into that slot
    (written under refusal) opened with 175 lines and 2,240 stations.
  - Save by hand twice: both saved (11.0 s and 5.1 s), slot 728,173 bytes, 175 lines, 2,240 stations.
  - An autosave within 10 minutes of those: not retried with a restart, as designed; the saves panel said "The
    browser ran out of memory saving this game. Close other tabs, then try again."
- Smoke: passed, 29 checks (a first run on 1 core timed out on the demand final at 300 s with nothing else failing;
  passed on 3 cores).
- Scratch: `joblimit.py`, `sample.py`, `probe-*.js`, `t3869-encode.mjs` in the agent's scratch folder
  (`scratchpad/savefail/`).
