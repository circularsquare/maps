## Read from the code

- `stateSteps` (clockMain.ts 553) builds `buildState` then `networkSteps` (map/network.ts 1989). On a load nothing is cached, so `lineBands` (map/lineBands.ts 148) runs its whole pass: `patchOn` puts every line on its edges, then `bands` orders every edge's lines pairwise and smooths ribbons. Its edit-time shortcuts (`changed`, `sameUsed`, `delta`, T-4153) need a last result, so none applies to the first build.
- What bands feed: each line's shifts along its path (strokes' `band`, `sampleBand` for trains' lane) and the Traffic view's corridor records. No trip figure reads them. Without them the lines would be drawn centred on their track, overlapping where lines share it.
- The first state is single-threaded in the clock worker: it competes with the demand workers only when cores are short. On Anita's 16-thread machine with the default pool (3 workers) nothing competes; on the pinned 5 cores here, 3 solving workers + helper + clock + page + GPU is about 7 threads. So B's saving is large on a busy or small machine and small on a roomy one; A saves work before the first draw whatever the cores.

## Proposal A: bands in a second piece (recommended)

Build the first state with `bands` empty for every line (the lines' own default when a line has none), post it, then run `lineBands` over all edges and post the strokes it changes through the existing patch path (T-4262's `strokes in place`, `stateRows`' kept rows).
- Saves: bands' 2.9 s of 6.1 s: first map at about 3.2 s, about 47% off the wait (about 40% if the quiet figures hold, bands about 1.4 of 3.7 s on dist). Lines.loop (0.4 s) is run again for all lines in the second piece.
- Costs: lines overlap on shared track (the NYC trunks, the Long Island Rail Road's thirteen branches) for the 1.5-3 s the bands take, then they part; trains ride the centre line until then; the Traffic view's corridor records come with the second piece. One more state post and page take (about 0.3-0.6 s of page time, one long task of 280-410 ms again). The full look lands at about today's first-state moment, not later: the CPU is the same.
- Risks: a station or line edit made while the bands piece is pending must restart or fold into it (the same hold rule T-4267 stage 1 adds for runs of edits; `later` in clockFollowUp.ts already drops and restarts a follow-up); the save checks that read strokes at load see the plain look first.
- About 4-6 h.

## Proposal B: pack open after the first state

Hold the demand client's pack open (the first full-level open after an import) until the clock worker posts its first state (the `state` message is already seen by the page).
- Saves: 2.2 s, 36% of the 6.1 s wait here (state 4.5 to 2.3 s), on a busy machine; near 0 where cores are free.
- Costs: demand's opening starts about 2.3 s later. The work is the same, so the riders and the trips figure arrive later by up to the gap, estimated 0-2 s (not measured: my hold broke the load). Trips are what the player waits on after the map. Held packs also leave the solving workers idle for the first 2-3 s.
- About 2-3 h. It touches demandClient.ts, which shownanswer is in (T-4265).

## With A, then B

With A the first state is 1.6 s contended (about 0.8-1 s quiet), so B adds about 0.6-0.8 s (about 10% of the wait) for the same cost to trips. Not worth it after A.

## How it fits T-4267

T-4267 leaves the load as one whole build and works on edits: a changed-records list per layer, the drawn map in small pieces, and a "built look" (the bands) after the edit's answer (stages 15-16 h). A is the same split at load: plain look first, built look after, with the whole-network list as the changed list. When the built-look stage lands, the load's second piece is that stage called with "every edge changed", so A does not need to be redone; A first only needs the plain-look build to leave `cache.bands` empty so the later pass takes the whole path. Nothing in A depends on how a record is built.
