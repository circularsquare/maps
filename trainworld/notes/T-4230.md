# T-4230: the clock worker's first state sooner on load

Measured on the real NYC save (T-007-real-nyc.save) imported over a new NYC game, dev build (Vite 6170, unminified, so
slower than the shipped build), headless Chrome pinned to the cores the ledger gave (2-3, other agents busy: noisy).
A temporary console line printed the worker's `netLaps` and `bandLaps` for the first (whole) build; removed again.

## Where the first state goes

| run | state (rows) | buffers (networkSteps) | lines.bands | of it corridors | q.sample | later |
|---|---|---|---|---|---|---|
| A, packs opening beside it, 2 cores, 1 demand worker | 1.84 s | 4.97 s | 3.65 s | 2.11 s | 0.70 s | 0.42 s |
| A, same | 2.23 s | 4.42 s | 3.43 s | | | |
| B, pack downloads held until the state was out, 3 cores | 0.96 s | 2.49 s | 1.81 s | 0.95 s | 0.37 s | 0.28 s |
| B after the corridor tweak below | 0.81 s | 2.27 s | 1.76 s | 0.84 s | 0.41 s | 0.24 s |

- **`lines.bands` is 70-75% of the buffers step** in every run; every other part of `networkSteps` together is under 1.4 s
  (edges.loop 0.03-0.27, lines.loop 0.25-0.39, rest.links 0.04-0.09, speeds, stations, splits all under 0.1).
- Inside bands, **corridors (map/corridors.ts `besideSamples`, which finds the track running beside each piece of track)
  is 40-45%**, then `q.sample` 15-17%, `later` 10%; the rest are small.
- Arm A against B is 6.8 against 3.4 s for state plus buffers, but the arms also differ in cores (2 against 3), so only
  the direction is safe to say: with the packs opening beside it the first state takes up to about twice as long.
  The shipped 0.4.6 figure (3.7 s on 5 cores, T-4225) sits between them.

## Tried

`recordsOf` (corridors.ts) kept "does this other edge carry on from mine" in a Map per edge redone; replaced by two typed
arrays. Same output, corridors 0.95 to 0.84 s in B, which is inside the run-to-run noise (total buffers moved 2.49 to
2.27 s with no other change). Reverted: no gain to name.

## Proposal (not built)

1. **Open the demand workers' packs after the first state is out** (a moment later, not at the same time). The map shows
   up about as fast as the quiet arm (3.4 against 6.8 s dev, see the caveat above; in the shipped build the saving is
   between a third and a half of the 3.7 s). The cost is the trips wait: the packs open about the first state's time later
   (2-3 s). It changes when numbers appear, so it is Anita's call. A middle way: start the helper and one worker now, the rest after.
2. **A cheaper corridors pass for the first build.** It is the single biggest part (about 1/3 of the buffers step). The sample
   loop is already grid-indexed; a real cut needs either corridors for each edge computed in parallel on the (idle at that
   moment) page side, or kept in the save/pack per zone. Several hours and a check against today's output; not small.
3. Nothing in `networkSteps` other than bands is worth touching for the first state.

No perf_bench run: no code change is left in the tree. Measuring took 6 probe runs (about 4 min of game checks).
