# T-2699: the boarding account's steps on all of Japan

T-2404 saw the clock worker's `boarding_step` take 250-750 ms a step (3 lines) on all of Japan and
guessed `ensure_some` re-hashing every line from the start each call. Done 2026-11-07 in tree `boarding`.

## What it was

Mostly not the hashing. In WASM nearly all of a step was **memory grows**: the account allocates
~0.4 MB a line and kind of day, std's allocator grows the linear memory by what each request lacks
(64 KB at a time), and each `memory.grow` costs about 1 ms or more however few pages it adds (more as
the memory gets big). The demand module already grows ahead of need (T-1594, `demand/wasm.rs`); the
clock worker's module did not. A CPU profile of the WASM (built with `--profiling --no-opt` for names)
put 5.5 s of 7.3 s in `dlmalloc::sys::System::alloc` (the grow) over 40 steps.

The hashing was real but small: natively 13-35% of a step, ~2.7 us a line key, 6.5 ms for a check of
all 2,421 line-days.

## Changes

- `sim/src/heap.rs` (new): `ahead(before, bytes)`, moved from `demand/wasm.rs` (which now calls it,
  unchanged at 32 MB), and a global allocator for wasm32 builds without `demand` (the clock worker's
  module; the diagram one too) that after any allocation that grew the memory allocates and frees
  max(32 MB, memory / 8) at the top, so the memory grows a few dozen times in all.
- `boarding.rs` `ensure_some`: a cursor (`Boarding::cursor`) the scan goes on from, wrapping round, so a
  round of steps hashes each line about once; a line's service hash (`key`, now without the riders'
  generation) is worked out once per call and shared by every kind of day, the generation mixed in after.
- `sim/src/bin/boarding_bench.rs` (new): the save's network, made-up riders for every running line (a
  fixed pattern, one line in seven crowded so some platforms carry over), three kinds of day, then two
  rounds of new weekday riders, 3 lines a step; `TW_DUMP` writes every line's `line_account`,
  `line_periods`, `today`, `past_day` and `boarding_hour`.
- No WASM interface change.

## Measured

`t737-japan-trains.save` (807 lines, 9,529 stops), clock 111600. Native: `boarding_bench`. WASM: the
same rounds in Node on the app's `app/src/wasm/track` module (a scratch script, not kept).

| | first round (3 kinds of day, 807 steps) | later rounds (269 steps) | up-to-date check |
|---|---|---|---|
| native before | 8.3 s; step p50 9.6, p95 18.9, max 38.7 ms | 2.0 s; p50 6.6-7.1, max 25-37 ms | 6.5 ms |
| native after | 4.1 s; p50 4.6, p95 10.0, max 24.9 ms | 1.35 s; p50 4.6, max 23 ms | 2.2 ms |
| WASM before | 359 s; p50 311, p95 1,216, max 3,919 ms | 2.9-6.6 s; p50 7.3, max 651-3,036 ms | 3.3-4.5 ms |
| WASM after | 6.6 s; p50 6.6, p95 17.3, max 86.6 ms | 1.8 s; p50 6.0, p95 13-14, max 30-33 ms | 1.7-2.6 ms |

The load in WASM went from 2.9 s to 1.4 s too (the same grows). The worst step left, 87 ms, is in the
first round as the memory passes 1 GB.

Figures: the native `TW_DUMP` before and after (17 MB of readouts) are byte-identical. Each line's
account is a pure function of its inputs, so the order lines are redone in changes nothing.
