# T-4433: what a phone's solving worker holds after a load, and the cut (agent phoneworker, 2026-11-27)

Tree `.tw-trees/phoneworker` from master dfb9e604b. Scratch (drivers, logs): the session scratchpad's `phoneworker/`
(`trace-run.mjs` Chromium as an iPad with the worker's temporary heap trace, `ipad-run.mjs` WebKit as an iPad, the
`trace*.log`, `wk1.*`, `perfbench.log`).

## The premise was a stale reading

The worker reports its heap only when a zone opens or closes and when a solve ends (`ready`, `opened`, `closed`,
`done`), and the peak resets as each solve starts (`wasm_heap_peak(true)` in `run`). T-4370 read "66" at the load's
final, but that was the last `opened` before the load's solve began; the "166" came with that solve's `done` a moment
later. **The 166 MB is the load's solve's own peak**, not a job after the final. The same stale reading made its edit
look like 162 in WebKit here too until the edit's `done` arrived.

## What the peak was (Chromium as an iPad, one solving worker that is the aux worker too, NYC save imported into a new New York game; MB of WASM heap in use)

A temporary trace in `demand.worker.ts` logged the heap in use and the peak after every population's pass, every
skims release and every message (removed again).

| piece | MB |
|---|---|
| the zones' solving copies (coarse) and the worker's base | 29 |
| the network set on each population | 13 |
| the five periods' results (7.3 each, nearly all New York) | 37 |
| **in use at rest after the load** | **79** |
| the old game's bare copy of New York, kept to the final | 24 |
| bare copies opened for the save's zones (T-4051 `bareFirst`), kept to the final | 10 |
| one period's skims table (searched by its first pass, freed after each period's round) | 40 |
| a pass's working space | 13 |
| **the load's peak (round 1, period 0)** | **166** |

The bare copies close with the first `sweep` after the final (-34). WASM memory keeps its high-water mark: 169.

**Every edit reached 162 on its own.** The edit's local solve (`localSolve`, T-1609/T-3512; also `sideJob`) forgets the
re-solved populations' old periods (-34), sets the new network (+10) and adds 6.8 a period, but freed the skims only
after a period's last round. Each crowding round prices a new graph, so it searches a new table, and the cache keeps
two: from round 1 on the round before's table (never read again) sat beside the current one. At period 4: 72 + two
tables (80) + 10 = 162. The other solve paths (the load's barrier rounds, T-2624's period after period, the edit's
whole rounds) already freed the skims after every round.

## Cut (figures identical)

1. `localSolve` frees the skims before each crowding round after the first (`demand.worker.ts`). Every device, every
   edit that takes the local path.
2. `bareFirst` is never true for a loading save (`demandClient.ts`): `stationsAhead` (T-889) opens the save's zones
   before its network arrives, so before `this.hold` is set, and T-4051's `!this.hold` did not see the load. A load's
   solve runs with the barrier anyway, so the bare copy bought nothing; on a phone its open and bare solve also took
   about 3.5 s of the one worker before the load's solve could start.
3. On a phone's pool (`auxShared`), when a shown round of a solve is published (`showEstimates`: a load's are), the
   bare copies of the zones it covers close before the `go` for the next round (T-327), so the worker frees them
   before that round starts (`closeCovered`). Same rule as `sweep`'s redundant copies, which cannot run in a load's
   hold. Desktop is unchanged (its bare copies sit in the aux worker, which solves nothing).

Docs: `docs/demand-runtime.md` (the bare copy's close, `bareFirst`), `docs/demand-kernel.md` (when tables go).
