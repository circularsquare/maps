# T-3302: two Tokyo saves a player can't load

Agent haru, 2026-11-12. Saves `trainsworld-tokyo-day-60.save` and `-day-77.save` (same game; kept as
`checks/fixtures/t3302-tokyo-day60.save` and `-day77.save`).

## What the files are

Both are whole and well formed: gzip with a good trailer, `TWG1`, header JSON parses (no nulls), network
`TWT6` decodes to the end with every block known (day 60: 458 nodes, 130 stations, 448 edges, 22 lines;
day 77: 598, 167, 582, 27). Day 77 has header `level` 14, so a v0.2.x build wrote it (level 15 came with
ed4f66fa, in v0.3.0); day 60 has level 15, so v0.3.0 or later wrote it. Probably: played to day 77 on v0.2,
the day-77 game hung on v0.3.0, a day-60 backup was restored there and re-saved.

## Where it fails

Start menu > Load from file, headless Chrome, one demand worker:

| build | day 60 | day 77 |
|---|---|---|
| v0.3.0 published (website 9ca1187, data 2026-11-11b) | loads, final, clock runs 5 min | sits at "Loading 17%" for 3+ min: the clock worker's `load` never returns |
| v0.3.1 published (cc14a89, data 2026-11-11b) | loads | loads in about 16 s, final about 45 s |
| v0.3.1 code (hotfix031), local data | loads | loads |
| master (tree haru), local data | loads | loads |

The day-77 hang is T-3238 (a local waiting out its own headway behind a frequent express at passing
tracks; the settle never ends), whose report these saves belong to: T-3238 worked from a reproduction
because the player's save had not arrived. Its fix is in v0.3.1 and master, so nothing new was changed.

The published builds were run from a local static server with R2 requests fetched outside the page (R2
allows only the site's origin); scripts in the scratchpad `haru/` (probe2.mjs, static.mjs).
