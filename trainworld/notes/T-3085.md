## 1. Flyover junctions

**What exists.** A junction is a node with 3+ edge ends. Two moves through it conflict when their paths cross at
one level (track positions in opposite order on the two sides); merges and diverges do not (track capacity
counts them). Each crossing move is a resource held 90 s per train, Kingman delay on top (track-and-service.md
6.2). A plain double-track Y has one crossing pair: the move into the branch from the far track crosses the
opposite direction. A **flyover is already a node flag**, `NodeData::flying` (save node flag 1, T-080): capacity
skips every move at a flying node (`capacity.rs` ~635, 659, 848), and `junction_cost` adds `FLYOVER_KM` 0.6 km of
track one level away from the ground (US$45M at grade, US$67.5M at +1, US$90M at -2; the switches alone are
US$9.4M at grade). It is bought from the junction inspector (Construct a flyover / Add a flyover), removed with
the delete tool or the inspector while blueprint. On the map a flying junction just loses its flat-fork badge
(`network.ts` ~1455); nothing else is drawn.

**And already wired to drawing.** `add_route` and `preview_route` take `flying: bool`, and `draw.rs` ~289 makes
any junction the route itself creates (`Resolved::new_junction`: a split of track, or a plain two-end node) flying
when it is true. The app has passed `false` since T-080 (`clock.worker.ts` 3517, 4082, 4395), after Anita found the
old flat/flying toggle unclear (DECISIONS-to-2026-10-19, batch 4).

**"Faster merges".** In the model a merge never waits; only the crossing move does. A flyover removes that 90 s
hold and its queue, which is what a player sees as trains waiting at the junction. It does not change speed.

**By hand, real geometry.** Today a player can draw a second branch leg that ramps over the main (the ramp switch
does it) to join from the far side, but routing takes the fastest leg both ways, so the return still crosses
flat at the first leg. One-way track (2) is what makes a hand-built flyover work, as in other games.

**Options.**
- A. *Flag, automatic* (recommended, T-3092). With the ramp switch on, pass `flying = ramp` to `add_route` and
  `preview_route`. The ghost's price includes the flyover, its flat-fork badge goes, and the blueprint breakdown
  already lists flyovers. Skip it where it buys nothing: a single-track route or a split of single track (one
  track position, no crossing pair), tram (the app already sends `ramp: false`), a crossover's end. The lie: the
  0.6 km of extra track is priced but not drawn, takes no room, and is not checked against stations, other
  junctions, water or other track; a flyover 20 m past a platform (`BRANCH_CLEAR`) is as good as one in open
  country. The player sees a plain Y that never waits, which is what they paid for. No room means no fallback
  needed. DECISIONS line to say so.
- B. *Real ramps.* The branch's first ~600 m laid as two one-way single tracks: the non-crossing one flat, the
  crossing one up 200 m of ramp (`RAMP_PER_LEVEL`, 4%), over, down, joining the main on its own node. Needs
  one-way track first, a new builder in `draw.rs`, room checks with fallback to flat and a notice, quad, delete
  and inspect as a unit. About 800-1200 Rust lines, 2-3 days. Not filed; only if A's lie shows in play.
- C. *A flyover setting of its own* in the tool bar: what Anita turned down in T-080; her ramp-switch idea is
  better (one switch: "keep my track out of other track's way").

Add a **flyover badge** in T-3092 (the junction badge with an arch, quiet on built track, `gradeMarks.ts` beside
`M_JUNCTION`, tip "Flyover"), so a player sees the flyover they got; ~40-80 TS lines.

## 2. One-way track

**Model.** Each edge has one directed track per direction, shared on single track; a line path is a list of
`(edge, direction)`. One-way = an edge flag `oneway: 0 both, 1 a to b only, 2 b to a only`.
- *Single track one way* (recommended): the useful case. A pair of one-way single tracks is directional double
  track drawn anywhere: hand flyovers, a balloon at a terminus, a one-way city loop, a bypass.
- *Double track both tracks one way*: doubles one direction's capacity, but platforms, junction track positions
  and train drawing all assume one track per direction. Not now. On double track the control is hidden.

**Routing.** Both Dijkstras in `net.rs` (`find_path_turn` ~2669 and the one at ~2812) skip a state against the
flag (one helper, two `continue`s); `check_line` refuses a path entry against it (`LinePath`). Turning back on a
one-way dead end is then impossible, as it should be.

**Capacity.** A one-way single-track section uses double track's per-direction rule (`edge_section_s + v /
SIGNAL_BRAKE`, 25/h at 160 km/h) in place of run time + 60 s (`capacity.rs` ~489): no opposing train holds it.
Platforms: unchanged (one shared track, one direction).

**Setting it.** Track inspector on single track: a switch "Run trains one way" and, when on, "Reverse direction"
(the way follows the drawn direction at first). The Select tool's bar gets the same for a picked run of single
track (all pieces set in drawn order). Arrows on the track every so far apart, reusing the one-way chevrons
(T-3008, T-2991's spacing), hover "One way". Free and undoable: it is signalling, not construction.

**Lines that run the other way.** Refusing the edit would trap the player: while the leg is two-way, routing keeps
using it both ways, so no line edit can clear it. So the edit re-routes each such line through its same stops
(`route_hops_turn`) in the same undo step; the confirmation lists them (as removal's `lineEffects` modal does),
and a line with no other way refuses the edit, naming it.

**Saves.** Edge flag bits 11-12 (bits 8-10 are `TrackKind`); widen the decoder's unknown check from `tb >> 11` to
`tb >> 13`. An older build reading a new save counts it unknown and runs both ways. Splits keep the flag (both
halves keep the a-to-b sense); pieces join only with the same flag; Double up on one-way single track refused
(or clears it; agent's call).

**Smallest cut.** Single track only, inspector switch and reverse, routing, `check_line`, capacity rule, save bits,
arrows, re-route with confirmation. Select-bar version can follow.

## How other games do it

None builds a flyover for you; all model individual tracks, made one way by signals, and the player builds
flyovers by hand with elevation. Our route-level double track (T-080's topology call) makes a flag the natural fit.
- NIMBY Rails: individual tracks with elevation; one-way signals restrict direction:
  https://wiki.nimbyrails.com/Path_signal_setup
- OpenTTD: one-way path signals ("trains cannot pass from the back side"); flyovers built from bridges, catalogued
  in the Junctionary: https://wiki.openttd.org/en/Manual/Signals,
  https://wiki.openttd.org/en/Community/Junctionary/High%20Speed%204-way
- Transport Fever 2: one-way signals, flyovers by hand (a "Flying junction" mod exists):
  https://steamcommunity.com/app/1066780/discussions/0/5153834725008443057
- Subway Builder: tracks cross at grade within 0.1 m or need 4 m clearance; v0.11 added direction arrows on
  track: https://wiki.subwaybuilder.com/index.php/Construction, https://www.subwaybuilder.com/changelog
- Flying junction, real railways: https://en.wikipedia.org/wiki/Flying_junction
