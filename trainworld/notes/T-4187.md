# T-4187: the clock worker's drawing cache on big player networks (agent drawmem, 2026-11-25)

From T-4184 (notes/T-4184.md), which named the drawing state for the player's track as the clock worker's extra on a
Community Tokyo-start save (t9gksxmu) and described the network draw cache's cut. The code had changed since (T-4153
stages 2-7), so the cuts were found again from heap snapshots of today's code.

## The save

t9gksxmu is now rev 2 (131 lines, 1,444 stations, game day 1,366; T-4184 measured rev 1, 123 lines, 1,335 stations,
which the server no longer has). Downloaded from the public share to scratch, deleted after. So the before figure here
is today's master on rev 2, not T-4184's 345 MB.

## What changed (all exact: the drawn map is the same, byte for byte)

1. **The Traffic table kept once** (map/lineBands.ts, workers/clockPost.ts). The table (`LineBands.corridor`, 4.9 MB
   here) was held four times in the clock worker: each line's records numbered for the table (`LineMemo.net.recs`), the
   bands' last result's copy (`last.corridor`, kept because the worker transferred the array it posted), the posted
   copy (`posted.arrays`), and a fresh copy made on every build that kept the bands. Now each line's records are views
   of the table, the bands keep the table itself, and the worker keeps it by reference and posts a copy (as it already
   did for the rows' phase tables, `BY_REFERENCE`). A view whose buffer has gone (only if something transferred the
   kept table) is made again from the line's own records. One copy fewer per build too.
2. **A piece of track holds fewer arrays** (map/network.ts `EdgeEntry`, `StrokeBuilder.keepTrack`, map/strokePost.ts).
   Each of 7,596 pieces held about ten typed arrays of a few numbers each, and in V8 an array of its own costs more than
   such numbers (the object, its buffer and the buffer's own record). Now: the points are the clock worker's own array
   (`given`, never changed in place) instead of a copy; colour, edge and flags, one value over a piece of track, are kept
   once by the piece and filled in as it is posted (`StrokePiece.colour`, `edge`, `flags`); the segments, levels,
   distances, lanes and speed limits are views of one buffer; a piece no train runs over shares one empty `train`
   (`NO_TRAIN`, -1 at every segment as posted), one with no ramps one empty list.
3. **A line's piece**: its strokes are views of one buffer, and its colour (the line's id at every segment) is kept once.
4. **A line's fastest-train speeds** (`lineTrainSpeeds`): one array a line with offsets per path entry, instead of an
   array per entry (14,500 arrays here).
5. **The facility grid** (map/facilityPlace.ts `CellLists`): each grid cell's segments were a JS array (50,000 cells,
   each grown to room for 17); now a list through two pooled Int32Arrays. A cell's segments are read as a set (room
   spots take the worst, lot tries the sum, cut short only once a try already loses), so their order changes nothing.
6. **The bands' kept orders**: each edge's pair signs and walks in one buffer.
7. checks/t4153-net.mjs now detaches what a post transfers, as the worker does, so an array the worker keeps and posts
   by mistake fails the check.

### Found on the way: identity matters

The first version kept a remade piece of track on the same points array when its points had not changed (base code
always made a new copy). The bands and the facilities read the points by identity, so after an anchor move a piece
remade for its legs' shift key no longer looked changed to the bands, which then carried their moved result over
instead of working it out again: the lines' strokes and the Traffic table came out different from master after an
anchor move (found by the anchor-move step of the probe below). Now a piece made again from the array it was made from
gets a copy, which gives master's identities in every case; after that the probe matched master through the moves too.

## What is left (named, not cut)

- The bands' memo, 27 MB in Node on t9gksxmu, mostly JS objects: each line's sample memo (`LineSamplesMemo`, 5.8: arrays
  of arrays and ribbon objects), its recipes (5.4, with their text keys), each edge's ribbons (3.6), and each line's own
  records (5.2, Float32). As typed columns they would be a few MB (filed as T-4310).
- `posted`'s copies of the per-sample arrays (about 10 MB here), kept to tell which are as last posted; the line pieces'
  strokes (15.7, numbers); the per-run samples (4.9, numbers).
- The clock worker's WASM (118 MB here), T-4184's open question.
