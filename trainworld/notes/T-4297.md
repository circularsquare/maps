## Fixed

**T-4283: a shared slot's other row given another headway kept its hold (real; fixed).** A slot a line's hours share
between rows (`Network::mixed`) runs every row's trains for its share of the hours (`running_trains`), and the hold a
settle keeps it by (`settle_kept`, `kept_key`) already hashed every row's train count there (`trains_key`), but the
edit's check of headways (`fleet_key`, T-4283's `rest_auto`) read only the slot's main row. So a row other than the
main one given another headway with the same trains kept its hold, on weekdays (since T-4239) and weekends (T-4283),
and the line ran the slot at its old rate where a settle without the hold moves it. Reachable when the row has no slot
of its own (hours 6, 12, 14, 20, 24: midday 12-14 lies inside the 10-16 period, whose main row is the morning), or its
own slot's rate is held by full track. Fix: one helper, `Network::mix_key` (service.rs), keys a value of the five rows
as a slot runs it (the main row's, or a hash of every row's in a shared slot); `trains_key` is it on the trains (to
the bit, so saved holds still match), `fleet_key` and `rest_auto` on the headways (world.rs). `Ahead::reshare_at`
reads `fleet_key` too, so the reshare now also sees that row's change. Test
`world::circle_tests::t4297_a_shared_slots_other_row_given_another_headway_drops_its_hold`: the midday row's headway
300 to 330 s on weekdays, 600 to 900 s on weekends, each edit keeping the trains; without the fix the hold stays and
slot 1 runs 12 tph (weekends 10) and keeps the midday's 6 trains, where the same game without the hold runs 11.62
(9.33) on the 5 trains a 330 s headway needs; with it rates and trains match that game to the bit. (`hours_tests::corridor`
made `pub(super)` for it.)

**T-4281 stage 2, finding 1: work waiting for a follow-up's state had no panic recovery and ran on a model that was down (real;
fixed).** Stage 2 moved trips asked while a follow-up waits (`sendTrips`, `nextHourLater`) into `afterState`, run in
the message queue once the state went. Every other queued message goes through `processMessage` (a panic recovered,
nothing run when the model is down); these caught a panic as a plain error, leaving the broken model to the next
message, and ran when `recover` had failed (`modelDown`; no game bump then, so the game check let them through).
Before stage 2 the same trips ran from a timer, where the worker's `error` listener recovered a panic. Fix:
`guardedAfter` (clockFollowUp.ts): skipped when the game changed or the model is down, a panic recovered as
`guardedFollowUp` does. Reached only through a Rust panic in trips, so no game run shows it; typecheck clean.

## Answered, left

**T-4281 stage 2, finding 2: repeated trips after a state, and an old hour's slice (real; harmless).** Every trips call deferred while
a follow-up waits runs after it, even when the state itself sent trips. Before stage 2 the same calls ran the follow-up
whole first and then sent their trips anyway, so the count of sends is unchanged. A `turnHour` call deferred across an
hour's turn sends that old hour's slice: the renderer files it under its past hour (`putTrips`) and drops it at the
next hour change, nothing drawn from it; its money shape (`shapeHour`) is that hour's from the same model. Collapsing
the deferred calls would save one trips pass (tens of ms on a big save) only when an hour turns during a click's
follow-up; not worth the bookkeeping now.

**T-4153 stage 7: the band memo's numbering keeps ribbons and recipes no line uses (real; too small to matter).**
`BandMemo.net` numbers ribbons and recipes in the order they come and never renumbers while the memo is kept, by
design (lineBands.ts `sameCorridor`'s note). Dead entries are never drawn: `trafficBands` places only the ribbons a
record names (`placesOf` is lazy) and skips the rest in one index loop. New keys come only from ribbons an edit
changed (tens per edit on shared track), so after hundreds of small edits the table holds some 100-200 KB more and
the loop a fraction of a ms; any edit over `MEMO_EDGES` (400) edges, a band mode switch or a load starts it fresh.

**T-4220 stage 4, finding 4: `planAside` sets the world frame from a message mid-solve (not real).** The frame changes only
with the game (`clockClient` "loaded"; `makeFrame` caches by spec, so the same game's frame is the same object and
`setWorldFrame` does nothing), and a load ends the focus pool (`stationsAhead`, `endFocus`, `FocusPool.end`
terminates its workers), so no solve of another game runs beside an aside. The `cells` question has set it the same
way since T-325.

Lines are master's at 56f35a0ff.

1. **Finding 1 (real once stage 6 runs side jobs): a side job leaves its fresh zones' populations holding its own network, and
   questions read them as the main solve's.** `sideJob` (demand.worker.ts 2631-2677) sets the worker's real
   populations of the fresh zones on its network and solves them (`localSolve`, `setUpPops` 2251-2319, `layoutAt`
   2305) but leaves `current`, `roundsHeld`, `ready`, `versions` and `layoutSpan` as the main solve left them, and its
   `finally` (2671-2675) clears only `held`, `heldQ` and `disturbed(p)`. `query` (1552-1600) decides from those alone
   (`atRound`, `live`, `sameNet` 1590-1597, `a` 1570, `cellModes`' span 1637-1638), so a question for the main
   solve's version about a fresh zone, between the side job's periods or after it, is answered from the side job's
   state as that version's. The focus pool answers the zone in view's questions (T-2533), so stage 6 meets it. Fix: at
   the side job's start mark each population it sets up (a WeakSet beside `shownIntact`, and `layoutSpan.delete(p)`),
   have `query` answer a marked population as holding nothing (mask 0, no live, sameNet or span answer), and unmark it
   when the main solve next sets it up (`setUpPops` from `run`); or route questions about the side job's fresh zones
   to the main pool while the focus pool holds its state.
2. **Finding 2 (real, dev call only today): opening fresh zones can close one the same job needs.** `aside()` (demandClient.ts
   3464-3473) skips a zone already open at the right level, then `pool.post` of another (demandFocus.ts 62-72) closes
   the oldest open zone past `ASIDE_MAX_ZONES`, which can be that skipped zone; `sideJob` then refuses `open`
   (demand.worker.ts 2640). Fix: `post` takes the zones to keep (the job's fresh ids) and closes the oldest open zone
   not among them; or a reused zone moves to the back of `open`.
3. **Finding 3 (real, dev call only today): a side job superseded before it starts never answers, and an overlapping dev call
   hangs.** onmessage "solve" (demand.worker.ts 1357-1365) overwrites `pending`; a side job waiting there is dropped
   with no `asideDone`. Fix: when the job replaced has `aside`, post its `asideDone` with `stale: true` first, as
   `sideJob` does when cut. `devAsk` (demandClient.ts 3405-3416) overwrites `devTake`, so an earlier call's promise
   never settles: call `this.devTake?.(null)` before taking the new one.
