# T-1064: long data builds on AWS (design and proof, 2026-10-23)

## In plain words (for Anita, and for Jean)

**Recommendation: a fresh spot machine per wave, not a long-lived box.** One `m7a.8xlarge`
(32 real cores, 128 GB) rented as spot for about 1.5 hours a wave, building the wave's packs from
the original sources, then terminated with its disk. Gates and the join stay at home.

| | Fresh spot machine per wave (recommended) | One long-lived machine, stopped between waves |
|---|---|---|
| A wave (about 1.5 h of a 32-core box) | **$0.55-0.75** (spot $0.31-0.44/h over the last month, plus disk, IPv4 and about 1 GB of results home) | $2.80-3.00 (a stopped-and-started box is on-demand, $1.86/h) |
| Idle, per month | **$0** (nothing left; the bucket empties itself after 14 days) | $8 (a 100 GB disk kept while stopped) |
| The four US waves, if done within a month | **about $3, at most $6 with reruns** | about $20 |
| What it saves | | 5-10 min of setup and downloads a wave, about $0.05 |

The long-lived box loses because each wave reads different states: its kept downloads are mostly
useless to the next wave, while its disk bills every hour of every idle day. A free-tier size cannot
help (below). None of this is inside any free tier: the free tier covers about 750 hours a month of
a 1 GB micro machine, which cannot run a build. **What to tell Jean: about $1 a wave, $3-6 for all of
the US, nothing while idle, and nothing of hers touched** (her t4g.nano and her ECS cluster, both in
Ohio, are the only other things in the account in any region; we only counted them).

**Free tier, measured.** Measured here (whole process tree, every half second): Atlanta (6.5M) peaks
at 1.10 GB in `build_city` and 1.00 GB in `routes`, Lowndes (0.57M) at 0.63 and 0.59 GB; the other
steps 0.1-0.3 GB. Reading a state's OSM extract, which every region does first, asks GDAL for a
6 GB node index and would not even open on a 4 GB machine (proof 3), let alone 1 GB. A 1 GB
t2/t3.micro would swap or be killed on any build, and its CPU credits run out in minutes. Nothing
useful runs there.

**Jean's "upgrading ram is fine"**, weighed: her pattern (one long-lived anitabuilder machine,
resized up for a wave, down and stopped after) works, but the numbers favour a fresh spot machine
clearly. A stopped machine cannot be spot and resized (AWS does not resize spot instances, and a
stoppable spot needs a persistent request, the relaunch trap), so each wave pays on-demand, 5.4
times the spot price; and the disk that holds the downloads bills every idle day while the next wave
reads other states anyway. If Jean would still rather see one named box, it costs about $8 a month
idle plus $2.80-3.00 a wave, and every guard here applies to it (a stop timer after each wave).

**What the proof showed.** Three test machines (each a 2-core spot `c7a.large`, $0.019/h) booted
Ubuntu, fetched files from our bucket and sent files back through presigned URLs, reached every
source the pipeline downloads from (Geofabrik, census.gov TIGER and LODES, JRC's GHSL, osmdata,
Wikidata, the World Bank, OurAirports) except Overpass, installed Python 3.9 with the pinned
packages, imported the whole pipeline, cached Rhode Island's census blocks and LODES with the
pipeline's own step, read Tennessee's OSM extract in 56 s, and compiled the Rust bins in 21-35 s.
Four machines in all cost **$0.013**, and the teardown listing showed nothing of ours left in any
region. See "The proof".

So **nothing has to be uploaded from home but the code and the plan** (about 6 MB). Downloading on
the machine is fast (Geofabrik 52 MB in 14 s, a GHSL tile in 2-3 s) and free inbound; the home
upload would be the slow path. A wave's downloads: about 3.5 GB of extracts for wave 1, 0.9 GB of
water polygons, 0.3 GB of national census files, 0.5-1 GB of GHSL tiles.

Steps that wrote outside the scratch tree: only data/raw downloads (the blocks .dbf, deleted after
the state cache was made). The `low` build in the scratch tree is the Windows reference for the
Linux comparison (T-1065): `scratchpad/t1064/root/data/{packs,work}`; its packs match the shipped
`low` in boundary and places byte for byte, and in cells (6,864; 59,194 at res 9), the rest differing
only by the joint solve's additions.

## 2. Linux

The pipeline is already portable where it matters: `shared_lock.py` has an fcntl branch,
`world_run.py` guards every Windows call (`CREATE_NEW_PROCESS_GROUP`, `taskkill`, the junction
repair) behind `os.name == "nt"`, paths go through `os.path`, and cargo is found on PATH. Prefer
Linux: Ubuntu 24.04 boots in under a minute and spot Linux is the cheapest.

What changes on the machine, all in its user data, none in the pipeline:
- **Python**: `uv` installs CPython 3.9.25 and `tools/aws/requirements.txt`, the venv's versions
  pinned (numpy 2.0.2, pandas 2.3.3, shapely 2.0.7, pyogrio 0.11.1 with GDAL 3.10.3, ...). The
  venv's `timezonefinder` pin conflicts with its own `cffi` (pip at home never checked); it is not
  needed for builds and is left out.
- **GDAL's OSM driver**: the Linux pyogrio 0.11.1 wheel carries GDAL 3.10.3 with the OSM driver,
  as the Windows one does. `osm_features._gdal` asks GDAL for a 6,000 MB in-memory node index a
  reader, so on a 4 GB machine the extract does not even open ("Failed to open dataset"): a read
  needs a machine of 16 GB or more (measured peak below).
- **Rust**: rustup's stable plus `build-essential` (Ubuntu's image has no `cc`); `pack_gravity` and
  `pack_walk` compile in 35 s on 2 cores.
- **Folders**: `git archive` carries no empty folders and the pipeline assumes `data/raw`,
  `data/work`, `data/packs` exist: `mkdir -p` first (the first proof failed there).
- **The `.cmd` wrappers and `start_hidden.ps1`** are not used: user data runs as root, detached from
  any session, and the timer ends it. `TW_SIM_DIR` is not needed (the machine's own `sim/` is the
  copy), so the junction checks never fire.
- **Downloads** need redirects followed (`curl -L`; the pipeline's `requests` does already).
- **Overpass** timed out from AWS (HEAD) and answered 502 (GET) in both tests. No US build needs it
  (T-1066, answered in T-1065): terminals, medical, parks, jobs and schools come from the extract
  through `canada.osm_caches`, places from `places.from_extract`; wave 1 ran with Overpass blocked.

## 3. Plan for a wave (wave 1, the South: 63 rows, 9 states)

- **Machine**: `m7a.8xlarge` spot in Ohio, 32 cores without hyperthreads, 128 GB, 100 GB gp3 root
  disk deleted on termination, timer 3 h. Builds are light (1.1 GB at most, Atlanta's `build_city`;
  32 at once about 35 GB), but **reading an extract took 26 GB** (Tennessee on proof 4: the 6 GB node
  index in each of the read's parallel readers). So at most 4 reads at once (about 105 GB): the wave
  script starts the regions a read at a time, Texas first, which costs a few minutes against 30+ of
  builds. (m7a.12xlarge, 48 cores and 192 GB at about $0.50/h, would take all six reads at once.)
- **Runs**: the wave's runner regions as at home (`lists.py`): Texas (15 rows), Oklahoma (4),
  Louisiana (5), Alabama (6), Arkansas-Mississippi-Tennessee chained by Memphis (14), the Carolinas
  chained by Charlotte (19). Six `world_run.py run --rows ... --build-only --coarse 1000` at once with
  4-8 workers each (about 32 in all), each logging to a file the machine uploads every minute.
- **Build only on the machine; gate and join at home.** The gate registers rows into the registry
  and market rows, snapshots the shipped world and runs a browser check on Vite: on the machine that
  would need all of `data/packs` (2.8 GB), node, Playwright and a registry that then has to be merged
  back against the home copy. At home the gate takes 0.5-2 min a row and the join 30-60 min, which a
  home machine does fine. `world_run.py` needs a `--build-only` switch (stop after the builds, rows
  "built", downloads cleaned); T-1065 adds it.
- **Time**: setup 5 min (apt, uv, rustup, cargo), downloads 3-5 min, Texas's read about 10 min, then
  builds: the pilot's 22 rows were 76 single-core minutes of steps, wave 1 about 3 times that, spread
  over 32 cores but bounded by the slowest region (Texas: Dallas 8M and Houston 7M after a 10 min
  read, 25-35 min). **About 1-1.5 h**, results packed and sent in 2-3 min.
- **What comes back**, one tar per runner region, PUT to `<run>/results_<region>` as each finishes
  (so a spot interruption loses at most the regions under way): `data/packs/<id>.{json,bin,
  boundary.geojson,places.json}`, `data/work/<id>.*` and `data/work/res9/<id>.*`, the state caches
  `data/work/usa/blocks_<fips>.npz`, the per-row OSM caches in data/raw, the batch logs
  `artifacts/trainworld/world_run/<batch>/`, and the rows' plan records (status, `run`). About
  15 MB a row, 0.8-1 GB a wave, $0.07-0.09 of egress.
- **Landing at home** (T-1065's `land.py`): refuse while any `world_run.py` lives; unpack into the
  inbox; check each row's four pack files; copy into data/ and the logs into their batch folder;
  under the plan lock set each row "built" with the machine's run record. Then `world_run.py run
  --rows <region's ids> --no-join` gates them (a built row with its packs skips download and build),
  then the join, as the pilot.
- **Spot interruption**: one-time spot, so an interrupted machine is gone with its disk. The user
  data polls the instance metadata's `spot/instance-action` every 5 s and on the 2-minute notice packs
  and sends what is built. A relaunch under a new run name takes only the rows not yet home. Over the
  last month the m7a.8xlarge price in Ohio moved within $0.31-0.44, a calm market.

## Wave 1 on AWS (T-1065, 2026-10-23)

US wave 1 (the South, 63 rows) was built on three spot machines in 0.81 machine-hours for **$0.32**;
gate and join at home (notes/T-1004.md "Wave 1"). Every run ended with `teardown.py` and an empty
bucket; nothing of ours is left in any region.

| Run | Machine | What it did | Time | Cost |
|---|---|---|---|---|
| us-w1 | m7a.8xlarge, $0.335/h | the check row `low` failed in `nocar`: the ACS B08201 file was asked for by hand, never fetched (T-1064's trace had it cached); torn down, `nocar` fetches it now | 0.16 h | $0.058 |
| us-w1b | m7a.8xlarge, $0.335/h | `low` (seeded with home's Georgia OSM caches), then the six regions: 58 built, 5 parked in Texas; a spot interruption notice came at 20:25:57, 4 s after the last region was sent | 0.35 h | $0.179 |
| us-w1c | m7a.4xlarge, $0.232/h | Oklahoma's 4 (its tar had come back corrupt) and Texas's 5, after the fixes: all built | 0.30 h | $0.085 |

**Time on the machine against home.** Setup (apt, uv, Python packages, rustup, the two bins) 1 min.
State caches for nine states 1 min 15 s. Extract reads 1-5 min each, three at once plus the check
row's: Texas (693 MB) 5 min 7 s, the rest under 3 min; all nine done 6 min after setup. Builds, all six
regions at once on 32 cores: Alabama 4.6 min, the Carolinas 4.6, Arkansas-Mississippi-Tennessee 5.7,
Louisiana 6.3, Texas 6.4, Oklahoma 9.5 (its 1.37M Oklahoma City built 107 s in build_city). Per row
the steps match home (zones median 1.8-2.2 min by division, Houston 4.5 min with 2 threads against Atlanta's
10.3 at home); the gain is 33 builds at once. Peak memory 58.6 GB of 128. **The wave's builds took 10
minutes from the go; at home at 10 builds the pilot's estimate was about 3 h.** Results about 800 MB
home over the three runs ($0.07 of egress, inside the costs above).

**Linux against Windows** (`low`, the same code, the same OSM caches seeded from home, a fresh
Windows build in a `--root` scratch tree): 6,864 cells and 1,995 zones both; 30 of the merged pack's
34 arrays byte-identical (people, jobs, commutes, zones, drive_near and drive_far, gravity factors
but 3 at 2e-9); the res-9 pack's people differ in 2 cells by under 0.01 (float32 rounding of the
block spread); boundary, places and stations byte-identical. The one real difference: 4 water-edge
entries (`water_x`, and 3 `walk_x` beside them), from the machine's fresh osmdata water polygons
against home's older copy. Header floats differ in the last digits. T-1064's own scratch reference
turned out to be half rebuilt by its memory measurement (res-9, no coarse grid), so it could not be
the comparison.

**Faults found and fixed** (general, small): `nocar` now fetches ACS B08201; GDAL's OSM driver can
return a ring of under four points (Dallas, Wichita Falls, Tyler: shapely's centroid raised in
`canada.osm_places`; its polygons are kept now); `enrich_medical` failed San Antonio and El Paso on
2 and 4 real hospitals with no cell within 500 m (it now fails only when over 5% of facilities miss,
and logs the misses); concurrent downloads of one file (GHSL tiles, census files) wrote one `.part`
(now a temporary name per process); the spot watcher and a region's own end packed one tar at once
(Oklahoma's came back corrupt; one sender a region now). Overpass (T-1066): no US build queries it
(osm_caches and places read the extract); wave.sh blocks the Overpass hosts so a query would fail at
once, and none did.

**Tooling** (T-1065): `world_run.py run --build-only`, `bundle.py`, `userdata/wave.sh` (with
`wavepack.py`), `land.py`, `launch.py --get`. The flow is in docs/aws.md.

acts when a tag, the region, the identity (`sts get-caller-identity` must be anita in account
429583250612) or a live run disagrees. The bucket `anitabuilder-builds-use2-k7q4`: tagged, public
access blocked, objects expire after 14 days, multipart uploads after 1.

checks 59 command lines (21 allowed, 38 refused), all as expected; fed the hook's JSON on stdin it
exits 2 with the reason for `aws ec2 terminate-instances ...` and 0 for a tagged `describe-instances`. Settings entry:

`artifacts/trainworld/aws/inbox/proof*/log`, records and costs in `artifacts/trainworld/aws/proof*.json`.

| Run | Machine | Found | Cost |
|---|---|---|---|
