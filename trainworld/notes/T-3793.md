# T-3793 Station rename takes about 4 s to show up

Anita, 2026-11-19: "station renaming takes a long time to show up. it looks like it doesnt go through for a while ...
takes like ~4s to update on my large save."

## Saves

- Big save: her own `artifacts/trainworld/t3600-asianita-1852.save` (221 lines, 2,647 stations, 123 zones). It is far
  bigger than any fixture in `checks/INDEX.md` (the biggest, `t3302-tokyo-day77.save`, is 36 KB against 565 KB).
- `T-007-real-nyc.save`: a rename already showed in 0.2-0.3 s there (client edit, paused, after the final), so all
  the work below is on her save.

## Measuring

Probes in the scratch folder (`abprobe.js`, `uiprobe.js`, `probe.js`): rename through the station panel's name box
(double click, type, Enter) and time from the Enter key to the panel title and to the map label (`StationLabels`)
showing the new name, then rename back the same way. Temporary stamps (removed) gave, on one clock across both
threads: the client's post, the worker receiving it (`onmessage`), apply, the rows or full state posted, the state
taken on the main thread, and the worker's long tasks (over 60 ms) meanwhile.

## Where the time went (before)

Paused, after the final, panel open (6 samples): panel and label 700-1,200 ms, median about 775.
- apply (the generic Rust edit path, `commit_with`) 55-100 ms
- the full state: rows 70-160 ms plus the renderer's network ("buffers") 230-650 ms, for an edit that changes
  nothing in it (`map/network.ts` has no names)
- trips and boarding ~50 ms, then the main thread: the state held for its trips, taken (~100-200 ms) and drawn

Clock running, station panel open: the label took 1.3-6.1 s, and nearly all of it was the edit waiting before the
worker even received it (the worker never yielded for 1-5.5 s). Its long tasks meanwhile: the panel's `today` query
(boardings in the past 24 hours, re-asked every 250 ms while the clock moves) at 140-745 ms each on this save,
`linesPeriods` at 60-380 ms each, and the hourly `epoch` at 300-830 ms (once 4.3 s). This was while other agents'
games loaded the machine, and it is the only condition that reproduced multi-second waits like her ~4 s; it has no
matching after run (the A/B below ran on a quieter machine).

A rename never starts trips calculating again (`stationsKey` has no names; checked, the demand version stays).

## The change

- `clock.worker.ts`: `nameOnly(op)` (renameStation, renameComplex, bindStation, bindAll, a stationProps that keeps the
  platform, a lineLook with only a name). Such an edit sends the rows at once (`sendRows`, as T-2766's stop clicks) and
  its answer after them; the full state follows unheld, with no trips or boarding steps (no train's run changed). The
  end state is the same as before, so save, undo and sync are untouched. Falls back to the old path when `sendRows`
  can't (before the first network, or a draw anchor move pending).
- `NameEdit.tsx`: the typed name stays shown from Enter until the edit's promise resolves or the name prop changes
  (the old name coming back looked like the rename had not gone through). `commit` compares against what the box
  shows, so retyping during the wait neither drops nor doubles.
- `today.ts`: after an answer, no new ask for twice its round trip, at most 1 s (250 ms floor from the interval); a
  forced ask (panel opened) and the one after a stop edit go at once. The cap: the round trip also counts reads held
  behind stop clicks or a long hour's turn.
- Not changed: Rust. apply is still ~50-100 ms of the generic edit path (`commit_with`); a name-only fast path there is
  the next step if wanted.

against 140-745 ms earlier), which is why the A/B was done in one game. linesPeriods asks per rename: 0-4 old, 0-5 new,
no doubling seen.
