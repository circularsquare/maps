# T-3902: is messy code slowing changes down (2026-11-20, agent codehealth)

Read only. Everything below is measured from the 2,249 subagent transcripts since 10-20 (streamed by script, never read
whole), git history, the landing logs (`artifacts/trainworld/finish-*.log`, from 11-17 only) and the checkers' reports.
Scripts and their outputs are in the scratch folder listed at the end.

## For Anita

- **Small and medium changes have not got slower.** A task with no big code change took a median 0.6-0.9 h from its
  agent starting to the change landing in late October and early November. This week it is 0.4-0.6 h.
- **Big or risky changes have.** Tasks with a large code change took 1.0-1.2 h to land before 11-17. Since 11-17 they
  take 1.8-2.3 h, about twice as long. That is probably the slowdown you feel: these are the changes you wait for.
- **Most of the extra time is checking, not the code.**
  - Since 11-17, 6 in 10 of these tasks get a checker agent. It takes a median 22 minutes, and some need a fix round
    after it. This is about half of the extra time. The checkers do find real bugs: about 10 real ones in 112 rounds.
  - The building agents also run the game much more than they used to: about 40 minutes of running and waiting on a
    big task now, against 15-25 before. That is about a third of the extra time.
  - The machine is fuller. Since 11-18, 16-31% of in-game checks got only 1 CPU core, against about 2% before. A
    wait for trips to be calculated takes a median 106 s on 1 core and 79 s on 3, so this costs something but is a
    small part.
- **The code's share of the slowdown is somewhere from nothing to about a fifth.** On big tasks, agents now take about
  12 minutes before their first edit, against 4-5 in October, and read about a quarter more before it. That could be
  the code, but it could equally be harder tasks or the model thinking longer (Opus has run at high effort since
  11-12). Since 11-17, 8 of about 140 landings stopped on a clash in a code file. 3 of them were in the clock worker,
  and 2 were today, caused by the splits themselves.
- **The big files do have a standing cost**, but it hasn't grown. A small or medium task that edits one of them takes
  about 10-20% longer than a similar task elsewhere, the same in October as now. Failed edits stay under 1%.
- **How badly we need a cleanup: not desperately.** Today's splits took apart three of the five files agents edit and
  clash on most (the clock worker, the renderer, the track and station tools), plus the track model. What is left is
  about 8-10 hours of agent time. Only one piece is clearly worth doing soon: splitting the two demand files.
- **Two changes that aren't cleanup would likely save more**, both about checking, and both your call. One, as a
  trial for a few days: when a checker will follow, the building agent proves its change with one run in the game and
  leaves the wider testing to the checker. Today builders test just as much whether a checker follows or not (43 and
  41 minutes). The risk is that a checker FAIL then costs a whole extra round. Two: fewer games running at once, so
  each check gets 2-3 cores.
- I can't tell yet whether today's splits sped anything up. They landed hours ago. Running these scripts again in
  about 5 days would show it.

## What was measured, and how

**The unit.** For speed, one landed task: every agent whose description names that one task id (builders, checkers,
fix rounds), from the first one's start to the first commit naming the id that touches `app/src` or `sim/src`. For
where time goes, one agent. Agents doing more than one task are left out of the task figures.

**Size.** By what the agent edited in `app/src` and `sim/src`: S is up to 3 files and 150 changed lines, M up to 8 files
and 600 lines, L bigger. That is fixed after the fact, so I also cut the figures by model and by kind (UI only,
touching the sim). The trend holds in each cut.

**Time.** Active time leaves out gaps over 20 minutes (an agent waiting to be resumed). It is split without double
counting into three parts: the model (API calls), shell commands (all Bash and PowerShell calls, overlapping ones
counted once), and other tools. "Gaps" is what is left: mostly the model writing its answer. Two transcript quirks:
the 11-12..11-16 band's tool timings look broken (typecheck at 0 s), so read that band loosely; and the usage records
of 146 agents carry several iterations, so context is read from the last one (summing them had made context look
twice as big).

### 3. Friction

- **Landing clashes** (`finish-*.log`, 11-17 to now, 281 logs, about 140 landings): 15 stopped. Code files: the clock
  worker 3 times, then tools.ts, renderer.ts, world.rs, achievements.ts, stateRows.ts with clockClient.ts, one check
  file. The rest were docs, TASKS.md or the main tree's uncommitted edits. Four doc clashes merged on their own. So
  about 6% of landings hit a code clash. Six of the eight came before today's splits (11-17 to 11-19); the two today
  were the splits themselves: drawsplit (the renderer split) clashed in renderer.ts on its first try, and tramrail,
  started before the clock worker split, clashed in clock.worker.ts after it. A split costs a clash or two for trees
  already in flight.
- **Checker FAILs** (11-17 to now): 112 rounds, 15 reports say FAIL near the top, but 4 of those are passes with a
  remark. About 10 found a real fault:
  - Edge cases of rules: weekend headways in headway mode (T-3521), negative income with every fare at 0x (T-3578),
    stairs charged at ground-level stations (T-3888), one packed-file case (T-2486).
  - State going back and forth: undo and redo giving other counts (T-3482), the first undo after a load (T-3646), an
    account copy wrongly retiring a shared game (T-3720), scrambled one-way stops in one click order (T-3565).
  - One caused by the code's layout: four standing checks still called an edit op the change removed (T-3101). The
    agent didn't find every caller.
  The state faults sit where several parts each keep their own idea of the game (undo, saves, the account copy); the
  11-18 refactor survey ranks that area first. Even so, they are faults a careful agent could have made in any layout.
- **Standing checks out of date**: at least six agent reports spent time proving that a failing check also fails on
  master, because it expected old text or old behaviour (t1826 save strings, t2787 "Fares minus running costs",
  t1898 single track to high speed, t2365 bins, t1965 follow, t3137 two buttons). This costs builders and checkers
  alike. It is test upkeep, not code mess.
- **Stale WASM in a tree** after a master update tripped agents twice (T-3264, and a checker that rebuilt it).
- **Agent mistakes are rare and flat**: failed edits 0.2-0.9% of edits in every band; typecheck failures 5-18% of
  runs with no trend.
- **Same bug twice**: a grep of ARCHIVE since 11-10 for "regression", "caused by" and "broke" finds about 10, mostly
  checks going out of date. No sign this is growing.

## Recommendation, ranked

Cleanup pieces (hours of agent time):

1. **demandClient.ts split** (T-2374), 2-3 h. The biggest file left (5,605 lines), the most-read code file in
   October and still second, edited by 12% of code agents. Saves reading on every demand task and clashes between demand
   trees. Waits on binzip (T-2486). Moves only, so it should pass typecheck and smoke unchanged.
2. **demand.worker.ts split** (T-2374), 1.5 h. 2,879 lines, 8% of agents. Same reasons, smaller. Waits on no tree
   holding demand.worker.ts (islands1 held it this morning; check `agent-tree.mjs list`), and can run beside 1.
3. **Standing checks that fail on master** (new; not cleanup of code, but the same kind of upkeep), about 2 h, one
   Sonnet agent. Run the checks agents use most on master, then fix or retire the ones expecting old text or behaviour
   (at least t1826, t2787, t1898, t1965, t3137). Saves builders and checkers proving a failure is old, which this week
   happened in at least six tasks. Waits on nothing; needs cores, so off-peak.
4. **T-2843 graphics loss apart from demand**, 1.5 h, after 1. A real wrong state, not a speed item.
5. **T-1183 fixed-rate path**, 3-4 h on Opus, before the track rework's build stages. It doesn't speed today's tasks;
   it saves the rework's agents one rate mode.

Not worth doing now:
- **More comment trimming** (T-3458 on the other split files): T-3726's A/B test found stripped comments took the same
  or more steps. Leave the clock worker pass as the last one unless a file is being moved anyway.
- **code-map.md cut** (2-3 h): agents grep it, and it isn't in this week's 30 most-read files. Do it only if it keeps
  growing past the Read cap's use.
- **T-2375** (debug probes, URL module, dead CSS): about 25 lines of CSS and a tidier main.ts; no measured cost.
- **network.ts, wasm.rs, service.rs splits**: each is edited by 4-9% of agents and fits one or two reads. Split one
  when a task finds it in its way.

Changes that don't need cleanup, and would save more:

Both are Anita's call.

- **Don't test twice on checked tasks, as a trial.** When a checker will follow, the builder proves its change with one
  scenario in the game, and the checker does the breadth. L builders now spend a median 43 minutes in shell after the
  edit when a checker follows (about 32 of it, as a mean, is play and wait calls), the same as without one, and the
  checker adds 22. If the builder's part halves, that is about 15-20 minutes saved on each checked task (68 in the four
  days since 11-17). The risk: a checker FAIL then costs a whole extra round, so compare FAIL rates after a few days. A
  line in docs/orchestrator.md's checker brief and in builder briefs.
- **Fewer games at once.** Since 11-18 up to a third of in-game checks run on one core, and each wait then takes
  about a third longer (106 s against 79). Either the orchestrator keeps the number of agents driving the game under
  what gives each 2-3 cores, or `cores.mjs` waits a short time for 2 cores instead of taking 1. The first is a line in
  the orchestrator's doc. The second is about 30 minutes of work and needs a decision on how long a check may wait. The
  saving is smaller than the trial above: a few minutes per big task.
- **Rerun this measurement on about 11-25** (the scripts take about 15 minutes) to see whether the splits changed the
  big-file premium and clashes. Five days of tasks are enough to compare.
