# T-2821: the game in Firefox (2026-11-09, agent firefox)

Player report via Anita: "someone complained it kept crashing on firefox". No crash reproduced. No game code changed.

## Evidence from players

`shonei-server/tools/feedback.py --days 0 --game trainworld`: 8 reports, none mention Firefox, a crash or an error. A report stores only the game version, not the browser or the last error, so a report like this one cannot be placed (T-2826).

## Method

Production build of 2026-11-09 00:05 (`.tw-snap/trainworld/app/dist`) on a static server of the agent's own, 3 cores pinned, one browser at a time, other agents running on the machine (timings are rough).

Playwright's Firefox is not a fair speed test: the real save took over 1,233 s there (88%, unfinished), against 170 s in Chrome and 196 s in the same save in Firefox with no automation. Probably Playwright's debugger on the workers keeps WebAssembly on the slow compiler; not confirmed further. Its error and memory readings are still useful. The figures below come from Firefox with no automation attached: a script added to index.html reports to the server every 5 s (scratch: probe-server.mjs, bare.ps1).

The one error: `demand sums worker: undefined` at 151 s in Tokyo. An error event with no message, once, in one run. `inSums` handles it (marks the worker broken, works inline after); the run reached its final. Cause not found, and it did not recur in any other run.

Under Playwright, also once: `uncaught exception: undefined` beside an aborted download of the WASM (`NS_BINDING_ABORTED`) when the page replaced a worker during an import (North America). Not seen without automation.

Firefox gets 2 solving workers on this 16-thread machine where Chrome gets 3: the existing rule when memory is not reported (`poolSize`). WebGL2 was available (ANGLE D3D11, 16384 texture limit), `zoom`, `:has`, `@layer` and OffscreenCanvas all present, SharedArrayBuffer absent as in Chrome here.

## What this does not rule out

- **Low memory, the likeliest cause.** Firefox does not report `navigator.deviceMemory`, so `memoryRefusal` and `smallDevice` never apply to a desktop Firefox. By reading the code, a machine of 4 GB gets the full treatment Chrome would refuse or cut down. A big save needs 7.2 GB here. Not measured on a small machine, and no browser API says how much memory there is, so no change was made.
- ESR, Linux, macOS, 32-bit Firefox, weak or blocklisted GPUs, extensions.
- WebGL context loss in the runs without automation (not measured; the probe's `lost` field is a stub). In Playwright the only loss was the logo's own deliberate one.
- Errors printed only inside a worker, in the runs without automation: the probe sees what reaches the page.
- Headless is not a real window. `about:memory` was not used.
