# T-2746: an idle bubble click sometimes ~2 s

Agent bubbleclick, 2026-11-07. Anita: "when not recalculating trips, it takes like ~150ms usually but occasionally like
~2 seconds. and it doesnt say its recalculating the city".

## Cause

**A bubble clicked within a second or two of the last one waits for the last one's longer trips.** Each bubble click
asks the demand workers two things: the far end (`flowRail` + `purposes` from every solving worker, then `flows` from
worker 0, then the sums worker; what the map draws) and the longer trips for the panel (`icSel`, every solving worker).
`icSel` runs 1.0-2.7 s in a worker on both saves at 2 cores (`selection_all_day` plus each market part's
`selection_rail_day`), and a worker answers one question at a time. So:

1. the new click's `flowRail`/`purposes` wait behind the old click's `icSel` (366-1666 ms measured), then
2. the new click's own `icSel` was sent at `FLOWS_FIRST_MS` (1 s) after the click, before its `flows` reached worker 0
   (that waits for the `flowRail` answers), so `flows` waited behind it too (1777-2578 ms).

No solve runs meanwhile, so the status shows nothing. Clicks spaced a few seconds apart never hit it.

## Why icSel is slow (for T-2747)

A CPU profile of the demand worker over 8 idle clicks on NYC (`wprof.mjs`: CDP `Target.attachToTarget` on the
worker, sampling at 200 us; `../artifacts/trainworld/t2746/wprof-nyc-1.cpuprofile`): 10.4 s busy, of which JS `query`
self 3.5 s (`Float64Array.from` of the WASM result and the per-part add loop), the wasm-bindgen `.slice()` copying
results out of WASM memory 3.6 s (`selection_all_day` 2.0, `selection_rail_day` 1.6), GC 0.9 s, the Rust `selection`
itself about 1.7 s, `flows_day` 0.3 s. The cause is the answer's size: **408,816,544 bytes** (51.1M f64) per worker
per click, measured on the reply. The layout (`selection.rs` `selection`) is per world 6 km zone (`n_gid`, every
place's zones, about 1.25M): 4 (longer trips) + 3 (zone x, y, place) + 4 (commutes) + 30 (`E_CROSS` 5 kinds x 6),
plus 12 per place. Nearly all of it is zero for a selection of a few cells. It is allocated and zeroed in WASM,
copied out, copied again, added per market part, transferred to the main thread, transferred to the sums worker
and walked there (`sumParts`, `selectionFlows`). Caching `zone_row` (the first idea) would touch only part of
the Rust 1.7 s, so it was not built.

### T-2747 design (proposal)

- **Answer**: the same head (matched share, per place 8 numbers: `1 + 8 * np`, small) and the two "elsewhere"
  numbers; every per-zone block as a list of the far zones it touches: gid, then that zone's numbers in the block
  (longer trips 4, commutes 4, each E_CROSS kind 6), with the zone's x, y and place read from the market once on
  the page (the zones' xy are the same for every answer; `write_zone_xy` today writes all 1.25M of them into every
  answer). The commutes' per-place block (4 per place) stays dense. One `Float64Array`: `[head..., nZones, (gid,
  k values)..., elsewhere 2]`, or one array per block.
- **Rust**: `selection` collects into a `HashMap<gid, [f64; 38]>` (or sorted vec) as it goes instead of the dense
  `out`; `selection_rail_day` zeroes the non-rail entries of that. Same sums, same order of addition per entry, so
  the figures match to the bit.
- **Readers**: `demand.worker.ts` `icSel` (adds each part's rail into the market's answer: a merge by gid),
  `demandSums.ts` `sumParts`/`addIntercity` for `icSel` (merge by gid over workers, in worker order as now) and
  `selectionFlows` (walk the listed zones instead of `for z < nz`; `intercityZones`/`intercityZoneXY` go for icSel).
  `icStation` (5 per zone, 6.25M entries) has the same shape and could follow in the same change.
- **Gain**: an answer of a few thousand entries; icSel per worker from 1.0-2.7 s to the Rust part alone, likely
  under 100 ms; no 409 MB per worker per click (memory peaks and GC with it); the rapid-click wait behind it gone.
  An interface change (`docs` rule: its own tree), Rust tests and a check comparing the panel's longer trips before
  and after on the real save.
