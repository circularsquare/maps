# T-2820: a save with a broken line would not open

Player report (brandon, 2026-11-09, live build 4f1b6fc8): "The train simulation could not start (Error: recursive
use of an object...)" on loading a save. The report is not in `tools/feedback.py`'s store, which has 8 trainworld
reports in 14 days, none from him, so no save or browser details were available.

## Cause

`delete_edge` and `DeleteEdge` keep a line whose track was deleted with no way round: it stays, broken, with its path
still on the dead edge (`world.rs`, "Lines using it reroute or break"). In the running game the dead edge's id is in
range. The save writes it as none (`edge_id`'s u32::MAX). `decode` read that back as `(prev as u32) << 1`, so the edge
is 0x7FFFFFFF, past the end of every array.

Then, on the load: `keep()` runs `a.save()`, `encode` indexes `edge_id[0x7FFFFFFF]` and panics at `save.rs:204`. `keep()`
swallows it in its try/catch, the panic leaves the object's borrow held, and the next `&mut self` call throws "recursive
use". The start path caught that as a load failure, carried on with the same stopped model, and reached `.catch` with
the second error. Clock messages then kept calling it ("Rust panic in clock", with the wasm-bindgen throw in the stack).

Nothing in the save is wrong: every save of a game with a broken line hits this on its next load, and the same save
opens now.

Reproduced three ways: a unit test (`a_broken_line_saves_and_loads_again_and_again`, panics at `save.rs:204` before
the fix); `line8.save` with a line's only track deleted, re-saved and loaded in WASM; and that file through the start
menu path in headless Chrome with the unfixed WASM, whose trace has the same `__wbg___wbindgen_throw_41e9ee4f547fc59a`
frame as his report. The encoder lines at 4f1b6fc8 are the same as master's.

## Fix

- `save.rs` `decode`: a stop or path edge past the dense ids points at one dead slot (allocated once, never on the free
  list), so a loaded network has the same in-range dead id the running game had. A first fix in `encode` alone left
  `net.rs` `path_nodes` panicking (`passed_stations`): the out-of-range id was the fault, not its readers.
- `save.rs` `encode` tolerates an id past the table the same way.
- `save.rs` `decode`: an edge's ends out of range is a damaged save (`Err`, "This save is damaged."), and `Vec::with_capacity`
  is capped by the file's size. Both only reachable with a corrupted file.
- `track/wasm.rs`: a panic hook and `last_panic()` as the demand module has (T-1174).
- `clock.worker.ts`: `panicWhy` gives the Rust message first. A panic while opening a game (start path, real network,
  stored slot, a file opened in game) replaces the model before anything else; the player gets
  `clockWorker.savePanic` with the message, and the game goes on (a new one, or the one in hand). A panic that reaches
  the start's `.catch` sets `modelDown`, so no later message calls the model.

## Tried

- Node sweep of the WASM load calls and every read the state makes (`sweep.mjs`, scratch): 79 of 110 saves on disk, all
  clean, before stopping it for time (the big real networks took minutes each). Not rerun on the fixed WASM.
- Byte-flip fuzz, 1,600 mutations of 4 small saves: before the decoder fix 52 panics (`save.rs:510`, 197, 204, capacity
  overflow); after it 0.
- Water and terrain are not in the node sweep; the browser runs have them.
- Browser, start menu path, unfixed encoder with the new worker: the broken save shows "This save could not be opened
  (panicked at src\track\save.rs:204:28: index out of bounds...)" and the page goes on with a new game. Same through a
  file opened in game.
- Browser, start menu path, fixed: the broken save opens (5 lines, 38 stations, the broken line kept). Anita's
  world day 17, Paris, Tokyo, North America day 476 and the real New York save all said "Game loaded", no console
  errors. North America and New York had not finished drawing when the check read them 5 s later, so their
  line counts were not read there; smoke loads New York whole.
- Not tried: his own save, which we do not have, and a scratch build of 4f1b6fc8 (its encoder lines are the same).

## Not known

That his save has a broken line is inferred: the error and trace match exactly and nothing else found panics, but only
his file could prove it. If he still fails on the new build, the notice now carries the Rust message and line, which
is the one piece of information that would pin it down.
