## What changed

### Terminal bays from the kept phase tables (clockDemand.ts `bayTimes`, stateRows.ts `phaseTablesNow`)
- Every trips send asked the model for every line's phase tables again (`line_phases` per line) to place trains at
  line ends. Now it reads the tables the rows keep, after reading again exactly the lines `phases` would (pending from a
  rows read, or moved since the last take: an edit not yet read, a trial). A line the rows have not seen is asked of the
  model.
- Measured in the edit's own timing (`bays`): 4-13 ms a send before (`?patch=walk` arm), 1-8 ms after. Small on a
  quiet game; in my first profile, taken while trips were still being calculated, the same reads were 4.8 s of 25 s
  busy worker time, from repeated sends.
- `?patch=walk` reads them from the model, as before; `?patch=check` compares every line with the model's.

### The money record posted by its changes, without walking every ledger (clockMoney.ts `moneyState`, clockPost.ts `moneyPost`)
- Each state and money message carries the money record as its changes from the last one (T-3803), worked out by
  comparing the whole record: every region's day and hour ledgers, about 2 MB on Asia, copied anew each time.
- Now an unchanged ledger entry's copy is the same object as last time (kept per entry while it is equal), and the
  record held for the next comparison keeps the ledgers by reference, so unchanged entries pass by identity.
- Measured in the post's own timing (`pMoney`) on Asia: 7-71 ms a post before, 1-2 ms after. The same record goes in
  every "money" message, four times a second while the clock runs.

### The panels' day figures per line (sim boarding.rs `window`, `past_day`)
- `today` read every line's past 24 hours from its boarding account (`past_day`), 125-445 ms on Asia, asked about
  twice an edit (on the new world and on the new boarding hour). Each line's block is now kept with what it was read from:
  the time, the two accounts (each made once and never changed, numbered as made) and the service parts the block reads
  (shift, crush and rated loads, loop kind, round trips, profile durations). After an edit only the lines whose account
  or service moved are read again. While the clock runs, the time moves, so every block is read again as before.
- Same game, same calls (`?patch=check` calls both): over 14 station, delete and copy edits and their undos, with trips
  being calculated again meanwhile, `past_day` took 659 ms in all against 2,872 ms for the whole read (77% less);
  `line_periods` 1,485 ms against 3,510 (58% less). An edit that moves one line's account (a colour, a reorder) reads
  one line again; while trips are calculated many accounts move, which is the case measured here.
- `past_day_whole` reads with nothing kept; `?patch=check` compares the two in the worker. Rust test
  `past_day_kept_blocks_equal_a_fresh_read`.
- The same for `line_periods` (the Lines tab's and line panel's crowding by period, `linesPeriods`, about 80 ms an edit
  on Asia for every line): kept per line and kind of day while its account and its crush and rated loads stand; it reads
  no time. `line_periods_whole`, the worker's check, Rust test `line_periods_kept_equal_a_whole_read`.

### The cause, in the code

Two lists the model hands the worker after an edit name far more than the edit touched, and the worker treated every
line on them as if all of it had changed:

- **The settle notes every line it scheduled.** On shared track (most of Tokyo on her save) an edit re-times dozens of
  lines, so `take_changed_lines` notes them, and T-4113's stamp hashes each one's whole row to find the few that moved.
  Each stamp read the line's weekends (`line_weekend`, `line_row_weekend`), and each of those worked out every line's
  track limits (`Capacity::line_limits`, a pass over the whole network) to use one line's: two whole-network passes per
  noted line, and two more per line the rows then read again. Now the limits are worked out once for all the lines one
  call reads (`TrackWorld::weekend_counts_in`'s shared limits, already used by `weekend_own`): the stamps take them once
  (wasm/touched.rs), and the rows read every deep line's weekends in one call (`line_weekends`, workers/stateRows.ts
  `weekendsOf`). Same numbers by construction; Rust test `line_weekends_are_each_lines_own_reads`.
- **A line whose profiles were worked out again was drawn again.** `forget` (workers/clockMain.ts) dropped the drawn
  run samples of every line in `dirty_lines` (profiles recomputed), so 38-44 lines were sampled again on every edit
  (`run_polyline`, `run_bends`), though a settle's timing moves no sample. Even the model's "rebuilt" list is broad
  (every bus line and every line with a way back is rebuilt on most edits, onto the same track). Now the service notes
  the lines whose runs lie anywhere new (sim service.rs `note_moved`: a rebuilt train line whose entries, offsets or
  length moved, or with a touched edge under it; every bus and ferry line), the worker takes that list
  (`take_moved_lines`) and samples only those again. Rust test `lines_left_off_the_moved_list_run_where_they_ran`.

### What an edit touched, one list (`ClockState.touched`)

Every state now names what it holds that the last state posted did not: the ids of the edges, nodes and lines whose
rows changed or are gone (its delta's, exact against what the page holds, so a dropped follow-up or a rows-only state
loses nothing), and the lines whose drawn runs moved since the last network posted (`paths`); `all` on a whole post or an anchor move (every drawn position moves). The construct-all
quote's trial (`trial_with`) puts the service's moved list back after its rollback, so its lines are not sampled again.
Built once in workers/clockPost.ts `touchedOf`, typed in protocol.ts `EditTouched`. The page (T-4150), the drawn
network (T-4153) and the clickable map (T-4214) can patch by it; none reads it yet.

### The equality check

`?patch=check` already built the whole rows from scratch beside the kept ones (T-1382). It now also compares every
line's kept run samples and bends with the model's (`checkSamples`: the network check builds its scratch network from
the same samples, so it could not see stale ones), and the weekends read together with each line's own reads. Her save
has no planned line, so the line rows were compared too. In Node over the twelve edits below with check on: no
difference.
