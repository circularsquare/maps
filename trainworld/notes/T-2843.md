### 1. A recovered panic leaves the game earning nothing (high when it happens, proven)
`workers/clock.worker.ts:2618-2623` (`restart` zeroes the income and clears riders), `:829` (`rebuildModel` calls it);
`workers/clockClient.ts:700,1059` (`forgetSent`); `workers/demandClient.ts:3451` (`key === lastKey` returns with no solve).

`restart` was written for a different game arriving, and panic recovery reuses it for the same game. It zeroes `incomePerHour`,
`ridesPerHour`, `lineIncome`, `lineRides` and `linePoints` and calls `clear_riders`, trusting "the next round" to send them again.
`forgetSent` only clears the client's memory of what it sent. The effects that post income, points and riders run again only when
their signals change, and after a recovery nothing changes: the network has the same key, so no solve; `moneyWorld` and `moneyTerms`
are kept by value.

Scenario: any panic the worker recovers from, on a network that is not mid-solve -> notice "restored to your last edit", the game
looks normal, then fares 0 and running costs carry on, until the player makes an edit that changes the network or reloads. Trains
also show no riders (the boarding account is empty) and points stop. The lost income is saved into the ledger.

Measured on the real save, 8 s at normal speed, US$M: before the panic fares +25.71, running +9.47; after it fares +0, running +9.47;
8 s later still fares +0. No new solve in between (a one-off probe: `tw.client.debugPanic('now')` once `demandUpdating` is false). t1007-panic.mjs checks only the network and cash.

`loadGame` from `openOnAccount` (`:640`) takes the same path if the account's copy has the same network. T-2820 (422dc0de) added a
`recover` on a panicking import, one more way in. Possibly a part of T-2793's "fares going to 0 ... even when its not saying
recalculating" for a player who panicked; there is no telemetry to say.

Fix: `loaded` says why it came (state machine A). On "rebuilt": no hold, no tool or selection reset, and a `resend` signal read by the
income, points, riders and transfers effects (`xferAsked = null` too). Only for a rebuild: reposting at a real game change would send
the last game's riders to the new one.

### 2. Demand that failed stays "updating" (medium, proven)
`workers/demandClient.ts:3429-3488`. `submitNetwork` has no `failed` check: `:3475` sets `demandUpdating = true`, then `send` -> `ensure`
returns at once (`:1127`). Nothing can set it false again, and `uncovered` keeps growing.

Scenario A, demand stopped mid-game, player presses play and edits a line -> the line reads "calculating" for good. The 8 s timer
(`game/lineFigures.ts:113`) needs `!demandUpdating`, and `demandStopped.subscribe` settled only what was pending when it stopped.
Probe: `tw.failDemand()`, a train count edit, 12 s later `pending: ["0"], demandUpdating: true, stopped: "error"`.

Scenario B, failed startup, "Play without demand" -> `demandStopped` is never set on that path (`game/loading.ts:216-233`, it is only
set when `startup === "ready"`), so `demandCapped` has no way out: the first line built holds the clock at 4x for the rest of the
session and the line stays pending. Traced, not run.

Fix: after `networkWorld.value = wv` in `submitNetwork`, `if (this.failed) { finalWorld.value = wv; return; }`.

### 3. The graphics notice can swallow a demand failure (low-medium)
`game/loading.ts:172-176,226`. 2658b2c4's restore handler clears `demandStopped` when it is `"graphics"`, but `loadFailed` only records a
failure when `demandStopped` is empty. Scenario: context lost for over 6 s, a demand worker dies meanwhile, context restored -> no
notice, the clock restarts, demand is dead, and finding 2 applies. Also: while the graphics notice is up, `demandStopped` settles
every pending line and lifts the cap though demand is solving normally. Fix: separate signals (state machine B).

### 4. A second tab cannot go back to the menu (low)
`workers/clock.worker.ts:426`. `flushBeforeSwitch` throws on `dirty && !activeLease`, and `settle` sets `dirty` every time the clock
moves. Scenario: the same game open in a second tab, clock running, press main menu or open another game -> "Make a copy of this game
before leaving it", with nothing of the player's unsaved. Same for a game another device took. Fix: test `edited`, as the `newer` line
above it already does.

### 5. Stale `held` and `earlyNode` after Backspace or undo (low)
`map/tools.ts:884-901` (`takeBackSegment` clears neither), `:920-922`, `:955`, `:976`.

Scenario A: chain two segments quickly, Backspace, click within 24 px of the removed segment -> the click sits for 3 s in `heldLanded`
waiting for a node that will never exist. Scenario B: place a segment with the pointer moving (its state is held up to 5 s), Ctrl+Z ->
the run's start is `earlyNode`, gone from the world, and `requestPreview` skips its "undone meanwhile" reset because of the early-node
exception: every ghost is refused (`NoSuchNode`, no crash) until Esc. Fix: clear both in `takeBackSegment`; in `requestPreview` treat
`earlyNode` as live only while `held` is non-empty or its edit is unanswered.

### 6. Reload from the notice (low)
`workers/clockClient.ts:763-768`. It watches `saveSlots.at` with a 1.5 s limit. A save slower than that is cut off (the old slot
survives, up to 60 s of play lost; paid edits were already autosaved). When nothing is dirty no `saveSlots` comes, so it always waits
the full 1.5 s. Fix: the worker answers `flush` with a message of its own.

### 7. Drags (low)
`map/nodeDrag.ts:189`: `onMove` never checks `e.buttons`, so a press whose mouseup was lost (alt-tab during the drag, a dialog) keeps
dragging with no button down, and the next click applies it. It is undoable blueprint. `edgeEdit.ts` has no check either (seen by grep).
`nodeDrag.ts:294-296`: `clear()` runs after `await edit`, so a new drag started while the edit was in flight loses its preview and
grabbing cursor for a moment.

### 8. A failed file from the start menu (low; beside T-2820)
`workers/clock.worker.ts:3681,3692`. `fileChoice` writes `from: ""`, so when `loadGame` throws, `msg.slot` is "" and the page opens
`ORIGINAL_SLOT`. Scenario: the file passes `decodeSave` but fails to open -> toast, and the player is in their oldest game or an unnamed
new one. Nothing is lost. Fix: on `pending.from === ""` go back to the menu with the reason.

### 9. Copies never removed (low)
`workers/clock.worker.ts:2576,3739`; `saveFile.ts:612` (`deleteSlot`). Each is a whole save in IndexedDB that no UI shows and deleting the slot leaves.

## Part 1: implicit state machines

### Worth converting, most trouble first

**A. What a `loaded` message means.** Five different events share `restart` and `"loaded"`: first open, file or backup, new game,
account copy swapped in, panic rebuild. The default new game sends none at all and relies on `holdArmed`'s initial value (worker init,
after `setNewGame`). The client treats all alike: `holdForGameLoad`, selection and tool reset, `forgetSent`, `gamesLoaded++`,
`mapBlank` going true.
Wrong combination: same game, treated as a new one. Result: finding 1, plus a blank map flash, a dropped run and a reset of the
achievements' load baseline after a panic.
Form: `loaded.reason: "opened" | "new" | "replaced" | "rebuilt"`, and a `switch` in the client. About 30 lines.

**B. Demand health.** `startup`, `loadFailure`, `demandStopped`, `gameFailed`, `DemandClient.status`, `demandUpdating`, and the graphics
watch. As they really are: loading -> ready; loading -> failed-at-startup -> playing-without-demand; ready -> stopped (memory or error),
paused once; and independently, graphics fine or lost. `demandStopped` stores two independent facts in one value.
Reachable and wrong: failed + `demandUpdating` true (finding 2); failed-at-startup + played on, with `demandStopped` null (2B); graphics +
demand failed (3); graphics lost + `demandCapped` false while demand is healthy (3); `memoryResolve` left true by `fail()`.
Form: `demand = { kind: "loading" } | { kind: "ok" } | { kind: "stopped", why, atStartup, playedOn }` with one writer in `loading.ts`, a separate
`graphicsLost` signal, and `demandCapped` and the status tag reading those. About 60 lines; T-2849 starts it.

**C. Who may write the slot.** `activeLease`, `leaseTaken`, `cloudTaken`, `cloudClaimed`, `newer`, `testPage`, `storageReady`, `saveFailure`, `switching`,
`unwritten`, `activeSlot === ""`, with `dirty` and `edited`. Four places each decide from their own subset: `writableNow`, `autosave`'s guard, `flushBeforeSwitch`,
the `reason` chain in `publishSlots`.
Wrong today: finding 4. Risk: this is the machine that loses saves, and a new blocker has to be added in four places.
Form: one `writeBlock(): null | "noLease" | "otherTab" | "otherDevice" | "newer" | "testPage" | "storage" | "switching"`, used by all four. About 30 lines, no behaviour change except finding 4.

**D. Figures while recalculating.** `linesPending`, `since`, `quietEdits`, `wideEdits`, `loud`, `baseline`, `editStamp`, `demandUpdating`, `demandBehindFrom`, `finalWorld`, `networkWorld`, and
three separate holds of old figures: `today.ts` `settled`, `clockClient.ts` `settledIncome`, `money.ts` `incomeFor`'s `old`. A line is really one of: settled, pending
(build or change, from world version v), solved-not-yet-counted. Two timers paper over the exits (8 s, 30 s).
Wrong combinations produced T-2823 #3 and #4 and much of T-2773/T-2793's rounds. **Overlaps T-2793; do it after that agent is done.**
Form: one module owning `lineFigureState(id)` and the single kept copy of each line's last settled figures. About 100 lines.

**E. The load hold.** `loading.ts` (`holdArmed`, `gameReady`, `viewFigures`, `wait`, `gameLoadSeq`, `clock.held`) and `demandClient.ts` (`hold`, `ahead`, `early`, `loadKey`, `cacheSolve`, `job.wait`) describe
one sequence: picked -> network arrived -> figures shown -> released, or failed. I found no live bug on the paths I traced; T-742, T-2552 and T-2560 were in this family.
Weak spots: `clock.held` doubles as "a game is loading" (`lineFigures.ts:98`, `today.ts`), and `holdForGameLoad` returns early once `loadFailure` is set, so a load after a failure is not "loading".
Form: one `gamePhase` signal written in `loading.ts`, the rest derived. About 50 lines, after A. Do it when this code is next touched.

**F. The track tool, narrowly.** `start`, `chain`, `placing`, `endRun`, `earlyNode`, `held`, `touchAt`, and three preview keys. Convert only `earlyNode` + `held` into one
`heldRun: { node, pts } | null`, cleared together (finding 5). The rest guards itself adequately through `this.start !== from`.

### Leave it, fine as is

- `NodeDrag` `press` -> `drag`, apart from finding 7. `Newest` in clockClient. `tool` + `lineDraft`, with `stopEditing` computed. `Tools.stopClicks` and its session counter.
