# T-2136: the page keeps no world corridor table

Agent corridor, 2026-11-18, tree `.tw-trees/corridor` (master 866e3212), Vite 6199. Advisor called twice: before
building it confirmed T-2485's design (per-place totals on the page, a place's rows asked of a worker) and named
the traps followed below (share codes, stale keys, the cached result at load, latency mid-solve, no whole-column
WASM calls); at the end it caught achievements asking for every built place's rows in one ask (now from the book)
and had the figures and the cache check rerun on the final code.

## Short version

- The page held the market's corridor table: **8,538,584 rows** on the real save today (5.9M at T-2485; it grows
  with the square of the places), about 100 MB of the page's ArrayBuffers, and every solving worker streamed its
  four whole columns through its WASM to hash a key (47-68 MB of WASM high water each, never given back) and kept
  a row index (23-34 MB of JS each).
- Now nobody holds it whole. The page has each market's **book** (`CorridorBook`: row count, key, three sums per
  place, 150 KB); a view that needs a place's rows asks the solving workers (`rows`), the first answer wins, the
  last 48 asked are kept. The workers answer from the WASM's own figures (`IntercityApi.place_rows`).
- **Real save, settled: the page and the two solving workers hold 229 MB less (1,197 -> 968 MB of heap, buffers and
  WASM, after a collection); renderer 2,434-2,518 -> 2,290-2,343 MB over two pairs of runs. Load peak renderer
  2,716-2,744 -> 2,371-2,524 MB.** Every reader's figures identical to the bit (565 readings, final code against
  the old code on the same data), but achievements' (equal within rounding, below).
- A place's rows: **5-8 ms with the workers idle; up to 2.5 s while trips are calculated** (the worker answers at
  its next break). The zone in view's and up to 16 built zones' rows are asked as a market's book comes, so their
  panels never wait; another zone clicked mid-solve shows "Calculating trips" for its trips to other places
  until the rows come.
- A reload that shows the cached result: no worker holds the market for about 20 s (21 s measured, the final at
  82 s), so the cache now keeps the page's one-place rows (the zone in view's first, up to 16): measured, the
  zone in view's rows are there the moment the cache shows (1.7 s). Any other zone waits until a worker sends the
  book (`rowsCanCome` clears the misses then). Each cache write is now 9.8 MB plus the rows; it carried the
  whole table (about 100 MB more) before.

Each now reads: the book's sums (`totalsOf`, now `corridorFigures.ts` `marketPairs`; achievements' trips); the
rail rows' own places and share code, carried with each period's rail (`pairs`, points, achievements' rail); one
place's rows from `rowsOf` (the rest; one place an ask, so the page holds at most 48 places' rows, about 4 MB). The
cache stores the book and up to 16 places' rows, not the table (`CACHE_FORMAT` 11; `heldRows`, `seedRows`).

Achievements first asked for every built place's rows in one ask: on a big save hundreds of thousands of rows a
build, in the page and in every solving worker's WASM (advisor's catch at the end). They now sum a place's trips
from the book and its rail from the rail rows, equal to the rows' sums within rounding (a different order of the
same additions): the one reader whose figures are not the same to the bit.

## What changed

- **Sim** (`sim/src/demand/intercity/exports.rs`): `table_summary(limit)` walks `table_rows` once: row count, an
  FNV-1a key over each row's corridor, trips, commute legs and shares, and per place below `limit` the three sums
  the city view used, added in row order with the share in the page's 1/65534 steps, so the figures are the
  page's to the bit. `place_rows(places)`: the table rows touching any of them, corridor ascending, 7 numbers each
  (the page asks one place at a time).
  `rows_at(corridors)`: the places and figures of given corridors (the rows with rail). `Corridors.trips_of` finds a
  corridor's trips through a rank of `has_trips` (4 bytes per 64 corridors, made when first asked); `commute_of`
  by bisection. Test `place_rows_are_the_table_rows_of_a_place`: rows, `rows_at` and the sums equal the
  `corridor_rows_*` columns to the bit.
- **Worker** (`demand.worker.ts`): `tableColumns`, `inPlace` and the row index are gone; `corridorBook` (once per
  `corridors_id`), `rowsFor` (the `rows` message, answered whatever is being solved, null for another key),
  `marketCorridors` keys the rail by corridor and adds each row's places and share code (`railMemo`, cleared with
  the book). The rows' ids are corridor numbers now, not table row numbers: the same order.
- **Page**: `game/demand.ts` `CorridorBook`, `CorridorRows`, `rowsOf` / `rowsNow` / `rowsLanded` (a signal, so a
  computed or component reading `rowsOf` works out again as rows land); `Corridors` carries `railFrom`, `railTo`,
  `railAir`. `game/corridorFigures.ts` holds the readers' sums (`marketPairs`, `zoneRowOf`, `placeFigures`,
  `pairFigures`, `ownModesFrom`). `demandClient.corridorRows` asks every solving worker, takes the first answer
  (null after all say none, or 20 s). `perfOff=inPlace` is gone.
- **Fixed on the way**: `intercityView.ts` subtracted the rail rows' plane trips with the raw 16-bit share code
  (T-3493's change of `air` to codes) where it meant the share. On the real save no rail row has a plane share, so
  nothing shown changed there; elsewhere a zone's plane trips in the city view would have gone hugely negative.
- While rows are not in: the zone inspector shows "Calculating trips" for its trips to other places (as a
  loading zone does), the trip graph waits, the city view's selected zone draws its own bubble and the others when
  they land, the trip panel's pair line waits. A cached result brings its 16 places' rows; others wait for a worker
  to send the book. With the demand pool stopped ("Demand stopped") a place not asked before keeps waiting.
  DECISIONS 2026-11-18 (T-2136) records these waits.

## Rebase onto T-3509

Agent corrmerge, 2026-11-18, onto master 3c1ade0f (T-3509 is 6771f7f5). The text conflict was one import line in
achievements.ts; the real clash was that T-3509's `withinOf` and `marketIn` read the page's corridor table, which this
task removed. Advisor called once, on where the within figure comes from; it agreed with the plan below and added
the 32-bit rounding, the cache format and checking that the book reaches a day no earlier than the table did.

- **Where a zone's within figure comes from now**: the book, no rows asked. `table_summary` skipped each place's own
  row (`a == b`); it now appends two numbers per place after the three sums: the own row's longer trips and commute
  legs (`CorridorBook.own`, the worker rounds the longer trips to 32 bits, as the old table's `Float32Array` held
  them). The rail is the day's rail row with `railFrom === railTo === place`, which the page already had. `withinOf`
  = own longer x `longerScale` + own commutes x `commuteScale`, rail from that row, same null rule and
  `min(rail, trips)`; `zoneView`/`zoneViews` unchanged. `marketIn` reads `book.n`: a day gets its book in the same
  step as master got its table (`corridorsOf` gives NO_CORRIDORS until it is in), and a cached day carries it.
- Also: `CACHE_FORMAT` 11 -> 12 (a book cached without `own` would read as no within while `marketIn` holds),
  t328's signature covers `own`, the Rust test checks the own sums to the bit on a world that has them,
  demand-runtime.md names the own sums. Every T-2136 reader is untouched; after the rebase nothing in app/ reads a
  corridor table (grep of `.table`, `eachCorridor`, `withinOf`, `marketIn`: only the book, rows and rail rows).
