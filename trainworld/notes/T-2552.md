## T-2557: the reload hits the cache

The reload hits, by the network's hash, on this tree's code (master): the import's final and the reload's network
are the same (`c011a806d823` on both sides, `before1`, `after1`, `after2`), the cached result is shown 24-30 s into the
page (the network's arrival), and the zone in view's bubbles with it. loadnotes' 193 s reload (T-2524) was a miss
on purpose: its `prof.mjs` sets `client.cacheWrites = false` before the import ("no cache written, so a reload
misses, as after an 8800 rebuild"), so its reload stood for a reload after a rebuild, not after an import.

| run | import: network in, final | reload: cached result shown, final |
|---|---|---|
| before1 (master, 3 cores) | 21.5 s, 248 s | 29.8 s, 218 s |
| after2 (4 cores) | 17.4 s, 198 s | 27.0 s, 174 s |

The reload's ahead read (T-1539, 3-4 s in) misses on the first reload after an import, as T-2499 found: the pointer
the import's final writes is keyed by the file's bytes and the slot's differ; a second reload hits ahead. With the
cache hit the loading card still stays until the fresh final (T-347), 174-218 s here, with the cached figures and
bubbles behind it.

## T-2552: the bar's faults and fixes

The player's path matters: Open a file reloads the page with the file pending (`switchGame`, `?load=file`), so an
import is a page start like a reload. The `*p` runs take that path (`PLAYER=1`, `importGame`); `before1`, `after1` and
`after2` posted the import into the running page as the checks do (`lib.importSave`), where the faults differ a little.

What was wrong, and the fix (all in `game/loadBar.ts`, `workers/demandClient.ts` unless named):

1. **A file's wait took the last game's remembered wait.** A pending file started its wait under "last", then at
   "loaded" under the active slot, which is still the last game's (the worker makes the file's new slot active only
   after loading it). Before the network `sameSize(rec, null)` accepts any record, so the last game's stage shares set
   the bar (a small New York game: 70% in the game stage), and the import's own wait was then remembered under the
   last game's slot. Fix: `game/loading.ts` `waitKey` starts a pending file or backup under "pending", where nothing is
   remembered; the worker's "loaded" names the slot it loads into (`clock.worker.ts` `loadingInto`, `protocol.ts`
   `slot`, `clockClient.ts`). `sameSize` stays: with the key right, a record found before the network is the game's.
2. **A game load before its network counted as needing no solve** (the check path: the network in hand is the last
   game's, with no zone): the solve's 70% share counted done. `jobNeedsSolve` is true for a game load still armed.
3. **The solve pace came from a 4.5 s solve.** The fresh profile's empty New York game set this browser's solve pace
   to 0.3 of the model and its later-round ratio from a trivial solve, so the 81-zone solve was expected at 22 s
   (real 135-170 s) and its share of the bar was 15%. `PACE_SOLVE_MS`: pace and ratio are learned only from a game
   solve of 10 s or more. (Anita's own browser has her big saves' pace; the fault was worst in a fresh profile.)
4. **The bar stood still after an estimate grew.** `keepPlace` (the anchor the card already had, now in loadBar.ts
   and shared with the zone bars) re-anchored only when the shown share fell below the best; a fraction falling
   below the anchor's own left the bar waiting until it climbed back. It re-anchors on any fall.
5. **The last round's converged period set its pace** (T-2524's third fault): `QUICK_LAND`, a later round's first
   period in under half a wave's expected time is not taken as the round's pace. And the first round's setup
   (`set_network`, 15 s here) is counted once, not times the waves (`setupOf`, `solveStage`'s `setup`).
6. **Zone bars outside the load** counted download and opening only, then sat at 99% (T-2524's second fault; on this
   save their values sat at 99% under the card, hidden): a zone a solve covers now also waits for that solve
   (`zoneShare`, the running solve's stage, else the next solve's estimate), its opening counts the solving workers'
   acks, each bar keeps its place (`keepPlace`), and none is kept while the card is up, so a bar shows from its own
   share when the card goes.

Check: `checks/t2552-load-bar.mjs` (in smoke's Node checks): `solveStage` and `keepPlace` on this save's measured
rounds with the solve expected right, at half and at twice; fails on master's `solveStage` ("A few seconds left"
with 24 s to go; 30 s on one percent at half).

### The real save misses its first reload (not fixed, for a task)

T-2531 saw the real New York save's reload miss on every build. Same flow here (`realp`): networks `7c1363f88e17`
against `3333d9431d26`, differing in the fare alone: base 0.12979761789682243 and perKm 0.008653174526454829 on the
first load, 0.1298 and 0.008655 on every later one. The real save is from before T-1521 (no fare `basis`): its fares
are converted on load and `game/fareCurve.ts` `faresOf` keeps a base and rate given without nodes to the last digit,
while a save with nodes (the slot's, written after) gets the rounded nodes' line, the exact base failing `isStraight`'s
1e-6. Only such old saves; Anita's North America save hits. Either fix changes some save's figures slightly (rounding
the first load changes the real save's smoke figure; keeping the exact base on reload changes old saves' later loads),
so it is left for a task of its own.
