# T-439: the commute pair loop's leftovers

2026-10-16. `kernel::mode_choice`, `routes::Routes::drive_factor_by`. Results identical to the bit.

## Measured first

A scratch copy of the crate (one worker solving all five periods natively, free flow and three
crowding rounds, as `demand.worker.ts` drives it; T-434's driver) on copies of the New York packs
and the real save's track, so T-453's pack rewrite could not move the figures mid-task. Commutes
only, 14 `mode_choice` calls a solve. Shares of `mode_choice`, from timers around each part:

| part | share |
|---|---:|
| the eight-lane pair loop (gathers, logsum, logit, scatter, bookkeeping) | 71% |
| zone walk (listing an origin's pairs) | 15% |
| per-origin-zone decay row `fz` | 10% |
| split back onto access stations | 3% |
| the origin rows A and B | 1% |

Per call: 9.6M zone iterations, 0.58M of them past the walk bound, none pruned
(`prune_trips` is 0), 17.4M pairs. The zone walk does little beyond what each visit needs (1.9
pairs a visit), so it was left alone.

`fz`: 5.2M entries a call at 12.3 ns each. Switching parts off: the routed drive factor about
6 ns, the decay/walk table lookup 3, `ride_offered` 2.2, the routed walk share 1.8.
Building it once per worker and reusing it across periods and rounds would hold all 5.2M
entries (16 bytes each, 83 MB a worker for New York): rejected, against T-419's direction.

## What changed

- `fz`: each destination zone's square and drive supercell travel in `DZone`, so the row reads
  nothing from `z` or the route tables by zone id; `ride_offered` inline on those; the routed
  drive factor through `drive_factor_by`, which reads both tables and picks one without a branch.
  Same expressions, same bits. 14.2 against 16.4 ns an entry in one binary (-14% of `fz`).
- The scatter into the y rows runs to the block's longest egress list (`kn`) for every lane, not
  each lane's own length: pads add 0 to their own dummy slots, and one count per block predicts
  well. Alone, about -2.5% of `mode_choice`.
- Each lane's walk-sum band is computed in the lanes (same add and multiply).
