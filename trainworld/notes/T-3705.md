# T-3705 Firefox: "can't build", vertical bars

Reports (2026-11-18): Discord bug-reports, natteru: "Anyone else can't build on firefox?". In-game 1795010433-960575a7,
Firefox 160: "vertical bars appear all across the map making it very hard to read or see details." No other Firefox
report in the last 7 days of feedback; no earlier Firefox work in notes/ or DECISIONS.

## Cause of the bars

Firefox with `privacy.resistFingerprinting` on (also fingerprinting protection with the canvas extraction targets, as
LibreWolf, Mullvad Browser and Tor Browser ship it) makes up the pixels of every canvas read: `getImageData`, `toBlob`,
`toDataURL`, `convertToBlob`. resistFingerprinting also hides `VideoFrame`, which MapLibre uses to get round this.
Default Firefox and Strict tracking protection read true (tested on a varied 256 px tile), and so did
`browser.privatebrowsing.autostart` (not checked that the page really was private). Fingerprinting protection with
`+CanvasRandomization` alone read true; adding `+CanvasExtractionBeforeUserInputIsBlocked` made reads up but kept
`VideoFrame`.

Measured in the installed Firefox 159.0.1 driven headless by Playwright's BiDi channel (`channel: 'moz-firefox'`, own
profile) with the pref on:
- `getImageData` of a decoded PNG: all 65,536 pixels wrong; only 8 distinct values over 4,096 pixels, a repeating
  placeholder. A Terrarium height tile decodes to heights of -32,000 to +32,000 m.
- The terrain tint (`map/terrainTint.ts`, shown with a build tool and Terrain on) went through `canvas.toBlob`: the
  image came back as the placeholder, drawn as pink, purple and green vertical bars over every block of land
  (under roads and water, as the layer sits). This is the report: it appears the moment a build tool is picked.
- The hillshade: our flattened tiles (`workers/demFlat.worker.ts`) and MapLibre's own DEM read both went through
  canvas reads, so the shading was noise: dark striped patches in blocks.
- The player's attached screenshot is itself the placeholder: `game/feedbackImages.ts` re-encodes through `toBlob`.
  Re-encoding a 1172x870 picture under the pref gives the same 8 px period with alternate rows shifted.

Before/after: `artifacts/trainworld/t3705_firefox_rfp_before_after.png` (track tool, Terrain on, Midtown).

## Fix

`map/canvasRead.ts`: `canvasReadsTrue()` (MapLibre's own test: 25 known pixels put and read back, once a thread), and
a PNG decode and encode without a canvas (DecompressionStream / CompressionStream, 8-bit, not interlaced). Every
canvas read in the app now has a branch for a browser that makes pixels up; Chrome never takes it.
- Heights (demFlat worker, `game/groundHeights.ts` for the cross-section): decoded by `decodePng`. Matches the
  canvas byte for byte on four real Terrarium tiles in Chromium and default Firefox; 3-10 ms a tile.
- Hillshade: under resistFingerprinting MapLibre has no way to read heights (no VideoFrame), so the layer is left
  off (`basemap.ts demReadable`). Water-over-shade and the tint still follow the setting. Where reads are made up
  but VideoFrame is there (the fingerprinting protection case above) the shade stays: 17 tiles flattened through
  `decodePng`, none failed, no noise in the shot.
- Terrain tint: the PNG is made by `encodePng` from the pixels already in hand; the 1x1 blank is a constant clear PNG.
  Checked on Todt Hill, Staten Island: the wash shows under the pref, as in Chromium.
- One-way arrow (bus roads): `chevronPixels` draws the chevron without a canvas (97% of the canvas chevron's cover).
- Feedback screenshots: sent as attached, unshrunk, if under the 1.5 MB cap, else "too big".
- Saved games: no picture is made (it would be the placeholder); the list's theme swap of a picture is skipped.
- Not changed: the schematic's Save picture (`diagram/view.ts`) still goes through `toBlob` (it would need a rasteriser
  of our own); Firefox may ask the player for canvas access on that click, untested.

Checks: typecheck clean; t3556-play (new-game part) passes on Chromium; build probe passes in Firefox 151
(Playwright's), Firefox 159 default (also on the final code), Firefox 159 with the pref, sandbox and normal mode.

## "Can't build"

Not reproduced. Track drawn, two stations placed and built by pointer in every Firefox setup above, with no page
errors. The likeliest reading is the same player setting: the bars cover the map as soon as a build tool is on.
Not proven; the reporter gave no more. Tested on 159, the reporter on 160.

Side findings, not Firefox's: in Playwright's own Firefox 151 the load card held at "Loading city data 98%" for about
16 s against about 4 s in Chromium (packs open slower in its workers), and a track drawn while the card was up was
priced $143M against $80.0M once loaded.

Probes (scratch, not kept as checks): probe.mjs (build), probe4.mjs (layer by layer), fpp.mjs / fpp2.mjs (readback
by pref), codec.mjs (decoder against the canvas), chevron.mjs. Playwright Firefox against Vite: use `http://[::1]:port`
(Vite listens on ::1 only) and ignore Playwright 1.61's `_onWebSocketOpened` assertion on Vite's socket.
