# T-124: reuse the periods an edit did not touch

Rules: docs/demand.md "Clusters" (the paragraph on periods) and "The pool".

## What was built

- Rust (`sim/src/demand/api.rs`, `everyday.rs`, `intercity.rs`): `set_network` compares the new
  network with the last (`Service::same_layout`, `same_periods`, to the bit). With the layout
  unchanged it keeps station access, subzones, the everyday pairs and the market's access (set-up
  6 ms instead of 600 ms a worker); it keeps each period whose level's run times and trains an hour
  are unchanged. `set_fares` with the same fare keeps them. `params_mut` makes the next
  `set_network` keep nothing. Test: `periods_an_edit_did_not_touch_are_kept_exactly` (a high-level
  change keeps periods 1, 3, 4; re-solving 0 and 2 equals a fresh solve to the bit).
- Worker: per population and period the `psig` it holds (demandClusters.ts, per period like
  `sig`); a period of a dirty cluster is skipped when every population kept it and holds its
  `psig`. `done` carries each worker's periods kept and solved. `?perfOff=periods` turns it off.
- Client: `periodsOfWorker`: with 2 workers the periods go 0, 1, 4 and 2, 3 (both peaks on
  different workers); 3 or more stay `q % n`. `?perfOff=spread` gives the old split.

Coupling checked: a period's commute trips home use its own station pairs (`pass`), everyday and
market passes are per period, and the money, purposes and weekend are worked out afterwards
from the results. Station access and subzones read no run time or frequency.

## Moving periods to idle workers: not built

With 3 workers (`q % 3`: 0, 3 | 1, 4 | 2) the two periods of any level already sit on different
workers, so a one-level edit leaves nothing to move. With 2 workers the level-by-level split gives
the same effect (12.4 s, below) with no change to which worker answers which period, which every
query relies on. One worker has nowhere to move to. So the gain from moving is zero at every pool
size; DECISIONS.md.
