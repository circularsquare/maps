- **What in T-4041**: each destination's strategy in a skims table gained the departures' shares and the inter-city

- Natively (one thread, every population, game order with the skims released after each step) the step peak went
  210.6 -> 237.1 MB (+26.5) with T-4041; T-4054 etc. later took a little back.
- The demand WASM figure moves in 32 MB steps (the desktop demand module grows its memory 32 MB at a time,
  `sim/src/heap.rs`), so a cut shows only when a worker's peak crosses a step edge.

## What changed (tree memgrowth)

Lossless compaction of the skims tables (sim/src/demand/kernel/search.rs, readers in assign.rs, everyday.rs, trip.rs):
- `Ix`: station, node and offset lists stored as u16 where every value fits (else u32), for change nodes' stations,
  shares' nodes and offsets, inter-city starts' stations, offsets and route nodes.
- Change nodes keep no offsets when every one has one word of departure bits (always on NYC: 917,833 of 917,833).
- A table keeps no expected waits (`Shares::without_waits`): only a search's own `walk_column` and the trip explorer
  read them, and the explorer (`trip::routes`) searches its destination again (one search, a few ms) for them.
- NYC table 61.7 -> 47.7 MB (v0.4.5 35.1). Native step peak 237.1 -> 224.4 MB (v0.4.5 210.6).
- Same figures: native loads hash identical (7c85dad2ae7bc2c5 in both orders tested, market hash 3e7ce87ed8668a99), rail
  trips identical on all three bench saves. Native solve time the same (74.4 / 81.8 s master, 74.9 / 80.6 s tree, ABBA).
- Tests: both suites pass (738 + 967).

## The zoneopen tree's 1,163 -> 1,003 MB (T-4051)

Not a saving: a measuring slip. perf_bench read each worker's WASM only until the load was playable, and a worker's
memory arrives with its `done` message. Tree zoneopen sends the off-screen zones' bubble sums after the results, so
one worker's `done` came after the probe stopped and its figure was the one from the zone opens (206 MB). perf_bench
now reads the workers' memory once more after playable (found here and by the orchestrator; master has its fix);
zoneopen base and head both read 1,163 (compare-2026-11-240553.json). Nothing in that tree to land for memory.

## Why "Calculate trips in less detail" barely cuts memory (her question)

Measured on this tree's build, perf_bench with `?lod=coarse` (the setting's mode), against the same build detailed:

| | detailed | less detail |
|---|---|---|
| Tokyo demand WASM, MB | 1687 | 1591 (-6%) |
| Tokyo heap peak per worker, MB | 487 / 596 / 474 | 458 / 567 / 448 (about -28 each) |
| Tokyo tab peak, MB | 2980 | 2863 (-4%) |
| Tokyo CPU in the load, s | 259.2 | 234.3 (-10%) |
| NYC demand WASM, MB | 1067 | 1067 (peaks -18 each, under a 32 MB step) |

Less detail coarsens each zone's own grid of homes and jobs (the cells and what scales with them). Most of a demand
worker's memory does not scale with that: natively on NYC, at rest 292 MB of which the zones' populations are 124 MB
(and only part of that is per cell; each holds five periods of network graphs and loads by station), the regional
market 119 MB plus 20 MB of market packs, and in each step a station-to-station table of 48 MB plus the market's pass
(about 60 MB). Those depend on the network and the market, not on the zones' detail, so coarse cuts work (CPU -10%)
far more than memory.

## Tool notes (for whoever runs perf_bench next)

- **Stale WASM in a tree-folder build**: this tree's first head build carried a partly stale demand module (it
  measured exactly master's heap peaks); fixed on master meanwhile (perf_bench touches lib.rs before a build, T-3939).
  The figures above are from a build after that fix's touch.
- perf_bench run records now also hold `demandHeap` (each worker's heap, peak and solve peak, from
  `client.memory()`): the 32 MB steps hide anything smaller in the WASM figure.
- `PERF_QUERY=lod=coarse` adds page flags for a one-off run (never for a ledger line).

## Not done, ideas

- `strategy_bytes` (the market's choice between the shared table and searching per window) still counts about 18 KB
  a destination on NYC where a strategy is now about 55 KB; counting it right would send big markets to the
  per-window search more often (less memory, a little more time, loads equal to rounding). Moves figures by rounding.
- A table's costs and real minutes are stations x stations even for a table of 8 destinations (4.6 MB on NYC for the
  second graph a step keeps); per-column storage would need every reader of `Skims::r` changed.
- Change nodes' bit words as u32 where a destination's fit (about 1 MB a table on NYC).
