# T-3933: a load out of memory retries with fewer workers

Agent oomretry, 2026-11-21. Anita, 11-21: "if people are unable to lod the game at all because o fmemory issues it
should probably autoset the memory cap lower and try again, if thats feasible".

## What happens when a load runs out of memory (measured)

Desktop Chrome 64-bit, dev server, the real New York save (T-007, 1,756 stations, 109 lines). Memory was limited by
putting Chrome's processes in a Windows job with a per-process commit limit (scratch `jobcap.py`, `jobtree.py`); the
renderer is the tab (page and every worker). Uncapped, the renderer peaks at 2,387-2,433 MB private with 2 solving
workers (the memory estimate cuts the page's 3 to 2 on this save) and 2,277+ MB with 1.

| path | limit (MB) | workers | what happened |
|---|---|---|---|
| `?new=1`, then the save posted in the page | 1,900, 2,000 | 2 | the tab died 1-2 s after the import (renderer exit `0xE0000008`, Chrome's out-of-memory crash); nothing in the page saw it |
| same | 1,600 | 1 | the tab died the same way |
| same | 2,000 | 1 | loaded to the final (peak 1,998) |
| same | 2,200 | 2 | loaded to the final (peak 2,194) |
| Saved games, Open a file (the player's path) | 2,000 | 2 | three runs, three endings: (a) a worker's WASM grow failed (`out of memory: 9043968 bytes`), the pool halved to 1 (`memoryShort`), the page's own `postMessage` then failed twice ("Data cannot be cloned, out of memory"), and the tab died at 131 s; (b) the same halving, then the last worker failed a grow too and the page showed the out of memory screen itself (tab alive); (c) the halving, then the tab died at 44 s |
| same | 2,150, 2,250, 2,350 | 2 | the tab died at 30-47 s |

So both happen: a worker's failed grow is catchable, but the tab usually dies soon after or instead, since every
allocation in the tab (page, clock worker, Blink) fails once the process is at its limit, and those failures crash
the renderer. On iOS only the tab death happens (the system kills the tab by its footprint, nothing fails first);
the five iPhone reports (T-3781) all came from the died-load flag.

## The fix

The retry runs on the next page load in the same tab (sessionStorage survives the tab dying and the reload; iOS
reloads by itself, Chrome shows its crash page with Reload). The died-load flag (T-2545, T-3927) now also holds
the most solving workers the load ran (after the memory estimate's planned cut, `noteLoadWorkers`; a worker
failure's own halving does not lower it) and the slot the game was in once the saves list shows it written.

- At start (`retryDiedLoad`, game/oomRetry.ts, from main.ts): when the last load died, it ran more than 1 solving
  worker, it was not itself the retry, and its game was in a slot: half the workers, at least 1, become the tab's
  pool cap (`rememberPoolCap`, the same session cap `memoryShort` sets) and that slot opens at once, no start menu.
  A note at the bottom of the map (ui/RetryNote.tsx, DeviceNote's look) says so until 45 s after the load is ready.
- Otherwise the out of memory screen as before; the lower cap still applies to its Try again.
- A load whose last solving worker fails in the page's sight (ending (b)): `loadFailed` hands it to the same rule
  (`retryLoadsInPage`): the game is saved, the flag kept, and the page reloads into the retry. Later failures on
  the way out are swallowed so the failure screen does not flash.
- Once per pick: the retry's own flag says `retry`, so a retry that dies gets the screen. The cap only goes down, so
  a Try again from there can halve again on its own death.

Results, all through Open a file with the page's own pool (2 after the estimate), the tab reloaded after it died:

| limit (MB) | first load | retry with 1 worker |
|---|---|---|
| 2,050 | tab died at 45 s | final, 12,886,431 rail trips a day (the same as an uncapped load), slot writable, note shown |
| 2,250 | tab died at 41 s | final, same figures |
| 2,350 (twice) | tab died at 38-47 s | final, same figures, slot writable |
| 2,000, 2,150 (once each) | tab died | died too; at 2,100 the same, and one more reload showed the out of memory screen ("it was already the retry" in the console), no third load |
| 2,000, 2,150 (once each) | tab died before the file's slot was written | no retry: the screen, cap lowered to 1 for Try again |
| 2,250 (once) | a worker's grow failed (2 to 1, `memoryShort`), the tab lived | no retry needed: final on 1 worker |

So on this save the retry rescued 4 of the 7 tab deaths where the slot was known, near the top of the range; below
about 2,150 MB the 1-worker load dies as well (it peaks near the 2-worker one early on: 2,277+ MB against 2,387).
The slot's lock (a Web Lock) dies with the tab, so the retried slot opens writable.

In the page (dev `debugPanic` out-of-memory text: worker 1, then worker 0 twice): saved, reloaded, final reached, twice.
Screenshot of the note: artifacts/trainworld/t3933_retry_note.png. Under the cap the clock worker once logged a Rust
panic in a timer during a retry (an allocation, presumably) and carried on to the final.

## What it does not cover

- **Phones**: a phone already runs 1 solving worker plus the aux worker, so there is nothing to retry with and the
  rule sends it to the screen. The aux worker (65-97 MB at the iPhone saves' peaks, T-3781) holds the bare zones,
  the no-rail pass and the questions all through demandClient.ts; leaving it out is a change of its own, not a
  retry setting. The phone deaths need the memory work (T-3939 clock worker, T-3373 stage B) and T-3940's warning.
- A game not in a slot yet when the tab died (a file still being written, a Community network only viewed, a test
  page): the screen as before.
- `?demandWorkers=N` fixes the pool, so no retry (checks keep their behaviour).
- A load's own catchable halving (`memoryShort`) stays silent, as T-3072 decided (its check asserts no notice).
- iOS Safari is said to show its own error page after a second quick crash instead of reloading; not checked here.

## Checks

its demand final, as did t2867 beside it); t2867-memory-fallback rerun alone on 3 cores passed (its fixed `demandWorkers` keeps the old screens).
