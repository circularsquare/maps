# T-3997 Search while running crashes the tab

A player on Discord (11-21): searching while the game runs crashes the tab; at 100x the trains stop and
stations overcrowd. Anita, trying it: bad at 100x, mostly fine paused. No related reports in the feedback
inbox (72 h). The search is the map's search box (`ui/Search.tsx`, `game/search.ts`); the Settings and
New game searches don't touch place lists.

## Cause

Two faults in the search box, both main-thread work that grows with the place lists loaded:

1. **Widening never stopped.** T-400: while a 3+ letter query finds fewer than five results, the box loads
   the next nearest zones' place lists, "until enough or all". The effect re-ran on every list arrival
   (`places.value.size`), each run asking four more, so the requests fanned out, and a query with few
   matches kept loading lists with no limit (the world has 4,765, 166 MB of JSON; 381 were in after
   50 s, then the tab hung). Each arrival also re-ran the whole search over every list in.
2. **`isRegistryCity` re-normalised all 4,765 registry names for every matching city or town place**,
   on every search. A short query matches most places: "s" took 6.8 s, "ville" 1.3 s with 201 lists
   (167k places); 97% of it in `normalise` under `isRegistryCity` (CPU profile).

Why trains stop: the renderer asks the clock worker for a game hour's trips only once a frame is drawn
in that hour (`renderer.sync` -> `epoch` -> `turnHour`); until they arrive the last hour's keep
running out. At 100x an hour is 0.6 s of wall time, so a busy main thread leaves the trips hours
behind: no trains drawn, and platform crowds (riders arrived since the last train) grow. Paused, the
clock doesn't move, so the same stalls show only as a slow box.

## Evidence (real save T-007-real-nyc, 100x, headless, 3 cores)

Scratch probes in the agent's scratchpad (`searchcrash/lib.js` sampler: every 100 ms the clock, the
renderer's trip epoch, lists loaded, heap; long tasks).

| | before | after |
|---|---|---|
| "qzxv st" typed at 250 ms a key, 25 s | lists 1 -> 241, main thread 81% busy, worst stall 13.7 s, trips up to 29 h behind | lists 0 -> 19 (all NYC zones within 200 km), 1% busy, worst gap 187 ms, trips never over 1 h behind |
| same, next 25 s | lists 381, 94% busy, trips 100% of samples behind (70 h) | lists 19, 0% busy |
| left open longer | page stopped answering within ~3 min (two runs); renderer process at 3.1-3.5 GB private memory | left open ~70 s in all: not hung, heap 280-470 MB, lists stay 19 |
| search("s"), dense case | 6.8 s at 201 lists | 104 ms at 115 lists / 73k places (NYC, Ruhr and Delhi widened), 81 ms again |

Control: a plain 7 s busy loop at 100x leaves the trips 12.6 h behind, and they recover within the
next sample or two once it ends. So a single stall recovers; the box's endless loading and re-search
kept the main thread saturated, so they never did.

Baseline at 100x with nothing open: trips are an hour behind in about 13% of samples (the pull's
round trip, ~80 ms of each 0.6 s hour). Not changed here.

## Fix

- `game/placeList.ts` `widenPlaces`: only the 48 nearest zones within 200 km of the view
  (`WIDEN_M`, `WIDEN_MAX`), four at a time, one batch in flight (a call while one loads gets that
  one); resolves true only when a list arrived, so a batch that all failed isn't asked again at once.
  Zones within 200 km: NYC 19, London 43, Ruhr 65, Delhi 85 (1-5 MB of JSON), so 48 is the cap only in
  the densest places. DECISIONS 2026-11-21; docs/ui-panels.md "Search".
- `ui/Search.tsx`: the widening effect asks for the next batch when the last one is in (a counter),
  not on every list arrival.
- `game/search.ts` `isRegistryCity`: registry names normalised once into 1-degree cells; the answer
  kept per place (WeakMap). Checked against the old rule on 2,855 loaded cities and towns: all 91 the
  old rule hid are still hidden.

Lie: a town far from the view (more than 200 km, or past the 48 nearest zones) is no longer found by
name until the player looks near it. Registry cities and zones are still found anywhere.

Opening a result at 100x (after the fix): picking Chicago by Enter, then an NYC station (Jamaica) by
click, leaves the trips 6.7 h and 4.9 h behind for a few seconds after each jump, then they are back to
the baseline. The same two jumps by `map.jumpTo` with no search: 5.2 h and 4.5 h. So that lag belongs to
any far camera jump (the clock worker loading the new view), not to search.

No standing check: the bound is a fixed rule in one function, and the probes above are in the scratch
folder; a check would need the full world's place lists to show the old failure.

Not done: the trips pull (`renderer.sync`) still leaves trains undrawn whenever the main thread stalls
at high speed; any other long stall would do the same, briefly.
