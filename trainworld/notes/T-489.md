# T-489 Placing a station lags: measurements (2026-10-16)

Headless Chrome on an agent's Vite (dev build), the real save imported, station tool picked with
key 2 (Build tab open), clicks on the midpoints of straight track edges. Time from mousedown.
The old build is commit 1fe8ed4 (before T-446/447/453/464/469/472/474/475/477), its own wasm.

| build | clock | spots | world updated, ms | next frame drawn, ms |
|---|---|---|---|---|
| 1fe8ed4 | paused | track off lines | 127-157 | 165-202 (median 180) |
| now | paused | track off lines | 119-200 | 156-258 (median ~200) |
| now | 240x | track off lines | 120-156 | 153-209 |
| now | 960x | track off lines | 131-169 | 159-222 |
| now | 960x | track on lines | 136-157 | 181-208 |

Where a placement's time goes, the same in both builds:
- ~10-20 ms: the station's name (`nameFor`) before the edit is sent.
- ~85-115 ms: the clock worker. `apply` 9-19 ms, `buildState` 7-19, the renderer buffers
  (`networkFromState` over the whole network) 51-73, boarding 4-10.
- ~40-65 ms: the main thread taking the state message (`clockClient.receive`), then effects:
  station labels (~25-30 ms incl. a forced layout), complexes ~15, end markers' forced layout ~15.
- ~40-50 ms to the next drawn frame.

Hover with the station tool on (median of 30 calls): `move` 1.6-1.7 ms in both, `snap` 0.3,
`place` 1-1.5, T-469's `lastStationTrack` 0.3-0.6. No long tasks while the clock runs at 960x
with no input (5 s). Placing a blueprint station did not start a demand solve in any trial.
Main-thread CPU in the 4.5 s around one placement: 189 ms old, 216 ms now (same functions).

Not reproduced: no regression in this setup. Not covered: a real GPU, the production build on
8800, other cities, Anita's own game, panels other than Build. Faster placement would come from
not rebuilding every render buffer on each edit (T-496).
