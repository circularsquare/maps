# T-4363 Patched rows differ from the state's (agent patchrows, 2026-11-28)

Outcome: the "edges N: cost" case is found and fixed (app only, the clock worker). "nodes 4: line" (once, 11-25) is not
explained. Advisor not called (no big design decision: a fix inside T-4506/T-4534's mechanism).

## Cause, from the code

- The page's check (clockClient.ts `checkPatched`) compares a state with every patch that arrived since the last state
  it took. The worker's guard for those patches started again at every state read instead: `stateRows.begin` clears
  the touched list (`take_touched`) and `patchedSince`, and `mapPatch` kept only the newest patch's prices
  (`laidCost`), which hold just the records touched since the last read.
- A read is often never posted. A follow-up builds its state in pieces (clockMain.ts `stateSteps`: the rows first, then
  the network a piece a task). An edit that comes between the pieces drops it: `standAside` sends the rows only when an
  edit still owes its answer (the track tool's free segments and the click-patched stations are answered at once), and
  `later` drops a begun job outright. Ground that moves the blueprint's price drops it too (`sendStateOutside`, from
  the road feed's burst end and `ensureBlocks`).
- So after a dropped read the page still holds the patch from before it, and the worker no longer watches its edges. A
  road tile (or a terrain block) that lands then and prices that track goes into the next read (`priced` is drained into
  the touched list), but no patch carries it: `patchOutside` tested only the newest patch's edges, and right after a
  dropped read it did not test at all (`patchedSince` false). The check then sees the first patch's price against the
  state's: "edges N: cost". It needs fresh ground (road tiles still to come) and quick edits, which is why it showed in
  new games far from loaded ground (smoke's Tokyo and dead-space games, T-4564's India game, Boston and New York line
  builds).
- What a player could meet: for the moment between the tile and the next state, the map the tools click on held the
  segment's price before its road crossings. The state itself was always right, and no trip figure reads it (trips
  read the network, never this map). So small, but the same gap T-4506 and T-4534 closed, and the check is what keeps
  that honest, so it is fixed rather than silenced.
- Ruled out: `derive` re-prices every edge at a touched node, but all of them go into the edit's Dirty (`d.edges`),
  so a price an edit moves is always touched. `edges_info` and `edges_info_of` make the price the same way.

## The fix

- clockPost.ts: `posted.posts` counts the states posted.
- clockPatch.ts: `laidCost` holds every edge's price as the patches sent since the last state posted gave it (`laid`
  clears it when `posted.posts` moved), newest last, gone edges dropped. `patchOutside` tests all of them, and the
  patch it sends carries the moved ones besides the touched records (`mapPatch`'s new `extra`).
- clockMain.ts `buildState`: `patchOutside(a, true)`, so a read tests even when the read before it was dropped. From
  ground the test still waits for a patch since the last read began (`patchedSince`): while a read is waiting for its
  post, a patch sent first would hold a newer price than that state.
- docs/architecture.md (the tools' map paragraph) says the test covers the patches since the last state posted.
- Cost: none unless a laid edge's price moved; then one patch with those edges, as before.

## Game run (App logic budget)

The real NYC save on Vite 6171 (play.mjs), trips final first. The probe (`probe3.js` in the agent's scratchpad) went to
east Pittsburgh (40.42 N, 79.80 W, zoom 12; the view's ground in) and held the zoom 14 road tiles with a Playwright
route. It placed an 8 km blueprint segment (early, as the track tool does) and a ghost 40 m beside it, whose 5 tiles
were held. It listened on a freeze-trace port, sent a second 2 km segment 3 km north the moment the first segment's
follow-up had read its rows ("build-state-end"), and let the tiles through then.

Messages (ms from the start; edge 1647 is the first segment):

| ms | what | edge 1647 |
|---|---|---|
| 71 | segment 1 applied, its patch | 882.5 |
| 300-308 | its follow-up reads its rows | |
| 308-317 | segment 2 sent, applied (the read is dropped: no state came) | |
| about 342 | the 5 road tiles let through | |
| 404 | outside patch | 1252.5 |
| 440 | state | 1252.5 |

The check on the 440 state: 3 patches, none missing, first 882.5, newest 1252.5, state 1252.5, no T-4214 error.
Before the fix nothing would have carried edge 1647 at 404: the guard held only segment 2's patch's edges. The check
would have compared 882.5 with 1252.5, which is the reported error (read from the code, not run).

Runs: three probes in two loads of the save. The first asked no ghost, so no road tile came (the dropped read was shown,
the price never moved). The second crashed the play server: the probe's own route handler fulfilled a request already
handled. About 6.5 minutes of game checks, no benchmarks. Typecheck clean.
