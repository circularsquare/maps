# T-4055 An edit reaching two new zones shows a stale final

Case (ordercheck 2026-11-22, stalefinal 2026-11-24, own Vite 6122): new NYC sandbox, a PHL line (-75.2,39.95 .. -75.1,39.97)
and a PVD line (-71.45,41.82 .. -71.35,41.84), 3 stops, trains 6/4/3, as one `edits` file (batch) or two (separate).
Scratch: scratchpad\stalefinal (run.sh, mk.sh, read.js, trace.js).

## Cause

A page trace (dispatch, opened, open-everywhere, relevel, final) of the batch case on master 82588e6e:

- The edits land while the new game's load hold is still on (play.mjs starts editing at "ready", before the viewed zone's
  bare open ends the hold). Under the hold `ensure` adds the reached zones to `lodZones` without making them fine
  (the rule for a loading save's reach), so PHL and PVD open coarse.
- v2 (barrier) is sent once both packs and the market are open everywhere. About 100-150 ms before its final the hold
  goes, `lodCheck` finds both zones held (edited) and opens them again fine (`lodApply`: out of `opened`, new download).
- v2's final still lands as final: demandUpdating off, cache written, `waiting` null, so `wait.final` and any reader
  take it. PHL 63,996, PVD 11,954 are coarse figures.
- 1-1.5 s later the fine packs are open everywhere and `flush` sends v3 (no barrier, 150 ms): PHL 68,341, PVD 11,728.
  So the figures did heal by themselves within seconds; ordercheck's reads came at v2's final, before v3 existed.
- Separate edits go the same way for PHL alone (coarse v2, fine v3), then PVD opens fine (hold gone), so the read after
  the second edit is fine. The difference was never batch against separate, only when the read happened.

## Fix (app/src/workers/demandClient.ts)

`covers(s, need)`: the solve covers every zone it needs, each open at the level it was solved at, no wanted market still
opening, and every market open. `flush` uses it for its "opened since the newest solve" re-solve (same test as before), and
the final in `publish` now asks it too: a final that does not cover what the page holds or is opening is stale. Its figures
are shown, but its network goes back to `waiting` (so demandUpdating stays on, no cache is written, `demandFinal` waits),
and `flush` sends the next solve as soon as the packs are open; that solve's final is the final. This covers any pack
that starts opening during a solve: a zone at another level, a zone newly reached, a market wanted or opened.

## Results (PHL / PVD / rail a day)

| run | before | after |
|---|---|---|
| batch, read at `wait.final` | 63,996 / 11,954 / 75,950 (v2) | 68,341 / 11,728 / 80,068 (v3) |
| PHL then PVD, separate | 68,341 / 11,728 / 80,068 | 68,341 / 11,728 / 80,068 (v4) |
| PVD then PHL, separate | 68,341 / 11,728 / 80,068 | 68,341 / 11,728 / 80,068 (v4) |
| batch save reloaded | 68,341 / 11,728 / 80,068 | 68,341 / 11,728 / 80,068 |

Standing check `checks/t4055-stale-final.mjs` (one game, about 30-90 s): both lines as soon as the game is up, the final read,
then the same network solved again (`resubmit`): equal within 0.5%. With the fix PASS twice (68,341 = 68,341); with the
stale test switched off FAIL (63,996 against 68,341).
