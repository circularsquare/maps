# T-2413: a high-speed train behind a slower one without passing tracks

Anita (2026-11-04): "if i have a high speed train and a non high speed train running on the same high
speed track without passing trcks the high speed rtain schedule should be waiting to match the slow one,
but if i check this it seems to only be delayed a little bit. im surprised by how small ti is. are our
delays realistic?"

Investigation only (agent hsrdelay); no code changed.

## Answer

Not a bug, and not unrealistic in the small direction. A fast train only loses time if it catches the
slow train ahead, and it catches it only when it gains more over the shared track than the gap between
slow trains. The game charges two different rules:

- **Same ends** (both lines run the identical path end to end, T-1965 "locked"): the whole difference
  `D`, at every headway. Large: 37 min one way on the 180 km test below.
- **Anything else** (the lines meet partway, one runs further, one starts later; T-1924): the average over
  a random meeting place in the slower headway, `D - (H - s)/2` or `D² / 2(H - s)`. Small when the
  shared stretch is short or the slow trains are well spaced: 60 km shared, ordinary every 30 min, the
  high-speed train loses 3 min one way (6m06s a round trip in the panel).

Her small delay is almost certainly the second rule (or a short shared stretch where `D` itself is
small). A real timetable would lose even less there: a planner puts the fast train just ahead of a
slow one, so it loses only `max(0, D + 2s - H)`. Where the game is off is the other way: both rules
charge **more** than a planned timetable at long headways, and the same-ends rule most of all
(37 min where a planner would lose 12 at 30/30, 6 at ordinary 60 / HS 30).

## The model today

`capacity::stretches` finds each shared run of path entries (same edges, same direction) per faster
run and slower run. `D` = slower run's time from leaving the stretch's start to leaving its end minus
the faster run's from leaving the start to reaching the end, from free profiles. `s` = 70 s + v/0.6
at the slower run's top speed there (144 s at 160 km/h). `capacity::follow_loss`:

- locked (`FOLLOW_LOCKED`: the stretch is both runs end to end and `D >= 30 s`): loss `D`;
- passing stations inside (`FOLLOW_PASSING`, T-2231): the overtake plan's best-phase loss;
- otherwise: `D - (H - s)/2` when `D >= H - s`, else `D² / 2(H - s)`, `H` the slower line's headway.

The loss is run off as one lowered speed over the stretch (T-2018), so it is in stop times, round
trips, fleet and demand; the panel shows it as "Behind slower trains" (round trip, both directions).
Locked pairs' departures are placed with the faster train the spacing *behind* a slower one (T-1965),
the worst place for it; other pairs are placed apart (T-1925) but charged the random average.
DECISIONS: 2026-11-02 T-1924 (the formula), T-1965 (locked: "with no passing, order on the line
never changes, so every faster train ends up behind a slower one").

The T-1965 reasoning is the flaw: order never changes, but a fast train that leaves just *before* a
slow one is ahead of it, and catches the slow train in front only if `D > H - 2s`. "Every faster
train ends up behind a slower one" holds only when slow trains run closer than `D + 2s`.

## Hand calculation: what a real timetable loses

No passing, so the order at the start is kept to the end. A fast train leaving `t` after the slow
train ahead (and `H - t` before the next one) arrives no sooner than `s` behind it:
`loss(t) = max(0, D + s - t)`, with `s <= t <= H - s` so neither train is held at the start.

- **Right behind** (`t = s`): loss `D`. This is the brief's "slow run time minus fast run time"; the
  headway buffer `s` cancels, since it leaves `s` behind and arrives `s` behind. The game's locked rule.
- **Random place in the gap**: about `D - (H - 2s)/2`. The game's other rule (it uses `H - s`).
- **Planned** (`t = H - s`, just ahead of the next slow train): `max(0, D + 2s - H)`.

Best phase over a cycle (scratch model in `probe2.mjs`, per faster train, minutes):

So with frequent slow trains (`H` under `D + 2s`) all three agree roughly: the fast train ends up
behind, as Anita expects. With slow trains well spaced, a planned timetable runs the fast train in the
gap and loses little or nothing; the game's random rule is a bit worse than that and the locked rule
far worse. The real cost of mixing speeds without loops is capacity: each fast train uses up `D + 2s`
of the slow line's gap (UIC 406 "heterogeneity"), which the game already charges as lost time.

  https://www.tt-forums.net/viewtopic.php?p=948824).

- NIMBY Rails: trains are simulated and protected from behind by the game; a timetable sets departures,

All four simulate trains, so the loss falls out of where the player put the departures. Ours is an
average rule, so it must pick a placement; the question is which.

## Proposal (changes how the game plays: Anita's call)

**Recommended: every shared stretch timetabled at its best phase**, reusing T-2231's overtake plan with
no passing points. `overtake::plan` returns a plan for every stretch, not only those with a passing
station (`next` then points at the end; no waits); `follow_loss` takes the plan's loss for all of them;
`follow_targets` places every pair at the plan's offset, as passing pairs are now, so drawn trains leave
just ahead of the slow ones. The locked rule and the random formula go (the random one stays only as the
fallback where one faster run follows two different slower lines on overlapping stretches, which one
phase cannot serve both).

For players: a high-speed line sharing track with a slow line loses about `D + 2s - H` instead of `D`:
same-ends 180 km at 30/30 37 -> ~12 min one way, at 10/10 37 -> ~32 (little change). Lines sharing a
short stretch with a sparse slow line lose nothing. Passing tracks are then worth building only where
slow trains run often enough to be caught, which is what real lines do. Capacity is unchanged (no
resource caps on following). Fleet and demand follow the new run times.

Files: `sim/src/track/capacity.rs` (stretches, follow_loss, follow_targets, build_follow: about 40
lines), `overtake.rs` (`plan` without the passing guard, ~15 lines), `spacing.rs` (locked placement
folded into the passing one); tests: `express_locked_behind_local`, `high_speed_behind_ordinary_trains`,
`express_behind_local_takes_about_its_time`, `following_loss_formula` rewritten to the new figures, one new
test for the 30/30 same-ends case; docs `track-and-service.md` 6.2 "Behind slower trains" and 6.3;
DECISIONS line superseding T-1965's. About half a day for one agent; the real save has no shared edges, so
it moves nothing there. Watch the plan's cost: one per stretch rather than per passing stretch, memoised
by rates, so fine on the saves we have.

**Smaller alternative**: keep the random rule, and change only the locked rule to the planned figure
`max(0, D + 2s - H)` with equal headways (or the random rule otherwise), placing the faster train just
ahead of a slow one. Fixes the largest overcharge in about 20 lines but leaves unequal headways rough.

**Or leave it**: the rules err on the pessimistic side, which nudges players toward passing tracks.

Small things seen on the way, not worth a task alone: several fast trains bunched behind one slow train
each keep only `s` behind it, not `s` behind each other (the 30/10 case undercounts a little).
