# T-1855: line groups lost from Anita's Japan save

Anita, 2026-10-30: "i loaded my japan save and it seems like my line groups got disbanded for some
reason? is that a one time thing or a bug"

## Answer: a bug, in the Lines tab's drag (T-1813), fixed

Dragging a whole group's row (its header row, `g:N`) into a gap to reorder it sent
`{ op: "lineGroup", lines: [Number("g:N")], group: 0 }` as well as the hand order. `plan()` set
`g = 0` for a group drag and compared it with `from = grp`, so every group-row drop counted as a
"leave". `Number("g:N")` is NaN, and the worker's `new Uint32Array([NaN])` made it line 0, so line 0
(the game's oldest line, ids being dense after every load) left its group; a group of two then
dissolves. One group per session at most (once line 0 is out, a later drag changes nothing), and
the hand order still moved, so the drag looked fine. In since b6a3bc04 (2026-10-29 17:57).

Reproduced on Tokyo's real network in a slot game (scratch run, then `checks/old/t1855-groups-kept.mjs`):
groups {0,1}, {2,3}, {4,5}; dragging group {2,3}'s row below another line dissolved group {0,1}.

Fix (`ui/LinesTab.tsx`): a group's row only moves the group (no join or leave in its plan), and
`dropLine` sends no group edit for a row id that is not a line number. No player-facing text changed.

## Paths checked and found sound

- Where groups live: `LineData.group`, `group_name`, `group_look` in the sim, saved in the track
  bytes' `LGR1` (lines and names) and `LGL1` (hand bullets) blocks; the UI's `LineInput.group*` are
  read from the model (stateRows, clockClient `toWorld`), nothing kept in UI state but which groups
  are closed.
- Format: LGR1's write and read order is the same in a8d08f74 (first groups build) and master;
  LGL1 and LOR1 come after it, so every build since 2026-10-29 14:01 reads every other's groups.
- Every sim edit that rewrites a line starts from `line_data` (group kept); only new lines, buses and
  the save decoder build a `LineData` with group 0, and the decoder sets groups from LGR1 after.
  Deleting a line clears its group (intended: a group left with one line dissolves).
- Load (`TrackApi.load`: names tidy, train allocation), frame conversion (`convert_frame` copies
  `line_data`), panic recovery (`keep()` stores `a.save()`), the autosave and T-1829's write-back,
  T-1826's read-only copy, export/import: all carry the same track bytes. The account uploads and
  downloads the slot record's bytes unchanged (`cloud.ts`), so a slot with its groups is an account
  copy with its groups.
- Checked in the browser: save by hand writes LGR1 and LGL1 into the slot, a page reload opens all
  three groups with name and bullet, export and import keep them.

## One other way to lose them

The live site is still 2026-10-28g (1550be70), before groups and before T-1826. If the Japan game
was opened there while signed in, that build reads the save without LGR1, and its autosave and
account upload write it back without groups; 8800 then loads that newer account copy. Not a bug in
the current build (T-1826 now keeps a newer save read-only), and it goes away at the next deploy.

## Recovery

Slot backups (Saves panel, earlier versions) and the account's day and week backups taken before the
drag hold the lost group, but opening one as a copy also drops whatever was played since. If only the
group with the oldest line is gone, grouping it again by hand is quicker.
