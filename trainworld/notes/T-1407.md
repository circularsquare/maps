# T-1407, T-1780/T-1788, T-1794, T-1815's leftover: lag after an edit (2026-10-30, agent t1407)

Anita: "let's look into lag after edit". The ghost (a track preview) asked right after an edit waited
for the whole of the clock worker's work on that edit: apply, state, stroke buffers, post, trips and
the boarding hour, and the edit's answer; for a blueprint segment the tool also waited for the main
thread to take the new state before it asked the next ghost.

## How it was measured

Real save (`T-007-real-nyc.save`), headless Chrome on the tree's own Vite, one demand worker.
- Placements: `checks/t1805-placement.mjs` (6 built edges; a = first segment off built track, which
  pays for a junction, b = first off blueprint, c = later segments; click to the next ghost answered).
- Service edits: new `checks/t1407-edit-ghost.mjs` (busiest line by riders: train counts +2 at every
  level and back, headway 240 s and off, the ghost moved every frame from the edit for 1.5 s; the first
  ghost's wait, the worst in the watch, the worst asked from 150 ms on, the boarding lines redone).

## Where the time went (before)

| edit | apply | state | buffers | post | boarding hour | main thread | next ghost |
|---|---|---|---|---|---|---|---|
| blueprint segment | 4-9 | 4-7 | 28-39 | 2-9 | none (T-1780) | takes the state 35-77 before the tool asks | 87-158 mean, 237 max |
| headway | 4-6 | 4-6 | (service: none) | 1-2 | 28-39 (2 hours sliced, no lines redone) | | 59 mean, 66 p95 |
| train count | 64-135 | 13-25 | (service: none) | 1-3 | 135-182 (78-93 lines redone, both hours) | | 328 mean, 370 p95 |

A train count's settle moves the rates or run profiles of most lines a little (93 of 109 accounts
redone, every line's phase table read again), so its boarding hour is nearly a whole one. Natively
(`edit_bench` on T-007's network) the same kind of count edit is 12-113 ms; in WASM 64-135 ms.

## What changed

1. **An edit's follow-up waits behind the previews** (`later` in `clock.worker.ts`). After applying an
   edit the worker answers the previews and station checks already asked, then builds and posts the
   state, the trips and the boarding hour, and answers the edit (so callers still find `world` up to
   date on the answer). Any other message, and any trips sent from a timer, run the follow-up first,
   so nothing but the previews sees the model ahead of its state. A panic drops it and answers the
   edit as failed (the rebuild posts its own state).
2. **The boarding account's lines the edit moved are worked out a few a task** before the follow-up
   (`boarding_step(3)`, the stepping new riders already use), with previews answered between steps,
   and the trips' next hour goes a task after this hour (T-1810's split).
3. **The track tool's free segment is answered early.** A `route` edit that changes no line for demand,
   sent with `early`, is answered right after apply; the worker waits up to 30 ms for the next ghost
   before building the state. The tool asks that ghost from the answer's node (its start-node check
   allows a node the world does not hold yet), the ghost just placed stays drawn as the stand-in for
   the new blueprint until the next network is set (`Renderer.keepPreviewAsPlaced`), and the client
   takes that state after the next paint (`ghostFirst`), so the ghost paints first. A junction paid for
   when the segment branches off built track has its money's split read off the state when it lands.
   States with no trips to wait for (`noTrips`) are no longer held for them.

The lie (DECISIONS): for one or two frames after a click the new blueprint is drawn as its ghost (the
same outline, rails and middle) rather than from the network.

## After

| edit (real save, 1x) | before | after |
|---|---|---|
| blueprint segment, first off built track (pays a junction) | 158 mean, 237 max | 13 mean, 15 max |
| blueprint segment, off blueprint | 65 | 9 |
| blueprint segment, later in a run | 87 mean, 145 max | 11 mean, 16 max |
| headway: first ghost | 59 mean, 66 p95 | 11 mean, 12 p95 |
| headway: worst ghost in the 1.5 s after | 59 mean, 66 p95 | 50 mean, 56 p95 |
| train count: first ghost (asked during the edit) | 328 mean, 370 p95 | 106 mean, 134 p95 |
| train count: worst ghost asked from 150 ms on | 328 mean, 370 p95 | 52 mean, 69 p95 |

The train count's first ghost now waits for the apply alone (the settle, 63-128 ms in WASM). A ghost
can only be asked that soon if the pointer is already over the map when the count changes (the
stepper is in a panel); a pointer coming back from the panel (from 150 ms on) waits about 50 ms.
Demand unchanged: smoke's real save 11,388,675 rail trips.

Shared New York (`artifacts/trainworld/t1305-shared/nyc_real.save`, after only, 4 rounds; the line
busiest by riders, which settles in 4-7 ms there, not T-1794's busiest by trains): first ghost 5-9 ms,
worst in the 1.5 s 43-71 ms, asked from 150 ms on 7-11 ms.

## Left (proposal)

- **The train-count settle itself** (63-128 ms in WASM on the real save, 320-570 ms on shared New
  York per T-1815): every edit's `settle_train_counts` re-times most lines a little, which also redoes
  ~90 boarding accounts and every phase table. Cutting it is T-1794's work (a held line's fill want
  from its fleet alone, so its share stops moving; or a settle that stops once each line's rate moved
  under what demand or the drawing can see). Then a count edit would touch the edited line and its
  neighbours only, and its follow-up shrinks with it.
- The follow-up's own run (state ~15-20 ms, one hour sliced ~14 ms, the main thread taking the state
  ~10-20 ms) is the ~50 ms a later ghost can still meet. Smaller would need the state built in parts
  between previews.
- A preview whose geometry needs a water mask still being fetched holds the follow-up until it is in.
