# T-015 overlay canvas without the panning lag

Done 2026-10-09 (measured 2026-10-08). Overlay is the only mode; the new app layout (T-027) is
built that way.

## Cause

In `?mode=overlay` the trains canvas was drawn from our own `requestAnimationFrame` tick, with the
camera matrix the empty `camera` custom layer saved on MapLibre's last frame. Our tick asked for its
frame during the previous frame, so it runs before MapLibre's frame callback (which a mouse move
asks for at the start of the frame). While panning, the tick drew with the previous frame's camera
and MapLibre then drew the new one: the overlay was one frame behind on every panning frame.

## Fix

Whenever MapLibre draws a frame, the `camera` layer's `render` callback draws the overlay right
there, in the same frame with the same matrix. Our own loop stays for the clock while the camera is
still. When both draw in one frame the later draw wins, and both canvases present together. The
cost is one extra overlay draw (~0.1 ms JS, ~0.2 ms GPU at 10k trains) only on frames MapLibre
draws anyway (~2 ms of its own). In the spike (`app/src/main.ts`) it is the default for
`?mode=overlay`; `?sync=0` gives the old behaviour for A/B. The new `app/src/map/overlay.ts`
(T-027, not yet the entry point) is built this way and has no layer mode.

## Measured

Headless Chrome on Anita's desktop (real GPU), 1280x800, Chrome pinned to 2 cores, 10k trains on
500 lines, zoom 10.2. Drags made of real CDP mouse events at ~60 Hz.

Offset between the basemap's camera and the overlay's at the map centre, sampled after every frame
(`spike.lagStart()` / `lagStop()`: a task posted from rAF runs after the frame is rendered):

| | Frames sampled | Frames off | Offset when off |
|---|---|---|---|
| overlay, old | 311 and 574 (two drags) | 122 and 244 (every drag frame) | 6.0 px = one drag step |
| overlay, fixed | 280 and 556 | 0 | 0 |

Composited frames (CDP screencast, PNG, every frame it delivered): one line on the overlay against
a blue dot drawn by MapLibre, offset of the line against the dot per frame:

| | Frames with the map moving | Off by more than 2 px | Max |
|---|---|---|---|
| overlay, old | 83 | 23 | 8 px = one drag step |
| overlay, fixed | 74 | 0 | 0 |

CPU, whole Chrome process tree, % of one core:

| | Playing, camera still | Playing and dragging | Paused |
|---|---|---|---|
| overlay, old | 17% | 37% | 0% |
| overlay, fixed | 21% | 38% | 0% |
| layer | 35% | 40% | 0.3% |

Playing with the camera still runs the same code in old and fixed (MapLibre 0 renders/s in both),
so 17 vs 21% is run-to-run noise (T-018 saw 17-21%). Overlay keeps its ~40% saving over layer
mode while playing.

Result: **overlay becomes the only mode** (trains above place names, which Anita accepted).

Scripts (scratchpad, not kept): `cdp.mjs` (CDP helper, CPU from `Win32_Process` filtered on the
profile path), `lag.mjs` (drags + `spike.lagStart/lagStop` + CPU), `cast.mjs` + `cast.py`
(screencast frames, blue dot vs line centroid).
