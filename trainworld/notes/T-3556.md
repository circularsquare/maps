# T-3556 Agent playtest harness

Stage 1 (built): one shared harness in `checks/lib/` that plays the game the way a player does. Stages 2 and 3 are
sketches below, for Anita before anything is built.

## Stage 1: the API in brief

`checks/lib/play.mjs` (how-to at its top), three files kept apart so the actions can sit on another driver later:

- `play.mjs`: the Playwright side. `openGame({ url, city | save, saveVia, mode, paused, ui, query, size, touch })`
  opens a game in a headless Chrome of its own (launchChrome: cores from the ledger, the page's demand workers capped
  to the claim, a throwaway profile, everything gone at `close()` or at exit). `launchGames()` gives several games in
  one Chrome. A save opens the player's way (Saved games, Open a file, the page reloads) or with `saveVia: 'post'`
  (smoke's import). English is pinned with `?lang=en`, since controls are found by their English names.
  Also `g.waitDemand()` (lib.mjs demandFinal), `g.shot(path, { element } | { box: [[w, s], [e, n]], pad } | { clip })`,
  `g.pageErrors()`, and `g.page` for a check's own probes.
- `actions.mjs`: the player's actions over a small driver (pointer move/press/tap at page px, press a control by
  role and name, fill a field, keys, camera, the in-page reads). No Playwright in it.
  - `g.act`: `camera(lngLat, zoom)`, `tab(name)`, `tool(name, { type, tracks, level, snap: { streets, real, roads,
    beside }, keepPlacing, ramp, oneTrack })` (each bar switch pressed only when it differs, read back by
    aria-pressed), `drawTrack(points, { before })` (per segment: placed, the edges it added, the ghost's length and
    cost, the notes shown; Shift carries the run on, Enter or the touch bar's stop ends it), `placeStation(p)`,
    `construct()`, `newLine(stops, { name, zoom })`, `openLine(name)`, `selectAt(p)`, `setTrains([h, m, l])`,
    `click(name)`, `type(name, text)`, `key(combo)`, `press(p)`.
  - `g.see`: `panel()` (title, subtitle, rows by visible label, tables, alerts, buttons, text), `line()` (schedule
    rows { demand, trains, headway }, stops with boardings, red figures), `money()`, `notes()`, `status()`, `toolbar()`.
  - `g.state` (named game-state reads for asserts; never for outside agents): `counts`, `lines`, `stations`,
    `edgesFrom`, `drawing`, `demand`, `selection`, `view`, `money`, `lastLoad`.
  - `g.toScreen([[lng, lat]])` / `g.toLngLat([[x, y]])`: the map's own projection plus its container's place, exact.
    Each press is hit-tested first: a point under a panel or button, or off the map, throws naming what is there.
- `reads.mjs`: the in-page reads, each a self-contained function of JSON (SEE and STATE lists).

No app code changed: `window.tw.map` (MapLibre's project/unproject) already gives the exact projection, and
lib.mjs's demandFinal already reads the demand final.

What I learned on the way, now handled in the harness:
- Chrome floors a mouse event's fractional pixel (the map's container starts at x 302.39), so presses were up to a
  pixel off; the driver rounds, and a point is now within half a pixel (t3556 measures 0.03, 0.13 px).
- Zoomed out (13) the map draws no stations, so the line tool's press finds none; `newLine` takes `zoom` and moves
  the camera to each stop, and otherwise says why the stop was not added.
- Buttons with a key hint are named with it ("New lineN"); the driver matches the name with an optional hint after.
- Typed train counts are capped by the panel (6 typed on a 3-stop line gives 4, T-3165), so the self-check types 3, 2, 2.

## Stage 2 sketch: outside agents playing (for Anita, not built)

What an outside agent calls: an MCP server (a small Node process) over the same `act` and `see` calls, each session
a headless Chrome on the public build with a fresh profile and `?new=1` (it never writes a slot). Tools:
`new_game(city, mode)`, `list_cities`, `camera(lngLat, zoom)`, `pick_tool(name, options)`, `draw_track(points)`,
`place_station(point)`, `construct`, `new_line(stops, name)`, `set_trains(line, [h, m, l])`, `press(name)`,
`read_panel`, `read_line`, `read_money`, `read_status`, `screenshot(box)`, and two this stage lacks:
`clock(play | pause | speed)` and `wait_days(n)`. Results are JSON and a PNG; errors say what is in the way.

What it must not be able to do: sign in or touch an account; save to the server, share a network, post to the
leaderboard or send feedback (those requests are blocked at the browser, `page.route` aborting the shonei-server
paths, and the controls left out of the tool list); see other players' games or shared saves; read `g.state`, import
`/src`, or run its own page code; load a save from anywhere but a file it was given. Each session gets a time limit,
a cap on calls a minute, and its share of the core ledger.

Two ways to offer it, smallest first:
- Local: an agent's owner runs the MCP server against the published game (an npm-style folder with play.mjs and a
  README). About 3-4 hours, plus 1 hour for the clock calls.
- Hosted, for "random agents on the internet": the same server behind a public endpoint with a queue and quotas,
  one Chrome per session. About 8-12 hours more, a server deploy (her word), and a machine's worth of CPU while busy.

An in-page `window.trainworld.agent` API is a third way, but its presses would be synthetic events the map may treat
differently from a real pointer, so the MCP route keeps "the player's path" honest.

## Stage 3 sketch: a save for a bug report (for Anita, not built)

- The feedback panel gets "Attach my game" (on by default for her, a choice for players): the current save (the
  real NYC save is 75 KB) goes with the report to the feedback inbox, with the camera, the speed and her UI settings
  (`trainworld-ui`). An agent then opens it with `openGame({ save, ui })` and stands where she stood.
- Smaller first step with no server change: a "Copy game for a bug report" item in Saved games that downloads the
  save with the camera and settings in one file; she drops it in the board's report.
- Later: a ring of her last 200 inputs (tool, presses as lon/lat, keys) kept in memory and attached too, so her
  slowdown can be replayed with `act` calls. About 2-3 hours for the attach, 3-4 more for the input ring.
