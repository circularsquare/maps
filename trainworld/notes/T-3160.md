# T-3160, T-3491: memory at the start menu, in a one-city game and on a phone's real-network start (agent phonemem)

## Method

`checks/t2802-memory.mjs` (notes/T-2802.md) on scratch production builds of the worktree (`TW_LINK_PACKS=1 vite build
--outDir <scratch>`, served by `checks/static-serve.mjs`), before and after the change, same machine, 4 claimed cores.
New: `DESKTOP=1` runs it in a 1400 x 900 desktop window with 3 solving workers (what T-3472 measured); without it, the
emulated Pixel 7 with 1 solving worker. Walk: start menu, Start in New York, demand final, five camera jumps, a

V8 heap used + ArrayBuffers + WASM. "Rest" is the renderer minus every context (Blink, compiled code, isolates,
WebGL in the renderer, allocator). Run-to-run spread is 30-50 MB at the renderer.

## T-3491: what changed

The page kept every zone's coarse outline decoded (61 MB of coordinate arrays) and, on desktop, every zone in
`OutlineEdges` (segment holders 40 MB, vertex numbers 23 MB, rings and keys 14 MB): about 150 MB from the start
menu on, plus a copy of every zone's lines in MapLibre's worker (97 MB of heap there at the menu against 45 now).

- `coarseOutlines.ts` keeps the file only as `PackedOutlines` on every device (decoded a zone at a time, the last 64
  kept), as phones already did.
- Desktop draws the coarse outlines from `map/coarseEdges.ts`: the packed file plus one Int32 a point, the other
  zone holding the border from that point to the next (5.4 MB), worked out once by `workers/outlineTopo.worker.ts`
  (0.3 s, about 60 MB passing in a worker that then ends). Same rule as `OutlineEdges`: a shared border is drawn by
  the first zone in the file's order still drawn coarse, none the focused zone holds. Compared with `OutlineEdges`
  over the whole file (every zone; 300 zones taken out with another focus; 400 zones only): the same segments for
  every zone. `OutlineEdges` now holds only exact outlines (and a phone's coarse zones near the view).
- No outline features while the map is blank (start menu, a game loading), where the layer was hidden anyway.
- The features of zones that leave the view's surroundings are dropped, so the page holds what MapLibre draws.

With every realm shown (`checks/t3491-outlines.mjs`, `opened=all`), page heap at world zoom 190 -> 82 MB, Europe
194 -> 50, Germany 196 -> 42, New York 197 -> 41; the same 4,015 features and 805,863 points at world zoom, and
the screenshots match pixel for pixel over the map (`artifacts/trainworld/t3491/`). In a fresh game only the
start realm's zones draw (28 features at world zoom).

Smoke 29/29 on the worktree's dev server. On the production builds the real save's demand final is 12,679,832 rail
trips before and after (the static server's 404s fail two checks on both).

## Stage 5: the commutes' exp tables (agent phonemem, 2026-11-21)

`mode_choice_rows` (`kernel/mode.rs`, `ExpRows`) replaces the S x S x bands `station_exp` table in a commutes pass
with a cache of rows, each worked out by the same loop (`fast_exp`, zero diagonal), only for the access stations of
the part's origins. A row stays until its slot is wanted by a row of a later origin (an origin's own rows are held);
at most 1,024 rows (about 6 MB at Tokyo's 1,454 stations), more only if one origin needs more. `api.rs` `pass` uses
it; `mode_choice*` with a table are unchanged for tests and the bench. Figures are exact: loads hash
6b583d415f907aa1 (2 rounds) and 0ba30c0488b4b61c (1 round) before and after; the new test in `api/tests.rs`
(`commute_fans_are_the_mix_of_two_choices`) compares table against rows (whole cache, 3-row and 1-row caches that force
eviction), parts (0,1) and (1,2), with and without fans, rule on and off, to the bit.

Native, `demand_mem --net tyo --zones tyo,tcg,gnm,yns,szo --market "" --rounds 2 --app-order --stages`: highest heap
**348.3 -> 323.5 MB**, rail trips 18,650,247.77 both. The first try (rows kept for the whole pass) gave 330.2: Tokyo's
own commutes pass touches nearly every row. Tokyo's commutes pass peak is now 303.7; the peak is in tyo everyday in
period 4 (323.5) and yns/szo commutes (316, the skims extended for their destinations).

Game (production builds, emulated iPhone, Tokyo real start, same method as stage 4): solving worker WASM 284 -> 280,
`peakNow` 278 -> 271, rail trips 17,468,887 and every round's rail the same. Only one run of the new build and the
base figures of the earlier run (284/278 in six runs): **a small gain in the game, not the tool's 25 MB**. The game's
peak (278) sits lower than the tool's (322 without the registry) so it is a different place that this table does
not reach; not traced. A second base arm failed (its production build's pack links had lost files), so no side by side
for the last run.

Time. Native paired runs (1 round, 4 pairs, both orders): commutes 55.2 s base, 58.5 s after (+6%); everyday, which
this change does not touch, 18.5 -> 20.1 s (+9%). So the shift is in the binary as a whole (layout), not in the
commutes' rows. In the game side by side (first version, no cache) the periods read 5-10% slower and the first
version did less work than the table; read as the same shift. Not resolved: if a slowdown shows on the batch checker,
this is the first suspect.

Next: the game's own peak (where `peakNow` 271 is reached), the five periods' results held (157), period 4's skims.

round's capacity cap (`cap_in`) and a period's estimate from another (`SubOut::scaled`). The lie: each station pair in
the two views within 1 part in 2,048 of before, their sums too; every other figure untouched.

## Stage 8: every graph array held once per worker (agents phonemem, then phonemem2, 2026-11-28)

### Why this piece

Stage 7's biggest piece left on the solving worker: each population (every zone's commutes and everyday layers, and a
desktop's market) builds its own graph for each of the five periods (`build_graph`, then `put_fares` and each round's
`set_crowding`, `rn_left`), and every cached skims table kept a copy of its graph's arrays as its key (`SkimKey`).
On the Tokyo start that is 10 populations x 5 periods, 2.24 MB a population, and nearly every array comes out the same
in all of them: one network, the same fares, and each round's crowding comes from every population's loads together.

### The cut (exact)

The graph's arrays are `kernel::Shared` (`sim/src/demand/kernel/shared.rs`): an `Rc<[T]>` never written in place,
made from a `Vec`, which looks for an array of the same bits already held on the thread (a hash of the bits, then a
full compare) and holds that one instead. A change makes a new array (`set_crowding`, `put_fares`, a round's
`rn_left`; tests use `edit`), which finds its own equal, so populations crowded alike share again; the last holder's
going drops it from the thread's registry. Equal means every element's bits, so a holder reads exactly the numbers it
made. The skim key holds the graph's own arrays instead of copies, and its compare finds the same array by pointer
first. The two bool arrays and the fare curve stay per graph (small). `demand::mem` counts each holder's share, so the
per-population reports add up to what is held; `demand_mem` prints the arrays held against every holder's own copy.
No other code changed (WASM interface, saves, app untouched).

Cost: one pass over an array's bits when it is made (a graph's 30-odd arrays per period and population, one edge
array a crowding round), against a search over every station each time; not timed apart.
