# T-3160, T-3491: memory at the start menu, in a one-city game and on a phone's real-network start (agent phonemem)

## Method

`checks/t2802-memory.mjs` (notes/T-2802.md) on scratch production builds of the worktree (`TW_LINK_PACKS=1 vite build
--outDir <scratch>`, served by `checks/static-serve.mjs`), before and after the change, same machine, 4 claimed cores.
New: `DESKTOP=1` runs it in a 1400 x 900 desktop window with 3 solving workers (what T-3472 measured); without it, the
emulated Pixel 7 with 1 solving worker. Walk: start menu, Start in New York, demand final, five camera jumps, a
three-station line with the clock running 45 s. MB after a forced collection: Chrome's private bytes; per context
V8 heap used + ArrayBuffers + WASM. "Rest" is the renderer minus every context (Blink, compiled code, isolates,
WebGL in the renderer, allocator). Run-to-run spread is 30-50 MB at the renderer.

## T-3491: what changed

The page kept every zone's coarse outline decoded (61 MB of coordinate arrays) and, on desktop, every zone in
`OutlineEdges` (segment holders 40 MB, vertex numbers 23 MB, rings and keys 14 MB): about 150 MB from the start
menu on, plus a copy of every zone's lines in MapLibre's worker (97 MB of heap there at the menu against 45 now).

- `coarseOutlines.ts` keeps the file only as `PackedOutlines` on every device (decoded a zone at a time, the last 64
  kept), as phones already did.
- Desktop draws the coarse outlines from `map/coarseEdges.ts`: the packed file plus one Int32 a point, the other
  zone holding the border from that point to the next (5.4 MB), worked out once by `workers/outlineTopo.worker.ts`
  (0.3 s, about 60 MB passing in a worker that then ends). Same rule as `OutlineEdges`: a shared border is drawn by
  the first zone in the file's order still drawn coarse, none the focused zone holds. Compared with `OutlineEdges`
  over the whole file (every zone; 300 zones taken out with another focus; 400 zones only): the same segments for
  every zone. `OutlineEdges` now holds only exact outlines (and a phone's coarse zones near the view).
- No outline features while the map is blank (start menu, a game loading), where the layer was hidden anyway.
- The features of zones that leave the view's surroundings are dropped, so the page holds what MapLibre draws.

With every realm shown (`checks/t3491-outlines.mjs`, `opened=all`), page heap at world zoom 190 -> 82 MB, Europe
194 -> 50, Germany 196 -> 42, New York 197 -> 41; the same 4,015 features and 805,863 points at world zoom, and
the screenshots match pixel for pixel over the map (`artifacts/trainworld/t3491/`). In a fresh game only the
start realm's zones draw (28 features at world zoom).

Smoke 29/29 on the worktree's dev server. On the production builds the real save's demand final is 12,679,832 rail
trips before and after (the static server's 404s fail two checks on both).

### What the page's buffers were

A heap snapshot of the page at the first line (desktop, 3 solving workers, after a collection): 215 MB of
ArrayBuffers, 156 MB of them one object, the market's corridor table (`demandClient` `modesTable`, also the newest
entry of `corridorTables`): 8,182,819 rows over 7,424 places, `longer` Float64 62 MB, `air` and `car` Float32 31 MB
each, `from` and `to` Uint16 16 MB each. So on a one-city game the 232 MB is held, not churn: it arrives with the
first solve that has a market (at demand final, before any line, the page held 34 MB of buffers). The rest: the
packed outlines (10), the coarse outlines' partner table (5), the published views (`pushed`, 10), bubbles (about 10).
The demand cache writer copies the whole table for each write (`writeStored`), so a write briefly holds it twice.

### What changed

- The table goes to the page with `longer` as Float32 and `air`, `car` as Uint16 shares (steps of 1/65,534; 65,535
  for NaN; `game/corridorShares.ts`): 156 to 94 MB, on the page and in each cache write's copy. Measured on this
  game: the world's longer trips 262,445,273.70 to 262,445,273.75; by plane 13,805,678.7 to 13,805,677.8; by car
  246,609,580.6 to 246,609,581.6. Rail figures are untouched (their columns stay Float64): the real save's demand
  final is 12,679,832 rail trips a day before and after. `CACHE_FORMAT` 9, so old cached results are not read.
- The realm shade's worker is started for each cut and ended with its answer on every device (a phone already did),
  and decodes only the zones a cut names. Desktop: 32-42 MB less all game. Cuts come when the realms shown change.
  Screenshots at four zooms in a fresh game match pixel for pixel over the map.

## Stage 3: the real-network start on an emulated iPhone (2026-11-21)

Why: five iPhone players' pages crashed right away (notes/T-3917.md, phones); the survey put the Tokyo and Kansai
real-network starts at 1.94-2.03 GB in the tab.

### Method

The survey's driver (scratchpad `phonemem/measure.mjs`, from `lagsurvey/`): emulated iPhone (iOS user agent, 390 x 844
at 3x, touch, no `deviceMemory`), 2 claimed cores, a new game then `data/packs/real/tyo.save` imported as a file. Added:
every context's JS heap and buffers every 3 s through the load, the demand workers' WASM (`WASMS=1`), Chrome's
memory-infra dumps by allocator (`MEMDUMP=1`, light every 3 s, detailed at chosen seconds), a timeline trace
(`TIMELINE=<s>`), heap snapshots of the page and clock worker (`SNAP=1`), `BUNNYOFF=1` (only the loading card's
animation paused). Saving claims are from scratch production builds (`TW_LINK_PACKS=1 vite build --outDir`, served by
`checks/static-serve.mjs`), with tracing and WASM sampling off, both arms run side by side.

**The dev server overstates the phone by about 0.4 GB**: the same load peaks at 1,995-2,070 MB in the tab on Vite and
1,602-1,641 on a production build (new game 826 against 516). Most of it is Blink's buffer partition (300 MB at the
new game on Vite, script sources with inline source maps in every worker). T-3917's phone figures are dev figures.

### Cut: the loading card's train no longer repaints the page (Chrome only)

The bunny's train animated parts inside one inline svg (a `stroke-dashoffset` and transforms on svg children), which
Chrome animates on the main thread: every frame restyled, laid out, painted and layerized the whole page (Layerize
473 ms per 10 s). With 1,444 station names in the page, each frame's paint left large dead objects in Blink's
garbage-collected heap, collected only with V8's rare major collections: `blink_gc/main` grew 76 -> 381 MB through the
load on Vite (live objects 16-20 MB of it), 290 MB on production. Pausing only the train (`BUNNYOFF`) kept it at 45-60.

Now `ui/Spinner.tsx` `BunnyTrain` draws the same drawing as layers over one box, each moving part (four wheels, the
ties, the car's chug, the ears) a div of its own moved by a CSS transform, which the compositor runs without painting.
The ties are drawn 12 longer and moved one dash pattern a cycle inside a clip at -12 to 112, the same pattern the
dash offset gave. The ears turn about Chrome's fill-box foot of the two ellipses (62.83, 31.68). Old against new at
eight frozen times: the same drawing; differences are anti-aliasing at most a device pixel wide, strongest at the
ties' two clipped ends (`artifacts/trainworld/t3160/bunny-old-new.png`, old, new, difference). A new timeline: Layerize
13 ms per 10 s, Paint 267 instead of 1,152 (about 27 a second remain; the load bar's width and text changes are among them, the rest not traced); Blink still
restyles the moving divs each frame (the app's own frame loop runs anyway).

### The solving worker's peak (every browser): measured, not cut

`sim/src/bin/demand_mem.rs` now takes `--net tyo` (Tokyo's real network in Tokyo's frame), `--market ""` (a phone's
solve) and `--stages`. On the start's zones (tyo, tcg, gnm, yns, szo, all fine on a phone):

    agent_cargo.py cargo run --profile agent --features demand --bin demand_mem -- --zones tyo,tcg,gnm,yns,szo --market "" --net tyo --rounds 2 --stages

- 94 MB live after set-up; period 0 peaks at 320.6 MB, later periods at 344-450 natively because the tool keeps
  every period's results. Rail trips 18,650,824.
- In the tool the peak is in a period's first crowding round: the free-flow skims stay cached (`SKIM_TABLES = 2`)
  while the crowded graph's are searched (39 MB more after that round, 0.2 after the second), and Tokyo's everyday
  pass needs about 93 MB of working memory on top (tyo everyday solved: live 162.6, peak 255.3 from 155.9).
- **Tried and reverted: forgetting a graph's skims when a crowding round changes it** (`forget_skims` before
  `set_crowding` in the three `crowd_with_external`). In the tool: rail trips exactly 18,650,824, period 0's peak
  320.6 -> 281.7 MB, every period 39-56 MB lower, the rounds a little faster. In the game: no change at all (solver
  WASM 343 and 351 against 343, `peakNow` 322 in every run, rail trips 17,468,887). The tool solves period by period
  (free flow, then that period's rounds); the game solves round by round over all five periods and releases the skims
  after each period's stage, so a round never finds the free-flow table cached. The tool's peak is not the game's.
- So the game's 322 MB in use is still unnamed. A likely shape: all five periods' results (the 157 left after the
  solve) plus one stage's skims plus the everyday pass's working set. Next step: an `--app-order` in `demand_mem`
  (round-major, `release_skims` after each period's stage) to find it, then cut the biggest piece. Each WASM memory
  keeps its high-water mark, so a peak cut there is a settled cut too, on iPhones as well.
