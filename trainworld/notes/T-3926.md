# T-3926: cached trips survive a release that leaves demand alone

From T-3917: the demand cache key carried `BUILD` (`Date.now()` at build time), so every release made the next
open of every save a cold load (5.5-7.5 minutes on a 2,000-station save).

## What the key is now

`CacheKey.demand` (was `build`) is `DEMAND_KEY` (workers/demandCache.ts), set by `vite.config.ts` `demandKey()`:

- In a build: a SHA-256 over `<path> <sha256 of bytes>` lines, sorted, for every file in the bundler's own module
  graph from `src/workers/demandClient.ts`: static and dynamic imports (from Rolldown's `getModuleInfo`), and
  every `new URL("...", import.meta.url)` in those modules. A URL that is a worker takes that worker build's whole
  graph (recorded by `demandWorkerGraph()` in `worker.plugins`); any other is hashed as a file (the demand WASM
  `sim_bg.wasm`, `market-rows.json`). Paths are from app/ (node_modules files from `node_modules/`), text has CRs
  dropped, so the same code in another checkout gives the same key. 156 files at the time of writing.
- The key goes over a placeholder in `renderChunk` (length kept, so maps stay right): worker builds run during the
  main build's transform, so every worker graph is known by then.
- Left out by name (`DEMAND_SKIP`): `src/i18n/messages/` (translations; every release changes them) and
  `src/workers/clock.worker.ts` with the track WASM it brings (every release changes them too). The clock's output
  reaches a solve only as the network snapshot, and the key's network hash (`canonical`) is of the service as
  demand reads it.
- Dev server: `"dev-" + BUILD`, new at each start, as before (a content key there would serve agents' edited
  demand code a stale result).
- `TW_DEMAND_KEY_FILES=<path>` on a build writes the hashed file list there.

Two related fixes the clock exclusion needs:

- `canonical` left out four service fields the solve reads: `back` (T-3348), `boat`, `brt`, `catches`. Before,
  the build stamp hid part of this across releases; within one build a network differing only in those already
  keyed the same. Now in the key where present.
- `saveNetKey` (the "ahead" key, T-1539) now holds `BUILD`: the stored snapshot was worked out by the clock
  worker, which is not in DEMAND_KEY. After a release the cached result shows once the network is in (17-42 s on
  the China save) instead of at once; within a build, as before.

If the graph may be short (a root not in the graph, a worker URL with no recorded worker build, a URL file
missing, or demand.worker.ts or the demand WASM not in the list) the build warns and its key is the build stamp:
a cold load, never a stale one. Checked by building with the worker graphs not recorded.

What a solve job carries besides the network and packs, gone through for inputs the key could miss
(`ToDemand` init/open/solve): the perfOff switches and worker count (in the key), pack levels (`:coarse` in the
key), the drives (in the market's hash), market-rows.json (hashed as a file), the zone in view and order
(`first`, `next`: order only), `heapStep` (memory only). `packService` reads one signal, `world.peek()`, for each
stop's fare scale by its zone, which comes from the station's position (in the key) through hashed code
(game/money.ts).

Nothing is hand-bumped. `CACHE_FORMAT` stays but is in demandCache.ts's source, so it is covered anyway.

## How often a release would have kept the cache

Over the last five releases (v0.4.0 -> v0.4.5, commits 0dd8659b 3ce746f9 37285c98 53fa4164 cea0f112 b0899150),
every one changed `workers/demand.worker.ts`, `workers/demandClient.ts` and `workers/demandProtocol.ts`, so none
would have kept it even with the narrowest file list. The gain comes in releases where demand work is quiet. Most
other changes in that window were in files that really are on the demand path (game/fareCurve, game/trip, ...).
Still over-inclusive: main-thread modules demandClient's imports reach (src/map/ 20 files, game/ui, game/money,
clockClient, saveFile): any edit there changes the key. Narrowing that means moving demand code out of modules
that import UI, not a list; a follow-up if releases with quiet demand still miss.

Changing a hashed file's comments changes the key (no attempt to tell a rule change from a reword).
