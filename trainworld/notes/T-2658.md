# T-2658: riders shown as settled while demand is still solving

Agent ridersnow, 2026-11-06, for maps-b9. Tree `ridersnow`, Vite 6153 (own dependency cache), headless Chrome pinned
to one core (the machine was full: the ledger granted 1), `demandWorkers=1`, the real New York save (109 lines).
Script `repro.mjs` and `summ.py` in the scratchpad `ridersnow\`; traces in `artifacts/trainworld/ridersnow/`
(`trace-before.jsonl`, `trace-after.jsonl`, one row each time anything sampled changed, every 250 ms).

## The run

A new 3-stop line "Probe" on Staten Island, every step through the game's `edit()` (Lines tab open, the line
selected); then a trains tweak on it; then a trains edit on a busy line and, while that edit's solve runs, a
trains tweak on Probe (the tweak waits behind it, `firm`, T-1734). Sampled: `linesPending`, the shown view's
entry for the line (riders, estimate, the tph it was solved with), the line as it is, `today`'s riders, the Lines
tab row's riders and money text, the line panel's Riders/Profit rows, the edit note.

## What each view reads

- Lines tab riders, group rows, line panel counts block: `today` (the clock worker's boarding account, past 24 h),
  with the pending label from `linesPending` (game/lineFigures.ts). No account entry: blank, except on a line's
  opening day, where `countingRiders` reads **0** until the first figure above 0 arrives.
- Profit (tab and panel): `profitKnown` = trains and (the view has an entry for the line, or it is not pending).
- Edit note: the shown day's view, settled when not updating, the view final, and stops match (`solvedForNow`).

## Found (before the change)

1. **Pending cleared by an older solve.** `linesPending` was cleared for a cluster's lines by any cluster final
   of the current solve, wholesale when `demandUpdating` went false, and wholesale 8 s after an edit if not
   updating. When an edit waits behind a running solve (always, after the local step, on a big game), the
   running solve is of the network *before* the edit. Trace, "during": Probe's tweak at 8 s is held
   (`waiting`), "loading..." shows; at 741 s the older solve's local result lands and clears Probe's label;
   the row and panel then show the old 4k riders as settled, the view's entry still solved at the old tph
   (25/25/23 against 25/23/15 now). The same older solve's whole final sets `demandUpdating` false for one
   moment before `flush()` sends the held edit: the blanket clear fires, and the edit note's effect, seeing
   "not updating, final, stops match", settles against a result without the tweak (a 0 or wrong gain), and
   takes that as the next base, so the following note is wrong too.
2. **The account lags the result.** Trace, "build": Probe's local result lands at 649 s (label cleared, the
   view has 3,835 riders a day), but `today` has no entry for it until 658 s: for 9 s the Lines tab row read
   "0" (opening day) and the line panel showed no riders at all. On a busier game the gap is longer.

Saying "a solve of the network covering the change has reported" needs the network's age; demand's solve
versions do not say which edit a network has. A world state always reaches the page before the snapshot made
after it (one worker, messages in order; a held state is released before any other message), so the world
version current when a network arrives is the newest world that network includes.

## The change

- `game/demand.ts`: `networkWorld` (the world version as the newest network reached demand) and `finalWorld`
  (the one of the network whose whole final is shown).
- `workers/demandClient.ts`: records each network's world version (`netWorld`, kept up to date when a same-key
  network arrives); sets `finalWorld` when a final shows (and on `settleIdle`); passes the solve's world version
  to `linesSettled` for a cluster's (local) result.
- `game/lineFigures.ts`: each pending line keeps the world version its change came in; a result clears it only
  when solved at that version or later; `finalWorld` settles every line changed before it; no clear when
  `demandUpdating` goes false; the 8 s fallback only when no network came after the change; demand stopping or a
  game load clears all.
- `game/today.ts` `pendingOf(l)`: the label also stays while the view has riders for the line and the account has
  not counted them (no entry, or 0 riders), "constructing..." when it has no entry. Lines tab rows and group rows,
  and the line panel's counts block, read it.
- `game/editNote.ts`: settles only once `finalWorld` reaches the world version the last edit came in; when no
  network came after the edit, after 8 s as before.

No player-facing text changed: the labels are the existing "constructing..." and "loading..." (Anita's own word
for a changed line, 2026-11-04) and the Profit row's "calculating...".

## After (`trace-after.jsonl`, same save and steps; the tweak 10/8/6 trains to 5/4/3, the held tweak to 8/6/4)

- **New line**: "constructing..." from the edit until 587 s. The local result landed at 579 s (label kept by
  `pendingOf`: riders solved, none counted yet), the account counted them 7.6 s later and the row counted up
  from there (506, 2k, 4k). No 0 at any point; the panel read "Riders constructing..." throughout.
- **Tweak** (its own solve): "loading..." over the old 4k from 0.6 s until its local result at 485 s, solved at
  the new trains (19/15/12 tph, as the line is). The account's old count then stood 1.4 s unlabelled (a real
  figure, the line's before the tweak) before 3,814.
- **Held tweak** (made 558 s into the busy line's edit, after that edit's whole was sent; `waiting`): "loading..."
  through the older solve's final at 825 s (`finalWorld` 13, the tweak came in at world 14), then until the held
  solve's local result at 1161 s (25/23/15 tph, as the line is). Before the change the older solve's local result
  cleared it.
