# T-180: smooth play while loading, and a loading card

Anita, 2026-10-12: "for startup the game does kinda run at like 3fps while we are loading (at
around ~6s in) and able to move around, so i think there is room for improvement there. also i
think the loading indicator should still be kinda center stage before we're loaded enough for the
timer to start. we should be able to interact but it should be very obvious that we're still
loading."

## What changed

- **The loading card** (`ui/LoadingScreen.tsx` `LoadingCard`, `style.css` `.loading-card`). While
  a loaded game's clock is held (startup, and any whole-game load), a plain card in the middle of
  the map says "Loading New York and New Haven, 34%" over the step ("Opening city data"), or
  "Calculating demand" when nothing needs loading. Its wrapper and the card have
  `pointer-events: none`, so a press on it pans the map (checked: `elementFromPoint` at its centre
  is the map canvas, and a drag started there moves the map). No transition or animation; it goes
  in the same render the clock starts. It sits in `#main` under the top bar (MapLibre wants its
  own container empty when it starts). While it shows, the top bar leaves the load out; later
  loads (a pan to Boston) still use the top bar. The failure screen is unchanged.
- **Top bar overflow** (QA, 900 px window): `.demand-busy` could not shrink, so "Loading New York
  and New Haven, 34%" ran over the cash. It now shrinks and ends in an ellipsis, with the whole text
  as its hover; the mode bar gives way first (`flex-shrink: 6`). Checked with a three-city text at
  900 and 1280 wide: it ends at the split's edge (657 of 657, 921 of 921), cash untouched.
- **Hovering a big network** (`map/pick.ts` `topSeg`, `map/overlay.ts` `toScreenInto`). Every
  pointer move without a button ran `pick` (and the track tag ran it again), which projected all
  117,701 line segments and 117,701 track segments of the real NYC save, two arrays allocated per
  point: about 5 ms a scan, several scans a move. `topSeg` now takes the pointer into local units
  once (screen position is an affine function of local units while the map has no pitch, which it
  cannot have) and skips a segment whose box, grown by the slop, its sideways offset, a pixel and a
  quarter of the scale, misses the pointer; the rest go through the old arithmetic unchanged,
  projected without allocating. Same answers: 4,000 picks on the real NYC save at zooms 10-16,
  lines (with offsets) and track, half of them next to a segment (1,682 hits), old and new
  `[index, distance]` identical (scratchpad `t180/pickcheck.mjs`). 5.0 ms -> 0.66 ms a scan
  (development build).
- **The regional market reaches the workers as bytes** (`demandClient.ts` `post`,
  `demand.worker.ts` `openPacks`, `demandProtocol.ts`). The main thread decoded 8.2 MB of JSON
  to a string and cloned it into six workers while the player could already pan; each solving
  worker now gets its own copy of the bytes (the last the original, transferred) and decodes it,
  and the aux worker, which never opens the market, gets an empty marker. Workers still accept the
  text (the Node checks send it).

## Measurements

Production builds of the tree before and after (`vite build` into the scratchpad), served by a
Range-capable static server with `no-store` (T-172's), headless Chrome 154 at 1920x960 on this
machine (ANGLE D3D11 on the RX 6600; chrome://gpu reports every feature hardware accelerated),
other agents using 40-55% of the CPU. The pointer is driven at 125 Hz without waiting for each
event (as a real mouse), from the moment the map has loaded (1.2-1.8 s). "Moved frames" are
animation frames on which the map's centre changed. Scripts: scratchpad `t180/frames2.mjs`,
`fsumm.mjs`, `loafs.mjs`, `psumm.mjs` (CPU profile), `pickcheck.mjs`, `shots.mjs`; not kept.

| | before | after |
|---|---|---|
| drag, new game, 2 s to clock | 60 moved frames/s, worst frame 17-33 ms (57/s, worst 19 ms rerun in the same minute as the after runs) | 56-57/s, worst 19 ms |
| drag, NYC save, 2-6 s | 49-60/s, worst 117-330 ms | 45-56/s, worst 37-360 ms |
| drag, after the clock starts | 56-60/s, worst 17-34 ms | 56-57/s, worst 19-35 ms |
| hover, NYC save, 2-6 s (loading) | 49 frames/s, worst 54-176 ms, 21-28 frames over 50 ms from the hover handler | 56/s, worst 18-36 ms, none |
| hover, main thread busy (CPU profile, 1.5-6 s) | 3.3 s of 4.5 s | 0.9 s of 4.5 s |
| clock runs, new game | 2.68-3.43 s | 2.90-3.16 s |
| clock runs, NYC save | 6.13-7.98 s | 5.78-5.98 s |

The single long frames while dragging are the first map frames after the style and the network
arrive (MapLibre compiling shaders, `getProgram`) and one result landing (`publish`, 40-70 ms on
the NYC save). The headless frame rate tops out at 56-60 depending on the minute.

## The 3 fps did not reproduce

Dragging during the load stayed at 45-60 frames a second in every condition tried, so the main
thread is not what Anita saw; during the NYC save's load it is idle about 78% of the time (CPU
profile: 1.4 s busy in 6.5 s while dragging) and gets a handful of worker messages a second.

| condition (drag during load) | moved frames/s in 2-8 s | worst frame |
|---|---|---|
| plain, 1280x720 and 1920x960 | 49-60 | 33-330 ms |
| 10 extra busy threads | 36-59 (map frames) | 118 ms |
| 16 extra busy threads (machine saturated) | 57-60 | 34 ms |
| two more headless games loading the NYC save at once | 49-60 | 146-167 ms |
| software compositing (`--disable-gpu-compositing`) | 46-59 | 67 ms |
| Homes bubbles, station riders and the City tab on | 49-60 | 134 ms |
| software WebGL (SwiftShader) | 0-11 | seconds |

Only software WebGL comes near 3 fps, and it is as slow after loading (10-14 fps), so it is not
the cause unless her Chrome had lost its GPU; her Chrome reports hardware acceleration on. The
remaining differences from her session are headed Chrome (real display and vsync), her own save
(which may be bigger than T-007's 117,701 segments), and whatever else the machine was doing then.
Hovering was the one main-thread cost found that grows with the network and lands on every pointer
move, during loading as after; it is fixed above. If it happens again: open with `?debug=1` and
read the readout's "Map ... frames/s" line while panning during the load (MapLibre's own frames),
and note whether the pointer was dragging or just moving.
