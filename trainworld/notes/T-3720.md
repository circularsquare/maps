# T-3720 A new game in the reused autosave slot inheriting an old game's id

Agents autolatch and latchfix2, 2026-11-18, tree `autolatch`. Reproduced, fixed. The first fix failed a check
(latchchk) on one path; latchfix2 fixed that, and a second checker's two points (latchchk2) after it.

## Reproduced

Local shonei-server (SHONEI_DEV=1, scratch copy of the data, 127.0.0.1:8083), own Vite, scratch `probe.mjs`. A
signed-in player plays a normal game in the original `autosave` slot (PUT normal 200), switches it to sandbox (PUT
`{"mode":"sandbox"}` 200, latched), shares it, deletes the game, then a new game starts in `autosave` (the load
fallback: the slot is gone, so `autosave` again) and is played.

- Account games unreachable (cloud routes aborted; the account's copy of A cannot settle): the slot's first write
  ties it with `ctx.ids["autosave"]`, A's id (`tieNew`, seen directly), the page's score entry still has A's latch,
  and B's score PUT goes under A's id: **403 "this game has been a sandbox"**. B never ranks.
- Account reachable: the tie takes A's id too, but the first upload finds A's game gone with a tombstone and moves B to a
  new id before the first score send, so B is listed. It depends on that settle landing before the send.

How an entry survives its game: `dropDeleted` skips the active slot, and takes nothing off while the account is
unreachable or signed out ("later"). A new game then starts in `autosave` with the entry still there.

## Fix (account.ts, cloud.ts)

Two questions, kept apart: whose game an entry is, and whether its figures may be taken off the account.

- **Whose game.** Score entries carry the game's `origin`. An entry is an **earlier game's** when its origin differs
  from the slot's **and** its id is not the slot's own account id (`slot.cloud.id`); one under the slot's account id is
  the slot's game whatever its origin, and takes the slot's origin. `tidyEntries` (synchronous; first thing in
  `sendScores`, `gameForShare` and `dropDeleted`) restamps the one and puts the other aside under `earlier:<id>`, so
  the slot's game writes its own entry and the earlier one is still there to take off later. `entryOf` and
  `cloudContext`'s `ids` never give an earlier game's entry, which is what stops a new game inheriting the id.
  Entries with no origin (from before) are trusted.
- **May its figures go.** `dropDeleted` sends a DELETE for an entry whose slot is gone (a deleted slot, or an
  `earlier:` one) only when a list of the account's games fetched in this page (`listGames`, kept 60 s) lacks the id,
  a deletion still owed counting as gone. An id the account still has is another version of a game, maybe played on
  another device (the old id after a `splitOff`), and is never taken off from this browser, whatever its origin. With
  the account unreachable there is no DELETE; the entry waits. A server that keeps no games has none to lack. This
  applies to plain deleted slots too, which before took their figures off whatever the account held.
- No DELETE either for an id any slot here holds as its account game (`keepOtherTabs` moves a tab's change, sync
  record and all, to a new slot): the entry moves to that slot if it has none, else is forgotten.
- `sendScores` never waits on or stops for a retire: the live game's figures go under its own id. It keeps the
  entry's `shared` mark when a share of the same id came while it was in flight (`gameForShare`); lost, a share of a
  sandbox game deleted later would stay up.
- `dropDeleted` is single-flight: one run per page (a call during a run gets one more run after it), and across tabs
  through `navigator.locks` with `ifAvailable` (a tab finding another's run under way skips; the entries are shared).
  Each entry is read again after the list's request and before its DELETE. It runs on every change of the slot list,
  the session and the account's state, so a put-aside entry goes once the account answers.
- cloud.ts `tieNew`: always a new id. A slot's first write has no live entry, so `ctx.ids` there is always an earlier
  game's.

An `earlier:` entry whose id the account keeps for good (another device's version) stays in this browser's entries;
it is small, and it takes that game's figures off if the account ever drops the game.

## The checkers' paths

latchchk: another device uploads the same game id with a different `facts.origin` (reachable by saves from before
T-2037 with a fork-time or " copy" name on two devices: init stamps origins with `stampAll(null)`, so devices can give
the game different roots). The pull (`writeFetched`) writes that origin into the slot; the first fix judged the slot's
own entry stale and sent its id two DELETEs (two `dropDeleted` runs at once), taking the Community share down for good.

latchchk2: (a) after a `splitOff` (the slot gets a new id; the old id, and its share, stay with the account's copy) and
then a pull with another origin, the entry naming the old id looked stale and would be DELETEd: another device's game.
(b) While a stale entry's DELETE failed, `sendScores` returned early on every call, so the new game never sent. Both
closed by the list rule and by `sendScores` no longer waiting.

Path audit, for which other route could make the slot's and the entry's origin disagree for one game: a slot's origin
is only replaced by `writeSlot` with an explicit origin, and for an existing key that is a pull (`writeFetched`, both
callers pull the slot's own id: `settleSlot`/`takeInto` and `openOnAccount`) or an autosave of `saves.gameOrigin`,
which `heldFrom` set from that same pulled save. `stampOrigins` fills only empty origins. New games, imports, restores
and Community views all go into a fresh key or no slot (`intoNewSlot`, `msg.newSlot`, `intoView`, the damaged-load
fallback); `msg.fresh` owns no slot; the `autosave` fallback only reuses a key whose sync record `deleteSlot`
removed. So a same-game origin change keeps the id (restamped), and an id change keeps the origin; only both together
look like an earlier game, and the list rule keeps that one's figures while the account has it.
