## What changed: no closing and reopening while a save loads in a running game

A save opened while another game runs (perf_bench's import; a slot or file opened from the game) sends its stations
ahead, so its packs start opening before its network arrives. Meanwhile the pool's sweep (`demandClient.ts`
`keepSet`/`sweep`) still went by the last game's reach, found the new save's opened zones spare, closed all but two
(KEEP_SPARE), and opened them again once the network came: 23 zones twice on this save (dev probe: 11 zones closed at
19 s and reopened at 32 s in every worker; the reopening was 10-14 s of each solving worker and 26 s of the helper).
Now `keepSet` keeps the save's prefetched zones and markets while `ahead` has not arrived.

A load from the start menu with a fresh page was not affected (startup is "loading" then, and the sweep waits). So this
is not her "initial load"; it is a load from inside a game, and every perf_bench measurement (the bench's import is that
path, and NYC sometimes reopened a zone too: 64.5 MB down against 62.9).

Figures the same: rail trips identical on both saves (82,603,971; 12,672,465).

### How it works

- **Found** as the kept result is today: the slot's (or any slot's) entry `demand:<slot>:<network hash>`, so the same
  network as demand reads it (`canonical`). Its key may differ from this build's only in the demand code's version
  (`DEMAND_KEY`) or the worker count; the zones, markets, every pack's bytes, the levels of detail, `CACHE_FORMAT` and
  the perfOff flags must match (`demandCache.ts` `standsIn`). Packs that differ mean a full load, as before: a rebuilt
  pack can renumber its cells (the kept bubbles are in pack cell order) or the market's places, so its figures could
  land on the wrong cells. A changed network form (`canonical`) finds nothing. `?perfOff=standIn` turns it off.
- **Shown** exactly as a kept result of this build (`applyCache`): the card goes once the network is in and the zone
  in view has figures, the clock runs, the status tag says "Trips in N cities being recomputed…", the workers solve
  the network under the load's barrier, estimates not shown, and the fresh final replaces it whole. No new text: a
  player sees what a same-build reload shows, plus the figures moving a little at the final, which the tag's
  "being recomputed" already covers.
- **Never written back**: a write takes only a solve's own final (every day's view at that solve's version), and a
  stand-in is shown under the cache's version 0. Its fresh final is written over it (`writeCache` no longer skips a
  network whose shown result stood in, `cachedStandIn`), under the same storage key, so the next load is an exact
  one. An edit before that final is an edit like any other (as under a kept result today, T-2560): its own final
  replaces everything and is written.
- **Storage**: nothing more is kept. The stand-in is the one result a slot already keeps; the fresh final overwrites
  it. On asianita that entry is 15.6 MB (`storedSize`, near enough), on NYC 10.1 MB.
- The ahead path (T-1539) misses after an update (its key holds the app build), so a stand-in shows when the network
  is in: the map's time.
