# T-172: startup time

Anita, 2026-10-12: "the game's initial load time is quite long now ... especially as it'll get
worse the more cities we add ... look into ways we could improve this or get it feeling better
at least." Covers T-167 (New York's everyday opening) and part of T-168. (Briefly numbered T-170,

## Result

Production build (`vite build`), served by a static server of my own with HTTP Range and
`Cache-Control: no-store` like serve.py, headless Chrome, default pool (5 solving workers + 1),
this 16-thread machine with other agents building at the same time. Seconds from navigation.
"Usable" = input works and the clock runs; after T-172 input works from "track drawn".

|---|---|---|---|---|---|
| new game | 0.3-0.8 | 11.8-19.6 (4 runs) | 0.3-1.0 | 4.3-5.4 typical, 7.2-10.1 in 3 of 10 runs | 6.9-12.9 |

Raw runs: scratchpad `t170/before*.json`, `after*.json` (startup.mjs, summ.mjs, table.mjs there;

The slow runs are one thing: New York's everyday opening takes 7-8.5 s instead of 1.3-2 s in all

## Where the time went (before)

New game, typical run (ms from navigation): page and module 0.4 s; packs downloaded by 0.3-0.7 s
(localhost); clock worker ready and track drawn 0.3-0.8 s (main-thread long tasks 0.2-0.3 s in
all). Then, in every solving worker, one after the other:

| step | before, Chrome (each of 5 workers, in parallel) | natively |
|---|---|---|
| regional market open (`IntercityApi::new`) | 1.9-2.5 s | 1.0 s |
| New York commute pack (`DemandApi::new`) | 0.02-0.05 s | 0.02 s |
| New York everyday purposes (`EverydayApi::new`) | 4.9-5.2 s, 9.4-16.7 s in the slowest worker | 5.0 s |
| warm-up | 0.01 s | |
| network setup (`set_network`, NYC save) | 1.2-1.4 s | 0.55 s (0.5 s of it the everyday pairs) |
| first estimate, one period (new game / NYC save) | 0.5 s / 9.6-10.2 s | 0.4 s / 3.3 s |
| each crowding round, one period | 0.4-0.5 s / 2.2-2.4 s | 0.3 s / 1.5 s |

Readiness waited for round 3, so a new game was ready about 2.7 s after its first estimate and
the NYC save about 8 s after. On the NYC save the first estimate was four times a crowding round
because the regional market's free-flow graph left the fare out (T-121), so it ran a strategy
search of its own towards every station a far zone reaches: 1.8 s natively a period, about 7.5 s
in Chrome with five workers searching at once. WASM compile, pack parsing and downloads were
small (wasm start 12-65 ms per worker).

Two Chrome effects: (1) a WebAssembly function is optimised only between calls (no on-stack
replacement), so one long call runs in the baseline compiler throughout; with
`--no-wasm-dynamic-tiering` (everything optimised up front) the market opened in 1.35 s instead of
2.1 s and the NYC setup in 0.75 s instead of 1.4 s. (2) Five workers opening at once contend.

Duplicate fetches: every boundary file 2-3 times (the reach test, the outline sources, the focus
shade), `nyc.json` twice (demand pool and the clock worker's water mask).

## What changed

**Rust (sim/src/demand/).**

- `everyday.rs`, the everyday opening: zone centres sit on the zone grid, so the destination
  gravity's decay depends only on the grid offset; one table per purpose (`DecayTable`) replaces
  a square root and an exp per zone pair (4 x 6,274^2 for New York). Origin zones with nothing to
  send are skipped. The sampled destinations agree with before to 7 significant figures in every
  purpose's trips, walk share and trip length (`info()`); New York's everyday rail on the real
  save +0.003% (the table's distances are exact grid multiples instead of float differences of
  absolute positions). Native 5.0 s -> 1.0-1.1 s; Chrome 4.9-16.7 s -> 1.3-2.0 s.
- The long loops of the opening (`DecayTable::cdf`, `Sampler::sample`, `add_totals`) and of
  `set_network` (`index_edges`) are functions called once per zone or per 16k samples
  (`chunks`), so Chrome optimises them after the first calls. `info()` reads trip kilometres
  summed at opening instead of a second pass over 3.2M samples (0.28 s). `set_network` checks a
  sample's subzones before computing its weights and uses a cheap hasher for the pair index (pair
  order is first-seen order either way): 0.5 s -> 0.32 s natively, on every edit too.
- `intercity.rs`: the free-flow estimate applies `set_crowding` (all ones) like the local
  populations, so round 0 shares their strategy search (fixes T-121; DECISIONS 2026-10-12):
  market round 0 1.8 s -> 0.11 s natively a period; NYC save first estimate per period 10 s ->
  2.4 s in Chrome. Market rail on the real save -21% (2,375 -> 1,886 trips a day); local rail
  +0.004%. The market's zone-pair rows are an out-of-line function (`decay_row`) that skips pairs
  under 40 km (no trips there; the same zeros) and looks corridors up by index. Opening 1.0 s
  natively (was 1.0 s: the decay itself dominates), 1.2-1.5 s in Chrome (was 1.9-2.5 s).
- `cargo test --release --features demand`: 114 pass. `npm run wasm` run.

**App (JS/TS).**

- **Gate** (DECISIONS 2026-10-12): no loading screen; the map, inspectors and building work as
  soon as the network is drawn. The clock is held until the first estimate (`READY_ROUND = 0` in
  `workers/demandClient.ts`), not round 3. Top bar: "Loading New York, 42%" during the load
  (previously only for later loads), "–" in the mode split until the city has opened, the time
  greyed with hover text "The clock starts when demand has loaded". The failure screen stays.
  Percentage weights 10 / 50 / 40 (download, open, first estimate).
- `main.ts` starts the demand pool before the map is set up (workers spawn 30-40 ms earlier,
  before MapLibre's and the clock worker's; small, but it is the critical path).
- `game/boundaries.ts`: each boundary file is fetched once and shared by `cityReach.ts` and
  `map/cityBoundaries.ts` (MapLibre sources get the data instead of a URL): 9 requests instead
  of 19.
- Checks: `npm run check`; `t149-worker-check.mjs`, `t116-coordinator-check.mjs`,
  `t066-worker-check.mjs` pass. `notes/t149-browser.mjs` tests T-149's blocked input and no
  longer applies. Gate check (scratchpad `t170/gate-check.mjs`): during loading there is no
  screen, the map drags, `1` picks the track tool, the clock stays at 07:00 and held; at the
  first estimate it is released and runs.

## Where the time goes now

NYC save, typical: downloads 0.4 s; market open in every worker until 1.6 s; New York open until
3.0-3.4 s; network setup 0.9-1.5 s; first estimate 2.4-2.6 s a period; clock runs at 7.5-8.2 s;
three crowding rounds about 2.6 s each. New game: open until 3.3-3.6 s, first estimate 1.0 s.

## Open: the slow mode

In about a third of runs (new game and NYC save alike) New York's everyday opening takes 7-8.5 s
instead of 1.3-2 s, in all five workers at once; the market opening before it is unaffected.
It happened only on the second or later page load in a browser, never on the first, and in none
of four runs with `--no-wasm-dynamic-tiering`, so it looks like Chrome not getting the hot
functions optimised in time (background compilation delayed, perhaps by the previous page's
teardown or the machine's load from other agents). A player opening the game once mostly gets
the fast path. Not resolved here; resolved by T-173 (a warm-up in one worker first), notes/T-174.md.

## How it scales to more cities

What grows with the number of cities registered (not the ones in play):

- **The regional market**: one pack for the whole region, opened in every solving worker, with
  two passes over every zone pair (2,913 zones, 4.2M pairs, 668k kept directed pairs). Time and
  pairs grow with the square of the zones: 30 cities in one market with about 3x the zones would
  take about 9 s natively per worker to open and hold about 6M pairs (about 140 MB per worker
  instead of 16 MB). This is the one that breaks. Fix (T-174): build the pairs offline in
  `pipeline/intercity.py` into a binary market pack (pairs, trips, drive minutes, corridor) so
  opening is a read; or split the market by region. Left for when the market's design is
  settled (Anita: intercity demand is rough on purpose and undecided). Done differently by
  T-174 (an O(zones) derived block, pairs only between served zones), notes/T-174.md.
- **Downloads**: the market JSON (8.2 MB now) grows with it; boundaries (9 files, 0.4 MB) and the
  clock worker's water masks (one header and one byte range per city) grow linearly. Fine on
  localhost; on R2 with compression and caching (T-060) only the first visit pays.
- **Per-city opening** is only for the viewed city and cities with construction (T-149). With the
  table, an everyday layer costs about O(zones^2) cheap multiply-adds per purpose plus 16
  samples per cell: about 1 s natively for New York (6,274 zones, 202k cells), a few hundred ms
  for a typical metro. A save with construction in many cities pays each of those once, in
  every worker, one after the other.
- **Solving** depends on the network built, not on the cities registered.

Estimate for 30 registered cities, today's code: new game about 4-5 s to the clock plus the
market's growth (several seconds per worker, all in parallel), i.e. roughly 10-15 s, almost all
of it the market; with the market prebuilt, about today's 4-5 s.

## Not done, and why

- Opening the everyday layer once and sharing it between workers, or precomputing its
  destinations into the pack: the destinations are 52 MB (4 purposes x 202k cells x 16 x u32),
  too big to ship or copy around; the table made opening cheap enough in every worker instead.
- IndexedDB caches of packs or derived data: downloads are not the bottleneck on localhost, and
  R2's HTTP caching (T-060) covers packs; derived data is now about 1 s to rebuild.
- Progress inside the long WASM calls: the longest is now 1.3-2 s (fast mode).
- Sharing one compiled WebAssembly module between the workers: Chrome already shares compiled
  code between workers of a page; untested whether it changes the slow mode (T-173).
- `nyc.json` fetched twice (10 kB): negligible.
- The percentage stalls at 60% during network setup and the first estimate on a big save
  (about 4 s on the NYC save): the workers report nothing between; harmless now that the game is
  playable meanwhile.
