# T-3666 A kept-open game for agents' probes, and a wait command

Proposal 1 of research/workflow-2026-11-18.md. Built by agent playkeep on 2026-11-18.

## What there is now

- `checks/play.mjs` (how-to at its top). `start <city|save> --port <Vite>` opens the game in a headless Chrome of
  its own, held by a background node process (cwd and log in `%TEMP%\tw-play\`, never in a tree), one per Vite port,
  its cores claimed in the shared ledger as `check-play-<pid>` (`--cores N` sets the ask). It prints one line when
  loaded. Then:
  - `do '<js>'`: runs in the open game with the harness in scope (`act`, `see`, `state`), plus `wait.final`,
    `wait.panel`, `wait.selection`, `wait.bubbles`, `wait.lines`, `wait.days`, `wait.until`, `clock({ run, speed })`,
    `sim`, `shot`, `g`, `page`. One line of JSON back (`ok`, `ms`, `result`, cut to 3000 characters); a failure gives
    the error, the tool notes, the status tag, and any new page errors. Calls queue: one runs at a time.
  - `sim <read> [json]`: a named STATE read (new: `trips`, `clock`, `bubbles`) or any page expression, Maps and Sets
    turned into JSON (Playwright returns `{}` for a Map without complaint).
  - `edits <file.json>`: raw edit ops with `{"$node": [lng, lat]}` / `{"$free": [lng, lat]}` points, or `line` /
    `across` items; each waits for the world to change instead of buildLine's fixed pauses; a line's stations are
    found among the nodes its own routes added, so a fixture in a built save does not grab the network's nodes; each
    step's refusal is named (`station 2: PlatformCrossing`). Answers `after` (the demand version before) for
    `wait.final({ after })`.
  - `reload [<city|save>]` after a Vite restart (the kept page still runs the old modules); `status`; `stop`.
  - Stops by itself after 30 minutes unused (`--idle`), so an agent that dies doesn't hold its claim.
- `checks/wait.mjs <file> <pattern> <timeout-s> [--new] [--pid N] [--fail <pattern>]`: prints the first matching
  line; a match already in the file counts; a missing file is waited for; exits 1 with the last lines on timeout,
  on `--pid` ending, or on a `--fail` line.
- `lib/reads.mjs` STATE `trips` (trips and rail trips a day, round, version, final, lines; `byLine` riders by line
  name), `clock`, `bubbles` (scans `twViews.click` over the map: one entry per bubble with its lngLat to press);
  `lib/actions.mjs` exposes them as `g.state.trips/clock/bubbles`.
- `checks/cores.mjs` fix (a real bug, every check from a worktree): the ledger path was `../../cores.py` from
  checks, which in a tree is the tree's own copy, so checks run in trees claimed in `.tw-trees/<name>/cores.json`,
  which nobody reads (found mine there with cap 10; tt2 has one too). It now goes to the main tree's ledger, and so
  does the registry of which cores each check holds (`artifacts/trainworld/check-cores.json`), so two trees' checks
  no longer both pick cores 13-15.

  Helptrip ran it 11 times, 16 minutes.
- With play: `start` 10.4 s, then one `do` 10.3 s: 21.5 s and 2 calls cold. A repeat (Escape, two bubbles) 3-4 s.
  Finding the flow from scratch took me 8 `do` calls, 2 `sim` calls and one restart of the game (to load a fix to
  play itself), about 5 minutes, most of it one 60 s timeout. What I
  learned: once a bubble is selected, the bubbles to press for a trip are kind `trip` (`wait.bubbles({ kind:

- The `do` body that works:
  `await act.camera([-73.985, 40.75], 9.5); await act.click("Destinations"); await wait.final(); const b = await
  wait.bubbles(); await act.press(b[0].lngLat); await wait.selection(); const t = await wait.bubbles({ kind: "trip"
  }); await act.press(t[0].lngLat); return (await wait.selection("trip")).kind`

## Snapshot and restore: not kept

- What a calculated state costs is the trips calculation, and every way back to a state recalculates:
  - Undo back to it: like any edit, 78 s on the real save (3 cores), and the undo count has to be exact.
  - Reopening its save: the full calculation (105 s after a reload in the same Chrome, 142 s cold).
- The game's own demand cache can show a final in seconds: a page reload of a game in a writable slot showed the
  cached final 25 s after the reload (load 17 s), same figures to the trip. It does not work as a snapshot:
  - only in a writable slot (`?new=1` writes none, so the harness's usual open never caches);
  - the key holds the build stamp, `Date.now()` when Vite starts (vite.config.ts `__TW_BUILD__`), so after the
    Vite restart an app edit needs, it misses;
  - one network per slot: a later final deletes the slot's other entries, so a state after edits can't come back.
- Possible follow-up, if real-save reopens stay common: a debug parameter that keeps the build stamp fixed in the
  cache key, plus opening saves into a slot. That would make a reload after an app edit about 25 s instead of about
  170 s, with the lie that figures computed by the old code are shown until the new solve lands (strict
  `wait.final()` still waits for that).

## Found on the way

- Seen in my session only, for the orchestrator to confirm: a Bash call still running at 180 s was moved to the
  background although its time limit was 400 s (twice: 2m48 and a wait past 3 minutes); a 500 s-limit call that
  took 136 s stayed in the foreground. CLAUDE.md's Waiting bullet says up to 10 minutes, and its "smoke in the
  foreground" can't hold if smoke runs past 3 minutes (a smoke on the ledger today was at 3m27 and running).
  play and wait.mjs cap their timeouts at 170 s and say to ask again.
- Windows refuses renaming the state file over one `start` has open to read (EPERM); the write retries.
- PowerShell 5.1 drops inner double quotes from native arguments (`do 'act.click("Destinations")'` arrives as
  `act.click(Destinations)`): from PowerShell use double quotes outside and single inside, or `do --file`.
- A detached node child (`detached`, `windowsHide`, stdio to a file) returns the tool call at once and outlives it.

## For CLAUDE.md (the orchestrator applies these; replacing the two bullets)

- **Playing the game in a check or a probe**: probe with `node trainworld/checks/play.mjs` (how-to at its top).
  `start <city|save> --port <your Vite>` keeps a game open in a headless Chrome of its own (cores claimed; it stops
  after 30 unused minutes); then `do '<act/see calls>'`, `sim <read>` and `edits <file>` answer in a second or two
  with short JSON, waiting on conditions (`wait.final()`, `wait.panel()`, `wait.selection()`); `reload` after
  restarting Vite, `stop` when done. A standing check makes the same calls through `checks/lib/play.mjs`. Build
  fixtures by the player's path where it matters; a new read goes in `checks/lib/reads.mjs`.
- **Waiting**: no `sleep`, no polling loops of your own: `node trainworld/checks/wait.mjs <file> <pattern>
  <timeout-s> [--pid N] [--fail <pattern>]` for a log or build, `play.mjs do 'wait.final()'` for the game. A call
  still running at 180 s is moved to the background, so keep each wait under 170 s and ask again if it times out;
  never end your turn while something you need is running. Work that needs no result from you may run in the
  background, with at most one light check every 4-5 minutes. Final checks (smoke) run in the foreground.
