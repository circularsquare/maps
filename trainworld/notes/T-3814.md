# T-3814 New games name stations independently, clearer confirm

Anita, 2026-11-19: the setting's question "is pretty confusing still", with her wording for both directions and the
buttons Cancel / Apply to new stations only / Rename all stations; and "for new players we default it to
independent naming", existing players keeping whatever they have. For hotfix v0.4.4 (tree `namedefault`, from
`hotfix-v0.4.4`, save level unchanged).

## What is true now

- **The setting is the player's, in the browser** (`DisplaySettings.bindNew` in the `trainworld-ui` store, T-3759),
  never in a save: `LSN1` holds only each unbound station's own name. So "new players" means a browser with nothing
  stored. The brief's premise (old saves load as on, a new game saves it) does not apply; nothing in the save
  changed, and no level change was needed.
- **Default** (`game/ui.ts`): `DEFAULT_DISPLAY.bindNew = false`. When the store holds anything and no `bindNew`
  (a player from before T-3759 who never had it written), it is set true: that player had the old default.
  Everyone who opened the game since T-3759 shipped already has `bindNew: true` written (the store effect writes
  the whole display object on load), so they keep on too. A new player's first load writes `false` at once.
  `stationBinding.ts` reads the boolean as is. The worker's Rust default (`bind_new: true`) is left: the page posts
  the setting on construction and after every load, a `?new=1` game included (probe below).
- **Follows the new default**: every way a game starts (new game, `?new=1`, sandbox, real-network saves, opened
  files), since they all read the browser's setting. The tutorial says nothing about complex names. `?video=1`
  keeps the stored value. The wiki states no default.
- **The question** (`ui/SettingsTab.tsx` `bindNew`): asked both ways whenever the game has any station (ports
  aside); with none, or no game loaded, the setting changes at once. "Rename all stations" with every station
  already bound (or unbound) changes only the setting and adds no undo step. The setting changes only on a button: Cancel, Escape and a click outside leave it; "Apply to new stations only"
  changes the setting; "Rename all stations" changes it and runs `bindAll` / `unbindAll` (one `Op::Batch`, one
  undo; undo restores the names and leaves the setting). While its question is the one up the box shows the click
  (`bindAsked`, compared with `ask`, so anything that clears the question puts the box back).
- **Three-button confirm**: the game had none. `ask` takes an optional `alt` (label, run), drawn between Cancel and
  the red action button, same `btn text` look; a dialog with three is 460 px wide (`.confirmation.three`, 380 for
  the others) so they fit one row in English. Other languages wrap (flex-wrap) as before. These two questions have
  no "Confirm?" heading (`ask.plain`, Anita 2026-11-19: "yes lets drop confirm"); every other confirm keeps it.

## Why turning it on didn't ask (Anita, 2026-11-19: "it seems to only apply one way")

The first rule asked only when some station would change: ticking asked only with some station unbound, unticking
only with some bound. Her games had every station bound (old saves load all bound, and so did every station placed
while the setting was on), so turning it off asked and turning it on found nothing to change and asked nothing.
The test was right by its own rule (binding an all-bound game changes nothing); the rule was wrong for her. Now it
asks both ways in any game with a station. Probe e (scratch `namedefault/probe-e.js`, by pointer): ticking with
every station bound and unticking with every station unbound, both silent before, now ask; Cancel keeps the
setting; Rename all stations there changes only the setting; the dialogs have no heading. t2683 5 PASS, t3286
19 PASS. Screenshot `artifacts/trainworld/t3814-confirm.png` replaced.
