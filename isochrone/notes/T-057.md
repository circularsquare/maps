## Storage of town blocks: the choice

Selection (`tools/fine/select.py`): 21,644 town blocks fall in **4,671** distinct 1 degree tiles,
only 161 of them with all 16 blocks. Sizes measured on 40 random tiles of the plan, the same
tile built both ways (`build_tile` with its mask and with the whole tile):

| Storage | 40 tiles | Scaled to the 4,672 tiles |
|---|---|---|
| selected blocks only (others zero) | 5.0 MB | ~0.59 GB |
| whole tiles | 10.2 MB | ~1.19 GB |

Elevation (stage 2) is per cell like the class, so the factor ~2 carries over: whole tiles would
put towns at ~3.5 GB with elevation against the ~1.4 GB Anita approved, and the whole rule past
5 GB. So blocks it is.

Three ways to store blocks were weighed:

- **Block files** (300 x 300, `n51w001_5.land.bin.gz`): 4x the requests per window, new names, a
  new cache key, `cutInto` per block. Most page work, no size gain over the next.
- **Whole-tile files with absent blocks zeroed, mask in index.json** (picked): same names, same
  layout, same decode; a zeroed block gzips to almost nothing (a 1-block tile is 13-34 KB).
  The worker decodes 1.44 MB per tile however many blocks are real; the window needs at most
  ~4 tiles, so that is nothing.
- Fill absent blocks with something that looks like L1 (the 1 km class repeated): no page change,
  but times there would be neither L1 nor 100 m, a quiet error. Rejected.

index.json keeps `tiles` = whole tiles only, so the page as it is reads whole tiles (test
regions, water country, the 161 full town tiles) and treats partial tiles as missing, which is
right: their zero blocks would read as water. `partial` = {tile: mask} is new.

## Page change

Built as T-086 (notes/T-086.md), with a least fine share of 5% of the view added to step 3.
The plan as written for it:

1. **`js/tiles.js` `fineIndex`**: also build `ix.mask = new Map()` with 0xFFFF for each of
   `ix.tiles` and `ix.partial[name]` for each partial tile; `ix.set` = both. `loadFineWindow`
   fetches every tile with a mask (`ix.mask.has(name)` in place of `ix.set.has`).
2. **Absent blocks from L1** (in `loadFineWindow`): load the L1 speeds over the same bounds
   (`loadWindow({ f: 1, ... })` on the fine window's west/east/north/south, which are multiples
   of 0.05 degree = 6 L1 cells, so the grids line up; the tiles are already in the shared cache
   from the L1 window) and write each L1 cell's speed into its 10 x 10 cells wherever the cell's
   block is absent (no tile, or its mask bit 0). Whatever T-028 does to L1 speeds for roads (the
   road byte) must be applied to those L1 values the same way. Bit of a cell: tile row
   `r = floor(row / 300) % 4` from the north, column `c = floor(col / 300) % 4`, bit `4 r + c`.
3. **`js/windows.js` `fineWindowFor`**: with (2), the window no longer needs every tile:
   replace the `fineCovers` test and the clip with "the view touches at least one present
   block" (`fineTouches(ix, v)`, the same block test over the view's bounds); cap and margin as
   now. Without (2), the least change is `fineCovers` testing every 0.25 degree block of the
   window against `ix.mask`, and the fallback clip to whole quarter degrees round the view
   (`Math.floor(v.west * 4) / 4` and so on) in place of whole degrees; then a one-block town gets
   100 m only once the view sits inside the block (zoom ~13), which is why (2) is proposed.
4. **Paint** stays as is: the L0.1 window paints over L1 everywhere it covers; in filled blocks
   the cells carry L1 speeds, so times match L1 there to the cell.
5. **Smoke**: add a start in a partial town tile (Lagos, n06e003, mask 0fff) that gets an L0.1
   window at zoom 12.
