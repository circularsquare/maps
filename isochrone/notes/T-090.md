# T-090: canoe corridors from Semnan drawn in pieces

Anita, 2026-11-06: "i found a weird canoe case where the yellow path lines dont seem to be correct.
they cutoff and appear too far north it seems." Canoe start at Semnan, zoom ~2.7 (L10 only): lines
north of the Caspian (Kama, Kazakhstan) in pieces, nothing across the Caspian or up the lower
Volga, the lines round Iran fine. Her screenshot: `maps/artifacts/isochrone/t090_before.png`.

## Cause

Not a coordinate or level offset: a fresh page draws Semnan's lines whole (L10 alone, after
windows, after other starts; L3 at zoom 5.2-5.5 over the Volga). The bug needs a session's
history, which is why it showed for her and not headless.

1. **A parent read back wrong.** `canoeFrom` (js/canoe.js) picks which of a cell's canoe nodes a
   node came from (cells with several since T-082/T-088). For getting out within the cell it
   costed the piece's access as time only; the search also adds K x the land hazard on those
   hours. With hazard on it could pick a node the search did not take. Semnan at L10: the land
   node of a cell near Surat (72.54 E, 21.96 N, reached at 1019.3 h) got as parent a canoe node
   of its cell reached at 1026.9 h, past the 1024 h limit.
2. **The counted tree leaked into the next count.** `corridors.count` keeps its work arrays (`nch`,
   children left per node; `share`; `ord`) across levels and clicks, relying on `nch` being all 0
   between calls. A parent outside the reached set gets `nch++` from its child but is never
   ordered properly: it was processed with stale `par`/`share` entries, decrementing whatever
   nodes those named, so `nch` was left at 255 (-1) somewhere after every such count (seen: node 0
   after each Semnan count, 254 after the second). A node whose `nch` starts one short is ordered
   one child early: that child's whole subtree is added to it after it has passed its count up,
   so the trunk between it and the start drops below the drawing threshold while the subtree's
   own lines stay. A -1 also survives every later count (it ends each one at -1 again), so the
   damage grows over a session, at any level, wherever the dirty indices fall. A node never
   ordered also made the final sum read stale `ord` entries past the ordered ones, adding counts
   along unrelated edges.

`t090_before_sim.png`: Semnan's L10 lines recounted with `nch` one short on 3000 random branching
nodes (`corr_poison.mjs` in the task scratchpad): the same kind of picture, trunks gone, tips and
pieces left. Her exact session cannot be replayed, so the "too far north" pieces are most likely
the stale-`ord` counts or tips whose trunks went; nothing found draws a line off its cells.

## Fix

- `js/canoe.js` `canoeFrom`: the within-cell get-out cost includes the hazard on the access hours
  (`1 + K hq / inv`), as `search.js` costs it.
- `js/corridors.js`:
  - `links`: a canoe-layer parent read back must be reached no later and at no more weight than
    its child; otherwise the cell's node that is (`earliest`). The start counted as a root also
    when it is only a candidate (a window's start can have no children).
  - `count`: sums over the nodes `reparent` ordered (it returns how many), not `nr`; if they
    differ, `nch` is zeroed over the reached nodes, so one bad count cannot spoil the next.

No data rebuild; `route.js` gets the corrected `canoeFrom` too.
