RELIGION DOT MAP — COMMAND REFERENCE
====================================

Design and reasoning: spec.md.  Sources and their gotchas: sources.md.  todo.txt is Anita's.

WHO GETS DRAWN, AND HOW FINELY, IS NOT A TECHNICAL QUESTION -- spec.md §14.  Before adding a
country whose state does not publish religion, or whose religious minorities are persecuted,
read it.  It ends by asking you to raise the question with Anita rather than decide alone,
and that is an invitation rather than a last resort.


---- ADDING A COUNTRY: THE CHECKLIST ----

Anita, 2026-09-06, on finding a half-wired Vietnam drawing a Chinese legend over Hanoi:
"maybe we need a new country checklist or something".  She is right, and the reason is that
the last three steps FAIL SILENTLY -- no error, no warning, and a map that looks built.

Run in order.  Every step, every time, even when only one country changed.

   1. python sources/<cc>.py --fetch       # -> data/normalized/<cc>.csv, with its own checks
   2. python sources/<cc>_geo.py --fetch   # -> data/geo/<cc>/, units + placement grid
   3. write taxonomy/<cc><YYYY>.py         # the mapping, with EXCLUDED and REVIEW
   4. add the entry to countries.py        # counts=, place=, place_weight=, note_public=
                                           #   AND gap= if part of the country is not
                                           #   drawn.  One short line, shown under the
                                           #   country's name in the legend: a blank on a
                                           #   dot map cannot tell "nobody here is
                                           #   religious" from "nobody counted here", and
                                           #   this is the only place that difference is
                                           #   stated while the blank is on screen.
                                           #   Currently ge and cn.  Most countries need
                                           #   none, and that is the healthy state.
   5. python taxonomy/build_tree.py        # NOT automatic.  Skip it and the viewer greys out
                                           #   whole countries -- it does not know the new nodes.
   6. python tools/check_mapping.py <cc>   # every source category resolves; every node exists
   7. python coverage.py                   # every drawn node is covered, all countries
   8. python scatter.py --country <cc>                  # 1:1,000
   9. python scatter.py --country <cc> --dot-value 10000  # 1:10,000, needed by --coarse below
  10. python country_shapes.py             # <-- SILENT IF SKIPPED.  Auto's "which country is
                                           #   the camera over" reads this file.  A country
                                           #   missing from it is invisible to Auto, which
                                           #   falls through to the dot tally and hands the
                                           #   legend to whichever NEIGHBOUR has dots in frame.
                                           #   That is exactly the Hanoi/China bug: Vietnam was
                                           #   drawn, correct, and absent from the shapes, so
                                           #   China's sparse Yunnan dots won the tally.
  11. python tiles.py --countries "$(python tools/built_countries.py)" --coarse --no-atomic
  12. python buffers.py --countries "$(python tools/built_countries.py)" --coarse

      DO NOT TYPE THE COUNTRY LIST BY HAND.  tools/built_countries.py derives it from the
      dots files actually on disk, intersected with countries.py's COUNTRIES, and prints it
      in the form both commands want.  Run it with --check first: it names every registered
      country that is MISSING an edition, which is the one thing a hand-typed list cannot
      tell you and the exact bug the two notes below are about.

          python tools/built_countries.py --check

  THE THREE SILENT ONES, because each cost someone an hour:

  * --countries REPLACES the archive and the manifest.  A country left OUT of either list is
    invisible even though its tiles, counts.json entry and legend are all perfect.  Ghana hit
    this 2026-09-05.
  * --coarse ON BUFFERS IS NOT OPTIONAL.  Without it buffers.py writes only the fine edition
    and the manifest it replaces loses the 10k edition FOR EVERY COUNTRY -- the 1:10,000
    control then greys itself out map-wide.  Hit 2026-09-06 while adding Bangladesh.
  * country_shapes.py is the one nothing else depends on, so nothing complains.  See step 10.

  AND ONE THAT IS NOT PER-COUNTRY BUT IS WORTH RUNNING WHEN A COUNTRY HAS DERIVED ROWS:

    python tools/check_rollup.py [cc ...]
        Since spec 7a-i, `inferred dots: not shown` ROLLS a derived dot up to the nearest
        level its country MEASURED instead of deleting it -- so an Israeli dot inferred as
        Haredi draws as plain Judaism rather than vanishing.  This reports, per country,
        how many people roll up and how many still disappear, and names the nodes.
        Read its docstring first: `derived` covers three different situations and only one
        of them is a defect.  Since spec 7a-i-1 (2026-09-07) the target is the SOURCE'S OWN
        COLUMN rather than an ancestor in the tree, which took 185.9M orphaned down to
        39.3M and 27.1M rolling up to 173.8M.  A country still showing up here wants a
        COLUMNS entry in its mapping module -- or a comment saying why it must not have one,
        which is what ch, cn, il and nz already carry.  What is left is all of ONE kind:
        sources that measured nothing at the unit their dots are drawn on.  If a country
        turns up here for the OTHER reason -- the source did measure it and the tree has no
        node for the cell -- that is a taxonomy question, not a roll-up one.

    python rollup.py [--countries cc,cc] [--dry-run]
        Builds data/processed/rollup.json -- per country, `node -> the level this country
        COUNTED it at`, which is what the viewer reads for `inferred dots: not shown`.
        RUN IT AFTER EDITING ANY `COLUMNS` DICT, then `tiles.py --refresh-meta`; neither
        needs a retile, because the table comes from the mapping and not from the dots.
        Skipping it is not fatal and is silent in the wrong direction: every country falls
        back to 7a-i's ancestor walk, so the UK's 22.1M unaffiliated vanish again.
        Loads every country's counts(), so the full run is a few minutes; --countries
        merges into the existing file rather than replacing it.

  THE ONE-LINE CHECKS, and they are worth running:

    python -c "import json;m=json.load(open('data/buffers/manifest.json'));print({k:len(v['countries']) for k,v in m['editions'].items()})"
        -> both editions, both with every country.  One edition means --coarse was forgotten.

    python -c "import json,sys;sys.path.insert(0,'.');import countries;g=json.load(open('data/processed/country_shapes.geojson'));print(sorted(set(countries.COUNTRIES)-{f['properties']['cc'] for f in g['features']}))"
        -> [] .  Anything listed is drawn but invisible to Auto.

    python tools/check_tiles.py <ALL> --coarse --no-atomic --max-zoom 6
        -> "IDENTICAL to the reference".  Decodes the built archive and compares it tile by
        tile against a reference implementation that shares no code with mvt.py.
        --no-atomic MUST MATCH STEP 11.  The flag was added 2026-09-07; before that the
        checker always expected an `atomic` layer that step 11 does not write, so the
        documented build could never pass the documented check — every tile came back
        DIFFERENT with the whole atomic layer "missing" and **0 unexpected**, which is the
        tell that it is a flag mismatch rather than a broken build.  Pass every country:
        the checker compares WHOLE tiles, so a country left out shows up as "unexpected"
        features belonging to its neighbours.

        A HANDFUL OF BAD TILES, ALL IN ONE COUNTRY, IS USUALLY ANOTHER SESSION'S RESCATTER
        AND NOT A BROKEN BUILD.  Hit 2026-09-07: six tiles, every one tagged c='in'.  The
        checker decodes the ARCHIVE and compares it against the geojson ON DISK NOW, so if
        somebody re-runs scatter.py for a country between your tiles.py and your
        check_tiles.py, the dots moved under you -- scatter placement is random, so the
        counts match and the positions do not.  THE TELL IS THREE MTIMES:

          ls -la --time-style=full-iso data/processed/religiondots.pmtiles \
              data/processed/dots_<cc>.geojson data/normalized/<cc>.csv

        dots_<cc>.geojson NEWER than the .pmtiles, with <cc>.csv OLDER than both, means the
        data never changed and only the scatter was re-rolled.  Re-run tiles.py AND
        buffers.py (they must agree with each other as well as with the geojson) and
        re-check.  Nothing is wrong with the numbers.  See [[reference_concurrent_sessions]].

    cd data/geo && unzip -o -q cb_2020_us_tract_500k.zip -d tracts2020
    cd data/geo && unzip -o -q cb_2020_us_county_500k.zip -d counties2020

   Tracts are built to ~4,000 people each, so an equal share per tract is already a
   population weighting and nothing here needs a population file (spec.md §8.2).  The US

   tract populations out of ancestrydots and still downloads nothing new.

                 real change.  New Zealand's structure is 2018 and its totals are 2023, so
                 its Hindu column misses by -14.7% and its Muslim column by -18.2% — both

                 to force a broken mapping through.
   --source-id   uk.csv holds England-and-Wales AND Scotland at geo_level 'output_area'.

---- US SUB-COUNTY WEIGHTS (spec §8.4) ----

    python us_weights.py --build      # tract segments + fit, ~4 min
    python us_weights.py --refit      # refit only, from the cached segments, ~40 s
    python us_weights.py --report     # print the validation table, write nothing

   Decides WHERE INSIDE A COUNTY the US dots go.  ASARB is county-level and there is nothing
   finer — it does not collect congregation addresses — so Cook County is 5.3M people and
   Los Angeles 10.0M in one polygon each, and §8.2 spread them evenly.  This places them by
   demographic composition instead, raked to the ASARB county total so no county's number
   moves.  Reads ancestrydots' ACS tract tables directly; downloads nothing.

   REQUIRES ancestrydots/data/raw to be populated (its `fetch_data.py --all`), plus three
   files that need NO API KEY -- api.census.gov refuses unkeyed requests now, but the ACS
   SUMMARY FILE on www2.census.gov is the same data as flat .dat files and is wide open.
   That is how B16001 (language at home) gets in, and B16001 is what fixes Judaism:

    curl -sSL -o data/geo/cbsa_list1_2023.xlsx \
      https://www2.census.gov/programs-surveys/metro-micro/geographies/reference-files/2023/delineation-files/list1_2023.xlsx
    curl -sSL -o data/geo/acsdt5y2023-b16001.dat \
      https://www2.census.gov/programs-surveys/acs/summary_file/2023/table-based-SF/data/5YRData/acsdt5y2023-b16001.dat
    curl -sSL -o data/geo/tract_to_puma_2020.txt \
      https://www2.census.gov/geo/docs/maps-data/data/rel2020/2020_Census_Tract_to_2020_PUMA.txt

   B16001's finest geography is the PUMA (~100,000 people), not the tract, so everything
   sourced from it is PUMA-resolution however finely the dots are drawn.  A PUMA's speakers
   are split across its tracts by the ancestry that CARRIES the language (Yiddish by white
   population, Malayalam by South Asian).  Without that, PUMA 3604303 -- "Bedford-Stuyvesant
   & Crown Heights North", 6.2% Yiddish because Crown Heights is the centre of Chabad --
   made Bed-Stuy 1.3x the borough rate for Orthodox Judaism.

   Writes data/geo/us_tract_segments.csv (8.8MB, cached — --refit reuses it) and
   data/processed/us_weight_model.json.  Both are gitignored; the hand-authored half lives
   in us_weights.py itself, which is the file to read.

   TWO TRACKS, and the difference matters more than anything else here:

   fitted     26 nodes that clear r >= 0.25 predicting ASARB's own within-metro variation
              with WHOLE METROS HELD OUT.  Catholic 0.45, Church of God in Christ 0.61,
              National Baptist 0.57.  Evidence.
   authored   31 nodes whose ethnicity is constitutive rather than correlated — Armenian
              Apostolic is Armenian by canon, Mar Thoma is Kerala.  A claim, not a
              measurement, and flagged `basis: authored` in the model file.  They exist
              because a body defined by a 0.2%-of-population ethnicity is NOT learnable
              from between-county variation at any ridge setting (spec §8.4 has the sweep).

   Everything else stays population-uniform.  DO NOT lower R_MIN to catch more: the gate is
   the design, and the one node that passed it on a meaningless coefficient — Armenian
   Apostolic at r = 0.35 with no `armenian` term — drew Armenian dots in San Gabriel.

   B16001 it drew Borough Park at 58% CATHOLIC: Orthodox Judaism correctly got no weights,
   and Catholic, which did, took the space.  A MISSING PREDICTOR IS NOT NEUTRAL -- the
   bodies that can be placed absorb what the missing one should have held.

    Williamsburg        -> 2.7x      Pico-Robertson, LA                   5.8x
    Midwood             -> 2.2x      Beverly-Fairfax, LA                  8.0x

---- US RE-BASING ON SELF-IDENTIFICATION (spec sec 3.5a) ----

    python us_rebase.py --report      # the state table and the overflow record; writes nothing

   NOTHING TO RUN AS A BUILD STEP.  countries.py calls residual_counts() itself, so a US
   scatter already includes this; --report is the only command and it is for reading.

   What it does: Pew's 2023-24 survey supplies each state's total per religion, ASARB's rolls
   stay exactly as they are INSIDE that total, and the difference is spread over each county's
   people who are on nobody's roll -- population minus adherents, which is the same pool the
   unaffiliated come out of.  The US goes from drawing 48.4% of Americans to 98.6%, and the
   American non-religious become drawable at all for the first time.

   THE RESIDUAL IS 166.2M PEOPLE, so a little over half the US map is a `derived` row and
   is tagged `derived` (sec 7).  NOTHING ON SCREEN SHOWS THAT -- the desaturation that used to
   was removed 2026-09-04, because every colour on the map has to be a colour in the legend.
   The country note is the only thing that says so.

   Four things that are easy to get backwards:

   - THE ROLL IT SUBTRACTS IS ASARB'S COUNTY SHEET, NOT ITS STATE SHEET.  The state sheet has
     160,786,973 mapped adherents and the county sheet 160,572,400 -- 214,573 people belong to
     a state and to no county in it.  Subtract the state figure and those people vanish from
     the national total.  countries.py passes its own frame in so both read the same thing.

   - _us_counts() IS STILL ASARB-ONLY AND MUST STAY THAT WAY.  us_weights.py fits its sec 8.4
     model against it, and fitting a model of where ASARB's adherents live against rows that
     are a survey residual is training on the output.  _us_counts_rebased() is the one
     COUNTRIES points at.
   - THE RESIDUAL DOES NOT GO THROUGH THE SEC 8.4 WEIGHTS.  Those betas predict where people
     ON a roll live; the residual is by definition the people not on one, so it takes tract
     population alone (`weights(..., plain=True)`).
   - 30 COUNTIES GET NO RESIDUAL, and that is right.  Those are sec 3.6's counties reporting
     more adherents than residents, so their pool is negative and clips to zero.  3,113 of
     3,143 counties receive the spread.

   The overflow record is the part worth reading: 94 (state, root) pairs where a roll beats
   the survey, 1.63M people, charged to those states' unaffiliated.  Islam is 1.18M of it
   across 30 states and is NOT a roll beating a survey -- ASARB's figure there is a body
   named "Muslim Estimate", so it is two estimates disagreeing.  Utah's Christianity is 295k
   more.  Everything else together is 153k.

   Per-country wiring is in countries.py; everything downstream is country-agnostic.

   WATER IS SUBTRACTED FROM THE PLACEMENT POLYGONS FIRST (water.py, spec 8.2c).  A shore
   tract owns half the river, so uniform sampling used to put 3.0% of the New York dots in
   open water; now 0.1%.  It needs
       ../data/water-polygons-split-4326/water_polygons.shp
   which is OSM's global coastline layer, already in the repo for other maps and NOT in
   religiondots/data.  If it is missing, scatter says so and carries on with wet dots.

   THE FIRST RUN PER COUNTRY PAYS FOR THE CLIP and the rest are free: the clipped layer is
   cached under data/geo/_waterclip/ keyed by the source file's mtime, so it is rebuilt
   only when the placement layer or the water layer changes.  Canada is the expensive one
   at ~547 s, the US ~167 s, the UK ~104 s, most countries a few seconds.  Add --no-water
   to skip it, which is the before picture.

   A unit losing more than water.py's KEEP_WHOLE_ABOVE (0.95) of its area is left
   UNCLIPPED -- Sama-Bajau stilt villages in Sulu and Basilan stand over open water and
   have no land under them in OSM (spec 8.2c-i).  That threshold is applied when the cache
   is READ, so changing it costs seconds and re-clips nothing.

   tier per pair instead drew 764 of Ireland's 4,295 measured dots as derived, because one

---- SWITZERLAND: THE 3.4 RESCALE, AND IT IS A STRONGER CLAIM THAN BRAZIL'S ----

    python ch_rescale.py             # seconds; reads data/normalized/ch.csv, writes
                                     #   data/normalized/ch_commune_rescaled.csv

   Switzerland is drawn from THIS file, not from ch.csv, and countries.py raises if it is
   missing rather than falling back -- drawing ch.csv would put a twenty-six-year-old
   Switzerland on the map.  spec 3.4.

   The country last asked everybody in 2000.  Since 2010 the question is in the
   Strukturerhebung, a sample that publishes EIGHT categories and stops at the CANTON.  So
   the survey supplies the magnitude and the census supplies the shape.

   WHY IT IS NOT JUST BRAZIL.  Brazil's rescale changes the CATEGORIES and keeps the
   geography, so a 2022 municipio total is measured for that municipio and 103.6M people
   pass through untouched.  Switzerland's changes the GEOGRAPHY too -- a canton total spread
   over its communes -- so EVERY drawn row is `derived` and spec 3.10 keeps all of it out of
   the presence ring.

   AND IT FITS TWO MARGINS, NOT ONE.  A plain Brazil-style rescale holds each commune's share
   of its canton fixed since 2000, which puts dots in alpine communes that have emptied and
   starves the suburbs people moved to -- Switzerland went from 7.29M to about 9M in between.
   So it is an IPF on current commune population (GISCO's POP_2021, already in the boundary
   file) AND the survey's canton category totals.  Both come out exact.  The 2000 census
   supplies only the ASSOCIATION between commune and religion.

   The universe becomes people aged 15+ in private households, and is NOT scaled back up
   (spec 14.4) -- the same call Brazil, Chile and Portugal make.

   RUN ORDER: sources/ch.py --fetch -> ch_rescale.py -> sources/ch_geo.py --fetch

    python tiles.py --refresh-meta                 # counts.json text only, ~1 second
                                                   #   also rewrites each country's `covers`,
                                                   #   so a taxonomy mapping fix reaches the
                                                   #   coverage wash without re-tiling
    python tiles.py --countries ... --jobs 1       # encode inline, when a worker traceback

   THE ARCHIVE IS THE WHOLE PICKER.  --countries is not a filter over an existing archive,
   it REPLACES it, and counts.json with it -- so retiling with a short list silently drops
   every country not named from the map.  This has already happened once: a rebuild with
   us,ca,cz removed Brazil and nothing reported anything.  The flag defaults to `us` alone.
   Always pass every country that has a dots_<cc>.geojson, and check the per-country lines
   at the end of the run against what you expected.

   All fifteen at z0-10 --coarse: about a minute, 156.6 MB, 34,216 tiles, 2.23M dots.

   IT USED TO BE ABOUT FORTY MINUTES AND ~3.5 GB OF MEMORY, and both were the same two
   causes (fixed 2026-09-04):

     - mapbox_vector_tile.encode does 11,400 features/s, because for every feature it
       builds a shapely object, checks its validity, enforces a winding order and runs it
       through shapely.ops.transform.  Every feature here is a POINT, for which all of
       that is dead weight.  mvt.py writes the bytes directly at 294,000 features/s, and
       a --coarse build encodes about 28 million of them -- `atomic` is every dot at
       every zoom, eleven times over, and is most of the archive.
     - the whole tile sink was built in memory and encoded at the end.  Zoom is now the
       outer loop and each zoom is written and dropped before the next starts, so the
       build holds one zoom rather than the whole pyramid.

   --jobs then encodes and gzips several tiles at once, which is worth about 2x on top --
   less than the core count because z0 is ONE TILE holding every dot in the world and
   nothing can split it.  --jobs 1 and --jobs 8 produce byte-identical archives.

   mvt.py IS THE ONLY HAND-ROLLED WIRE FORMAT IN THE PROJECT.  tools/check_tiles.py is the
   check on it and shares no code with it -- see CHECK THE ARCHIVE below.

   --refresh-meta still exists, and is still the right thing for editing a country's name,
   source, basis, note or view box: it rewrites only those fields in counts.json from
   countries.py and leaves the tiles and the tallies alone.

   THE DEV SERVER BLOCKS THE LAST STEP.  The archive is built as religiondots.pmtiles.tmp
   and moved into place at the end, so a build that dies leaves the old archive intact
   rather than a truncated one.  Windows will not let that move happen while `npx serve`
   holds the old file open, which it does for as long as the local map has been loaded --
   so the run ends by telling you to stop the server and `mv` the .tmp yourself.  Nothing
   is lost when that happens: counts.json is written first and matches the new archive.

   Writes data/processed/religiondots.pmtiles and counts.json.  Countries go into ONE archive
   because the tile pyramid is shared, but every feature carries `c` and the merge groups by
   it, so marks never combine across a border -- the viewer draws one country at a time and a
   mark merged across the 49th parallel would belong to neither side of it (spec §6.2).

   counts.json is per country: name, source, basis, note, bbox and the dot/ring tallies, all
   read from countries.py.  A new country that does not fill in `name`/`source`/`basis` shows
   up in the picker as its bare country code.

   NOT tippecanoe.  Tippecanoe's job at low zoom is to DROP features until the tile fits a
   byte budget, so which dots survive is close to arbitrary and a small group blinks in and
   out as you pan.  tiles.py MERGES instead: nearby dots of the same religion become one
   mark carrying `k`, and the viewer draws area proportional to k (spec.md §4.2).  Nothing
   is ever dropped.  It also means no WSL, whose C: mount is broken on this machine.

    python tools/check_tiles.py us --max-zoom 10 --coarse
    python tools/check_tiles.py us,ca,cz,br,au,ie,mx,nz,uk,pl,ro,ee,hr,in,de,hu,mk --max-zoom 6 --coarse
    python tools/check_tiles.py cz --archive data/processed/religiondots.pmtiles.tmp

   Rebuilds what every tile SHOULD hold straight from the geojson -- with the old pandas
   groupby, dict features and mapbox_vector_tile, all reproduced inside the tool -- then
   decodes the real archive and compares.  This is the check on mvt.py, and it deliberately
   shares no code with it.  Run it after touching mvt.py or tiles.py.

   PASS THE SAME --countries THE ARCHIVE WAS BUILT WITH.  At low zoom one tile holds several
   countries, so checking a subset reports every other country's marks as unexpected.  The
   exception is a country with no neighbour in the set -- in, au, nz, br -- which can be
   checked alone at any zoom.

   Feature ORDER is not compared and must not be: §4.2's draw-order shuffle is a numpy
   permutation now rather than random.Random.  Tiles are compared as multisets, which still
   catches a dropped feature, a duplicate, a coordinate off by one or a property pointing at
   the wrong value-table entry.

   The reference half is slow -- it is the code the archive stopped using because it was
   slow -- so a full-zoom check of every country takes far longer than the build does.
   --max-zoom 6 over everything plus a full-zoom check of one country is the useful pair.


---- CHECK A TAXONOMY MAPPING ----

    python tools/check_mapping.py pl           # or ro / cz / au / br / ie / mx / nz / uk / ca
    python tools/check_mapping.py gh           # 272 units -- see DEFAULT_LEVELS below
    python tools/check_mapping.py gh --level district,submetro,region   # any subset

   Checks a country's taxonomy mapping against its normalised data: every source category
   either resolves or is explicitly EXCLUDED, every node it points at exists in
   branches.py, and how many people land on each node.  An unmapped category is NOT an
   error anywhere downstream -- countries.py drops rows whose node is NaN -- so without
   this it silently removes people from the map.  build_tree.py has always checked
   usrc2020.py this way; no other country's mapping had anything until 2026-09-03.

   --level TAKES A COMMA-SEPARATED LIST, and the default is per country.  It used to pick
   "the geo_level with the most units", which is right for every country whose drawn tier
   is one level and silently wrong for Ghana, whose 272 drawn units are 255 `district`
   plus the 17 `submetro` rows that REPLACE six metropolitan parents.  The old default
   reported 255 units and 1.7M too few people and nothing about it looked wrong.
   DEFAULT_LEVELS at the top of the file is where a country declares a split tier.

    python tools/check_palette.py --all        # list every colour and its contrast

   The top-level family colours are hand-written in ROOT_HSL in index.html (spec §6.3).  This
   reads them back OUT of index.html -- not a copy -- and measures, against counts.json, whether

   told apart as two 2px dots.  21 of the 30 families share one indigo-magenta wedge, so

   position, which looks fine and means nothing -- add a line to ROOT_HSL instead.

    python tools/check_overview.py
    python tools/check_overview.py --all               # list every drawn colour
    python tools/check_overview.py --depth 3
    python tools/check_overview.py --focus christianity   # the full-wheel palette instead

   check_palette.py measures the thirty family hues against each other, which is the depth-1
   question.  This is the depth-2 one, and it is where the collisions actually are: the
   all-religions view puts every family inside a band around its own hue (spec §6.9), so what a
   reader compares is Catholic against Baptist inside 46 degrees of yellow.

   It splits its report in two and the split is the point.  Pairs ACROSS families under dE 25
   are failures -- the first thing a dot has to say is which family it is.  Pairs INSIDE one
   family are held to dE 12 and listed separately, because the overview MEANS those to be close
   (spec §6.9's honest limit: 22 Christian branches do not fit in 46 degrees and no allocation
   fixes that).  One bar would bury the two real failures under three hundred expected ones.

   Needs node on PATH.  The colours come out of index.html itself via tools/palette_dump.js,
   which slices the allocator's own declarations out of the inline script and runs them -- same
   rule as check_palette.py reading ROOT_HSL, so the checker cannot drift from the palette.  If
   index.html stops declaring one of the names it slices, palette_dump.js says which.

    python tools/scan_identities.py

   Finds nodes that are the SAME THING at two depths -- a branch whose single child is the
   branch, which is what "Hindu Temples" under Hinduism and "Catholic Church" under Latin
   Catholic both were (spec §2.5).  Lists single-child branches, branches where one side of a
   split holds under 2%, and which countries put the dots on each side.  Run it when a source
   lands: this defect is invisible in the taxonomy and obvious on the map.

   Read the second half too.  A branch whose one drawn child holds 96% of it is usually NOT an
   identity -- the siblings are below the dot floor, presence pruning already draws it as one
   row, and collapsing it would throw away what the next source reports.

    python tools/scan_congregations.py

   What one congregation is worth, for spec sec 4.4.  155 of ASARB's 373 bodies report
   congregations and no membership, and this is the check on whether a per-family ratio can
   convert them.  Prints the spread of adherents per congregation, whether it tracks body
   size, the spread within each branch, every counted body outside Christianity, and what
   each congregations-only body would be estimated at and from what.

   The finding is in the docstring: the ratio runs 18 to 3,188, and the largest cut is not a
   Christian family boundary but Christianity itself -- 134 per congregation against 541
   outside it, Hindu temples at 1,920.  A fallback that crosses that line is wrong in a fixed
   direction, so the search stops at the L1 root.  That still carries 144 of the 155 bodies;
   the 11 left are religions ASARB counted nobody in.

    python tools/scan_selfid_gap.py

   Whether a self-identification total survives subtracting ASARB's rolls -- the feasibility
   check behind spec sec 3.5a, run before the decision rather than after.  Pew's figures are
   hand-entered with their URLs beside them rather than read from us_pew.csv, deliberately:
   this is the check, so it does not share code with the thing it checks.

    python tools/check_pew_mapping.py            # the four checks and the national table
    python tools/check_pew_mapping.py --states   # every state, every root

   Checks taxonomy/us_pew2024.py, the sec 3.5a cut across Pew's tree.  check_mapping.py
   cannot do this one: it tests a flat category list against a normalised <cc>.csv, and the
   thing that goes wrong with a TREE is not an unmapped category but a mis-placed cut --
   take a node and its child and those people are counted twice, take neither and they are
   dropped.  So it checks that the cut partitions all 51 states exactly, that nothing is
   stranded, that every target exists in branches.py, and that every root ASARB counts
   adherents in has a survey line.

   Then it prints the two tables worth having.  The first is what the cut gives each root.
   The second is WHERE SEC 3.5a's CAP-AND-RECORD ACTUALLY FALLS, over all 51 states rather
   than the eight scan_selfid_gap.py checked by hand, with the child conversion applied:
   62 of 255 (state, root) pairs are negative but they are only 1.69M people, 70% of that
   is Islam -- the "Muslim Estimate" calibration case sec 3.5a already named -- and
   CHRISTIANITY IS NEGATIVE IN UTAH AND NOWHERE ELSE, which is the spec's claim confirmed
   at full coverage.
